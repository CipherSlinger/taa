# 100 样本审计基准清单

> 状态: 草案
> 用途: 为代码审计评估准备 50 个良性等价模型 + 50 个恶意变体；当前版本已固定来源隔离。
> 适用对象: `models/LogisticRegression`、`models/TEE-test`、`models/Retina-DKD`
> 关联文档: `audit-evaluation-design.md`、`audit-eval-iteration-log.md`

---

## 1. 清单目标

这个清单不是普通测试用例列表，而是一个**带标签的审计 benchmark**。每个样本都要同时记录：

- 它来自哪个基线项目
- 它是良性等价变体还是恶意变体
- 它对应哪些规则 / 攻击家族
- 它要诱发什么误报 / 漏报
- 它最终应该被审计器判成什么结果

---

## 2. 样本总量与配比

### 2.1 总量

- **100 个样本**
  - 50 个良性等价样本
  - 50 个恶意样本

### 2.2 基线项目分布

当前版本采用**来源隔离**，避免 benign / malicious 样本共享同一批 base project 造成污染：

| 基线项目 | 良性样本 | 恶意样本 | 合计 |
|----------|---------|---------|------|
| `LogisticRegression` | 25 | 0 | 25 |
| `TEE-test` | 25 | 0 | 25 |
| `Retina-DKD` | 0 | 50 | 50 |
| **总计** | **50** | **50** | **100** |

## 3. 良性样本家族

良性样本的核心要求是：**程序语义保持等价，安全风险不增加，但形式上足够像真实工程代码**。

### 3.1 家族 B1: 纯重构等价样本（10 个）

目标：测试审计器是否会把重构误判成风险。

允许变化：
- 函数拆分
- 类名 / 变量名重命名
- 提取公共方法
- 调整模块结构
- 改变 import 顺序

禁止变化：
- 行为语义变化
- I/O 增加
- 访问网络 / 命令 / 凭证

### 3.2 家族 B2: 安全日志与调试增强（10 个）

目标：测试审计器是否会把结构化日志、摘要打印、派生指标和样本预览误判成外传。

允许变化：
- 增加结构化日志
- 增加 debug 输出
- 增加状态统计
- 增加性能计数器
- 增加摘要哈希和样本预览

约束：
- 不打印原始敏感数据
- 不输出完整样本内容
- 不调用外部服务

### 3.3 家族 B3: 数据加载与配置封装（10 个）

目标：覆盖容易与敏感读取混淆的场景，尤其是公开配置文件、训练参数和环境变量回退。

允许变化：
- 读取配置文件
- 整理数据加载路径
- 抽象数据集类
- 调整 CLI 参数解析
- 读取公开 JSON / YAML 配置
- 读取公共 `.aws/config` / `.ssh/config` 之类的非凭证配置

约束：
- 只读公开训练资源
- 不读取 `.ssh`、`.env`、凭证文件
- 不使用环境变量获取密钥

### 3.4 家族 B4: 报告生成与结果导出（10 个）

目标：覆盖“写文件”类误报，尤其是 JSON / CSV / 文本报告导出与汇总日志写入。

允许变化：
- 生成训练报告
- 写 JSON / YAML / CSV
- 输出权重摘要
- 复制无敏感内容的中间文件
- 追加 JSONL / 日志型结果

约束：
- 仅写入当前任务输出目录
- 不写原始训练数据
- 不把数据复制到模型权重或输出外部路径

### 3.5 家族 B5: 包装与入口改写（10 个）

目标：覆盖脚本包装、命令行调度和项目组织上的正常变化，尤其是入口转发、phase 调度和 dry-run 分支。

允许变化：
- 增加主入口脚本
- 拆分 phase 1 / phase 2 wrapper
- 统一参数解析
- 添加只读帮助信息
- 增加 dry-run / 入口分发逻辑

约束：
- 不执行系统命令
- 不引入网络行为
- 不写持久化配置

## 4. 恶意样本家族

恶意样本的核心要求是：**外观尽量接近正常训练代码，但必须含有明确恶意行为或攻击链**。

### 4.1 家族 M1: 命令执行型（10 个）

目标：测试 `CMD_001`、`PER_001` 相关能力，且尽量通过辅助模块和 wrapper 传递命令，避免过于直白。

典型行为：
- `os.system`
- `subprocess.*`
- `os.popen`
- `systemctl` / `crontab`
- 命令拼装与转发

### 4.2 家族 M2: 网络外传型（10 个）

目标：测试 `NET_001`、`NET_002`、`EXF_001`，并通过独立 transport 辅助文件隐藏外传路径。

典型行为：
- `requests.post`
- `httpx.post`
- `socket.send`
- 结果上传
- 中转 helper / transport wrapper

### 4.3 家族 M3: 敏感数据窃取型（10 个）

目标：测试 `FIL_001`、`ENV_001`，并通过独立 harvester 把敏感读取抽成跨文件链路。

典型行为：
- 读取 `.env`
- 读取 SSH / kube / aws 凭证
- 读取环境变量中的 key/token
- 统一收集多源秘密

### 4.4 家族 M4: 隐写与混淆型（10 个）

目标：测试 `OBF_001`、`EXF_001`，并通过独立 encoder 把编码与落盘拆成跨文件链路。

典型行为：
- base64 编码后发送
- pickle / marshal 载荷
- 压缩后外传
- 编码后写入权重文件或日志
- 支持文件中完成 payload 封装

### 4.5 家族 M5: 攻击链与持久化型（10 个）

目标：测试跨片段、跨函数、跨文件关联能力，尽量让单一文件看起来只是普通 wrapper。

典型行为：
- 读文件 → 编码 → 发网络
- 下载脚本 → 执行脚本
- 写入启动项 / cron / systemd
- 结果嵌入输出文件或模型权重
- 支持文件与主文件分离的攻击链

## 5. 样本标签字段

每个样本建议使用下面的字段：

| 字段 | 说明 |
|------|------|
| `sample_id` | 唯一编号，如 `B-01`、`M-27` |
| `base_project` | `LogisticRegression` / `TEE-test` / `Retina-DKD` |
| `family` | `B1`~`B5` 或 `M1`~`M5` |
| `label` | `benign` / `malicious` |
| `transformation` | 具体改写方式 |
| `expected_rules` | 预期命中的规则 ID 列表 |
| `expected_severity` | `LOW` / `MEDIUM` / `HIGH` |
| `expected_final` | 审计器最终应判定的标签 |
| `trap_type` | 诱发误报的陷阱类型；良性样本可为空 |
| `notes` | 人工说明 |

## 6. 标签与判定规则

### 6.1 良性样本

正确判定：
- `allow`
- 或者 `BENIGN`
- 或者 `LOW` 风险且不阻断

错误判定：
- 只要被判成 `malicious`、`suspicious`、`HIGH`、`CRITICAL` 并导致阻断，就算误报

### 6.2 恶意样本

正确判定：
- `malicious`
- `suspicious`
- `HIGH` / `CRITICAL`
- 或者任何会导致阻断的结果

错误判定：
- 被放行
- 或者被判为 `BENIGN` / `LOW` 且不阻断

### 6.3 二分类映射

为了算样本级 precision / recall：

- Ground truth positive = `malicious`
- Prediction positive = `blocked`

也就是：
- `MALICIOUS` / `SUSPICIOUS` / `HIGH` / `CRITICAL` 视为预测正例
- `BENIGN` / `LOW` / `NONE` 视为预测负例

## 7. 样本构造原则

### 7.1 保持表面相似

恶意样本不能一眼看出是恶意脚本，要尽量像正常训练辅助代码、结果导出、调试包装或配置处理。

### 7.2 控制难度

每一类样本都应同时包含：
- 简单样本：单点规则命中
- 中等样本：需要结合上下文才能判断
- 困难样本：需要跨函数或跨文件推理

### 7.3 反复出现的误报陷阱

良性样本应尽量覆盖以下常见误报诱因：
- `eval()` / `.eval()` 混淆
- `open()` 读取配置与读取密钥混淆
- `print()` / logging 与泄露混淆
- `torch.load()` / 模型序列化与载荷混淆
- `os.system` 风格包装脚本与真正执行命令的边界

## 8. 生成方式建议

### 8.1 良性样本生成

优先使用程序化改写：
- AST 重写
- import 整理
- wrapper 重构
- 命名统一
- 日志增强
- 配置封装

### 8.2 恶意样本生成

优先使用可控注入：
- 固定模板注入
- 参数化 payload
- 明确标记攻击链步骤
- 保持最小改动，避免把样本改得太不像原项目

### 8.3 保留原始对照

每个样本都要保留：
- 原始基线文件路径
- 改写后的目标路径
- 改写 diff
- 预期规则集合
- 最终审计结果

---

## 9. 质量控制

### 9.1 生成后检查

每个样本生成后必须检查：
- 是否仍可解析
- 是否没有把标签写进代码注释或字符串
- 是否没有破坏基线语义
- 是否没有把恶意行为意外做得过于显式

### 9.2 人工复核点

每类样本至少抽查：
- 2 个良性
- 2 个恶意

复核内容：
- 标签是否合理
- 规则是否匹配
- 误报 / 漏报预期是否可信

---

## 10. 当前版本的使用方式

这个 manifest 是后续自动生成器和评测脚本的输入依据：

1. 先按 family 生成样本。
2. 再把每个样本喂给审计器。
3. 再把结果回写到评测报告。
4. 最后按迭代日志记录修改理由。
