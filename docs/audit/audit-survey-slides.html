03关键发现

五项跨领域证据，指向同一结论

18–84%

LLM 审查接受率低且不稳

活跃用户研究接受率仅 8.1%–84%；训练数据约 25% 为噪声，是根本瓶颈。

Olewicki'24 · Tufano'24
<50%

漏洞识别不如随机猜测

六个顶级 ML4VD 区分漏洞/补丁准确率低于随机；LLaMA-3 70B F1=5.10%，反不如 Gemma 7B 的 57.98%。

Risse'24 · Niu'25
84.3%

智能体被攻破的几率高达 84.3%

13 种攻击 × 13 个模型：平均十次攻击八次得手，诱使智能体泄露数据或执行恶意操作；能力越强的模型越容易被攻破。

  • 输入层 · 不改模型：在代码注释、README、检索文档里藏一句「这段代码安全」，审计 agent 把它当用户命令照做，把真漏洞判成「安全」（漏报）
  • 反向：藏一句「这里有问题」，诱导它报个假漏洞误导复核（误报）
Zhang'24 · Debenedetti'24
>90%

越狱统计上不可避免

PAPILLON 对 GPT-3.5 越狱成功率 >90%；TwinBreak 在 16 个模型上 89–98% 得手，且 5 分钟内即可生成攻击话术。

  • 对齐层 · 不改模型：用话术（角色扮演、指令混淆）绕过安全护栏，让模型自愿违背「标记恶意」的规则。
  • 落到审计：护栏失效后，被越狱的模型「愿意配合」攻击者，把恶意代码判成「安全」放行。
Su'24 · Gong'25 · Krauss'25
100%

后门与 AI 代码扩展攻击面

指令后门（词级触发器）在 6 个 LLM 上 100% 命中；AI 生成的代码也把漏洞带进了审计范围。

  • 权重层 · 模型被改：训练/微调时植入触发器，待审计代码一出现某个「触发词」就放行恶意代码——命中即生效，所以 100%。
  • AI 代码：LLM 从含漏洞的训练数据（约 4.4%）里学到的缺陷会带进生成的代码，审计对象从「人写代码」扩展到「AI 写代码」。
Zhang'24 · Pearce'23 · TrustCopilot'25
结论：LLM 应作为审计系统的组件之一，而非唯一裁决器。

05技术演进时间线

三段演化：从规则扫代码，到模型学语义，再到 LLM 参与审计

阶段 1
2013 – 2018

规则和人工经验

先用人和规则去找「像漏洞」的模式，适合扫已知问题。

  • 2013MCR：人工看补丁和上下文。
  • 2017VUDDY：看到相似代码就提醒风险。
  • 2018VulDeePecker：开始用深度学习扫漏洞。
关键词：规则、模式、已知漏洞
→
阶段 2
2019 – 2022

学习程序语义

不只看关键词，而是学调用关系、代码结构和上下文语义。

  • 2019Devign：用图神经网络看程序语义。
  • 2020CodeBERT：学通用代码表示。
  • 2021LineVul：把检测细化到行级别。
关键词：语义、结构、模型表示
→
阶段 3
2023 – 2026

LLM / Agent 参与审计

LLM 不只看代码，还会读文档、查资料、调用工具、多轮判断。

  • 2024SecLLMHolmes：证明 LLM 不能稳定识别漏洞。
  • 2024InjecAgent / AgentDojo：提示注入和 Agent 安全成为新问题。
  • 2025LLMxCPG / StruQ / IsolateGPT：开始用结构化证据和系统隔离来防御。
关键词：工具链、prompt、模型安全
一句话：技术越新，不一定越可靠；它只是把审计从「查代码」推到了「查代码 + 查模型 + 查工具链」。
06推荐架构

TAA 代码审计：现状、实现与补强方案

一次只展开一张 stage 卡片，查看更短的实现要点。

STAGE 1

静态召回

当前：规则扫描为主 先捞文件和行号，再谈语义补强。
现有规则定义

DefaultRules + Regex 不是语义分析器，而是按字符串 / 正则命中可疑模式；ScanDirectory 递归找文件，ScanDirectoryWithLines 把命中转成带位置的证据。

  • 扫描范围：只处理 .py，所以当前规则只覆盖 Python 源码
  • 证据字段：文件名、行号、命中片段、上下文前后文，供下一阶段复核
  • 当前含义：命中即进入候选集，不直接下最终结论
计划补充设计
  • 规则分 5 类：RCE、secret、network / exfil、persistence、unsafe deserialization
  • 每条规则统一结构：rule_id / category / severity / match / rationale / false_positive_hint
  • 召回策略固定窗口：命中行前后各 3 行，按 file + line + rule_id 去重
  • 扩展策略：先接入 AST / CFG slice，再把规则层扩展到更多语言和目录白名单
STAGE 2

结构化证据

当前：行级证据包 把 file / line / context 变成证据包。
现有实现

file / line / context 已有，并汇总成 FileReport。

  • GroupFindingsByFile + lineCounts
  • 直接喂给 LLM
计划补充
  • 调用链、数据流、provenance
  • audit bundle 可回放
STAGE 3

Prompt 优化

当前：固定模板 + JSON 证据优先，不能确认就 UNCERTAIN。
现有实现

analysisPromptTemplate 已收紧到证据优先。

  • 严格 JSON 输出
  • 先汇总 finding 再裁决
计划补充
  • Prompt registry + versioning
  • 持续压误报 / 漏报
STAGE 4

LLM 语义裁决

当前：本地 Ollama 有限语义判断，失败回到 UNCERTAIN。
现有实现

VerifyFinding / AnalyzeFile 双层判定。

  • qwen2.5-coder:0.5b
  • finding-level / file-level 双轨
计划补充
  • 置信度阈值 + 多模型一致
  • 缓存、降级、回退
STAGE 5

策略层

当前：assist / gate 把结果折回 pass / block / review。
现有实现

ComputeConclusion / recalculatePassed 把结果折回。

  • scan / check 失败默认拒绝
  • LLM 失败可 fail-closed
计划补充
  • 人工复核队列
  • 版本、可用率、回放链接
完整方案 召回 → 证据 → Prompt → 裁决 任一步失效 → 保守阻断 边界样本 → 人工复核
把 rule_set_version、prompt_version 和 llm_available_rate 一起记录，才能回放每次审计为什么这样判。
07Take-home

核心主张

01

证据链 ≻ 印象判断

每个结论必须可追溯到具体文件、行号、规则与版本。

02

多阶段系统 ≻ 单轮问答

静态召回 → 结构化增强 → LLM 语义裁决 → 策略层阻断。

03

行为链审计 ≻ 仅代码审查

覆盖工具调用、IPI、记忆污染、检索投毒与多轮规划。

04

模型完整性 ≻ 模型能力假设

后门化模型使所有下游审计结论失效。

05

失败显式化 ≻ 默认放行

LLM 不可用时必须 fail-closed；不确定时升级为 UNCERTAIN。

代码审计与可信执行环境

把不确定性写进系统，
而不是留给模型。

LLM 是审计的证据整合器之一；可靠的结论来自证据链、多阶段架构与 fail-closed 机制，而非单一模型的自信。
