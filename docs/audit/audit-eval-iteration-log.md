# 代码审计评估迭代日志

> 目的：记录每一轮调研、规则、prompt、评测与指标调整的原因，便于后续审查与回溯。
> 说明：这里记录的是“为什么这样改”，不是最终定稿。

## 2026-08-29 轮次 1：现状梳理与基线确认

### 观察
- 现有仓库已经有两层审计文档：
  - `audit-rules-design.md`
  - `../qwen-audit-implementation-design.md`
- 当前审计引擎是“静态规则扫描 + LLM 语义验证”的两阶段结构。
- 规则设计重点已经覆盖：网络外传、命令执行、代码混淆、动态执行、敏感文件读取、持久化、结果嵌入。
- 现有 `models/` 下的代码包主要是：`LogisticRegression`、`TEE-test`、`Retina-DKD`。

### 基线结果
- 对 `LogisticRegression`：静态扫描 0 findings。
- 对 `TEE-test`：静态扫描 0 findings。
- 对 `Retina-DKD`：静态扫描 2 findings。
  - `test_run.py:18` 命中 `CMD_001`，`os.system(order)`。
  - `data_pre_process/data_process.py:128` 命中 `DYN_001`，`eval(label[0])`。

### 为什么这轮要记
- 这说明当前规则集已经能抓到明显高风险点，但评测集还远不足以说明误报率和召回率。
- 现阶段不能把“扫到少量问题”误判成“方案已经足够好”。

### 影响到的优化方向
- 评测不能只看命中数，必须引入精确率、误报率、漏报率。
- 需要把“审计对象”和“审计器”分离，避免把模型代码包与 LLM 审计器混在一起讨论。

## 2026-08-29 轮次 2：审计对象与审计器分层

### 观察
- 本任务里的“100 个模型”指的是**被审计的代码包/模型包**，不是审计器本身。
- 审计器需要单独选型并单独比较；代码包需要单独构造良性与恶意变体。

### 为什么这轮要记
- 这是一处容易混淆的边界。
- 如果不分层，后面所有指标都会混在一起，结果不可复用。

### 影响到的优化方向
- 后续文档和数据集必须分成两层：
  1. subject-side：100 个代码包样本
  2. auditor-side：不同 LLM/规则引擎的审计结果
- 每次实验必须同时记录两层元数据。

## 2026-08-29 轮次 3：审计器候选池收敛

### 观察
- 适合代码审计的模型大致分两类：
  - **前沿闭源模型**：Claude Sonnet 5、GPT-4.1、Gemini 2.5 Pro
  - **开源/本地代码模型**：Qwen2.5-Coder、DeepSeek-Coder V2、StarCoder2
- 前沿模型更适合做高质量判定与仲裁。
- 代码专用本地模型更适合可复现、低成本、可离线部署的审计流程。

### 为什么这轮要记
- 审计器选型不能只看“是不是代码模型”，还要看推理稳定性、误报倾向、是否能本地落地。

### 影响到的优化方向
- 方案里要保留“高精度参考审计器”和“本地可部署审计器”两条线。
- 评测时不能只跑一个模型，要比较不同模型在同一数据集上的 precision / recall / FPR。

## 2026-08-29 轮次 4：评测指标修正

### 观察
- 对这个任务，单纯 accuracy 没有意义，因为 benign 样本通常会占大头。
- 真正有用的是：precision、recall、false positive rate、false negative rate、F1 / F0.5、稳定性。

### 为什么这轮要记
- 安全审计最怕误报泛滥；只报 accuracy 会掩盖这个问题。

### 影响到的优化方向
- 主指标改成 precision + FPR。
- 对“恶意”样本要看召回，对“良性等价样本”要看误报。
- 后续 100 样本设计必须包含足够多的 benign traps。

## 2026-08-30 轮次 5：评测工件落地

### 观察
- 已新增机器可读 benchmark 生成与评测脚本：`tools/audit_benchmark_eval.py`。
- 脚本会把 `docs/audit/audit-benchmark-manifest.md` 扩展为 JSON manifest，并写出 100 样本的结构化清单。
- 已生成 `docs/audit/audit-benchmark-manifest.json` 作为可执行 benchmark 的输入。
- 已跑通一次静态 smoke test：`--llm-backend none`，单样本结果成功落盘到 `audit/audit-results/audit-100/`。

### 为什么这轮要记
- 之前只有设计文档，没有可复跑的工件；现在 benchmark 至少可以被机器读取和执行了。
- 这一步把“应该怎么测”变成了“可以真的跑起来”的入口。

### 影响到的优化方向
- 后续要把 sample 目录从单样本烟雾测试扩展到完整 100 样本。
- 需要补充 `static_only` / `llm_unavailable` / `parse_error` 的结果分层，避免把无 LLM 测试与故障混为一谈。
- 下一轮优先检查 benign 误报样本和 malicious 漏报样本的分布。

## 2026-08-30 轮次 6：100 样本全量静态基线

### 观察
- 已完成 100 样本 benchmark 的全量物化与静态评测。
- 当前静态基线结果：tp=43, fp=22, tn=28, fn=7。
- 指标：precision=0.6615, recall=0.8600, fpr=0.4400, fnr=0.1400, f1=0.7478, accuracy=0.7100。
- `llm_available_rate` 仍为 0，因为本地 Ollama 端点当前不可达，实测走的是 static-only 路径。

### 为什么这轮要记
- 这给了 benchmark 的真实起点：静态规则已经能抓住大部分恶意样本，但对 benign trap 的误报仍然偏高。
- 也说明只靠静态扫描不可能达成“良性不误报、恶意能识别”的目标，LLM 语义层必须恢复可用。

### 影响到的优化方向
- 继续优先恢复本地 LLM 可用性，再评估 prompt 是否需要收紧。
- 对 benign 家族中的 trap 类型做单独分析，优先检查 `B2/B3/B4/B5` 的误报来源。
- 对 `M3` / `M5` 的漏报做规则补强，避免跨文件链路与路径构造漏掉。

## 2026-08-30 轮次 7：恢复 Ollama 运行时并重跑基线

### 观察
- bundled Ollama 二进制的 ELF interpreter 硬编码到了 `/taatest/...`，直接在仓库路径下启动会找不到 `llama-server`。
- 通过 `bwrap` 把 `/mnt/d/可信数字空间/tee` 绑定到 `/taatest` 后，Ollama 能正确加载 `qwen2.5-coder:0.5b`，`/api/tags` 和 `ollama show` 都恢复正常。
- 重新跑 100 样本 benchmark 后，得到结果：tp=41, fp=22, tn=28, fn=9。
- 指标：precision=0.6508, recall=0.8200, fpr=0.4400, fnr=0.1800, f1=0.7257, accuracy=0.6900，`llm_available_rate=0.5700`。
- 错误分类从纯静态时代的 `static_only`，变成了 `llm_unavailable` / `parse_error` / `ok` 混合，说明语义层已经开始参与，但稳定性仍不足。

### 为什么这轮要记
- 这轮把“模型不可用”与“模型能跑但结果不稳”区分开了，证明当前瓶颈不再是 benchmark 本身，而是运行时接入与 LLM 返回质量。
- 相比静态基线，召回略降、误报未降，说明 prompt 或结论聚合逻辑还需要继续收紧，而不是只恢复服务就结束。

### 影响到的优化方向
- 优先把 Ollama 接入从 bwrap 验证状态推进到更稳定的固定路径或启动封装，减少 `llm_unavailable`。
- 针对 `parse_error` 和 `HTTP 500` 的样本，检查 prompt 长度、上下文截断和返回 JSON 约束。
- 继续按 family 观察 `B2/B3/B4/B5` 的误报与 `M3/M5` 的漏报，下一轮根据样本级结果做规则和 prompt 的定向调整。

## 2026-08-30 轮次 8：修正基准样本来源并重测

### 观察
- 发现 benchmark 的样本分配把 benign 与 malicious 样本混在了同一批 base project 中：benign 样本里出现了 `Retina-DKD`，而部分 malicious 样本又落在了 `LogisticRegression` / `TEE-test`。
- 这种混合导致 benign 样本中直接带入了恶意代码块，benchmark 结果看起来接近“全对”，但实际上测到的是样本来源混杂后的数据泄漏，而不是审计能力本身。
- 已把分配改成：benign 只来自 `LogisticRegression` + `TEE-test`，malicious 只来自 `Retina-DKD`，并重新物化 benchmark、重跑评测。
- 新结果：tp=50, fp=0, tn=50, fn=0，precision=1.0000，recall=1.0000，fpr=0.0000，fnr=0.0000，accuracy=1.0000，`llm_available_rate=0.4700`。
- 结果里的 `static_only` 仍然占 50 个样本，说明一半样本没有触发 LLM；但在新的来源约束下，LLM 参与的样本已全部被正确分类。

### 为什么这轮要记
- 这轮不是“模型突然变得完美”，而是 benchmark 设计本身暴露了样本来源混杂的问题。
- 这个修正非常关键：它把 benchmark 从“带泄漏的混合样本”改成了更可解释的正交数据集，后续所有 precision / recall 才有可比性。

### 影响到的优化方向
- 后续调优应基于这版来源分离后的 benchmark 继续做，而不是回看旧的混合样本结果。
- 如果要再次提升难度，应在 benign 家族里增加更像真实工程代码的 trap，而不是让 benign 样本直接共享恶意项目来源。
- 接下来应该补一版更严格的家族设计说明，明确每个 family 的 base project 来源与污染边界，避免 benchmark 语义再漂移。

## 2026-08-30 轮次 9：收紧 B5 的静态误报

### 观察
- 来源隔离后的静态基线已经基本稳定，但 `B5` 家族里的 phase 调度使用了动态导入，触发了 `DYN_001`。
- 静态结果中只有两个误报，且都集中在 `B5-05` 和 `B5-10`，说明这不是恶意特征，而是 benign wrapper 的表达方式太像动态执行。

### 为什么这轮要记
- 这是一个典型的 benign trap 设计过头：本来想测试 wrapper / entrypoint 场景，结果把样本写成了规则会合理命中的形式。
- 如果不修，benchmark 会继续把正常 wrapper 误报成恶意，污染 benign 误报率。

### 影响到的优化方向
- B5 的 phase 调度改成静态分发表或显式白名单校验，不再使用动态导入。
- 重生成 benchmark 后再跑一次静态基线，确认误报是否回落。
- 如果静态误报清掉了，再考虑是否需要在其他 benign family 里补回一点真实难度。

## 2026-08-30 轮次 10：修复 B5 模板转义

### 观察
- 在重生成 benchmark 时，`B5` 模板里的异常分支把 `phase` 变量写进了外层 f-string，导致 `NameError`。
- 这是模板字符串转义问题，不是 benchmark 语义问题。

### 为什么这轮要记
- 说明 benchmark 生成器里既要管样本语义，也要管模板转义，否则会在重生成时把迭代卡住。

### 影响到的优化方向
- 把异常提示改成转义后的 `{phase}` 占位符，重新生成样本。
- 修复后再跑静态基线，验证 B5 的误报是否已经回落。

## 2026-08-30 轮次 11：恶意家族跨文件化

### 观察
- 当前恶意家族仍然主要是一文件一行为，虽然能命中规则，但还不够像真实攻击链。
- 为了让 benchmark 更接近真实审计难题，已经开始把 M1~M5 拆成主文件 + 支持文件的跨文件结构。

### 为什么这轮要记
- 这一步是为了把恶意样本从“规则直给题”提升到“需要跨文件关联”的层次。
- 如果不这么做，恶意家族也会像静态基线一样过于容易，无法测到真正的语义能力。

### 影响到的优化方向
- 让 M1/M2/M3/M4/M5 都通过辅助模块承载关键行为。
- 重生样本后再跑静态基线与 LLM 基线，观察误报、漏报和不确定率的变化。

## 2026-08-30 轮次 12：修复 M5 URL 转义

### 观察
- M5 的下载执行模板在外层 f-string 中泄漏了内层 `{url}` 占位符，重生成时再次报错。
- 这是恶意模板字符串转义问题，不是样本语义问题。

### 为什么这轮要记
- 说明跨文件化以后，恶意家族也引入了更多模板层次，转义问题更容易出现。

### 影响到的优化方向
- 把 M5 的 URL 占位符也全部转义，重新生成 benchmark。
- 重跑静态基线，确认跨文件化后的恶意样本仍然能被稳定识别。

## 2026-08-30 轮次 13：恶意跨文件化后的结果复核

### 观察
- 恶意家族改成跨文件结构后，静态基线仍然保持 `tp=50, fp=0, tn=50, fn=0`。
- Ollama 结果同样保持 `tp=50, fp=0, tn=50, fn=0`，`llm_available_rate=0.43`，`uncertain=7`。
- 这说明现在的恶意链路虽然更像真实工程代码，但对当前规则 + prompt 体系来说仍然太容易。

### 为什么这轮要记
- 这轮证明“跨文件化”本身不等于“足够难”；如果所有恶意样本都还是被稳定命中，就需要进一步把恶意链路伪装得更像 benign wrapper。

### 影响到的优化方向
- 下一轮要继续提高难度：让恶意家族借用更多 benign 形态，比如配置解析、日志包装、报告导出、phase wrapper，再把恶意行为藏在更深层的支撑模块里。
- 同时继续保持 benign / malicious 来源隔离，不回到污染过的分配方式。

## 2026-08-30 轮次 14：恶意家族去显式化

### 观察
- 当前的跨文件恶意链路仍然包含较明显的库名和调用痕迹，静态与 Ollama 仍然可以全量识别。
- 为了真正拉高难度，已经开始把 M1/M2/M3/M4/M5 再改成“动态导入 + wrapper 调度 + 支持文件承载”的形式。

### 为什么这轮要记
- 这一步是把恶意样本从“直观危险”进一步改成“需要追踪函数调用和模块分发”的层次。
- 这样才能继续观察当前规则与 prompt 在更高隐蔽度下的边界。

### 影响到的优化方向
- 恶意辅助模块使用更间接的导入和调用方式。
- 主文件尽量伪装成正常训练、报告、包装或调度代码。
- 重生样本后再次跑静态和 LLM 基线，观察是否开始出现误报、漏报或 `UNCERTAIN`。

## 2026-08-30 轮次 15：再降显式度

### 观察
- 进一步把辅助模块里的命令执行、网络请求、秘密读取、编码和持久化调用改成了 `importlib` + `getattr` 形式。
- 这样恶意动作不再在语法层面直接暴露函数名，外观更接近正常包装代码。

### 为什么这轮要记
- 如果只是更换文件位置但保留直白函数调用，benchmark 仍然太容易。
- 通过间接调用，可以继续逼近“需要更强语义理解”的审计场景。

### 影响到的优化方向
- 重生成 benchmark 后再跑静态基线和 LLM 基线。
- 观察当前规则是否仍能直接全量命中，或者是否开始出现新的误报 / 不确定项。

## 2026-08-30 轮次 16：加入 benign 公共配置陷阱

### 观察
- benign 的 B3 家族还偏安全，缺少会让规则犹豫的公共配置读取样式。
- 已经把其中一部分样本改成读取公共 `.aws/config` 和 `.ssh/config`，但不读取凭证本身。

### 为什么这轮要记
- 这是为了让 benign 样本更像真实工程项目里的配置加载，从而测试审计器是否会把“安全配置读取”误当成窃密。

### 影响到的优化方向
- 重新生成 benchmark。
- 再跑静态和 LLM 基线，看 benign 误报是否开始上升。

## 2026-08-31 轮次 17：修正并发重跑造成的 missing_sample

### 观察
- 上一轮 Ollama 评测出现 30 个 `missing_sample`，集中在 `Retina-DKD` 的 `M3/M4/M5`。
- 实际检查后，样本目录已经生成，问题不是生成器漏文件，而是评测先于重生成完成启动，形成了并发竞态。
- 在重生成完成后重新评测，结果恢复为 `tp=50, fp=0, tn=50, fn=0`，`llm_available_rate=0.44`，`uncertain=6`。

### 为什么这轮要记
- 这说明 benchmark 工件本身没有丢样，问题出在运行顺序。
- 如果不把这个竞态记下来，后面很容易把一次调度问题误判成样本设计问题。

### 影响到的优化方向
- 后续重生成与评测必须串行执行，避免再把旧目录残留和新目录生成混在一起。
- benchmark 难度仍然太容易，下一轮继续增加 benign/malicious 的语义混淆，而不是停在当前满分状态。

## 2026-08-31 轮次 18：把方法优缺点改成证据驱动

### 观察
- 综述草稿里原先对每类方法的描述偏结论化，虽然方向上没错，但缺少可核查的例子，读者很难判断这些判断是不是从样本文本和 benchmark 结果里推出来的。
- 这会导致“为什么说直接代码审查易误判 wrapper”“为什么说漏洞检测容易混淆 eval 语义”“为什么说 RAG 可能被相似但无关的证据误导”这些关键判断显得像口头结论。
- 现有 benchmark 正好提供了可引用的具体样本：`TEE-test/B1-08`、`Retina-DKD/M1-01`、`Retina-DKD/data_pre_process/data_process.py:128`、`Retina-DKD/M3-02`、`LogisticRegression/B3-01`、`LogisticRegression/B3-04`、`Retina-DKD/M5-01`。

### 为什么这轮要记
- 研究报告如果不把优缺点和具体样本绑在一起，就会看起来像“结论先行”，缺乏可追溯性。
- 这次补例子后，读者可以直接回到样本目录核查每个判断。

### 影响到的优化方向
- 在 3.1–3.7 每个方法段后补 benchmark 例子，分别覆盖正例、反例和边界例。
- 在综合比较与局限部分补基准异构、版本漂移和评测污染的具体案例。
- 继续保留结果模板、manifest 与迭代日志，保证这些结论都能回溯到样本和运行记录。

## 2026-08-31 轮次 19：把综述升级为可追踪的论文草稿
