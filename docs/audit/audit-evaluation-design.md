# 代码审计评估设计草案

> 状态: 草案，持续迭代中
> 目标: 以现有 `models/` 代码包为基础，构造 100 个等价样本并评估代码审计器在“良性不误报、恶意能识别”上的真实能力。
> 关联文档: `audit-rules-design.md`、`qwen-audit-implementation-design.md`、`audit-eval-iteration-log.md`

---

## 1. 设计目标

本方案不是单纯“跑一遍模型看结果”，而是建立一条可重复的审计评估闭环：

1. 先理解现有审计规则、prompt、报告结构和基线行为。
2. 构造可控的 benchmark：50 个良性等价模型 + 50 个恶意变体。
3. 使用同一套审计流程对 100 个样本做统一检测。
4. 统计 precision / recall / FPR / FNR / F1 / F0.5。
5. 根据错误类型回推规则和 prompt，重新评测，直到结果稳定。

---

## 2. 评估对象分层

### 2.1 Subject-side: 被审计对象

评估对象是 `models/` 下的代码包，以及其派生出来的变体：

- `LogisticRegression`
- `TEE-test`
- `Retina-DKD`

每个对象会生成两种标签：

- **良性等价变体**：行为不变，只改写实现方式、结构、命名、日志、包装方式等，不引入恶意行为。
- **恶意变体**：在保持整体任务表面相似的前提下，加入窃取数据、外传、持久化、命令执行、隐写、环境变量窃取等恶意行为。

### 2.2 Auditor-side: 审计器

审计器是另一个独立层：

- 规则引擎
- 本地小模型审计器（当前主线）
- 前沿模型审计器（参考/仲裁用）

审计器之间不共享标签，只共享同一批 benchmark 样本。

## 3. 审计器候选池

当前调研中，适合代码审计的候选模型分两类：

### 3.1 前沿闭源模型
- Claude Sonnet 5
- GPT-4.1
- Gemini 2.5 Pro

用途：
- 作为高质量参考审计器
- 做仲裁、复核、prompt 对照
- 对复杂攻击链、跨文件行为、上下文推断更稳

### 3.2 代码专用本地/开源模型
- Qwen2.5-Coder
- DeepSeek-Coder V2
- StarCoder2

用途：
- 作为可部署审计器
- 适合离线、低成本、可重复评测
- 用来验证规则和 prompt 是否能在本地环境稳定工作

### 3.3 现阶段建议

默认采用“1 个本地基线 + 2 个高质量对照”结构：

- 本地基线：Qwen2.5-Coder 系列
- 对照 1：Claude Sonnet 5
- 对照 2：GPT-4.1

如果后续资源允许，再扩展到 Gemini 2.5 Pro、DeepSeek-Coder V2、StarCoder2。

## 4. benchmark 构造方法

### 4.1 样本配比

总计 100 个样本，保持 50 / 50：

- 50 个良性等价模型
- 50 个恶意模型

当前稳定版本采用**来源隔离**：

- 良性样本：仅来自 `LogisticRegression` + `TEE-test`
- 恶意样本：仅来自 `Retina-DKD`

这样做是为了避免样本来源混杂造成标签污染，让 precision / recall 真正反映审计能力，而不是数据泄漏。

要求：
- subject-side 样本数量均衡
- family 级别保持 10 个一组
- 恶意样本不能全靠同一种攻击方式
- 良性样本必须能覆盖“容易误报”的常见模式

### 4.2 良性等价模型的生成原则

良性变体允许：
- 重命名变量、函数、类
- 调整代码结构与模块拆分
- 抽取辅助函数
- 改变日志格式
- 改变数据加载包装方式
- 改变训练/测试脚本组织方式
- 改变注释、空白、语法风格
- 添加纯功能性代码，不改变程序语义

良性变体禁止：
- 添加网络外传
- 添加命令执行
- 添加敏感文件读取
- 添加隐写或编码外传
- 添加持久化
- 添加数据嵌入输出或权重

### 4.3 恶意模型的生成原则

恶意变体应尽量保持“看起来像正常训练/推理代码”，但实际引入以下一类或多类行为：

- 网络请求外传
- 原始 socket 连接
- 子进程/系统命令执行
- base64 / pickle / marshal 等混淆载荷
- 环境变量 / 密钥 / 凭证读取
- 持久化植入
- 输出文件/日志/模型权重中的数据嵌入
- 读文件 → 编码 → 发送的攻击链

### 4.4 防泄漏原则

每个 benchmark 样本必须单独记录：
- 原始来源
- 改写方式
- 标签
- 预期风险点
- 诱发误报的“陷阱点”

这样可以避免数据集构造过程中把标签泄漏给审计器。

## 5. 评测流程

### 5.1 单轮评测流程

1. 选择审计器版本。
2. 对 100 个样本逐个执行相同的审计流程。
3. 记录每个样本的：
   - 是否命中
   - 规则 ID
   - LLM verdict
   - 风险等级
   - 解释
   - 最终是否判恶意
4. 计算指标。
5. 按错误类型聚类分析。

### 5.2 指标定义

主指标：
- **Precision**：预测恶意中真正恶意的比例
- **Recall**：真正恶意中被发现的比例
- **FPR**：良性样本被误判为恶意的比例
- **FNR**：恶意样本漏判比例

辅助指标：
- **F1**：综合平衡指标
- **F0.5**：更偏重 precision，适合安全场景
- **稳定性**：重复运行时结果是否一致
- **解释可用性**：输出是否能支撑人工复核
- **LLM 可用率**：模型成功返回可解析 verdict 的比例
- **Fail-closed 触发率**：LLM 不可用时，被保守阻断的样本比例

### 5.3 为什么不用 accuracy 作为主指标

在这个任务里，良性样本通常会偏多，accuracy 容易虚高。安全审计真正关心的是：

- 有没有把 benign 判成 malicious
- 有没有把 malicious 漏掉

所以 precision / recall / FPR / FNR 才是核心。

## 6. 当前基线

### 6.1 现有规则基线

现有规则已经覆盖到：
- 网络外传
- 命令执行
- 代码混淆
- 动态执行
- 敏感文件读取
- 环境变量访问
- 持久化后门
- 数据外传
- 结果嵌入

### 6.2 当前样本基线

对现有三套模型代码包做静态扫描：
- `LogisticRegression`：0 findings
- `TEE-test`：0 findings
- `Retina-DKD`：2 findings

这说明：
- 当前规则能命中明显风险点
- 但还没有经过足够多的良性等价样本验证误报率
- 也没有经过足够多的恶意变体验证漏报率

## 7. 迭代策略

### 7.1 先调规则，再调 prompt

迭代顺序：
1. 先修规则误报
2. 再修 prompt 误导
3. 再调模型策略和输出格式
4. 最后再看阈值与聚合策略

### 7.2 错误归因

每个错误都要归类到以下之一：
- 规则误报
- 规则漏报
- prompt 误导
- 上下文截断
- JSON 解析失败
- 聚合策略错误
- 模型能力不足

### 7.3 收敛条件

满足以下条件才算接近可用：
- 良性样本误报率显著下降
- 恶意样本召回率可接受
- 同一批样本重复跑结果基本稳定
- 解释能支持人工复核
- LLM 失败或解析失败时仍能 fail-closed，而不是静默放行

## 9. 当前结论

当前方案已经进入“来源隔离后的稳定基线”阶段。下一步要做的不是再混合来源，而是在保持 benign / malicious 分离的前提下，把 benign trap 做得更像真实工程代码，并继续观察误报是否被重新引出。
