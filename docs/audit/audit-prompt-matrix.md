# 代码审计 Prompt 矩阵

> 状态: 草案
> 用途: 记录当前审计器 prompt 的版本、目标、优缺点和后续优化方向。
> 关联文档: `audit-evaluation-design.md`、`audit-eval-iteration-log.md`

---

## 1. Prompt 设计目标

审计 prompt 不是让模型“自由发挥”，而是让它稳定输出三类内容：

1. **判断**：恶意 / 可疑 / 良性 / 不确定
2. **理由**：简短、可复核、指向代码上下文
3. **风险**：明确说出为什么危险或为什么可接受

---

## 2. 当前 prompt 结构

### 2.1 Finding 级 prompt

当前设计要求：
- 输入文件名、行号、上下文、规则 ID、类别、描述
- 输出严格 JSON
- 低温度
- 面向单个触发点判断

### 2.2 File 级 prompt

当前设计要求：
- 输入文件摘要、发现数量、文件级代码片段
- 输出风险等级、摘要、链式行为、外传行为
- 用于聚合多个 finding 的上下文

---

## 3. 当前优点

- 结构简单，容易落地
- 兼容本地小模型
- 已经能覆盖单点风险和文件级组合风险
- 可以直接嵌入到 TAA 流程中

---

## 4. 当前不足

### 4.1 输出解析脆弱

当前实现通过文本正则提取 JSON，遇到复杂嵌套、额外解释或格式波动时容易失败。

### 4.2 提示词仍偏描述性

现有 prompt 更像“让模型自己判断”，缺少明确的判定优先级：
- 先看上下文
- 再区分“敏感信息访问”与“正常配置读取”
- 再看是否真有外传、持久化或载荷隐藏
- 再看是不是框架常见 API

### 4.3 缺少 reject/uncertain 规则

如果上下文不足、无法判断或输入不完整，prompt 里没有强制模型显式返回 `UNCERTAIN`。

### 4.4 benign trap 需要显式豁免

像配置读取、训练参数、报告导出、路径封装、日志统计这类 benign trap，应在 prompt 中明确要求判为 BENIGN，避免把普通工程代码误判成恶意。

---

## 5. 建议的优化方向

### 5.1 结构化约束更强

- 明确要求只输出 JSON
- 明确要求字段顺序
- 明确要求不能输出额外说明
- 明确要求无法判断时返回 `UNCERTAIN`

### 5.2 增加判定步骤

建议 prompt 中要求模型按顺序思考：
1. 这是不是安全相关 API？
2. 有没有上下文证明它是良性用法？
3. 有没有数据外传 / 载荷隐藏 / 持久化意图？
4. 如果证据不足，是否应保守返回 `UNCERTAIN`？

### 5.3 增加对 benign trap 的约束

对于容易误报的模式，prompt 中要明确要求识别良性上下文，例如：
- `.eval()` 的模型评估模式
- 训练指标日志
- 配置读取
- 正常报告生成

---

## 6. Prompt 版本控制建议

每次改 prompt 时必须记录：
- 版本号
- 改动点
- 改动原因
- 影响的样本 family
- 是否提升 precision / recall

建议和 benchmark 结果绑定，避免只凭主观感觉改 prompt。

---

## 7. 当前结论

当前 prompt 可以作为第一轮基线，但还需要在实际跑分后继续收紧：
- 更强的 JSON 结构约束
- 更明确的 `UNCERTAIN` 触发条件
- 更明确的 benign trap 识别规则
