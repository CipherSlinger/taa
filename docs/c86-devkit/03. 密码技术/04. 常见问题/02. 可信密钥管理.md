## 1. 环境依赖与版本兼容

### Q: 某些用户使用 glibc 版本为 2.13 时链接 hct 动态库失败

我们发布的动态库包含一些 2.17 版本的 glibc 符号，例如 `secure_getenv@@GLIBC_2.17`，因此推荐用户升级自己的 glibc 环境到 2.17 及以上。

### Q: HCT库新旧版本混用导致执行报错

**现象**：

- 先执行旧版本后（如HCT2.0），新版本执行报错：`current psp_config runtime version 5, but local record version 3`
- 先执行新版本后（如HCT3.0），旧版本执行报错：`open mmio failed with No such file or directory`

**原因**：HCT2.0与3.0间由于架构优化，存在多版本共用不兼容情况；版本使用建议见：[版本使用建议](../HCT版本说明和阅读指引.md)

**解决方案**：

1. 统一使用相同版本的HCT，确保 hag 工具和应用进程所使用的 so 版本一致。
2. **重要**：若已出现以上混用异常，需要将版本统一后，**重启系统**以恢复执行环境。

## 2. 初始化与运行报错

### Q: 初始化时 psp mmio mmap 映射失败

初始化时 psp mmio mmap 映射失败，返回错误码：22 - Invalid argument，龙蜥系统（OS：NAME="Anolis OS" VERSION="8.4" 5.10.134-13.1.an8.x86\_64）发现。

原因是内核的 `CONFIG_IO_STRICT_DEVMEM` 配置为 y 会导致不允许用户态访问 pci 空间导致，龙蜥系统存在。

**解决方案（二选一）**：

1. 一个绕过方案：`grubby --update-kernel=ALL --args="iomem=relaxed"`。
2. 将 `CONFIG_IO_STRICT_DEVMEM` 配置为 n 重新编译内核

### Q: tkm 初始化时报错：psp\_pci\_device failed

两种可能性会导致出现 `psp_pci_device failed`：

1. 内核版本在 5.10 以下并且开启了 SME 功能，有可能是缺少了[这个内核补丁](https://github.com/torvalds/linux/commit/f8f6ae5d077a9bdaf5cbf2ac960a5d1a04b47482)
2. 把主 PSP 绑定到 vfio-pci 上了

**可以通过以下两种方式解决（二选一）**：

1. 安装 vfio-pci 驱动时，添加 `disable_idle_d3=1` 参数：
   
   ```bash
   modprobe vfio-pci disable_idle_d3=1
   ```
   
   若方式一未生效，需要确认客户内核是否打了海光 CPU 基础补丁，未打基础补丁的内核即使配置了 `disable_idle_d3=1` 也可能没有效果（奇安信遇到过此问题）

2. 在 psp 已经绑定了 vfio 驱动的情况下，假设 psp pci 设备 id 为 `0000:22:00.1`，手动解除绑定：
   
   ```bash
   echo -n "0000:22:00.1" > /sys/bus/pci/drivers/vfio-pci/unbind
   ```

### Q: 主机下 TKM/SDF 返回 platform\_init 失败，错误码 -6

**现象**：使用 TKM/SDF 时，主机下首个进程返回 platform\_init 失败，错误码为 -6（`OSAL_ERROR_INVALID_CERTIFICATE`），platform\_status 为 uinit，确认内核有 `/dev/sev` 节点。

**原因**：机器 flash 中已经有了 CPU 证书信息，之后机器换了 CPU 导致 CPU 与 flash 中证书对不上导致。

**解决方案**：采用 `hag csv factory_reset` 命令来将证书信息去除，之后重新 platform\_init 即可恢复正常。

### Q: 密钥隔离虚拟机执行 hag tkm dev\_info\_get 命令返回 -7

**现象**：虚拟机执行任意命令都会返回 -7 错误。

**原因**：检查 qemu 启动时指定的 vid 参数。是否真实被创建了。

**解决方案**：在物理机创建 vid 后再启动虚拟机。

### Q: 麒麟桌面版 V10 SP1 初始化 SDF 失败

**现象**：

1. hag 命令无法运行，即使有可执行权限以及 root 下跑也无法执行
2. `SDF_OpenDevice` 时报，`shm_open` 失败，`Permission denied`

**原因**：

1. 原因为该 OS 下默认配置应用程序策略为阻止
2. 原因为麒麟自身 KID 机制影响，KID：基于应用 id 标记将系统资源等级进行分类分层划分，通过对系统资源访问权限管控，实现系统资源完整性保护

**解决方案**：

1. 在"安全中心 → 应用控制与保护 → 应用程序执行控制"中将策略调整为关闭
2. 通过 `setstatus disable` 关闭，之后恢复正常

## 3. 配置与密钥管理

### Q: SDF 的 sdf\_config/hct\_config 配置文件中的内容是什么意思

#### 一、hct\_config（HCT 3.0）

##### 1. 默认配置说明

以下为必填/出厂默认配置项，缺失 `filekey_index` 与 `filekey_auth` 会导致 `SDFOpenDevice` 失败：

```json
{
    "filekey_index" : 1,
    "filekey_auth" : "11111111",
    "hct_log_level" : "error",
    "balance_policy" : "auto"
}
```

| 配置项 | 类型 | 含义 | 默认值 |
|---|---|---|---|
| `filekey_index` | int | 文件密钥（KEK）索引。SDF 打开设备时**必须配置**，否则返回 `SDR_NOTSUPPORT` | 1 |
| `filekey_auth` | string | 文件密钥口令，用于计算文件密钥认证码 | 11111111 |
| `hct_log_level` | string | 日志级别：`error`/`warning`/`info`/`debug`/`auth`。 `auth` 为开启认证审计日志，接口调用日志记录到/var/log/hct/auth.log，同时日志级别设为 error | `error` |
| `balance_policy` | string | 算法走硬件 CCP 还是软件 CIS 的负载均衡策略：`ccp`/`cis`/`auto`，TKM/SDF中涉及带密钥管理的私钥及对称密钥运算不受该配置影响。 | `auto` |

##### 2. 其他附加配置说明

以下为可选调优/功能扩展配置项：

| 配置项 | 类型 | 含义 | 默认值 |
|---|---|---|---|
| `sk_cache_num` | int | 会话密钥密文缓存条数上限，范围 \[0, 4\] | `4` |
| `unified_kek_auth` | "on"/"off" | 是否统一 KEK 认证。off 时 SM4 类型 KEK 跳过统一认证检查 | `on` |
| `gcm_64GB_limit` | "on"/"off" | SM4-GCM 单密钥 64GB 数据上限保护（防止 IV 重用） | `on` |
| `hcm` | "on"/"off" | HCM（[Hygon Cryptographic Monitoring Tool](<../02. 用户指南/通用指南/04. 海光密码模块状态检查工具使用手册.md>)）开关，on 时上报 SM2/RSA/SM3/SM4 运算状态/错误码 | `off` |

#### 二、sdf\_config（HCT 2.0）

```json
{
  "filekey_index" : 1,
  "filekey_auth" : "11111111",
  "hct" : "on",
  "signalcatch" : "on"
}
```

| 配置项 | 类型 | 含义 | 默认值 |
|---|---|---|---|
| `filekey_index` | int | 预留该 KEK 密钥给文件操作接口使用，用户需要提前配置好该 KEK 后才能使用文件操作接口。 | 1 |
| `filekey_auth` | string | 文件加密密钥授权口令 | 11111111 |
| `hct` | "on"/"off" | 非敏感接口是否调用 HCT-CAE（密码加速引擎）的开关，配置为 `"off"` 时可关闭 HCT-CAE 调用，使用纯软件运算。 | `on` |
| `signalcatch` | "on"/"off" | 是否在驱动中抓取异常信号（如段错误等），用于抓取对应异常日志并主动在终端输出提醒用户。默认 `on` 时抓取，若需关闭配置为 `off`。 | `on` |

### Q: SDF 中 KEK 不需要授权的使用方法

**现象**：默认配置 KEK 需要权限，其通过统一授权接口 `SDF_GetPrivateKeyAccessRight` 授权，此时不能使用HYSDF\_GetKEKAccessRight（会返回错误），0018 标准中该接口主要对非对称密钥授权，KEK 无需授权。

**原因**：我方及部分用户认为 KEK 不授权存在安全隐患，因此增加了该授权要求，但考虑到有用户有严格按照标准的需求，因此增加了通过配置方式与标准一致。

**解决方案**：若不想使用权限，可以通过 `/etc/sdf_config`(hct2.0)或 `/etc/hct_config` (hct3.0) 中配置为非统一授权：`"unified_kek_auth" : "off"`，配置后，生成 KEK 时不输入授权信息，即授权位置传入 NULL，则不需要调用授权接口即可使用；若生成 KEK 时输入授权信息，则依然需要授权才能使用，此时授权接口为HYSDF\_GetKEKAccessRight。

### Q: 如何查询密码模块中密钥的类型、数量等信息？

A: 推荐使用 hag 工具的密钥信息查看命令，命令会根据当前环境（主机或虚拟机）展示对应密钥空间的情况，包括支持的密钥类型、每种类型的最大密钥数量以及当前已使用的密钥数量。常用命令如下：

- 查看当前环境的密钥使用情况（**主机、虚拟机下均可使用**）：

```
sudo hag tkm get_key_usage
```

- 查看主机下指定 vid 对应密钥空间的密钥使用情况（**仅主机下可使用**）：

```
sudo hag tkm vtkm_key_usage_by_vid -vid 1
```

- 查看主机下所有 vid 对应密钥空间的密钥使用情况（**仅主机下可使用**）：

```
sudo hag tkm vtkm_all_key_usage
```

各命令的输出示例、图中字段含义及更多 TKM 密钥操作命令，可参考[TKM命令说明](<../02. 用户指南/通用指南/05. TKM命令说明.md>)。

## 4. 固件、系统与性能

### Q: tkm 接口性能波动的问题，在不同的 BIOS 版本和机器上，性能可能存在差异

影响性能的原因有两点：

1. **numa0 是否存在物理内存**：使用 `cat /sys/bus/node/devices/node*/meminfo | grep MemTotal` 检查物理各个 node 上的内存分布。如 node0 无内存，应该更换内存条的插槽。
2. **BIOS 版本差异**：各个 BIOS 版本由于编译时会导致代码布局变化，影响指令 cache 的访问效率，具体性能除开参考测试文档外，还应该实际按照各个 BIOS 版本为主。

### Q: download firmware 返回 2066

**现象**：海光 4 号 download firmware 返回 -2066（0x812）错误码。

**原因**：安全固件验证失败，常见错误原因如下：

- 海光 4 号和 3 号的安全固件不通用，交叉使用会报该错误
- 海光 4 号的 PI 版本小于 PI 4606 时（bootloader 版本小于等于 3.7.1.251），存在已知问题

**解决方案**：升级 BIOS 版本大于等于 PI 4606。

### Q: 通过 grubby 设置 memmap=32M\\$512G 无效

**现象**：使用以下参数设置 grub 参数：

```bash
sudo grubby --update-kernel=ALL --args="memmap=32M\\$512G"
```

重启后，进 grub 菜单查看只剩下 `memmap=32M\`，$ 后的所有符号都消失了。无论 update-kernel 时前面加多少个 `\` 都是一样的效果。

**原因**：grubby 是 BLS 的管理工具。BLS (Boot Loader Specification) 是一种启动加载器规范，使用 `/boot/loader/entries/` 目录下的 `.conf` 文件管理启动项，这个优先级比 grub.cfg 文件更高，所以重新生成 grub.cfg 是无效的。BLS 解析 grub 参数应该本身就有问题，对 `$` 忽略了转义符号。

**解决方案**：关闭 BLS 功能，编辑 `/etc/default/grub`，添加参数：

```
GRUB_ENABLE_BLSCFG=false
```

其余步骤和传统的 `grub2-mkconfig` 生成配置文件方式相同。
