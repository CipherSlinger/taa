# OpenSSL EVP 适配 SDF 用户使用指南

本文说明如何通过 HCT OpenSSL 3 Provider，将标准 OpenSSL EVP 接口的 SM2、SM4 和 HMAC 运算路由到 SDF 接口。

## 1. 工作方式

应用加载 `hct` Provider，并在算法获取或 EVP 上下文中指定属性查询：

```text
provider=hct,hct.mode=sdf
```

其中 `hct.mode=sdf` 指定使用 SDF 后端；`provider=hct` 防止同名算法被 `default` Provider 选中。对于公钥验签、证书解析等不需要 SDF 私钥的操作，可使用 `default` 或 `base` Provider。

当前源码中 SDF 路径覆盖的主要能力如下：

| 能力 | EVP / OpenSSL 接口 | 说明 |
| --- | --- | --- |
| SM2 签名、验签 | `EVP_PKEY_sign`、`EVP_PKEY_verify` | 使用 SDF 内部签名密钥 |
| SM2 加密、解密 | `EVP_PKEY_encrypt`、`EVP_PKEY_decrypt` | 使用 SDF 内部加密密钥 |
| SM4 | `EVP_Cipher*` / `EVP_Encrypt*` / `EVP_Decrypt*` | ECB、CBC、CTR、CFB、OFB；密钥以 SDF 描述符传入 |
| HMAC | `EVP_MAC_*` | 支持 SM3 摘要；密钥以 SDF 描述符传入 |

Provider 在每个线程首次使用 SDF 时创建并缓存一个 SDF Session。因此，**多线程应用应让每个工作线程独立创建并使用自己的 EVP 上下文**；进程退出前正常释放 Provider 与 EVP 对象。

## 2. 前置条件

1. HCT、SDF 服务及其依赖已经安装、启动，并可通过 SDF API 访问设备。其中，HCT的开发包版本应大于等于3.0.16。

2. 使用与 HCT 构建/安装相匹配的 OpenSSL 3 `openssl` 程序与 `libcrypto`。不要混用系统中其他版本的 OpenSSL。

3. Provider 模块 `hct.so` 默认安装路径为：
   
   ```text
    /opt/hygon/hct/lib64/ossl-modules/hct.so
   ```

4. 进程能够找到 Provider；非默认安装路径时设置：
   
   ```bash
   export OPENSSL_MODULES=/opt/hygon/hct/lib64/ossl-modules
   ```

5. 预先在 SDF 内部创建将要使用的密钥。以下示例使用索引 `128`、口令 `12345678`，实际部署请替换为受控索引和安全口令：
   
   ```bash
   hag tkm intl_key_gen -idx 128 -password 12345678 -type sm2sign
   hag tkm intl_key_gen -idx 128 -password 12345678 -type sm2enc
   hag tkm intl_key_gen -idx 128 -password 12345678 -type sm4
   ```

先验证模块能被加载：

```bash
openssl list -providers -provider-path "$OPENSSL_MODULES" -provider hct
```

输出中应出现 `hct`。若未设置 `OPENSSL_MODULES`，可省略 `-provider-path`，由 OpenSSL 使用其默认模块目录。

## 3. 属性查询与密钥参数

### 3.1 通用属性查询

在命令行中使用：

```bash
-provider hct -propquery 'provider=hct,hct.mode=sdf'
```

在 C 程序中使用：

```c
const char *sdf_propq = "provider=hct,hct.mode=sdf";
```

`?hct.mode=sdf` 是可选属性查询，适合“优先选择 SDF、允许 OpenSSL 为辅助操作选择其他 Provider”的场景；涉及私钥运算或要求必须在 SDF 执行时，使用严格查询 `provider=hct,hct.mode=sdf`。

### 3.2 SM2 内部密钥参数

创建 SM2 EVP 密钥对象时，需要提供下列参数：

| 参数名 | 命令行 `-pkeyopt` | 类型 | 取值 |
| --- | --- | --- | --- |
| `type` | `type:sign` 或 `type:enc` | UTF-8 字符串 | 分别选择签名密钥、加密密钥 |
| `index` | `index:128` | `uint32_t` | SDF 内部密钥索引 |
| `password` | `password:...` | UTF-8 字符串 | 该私钥索引的访问口令 |

在 C 程序中，使用 `OSSL_PARAM_BLD` 传递 `password`、`type` 和 `index`；对应宏定义位于 `include/hysdf.h`：`SDF_PROV_KEYMGMT_PARAM_PASSWORD`、`SDF_PROV_KEYMGMT_PARAM_KEY_TYPE`、`SDF_PROV_KEYMGMT_PARAM_KEY_INDEX`。

### 3.3 SM4/HMAC 的 SDF 密钥描述符

SM4 和 HMAC 的 `key` 参数不是明文 SM4 密钥，而是指向 `struct sdf_prov_sm4_key` 的字节串。结构定义在 `include/hysdf.h`，调用方必须传入完整结构大小 `SDF_PROV_SM4_KEYSZ`。

最常用的是引用设备内 KEK/SM4 密钥：

```c
#include <string.h>
#include <hct/hysdf.h>

struct sdf_prov_sm4_key key = {0};
key.ktype = SDF_PROV_SM4_TYPE_INDEX;
key.key.index = 128;
key.key.auth_len = strlen("12345678");
memcpy(key.key.auth, "12345678", key.key.auth_len);
```

另一种 `SDF_PROV_SM4_TYPE_PROTECTED` 形式用于传入由 KEK 或 SM2 加密密钥保护的会话密钥。它需要填写父密钥类型、父密钥索引/口令和 `encrypted_key`；应用不能把普通 16 字节明文 SM4 密钥直接作为 SDF 模式的 `key` 传入。

## 4. 命令行快速验证

以下命令假设 `openssl`、`hag` 和 Provider 已正确安装，且第 2 节的密钥已创建。

### 4.1 SM2 签名与验签

```bash
dd if=/dev/urandom of=data.bin bs=32 count=1

openssl genpkey -provider hct \
  -propquery 'provider=hct,hct.mode=sdf' -algorithm SM2 \
  -pkeyopt type:sign -pkeyopt index:128 -pkeyopt password:12345678 \
  -out sm2_sign_private.pem -outform PEM

openssl ec -provider hct -provider base -propquery '?hct.mode=sdf' \
  -in sm2_sign_private.pem -pubout -out sm2_sign_public.pem \
  -passin pass:12345678

openssl pkeyutl -provider hct -provider base -propquery '?hct.mode=sdf' \
  -sign -inkey sm2_sign_private.pem -in data.bin -out signature.bin \
  -passin pass:12345678

openssl pkeyutl -provider default \
  -verify -pubin -inkey sm2_sign_public.pem -in data.bin -sigfile signature.bin
```

### 4.2 SM2 加密与解密

```bash
dd if=/dev/urandom of=data.bin bs=32 count=1

openssl genpkey -provider hct \
  -propquery 'provider=hct,hct.mode=sdf' -algorithm SM2 \
  -pkeyopt type:enc -pkeyopt index:128 -pkeyopt password:12345678 \
  -out sm2_enc_private.pem -outform PEM

openssl ec -provider hct -provider base -propquery '?hct.mode=sdf' \
  -in sm2_enc_private.pem -pubout -out sm2_enc_public.pem \
  -passin pass:12345678

openssl pkeyutl -provider default \
  -encrypt -pubin -inkey sm2_enc_public.pem -in data.bin -out encrypted.bin

openssl pkeyutl -provider hct -provider base -propquery '?hct.mode=sdf' \
  -decrypt -inkey sm2_enc_private.pem -in encrypted.bin -out decrypted.bin \
  -passin pass:12345678

cmp data.bin decrypted.bin
```

### 4.3 生成 CSR 与证书

私钥 PEM 只保存 Provider 可恢复的 SDF 私钥引用及公钥信息，并不等同于导出设备内私钥。以下命令以索引 `128` 创建用户签名私钥 PEM；其前提是该索引已创建为 SDF SM2 签名密钥：

```bash
mkdir -p user ca
openssl genpkey -provider hct \
  -propquery 'provider=hct,hct.mode=sdf' -algorithm SM2 \
  -pkeyopt type:sign -pkeyopt index:128 -pkeyopt password:12345678 \
  -out user/sm2_private.pem -outform PEM
```

再用该私钥生成用户 CSR：

```bash
openssl req -provider hct -provider base -propquery '?hct.mode=sdf' \
  -subj '/C=CN/ST=Beijing/O=MyOrg/CN=mydomain.com' \
  -key user/sm2_private.pem -new -out user/server.csr -passin pass:12345678

openssl req -in user/server.csr -noout -text
```

如需用 SDF 中的 CA 私钥签发，需要为 CA 选择一个独立索引。以下以索引 `0` 为例，依次创建 SDF CA 签名密钥、CA 私钥 PEM、CA CSR 和自签名 CA 证书：

```bash
openssl genpkey -provider hct \
  -propquery 'provider=hct,hct.mode=sdf' -algorithm SM2 \
  -pkeyopt type:sign -pkeyopt index:0 -pkeyopt password:12345678 \
  -out ca/ca_private.pem -outform PEM

openssl req -provider hct -provider base -propquery '?hct.mode=sdf' \
  -subj '/C=CN/ST=Beijing/O=MyOrg/CN=ca_test.com' \
  -key ca/ca_private.pem -new -out ca/ca.csr -passin pass:12345678

openssl x509 -req -provider hct -provider default -propquery '?hct.mode=sdf' \
  -in ca/ca.csr -signkey ca/ca_private.pem -out ca/ca.crt -days 365 \
  -passin pass:12345678
```

最后使用 CA 证书和 CA 私钥签发用户 CSR：

```bash
openssl x509 -req -provider hct -provider default -propquery '?hct.mode=sdf' \
  -days 365 -CA ca/ca.crt -CAkey ca/ca_private.pem \
  -in user/server.csr -out user/server.crt -passin pass:12345678

# 输出并检查已生成的用户证书
openssl x509 -in user/server.crt -text -noout
```

## 5. C 应用接入

### 5.1 SM4：两种 SDF 密钥用法

SM4 的 EVP 调用流程相同，区别只在传给 `EVP_EncryptInit_ex2()` 的 `struct sdf_prov_sm4_key` 内容。两种方式都**不能**直接传入 16 字节明文 SM4 密钥。

#### 用法一：直接引用设备内 SM4/KEK 密钥

适用于长期保存在设备内、以索引管理的 SM4（KEK）密钥。调用前用 `hag tkm intl_key_gen -type sm4` 创建密钥；

```c
#include <string.h>
#include <hct/hct.h>

static void init_index_key(struct sdf_prov_sm4_key *key,
                           uint32_t index, const char *password)
{
    memset(key, 0, sizeof(*key));
    key->ktype = SDF_PROV_SM4_TYPE_INDEX;
    key->key.index = index;
    key->key.auth_len = strlen(password);
    memcpy(key->key.auth, password, key->key.auth_len);
}

struct sdf_prov_sm4_key key;
init_index_key(&key, 128, "12345678");
```

此描述符只引用设备内密钥，应用不持有该 SM4 密钥值；可在多次 EVP 操作中重复构造和使用。删除或轮换索引密钥后，旧描述符将失效。

#### 用法二：使用受 KEK 或 SM2 加密密钥保护的会话密钥

适用于为一次会话/报文生成独立 SM4 密钥，同时让该会话密钥始终以密文形式离开 SDF。调用方先通过 SDF 生成受保护的会话密钥，随后把受保护密钥材料和父密钥信息填入描述符。Provider 在每次初始化时利用父密钥恢复该会话密钥并执行运算。

以下示例以索引 `128` 的 KEK 保护会话密钥。该索引必须已存在；示例不会创建或销毁父 KEK。`encrypted_key` 可以保存或随报文传输，但其父索引和访问口令应受到同等级保护。

```c
#include <string.h>
#include <hct/hct.h>

static int make_kek_protected_key(struct sdf_prov_sm4_key *key,
                                  uint32_t kek_index, const char *password)
{
    void *device = NULL, *session = NULL, *session_key = NULL;
    int ret;

    memset(key, 0, sizeof(*key));
    ret = SDF_OpenDevice(&device);
    if (ret != 0)
        return ret;
    ret = SDF_OpenSession(device, &session);
    if (ret != 0)
        goto close_device;

    ret = SDF_GetPrivateKeyAccessRight(session, kek_index,
                                       (unsigned char *)password, strlen(password));
    if (ret != 0)
        goto close_session;

    key->ktype = SDF_PROV_SM4_TYPE_PROTECTED;
    key->protected_key.parent_type = KEK_SM4;
    key->protected_key.parent_index = kek_index;
    key->protected_key.parent_auth_len = strlen(password);
    memcpy(key->protected_key.parent_auth, password,
           key->protected_key.parent_auth_len);
    ret = SDF_GenerateKeyWithKEK(session, 128, SGD_SM4, kek_index,
        key->protected_key.encrypted_key, &key->protected_key.key_len,
        &session_key);

    if (session_key != NULL)
        SDF_DestroyKey(session, session_key);
close_session:
    SDF_CloseSession(session);
close_device:
    SDF_CloseDevice(device);
    return ret;
}

struct sdf_prov_sm4_key key;
if (make_kek_protected_key(&key, 128, "12345678") != 0) {
    /* SDF 错误处理 */
}
```

若希望由 SM2 内部加密密钥保护会话密钥，将 `parent_type` 设为 `ISK_SM2_ENCRYPT`，并使用 `SDF_GenerateKeyWithIPK_ECC()` 生成 `encrypted_key`；该方式要求父密钥是加密用途的 SM2 内部密钥，而不是签名密钥。

#### 以任一描述符执行 EVP SM4-CBC

将上面任一用法得到的 `key` 传给相同的 EVP 流程：

```c
#include <openssl/evp.h>
#include <openssl/provider.h>

OSSL_LIB_CTX *libctx = OSSL_LIB_CTX_new();
OSSL_PROVIDER *hct = OSSL_PROVIDER_load(libctx, "hct");
EVP_CIPHER *cipher = EVP_CIPHER_fetch(libctx, "SM4-CBC",
                                      "provider=hct,hct.mode=sdf");
EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
unsigned char iv[16] = "1234567887654321";
unsigned char plaintext[] = "1234567887654321";
unsigned char ciphertext[sizeof(plaintext) + EVP_MAX_BLOCK_LENGTH];
int outl = 0, finl = 0;

if (libctx == NULL || hct == NULL || cipher == NULL || ctx == NULL ||
    EVP_EncryptInit_ex2(ctx, cipher, (const unsigned char *)&key, iv, NULL) != 1 ||
    EVP_EncryptUpdate(ctx, ciphertext, &outl, plaintext, sizeof(plaintext)) != 1 ||
    EVP_EncryptFinal_ex(ctx, ciphertext + outl, &finl) != 1) {
    /* 使用 ERR_print_errors_fp(stderr) 输出错误后清理 */
}
outl += finl;

EVP_CIPHER_CTX_free(ctx);
EVP_CIPHER_free(cipher);
OSSL_PROVIDER_unload(hct);
OSSL_LIB_CTX_free(libctx);
```

ECB/CBC 默认启用 PKCS#7 填充。若协议要求输入严格为块对齐且不填充，在初始化后设置：

```c
EVP_CIPHER_CTX_set_padding(ctx, 0);
```

CTR、CFB 和 OFB 是流式模式，不使用填充。ECB 没有 IV；CBC、CTR、CFB、OFB 的 IV 长度均为 16 字节。

### 5.2 HMAC-SM3

HMAC 同样使用 SDF SM4 密钥描述符作为 `EVP_MAC_init()` 的 key。

```c
#include <openssl/core_names.h>
#include <openssl/evp.h>

EVP_MAC *mac_alg = EVP_MAC_fetch(libctx, "HMAC", "provider=hct,hct.mode=sdf");
EVP_MAC_CTX *mac_ctx = EVP_MAC_CTX_new(mac_alg);
OSSL_PARAM params[] = {
    OSSL_PARAM_construct_utf8_string(OSSL_MAC_PARAM_DIGEST, "SM3", 0),
    OSSL_PARAM_construct_end()
};
unsigned char mac[EVP_MAX_MD_SIZE];
size_t mac_len = 0;

if (mac_ctx == NULL ||
    EVP_MAC_init(mac_ctx, (const unsigned char *)&key, SDF_PROV_SM4_KEYSZ, params) != 1 ||
    EVP_MAC_update(mac_ctx, (const unsigned char *)"message", 7) != 1 ||
    EVP_MAC_final(mac_ctx, mac, &mac_len, sizeof(mac)) != 1) {
    /* 错误处理 */
}

EVP_MAC_CTX_free(mac_ctx);
EVP_MAC_free(mac_alg);
```

### 5.3 SM2 SDF 内部私钥

SM2 的“生成”操作用于根据已有的 SDF 内部密钥索引构造 `EVP_PKEY`，不是在调用时新建一个设备密钥。需先用 `hag tkm intl_key_gen` 建立索引密钥。

```c
#include <openssl/evp.h>
#include <openssl/param_build.h>
#include <hct/hysdf.h>

EVP_PKEY_CTX *kctx = EVP_PKEY_CTX_new_from_name(
    libctx, "SM2", "provider=hct,hct.mode=sdf");
EVP_PKEY *pkey = NULL;
OSSL_PARAM_BLD *bld = OSSL_PARAM_BLD_new();

OSSL_PARAM_BLD_push_utf8_string(bld, SDF_PROV_KEYMGMT_PARAM_PASSWORD,
                                "12345678", 0);
OSSL_PARAM_BLD_push_utf8_string(bld, SDF_PROV_KEYMGMT_PARAM_KEY_TYPE,
                                SDF_PROV_SM2_ISK_SIGN_NAME, 0); /* 或 "enc" */
OSSL_PARAM_BLD_push_uint32(bld, SDF_PROV_KEYMGMT_PARAM_KEY_INDEX, 128);
OSSL_PARAM *params = OSSL_PARAM_BLD_to_param(bld);

if (kctx == NULL || params == NULL || EVP_PKEY_keygen_init(kctx) <= 0 ||
    EVP_PKEY_CTX_set_params(kctx, params) <= 0 ||
    EVP_PKEY_keygen(kctx, &pkey) <= 0) {
    /* 错误处理 */
}
```

随后用相同属性创建操作上下文。例如，签名流程为先调用 `EVP_PKEY_sign_init()`，再以两次 `EVP_PKEY_sign()` 分别查询签名长度和生成签名：

```c
EVP_PKEY_CTX *signctx = EVP_PKEY_CTX_new_from_pkey(
    libctx, pkey, "provider=hct,hct.mode=sdf");
size_t sig_len = 0;

if (signctx == NULL || EVP_PKEY_sign_init(signctx) <= 0 ||
    EVP_PKEY_sign(signctx, NULL, &sig_len, message, message_len) <= 0) {
    /* 错误处理 */
}
unsigned char *sig = OPENSSL_malloc(sig_len);
if (sig == NULL || EVP_PKEY_sign(signctx, sig, &sig_len, message, message_len) <= 0) {
    /* 错误处理 */
}
```

加解密分别使用 `EVP_PKEY_encrypt_init` / `EVP_PKEY_encrypt` 和 `EVP_PKEY_decrypt_init` / `EVP_PKEY_decrypt`，同样先以输出缓冲区为 `NULL` 查询长度。仅需用公钥验证或加密时，可将 HCT 密钥导出为公钥参数，通过 `EVP_PKEY_todata()` 后在 `default` Provider 用 `EVP_PKEY_fromdata()` 重建公钥对象。

完成后释放资源：`OPENSSL_free(sig)`、`EVP_PKEY_CTX_free(signctx)`、`EVP_PKEY_free(pkey)`、`OSSL_PARAM_free(params)`、`OSSL_PARAM_BLD_free(bld)`。

## 6. 编译、运行与排障

编译应用时，包含 HCT 头文件目录并链接目标 OpenSSL 的 `libcrypto`；如直接使用 SDF 密钥描述符，也包含 HCT 的 `#include <hct/hct.h>` 头文件目录。Provider 自身由 OpenSSL 运行时加载，应用通常不需要直接链接 `hct.so`。

常见问题：

| 现象 | 检查与处理 |
| --- | --- |
| `Failed to load 'hct' provider` | 确认 `hct.so` 存在，设置 `OPENSSL_MODULES` 到 `/opt/hygon/hct/lib64/ossl-modules`，并确认 `openssl` 与 Provider 使用同一套 OpenSSL 3 库。 |
| 算法未找到或落到 default Provider | 获取算法/上下文时使用严格属性 `provider=hct,hct.mode=sdf`；使用 `openssl list -cipher-algorithms -provider hct` 等命令确认模块已加载。 |
| 私钥访问失败 | 确认索引、`type` 与通过 `hag` 创建的密钥类型一致，口令长度和内容正确，并确认当前 SDF 设备/租户可访问该索引。 |
| SM4 或 HMAC 初始化失败 | 确认传入的是完整 `struct sdf_prov_sm4_key`，且 `keylen == SDF_PROV_SM4_KEYSZ`，不是原始 16 字节密钥。 |
| 与其他 Provider 互操作失败 | 需要默认 Provider 执行公钥、PEM、X.509 等辅助操作时显式加载 `default` 或 `base`；私钥操作仍以 HCT 的属性查询创建上下文。 |

排障时可在失败分支调用：

```c
#include <openssl/err.h>
ERR_print_errors_fp(stderr);
```
