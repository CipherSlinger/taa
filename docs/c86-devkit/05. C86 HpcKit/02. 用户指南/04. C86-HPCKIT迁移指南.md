# C86-HPCKit 迁移指南（Intel oneAPI / 开源数学库 → C86-HPCKit）

## 1. 概述

本文指导用户将依赖 Intel oneAPI 或 OpenBLAS、Netlib LAPACK、FFTW 等开源数学库的 CPU 应用迁移到海光 C86 平台，并使用 C86-HPCKit 中的编译器、MPI 和海光数学库（Hygon Math Library，HML）完成重新构建。

本文当前重点覆盖以下迁移：

- Intel oneMKL Classic CPU 接口 → HML；
- Intel C/C++/Fortran 编译器 → HCC 或 HGCC；
- Intel MPI → HMPI；
- Makefile 和 CMake 构建脚本修改；
- 一个可独立编译、运行和验证的 BLAS 迁移示例。

OpenBLAS、Netlib LAPACK、FFTW 等开源数学库的迁移见第 5 章。应用级案例已提供 VASP、GROMACS、OpenFOAM 迁移示例（见第 12 章），AI 框架等将在后续版本中补充。

### 1.1 适用范围

本文适用于满足以下条件的应用：

- 运行目标为海光 C86 处理器；
- 使用 C、C++ 或 Fortran；
- 使用 oneMKL Classic 的 BLAS、LAPACK、Sparse BLAS、VML、DFTI、ScaLAPACK、PARDISO、RCI 或 VSL 等 C/Fortran 接口；
- 使用 Intel 编译器或 Intel MPI，且计划切换到 C86-HPCKit 工具链。

本文讨论的是**源码重新构建迁移**。即使源平台和目标平台同为 x86-64，也不建议直接复用原有二进制文件：原程序可能包含特定 Intel CPU 指令、Intel OpenMP 运行时或 Intel MPI ABI 依赖。

### 1.2 名词说明

| 名称 | 含义 |
|---|---|
| Intel oneAPI | Intel 提供的编译器、数学库、MPI 及多个开源项目组成的开发工具体系 |
| oneMKL | Intel oneAPI Math Kernel Library；本文特指其 Classic CPU C/Fortran 接口 |
| HCC | C86-HPCKit 中基于 LLVM/Clang 的 C、C++、Fortran 编译器 |
| HGCC | C86-HPCKit 中基于 GCC 的 C、C++、Fortran 编译器 |
| HMPI | C86-HPCKit 中基于 Open MPI 的 MPI 实现 |
| HML | 海光数学库，包含 HygonBLAS、HygonSPARSE、HygonLapack、HygonVML、HygonLibM、HygonFFT 和 HygonVSIP 等组件 |
| LP64 | BLAS/LAPACK 整数参数使用 32 位整数 |
| ILP64 | BLAS/LAPACK 整数参数使用 64 位整数 |

### 1.3 Intel oneAPI 与 C86-HPCKit 的定位差异

Intel oneAPI 同时包含编译器、数学库、通信库及面向异构计算的组件。C86-HPCKit 当前主要面向海光 C86 CPU，提供本地编译器、MPI 和 CPU 数学库。因此，oneAPI 组件并不都能在 C86-HPCKit 中找到一一对应的替代物。

| Intel 组件 | 主要用途 | C86-HPCKit 迁移方向 | 迁移方法 |
|---|---|---|---|
| oneMKL Classic BLAS | 稠密基础线性代数 | HygonBLAS | 对已覆盖的 LP64 标准接口，通常只需调整构建和链接 |
| oneMKL Classic LAPACK/LAPACKE | 线性方程、特征值、SVD | HygonLapack | 对已覆盖接口通常保持函数名，需核对头文件、整数类型和 ABI |
| oneMKL Classic Sparse BLAS | 稀疏矩阵计算 | HygonSPARSE | 需要替换头文件、类型、枚举和函数前缀 |
| oneMKL Classic VML | 向量数学函数 | HygonVML | 基础数组函数多为同名接口，控制模式和扩展接口需逐项核对 |
| oneMKL Classic DFTI | 快速傅里叶变换 | HygonFFT 的 FFTW 兼容接口 | DFTI 与 FFTW API 不兼容，需要改写调用 |
| oneMKL Classic ScaLAPACK | 分布式线性代数 | 以目标 HML 发行包为准 | 只有发行包实际提供对应库时才能迁移 |
| oneMKL Classic PARDISO/RCI/VSL | 稀疏求解器、迭代求解器、随机数 | 无直接 HML 等价组件 | 需要保留可用的第三方实现或选择其他开源库 |
| icx/icpx/ifx/ifort | C/C++/Fortran 编译 | HCC 或 HGCC | 需要重新编译并转换不兼容选项 |
| Intel MPI | MPI 通信 | HMPI | 标准 MPI 源码通常可保留，需修改包装器、运行参数和环境变量 |
| oneTBB | 任务并行、并发容器 | 无直接等价组件 | 可继续单独构建开源 oneTBB，不能用 HML 内部线程代替 |
| oneDNN | 深度学习算子 | 不属于本文 HML 迁移范围 | 可在海光平台单独构建并验证 |
| oneDPL/oneDAL/oneCCL | 并行算法、数据分析、集合通信 | 无直接一一对应组件 | 按项目依赖单独评估 |

> “oneAPI 开源组件”和“Intel oneAPI 工具包中的二进制组件”不是同一个概念。迁移前应根据实际头文件、链接库和构建配置识别应用使用的具体组件，而不是仅根据安装了 oneAPI 作出判断。

> 本文不讨论基于 `<oneapi/mkl.hpp>`、`sycl::queue` 和 `oneapi::mkl::*` 的 oneMKL SYCL 接口。此类接口属于 C++ 异构编程模型，与 HML 的 Classic C/Fortran 接口不兼容，应另行制定迁移方案。

### 1.4 兼容性结论的边界

本文中的“可直接替换”只表示：在目标 HML 发行包确实包含该符号、程序使用 LP64 接口、编译器 ABI 兼容且未使用 Intel 扩展的前提下，业务调用代码通常不需要修改。它不表示 oneMKL Classic 与 HML 在所有版本、所有接口和所有二进制场景下完全 ABI 兼容。

迁移前必须确认：

- C86-HPCKit 和 HML 的具体版本；
- 目标处理器代际和操作系统；
- LP64 或 ILP64；
- C/C++/Fortran 及编译器组合；
- 动态或静态链接；
- 串行、OpenMP 或 MPI+OpenMP 运行方式；
- 使用的 oneMKL Classic 函数是否存在于目标 HML 头文件和动态符号表中。

## 2. 环境准备

### 2.1 安装并加载 C86-HPCKit

安装方法见《C86-HPCKit 安装指南》。安装完成后，选择 HCC 或 HGCC 环境：

```bash
# HCC：clang、clang++、flang
source /path/to/hygon/hpc-setenv.sh hcc

# 或 HGCC：gcc、g++、gfortran
source /path/to/hygon/hpc-setenv.sh hgcc
```

本文使用 `HML_ROOT` 表示 HML 安装根目录。请根据实际安装结果设置，不假设环境脚本一定创建同名变量：

```bash
export HML_ROOT=/actual/path/to/hml
```

确认编译器、MPI 包装器和 HML 文件可见：

```bash
"${CC:-cc}" --version
mpicc --showme:command 2>/dev/null || mpicc -show
find "$HML_ROOT/include" -maxdepth 2 -type f \
    \( -name 'cblas.h' -o -name 'hml_sparse.h' -o -name 'hml_vml.h' -o -name 'fftw3.h' \)
find "$HML_ROOT/lib" -maxdepth 1 \
    \( -name 'libhblas*' -o -name 'libhlapack*' -o -name 'libhsparse*' -o -name 'libhvml*' -o -name 'libfftw3*' \)
```

如果发行包提供 pkg-config 文件，可进一步检查：

```bash
pkg-config --list-all | grep -iE 'hblas|hlapack|hml|fftw'
```

后续命令中的库名以当前文档对应的 HML 发行方式为例。若实际包中的文件名不同，应以安装包、公共头文件和 `pkg-config` 输出为准。

### 2.2 保存迁移基线

修改前至少保存以下信息：

```bash
./app --version 2>&1 | tee baseline-version.txt
ldd ./app | tee baseline-ldd.txt
env | grep -E '^(MKL|I_MPI|OMP|KMP)_' | sort | tee baseline-env.txt
```

同时保存一组可重复的输入、数值结果、运行时间、进程/线程数和 CPU 绑定方式。迁移完成后应使用相同输入进行正确性和性能对比。

## 3. 识别 Intel oneAPI 依赖

迁移前需要识别应用实际使用的组件，而不是把所有 `-lmkl_*` 机械替换为某一个 HML 库。

### 3.1 搜索源码和构建脚本

在项目根目录执行：

```bash
# 头文件、Fortran module 和函数调用
rg -n -i \
  'mkl\.h|mkl_[a-z0-9_]+\.h|use[[:space:]]+mkl|Dfti[A-Za-z]+|mkl_sparse_|vsl[A-Za-z]+|pardiso|dfgmres|dcg' .

# 编译器、MPI 包装器、CMake target 和链接参数
rg -n -i \
  'icx|icpx|icc|icpc|ifx|ifort|mpiic|MKLROOT|MKL::MKL|-lmkl_|I_MPI_|KMP_' \
  --glob 'Makefile*' --glob '*.mk' --glob '*.cmake' --glob 'CMakeLists.txt' --glob 'configure*' .
```

典型识别特征如下：

| 组件 | 头文件或符号 |
|---|---|
| BLAS | `mkl_cblas.h`、`cblas_*`、`dgemm`、`sgemm` |
| LAPACK | `mkl_lapack.h`、`mkl_lapacke.h`、`LAPACKE_*`、`dgesv` |
| Sparse BLAS | `mkl_spblas.h`、`mkl_sparse_*` |
| VML | `mkl_vml.h`、`vs*`、`vd*`、`vc*`、`vz*` |
| DFTI | `mkl_dfti.h`、`DftiCreateDescriptor`、`DftiCompute*` |
| ScaLAPACK | `mkl_scalapack.h`、`p?gemm`、`p?gesv` |
| PARDISO | `mkl_pardiso.h`、`pardiso`、`cluster_sparse_solver` |
| RCI | `mkl_rci.h`、`dfgmres`、`dcg` |
| VSL | `mkl_vsl.h`、`vslNewStream`、`vdRng*`、`viRng*` |

### 3.2 检查已有二进制

动态链接程序可使用：

```bash
ldd ./app | grep -iE 'mkl|iomp|imf|mpi|fftw|blas|lapack'
readelf -d ./app | grep -E 'NEEDED|RPATH|RUNPATH'
readelf -Ws ./app | grep -iE 'mkl_|Dfti|pardiso|vsl|cblas_|LAPACKE_'
```

`ldd` 不能发现已静态链接进可执行文件的库。怀疑静态链接时，还应检查未剥离的目标文件或静态归档：

```bash
nm -A build/**/*.o 2>/dev/null | grep -iE 'mkl_|Dfti|pardiso|vsl'
```

### 3.3 建立迁移清单

建议逐项记录：

| 调用点 | oneAPI 组件 | 接口/符号 | 数据类型 | LP64/ILP64 | 线程模式 | HML 对应 | 改动级别 |
|---|---|---|---|---|---|---|---|
| 示例 | oneMKL Classic BLAS | `cblas_dgemm` | double | LP64 | OpenMP | HygonBLAS | 仅构建修改 |

改动级别分为：

- **仅构建修改**：公共标准接口名称不变，只调整头文件搜索路径和链接库；
- **源码适配**：需替换头文件、类型、枚举或函数名；
- **算法/依赖替换**：目标 HML 没有等价接口，需要改写算法或引入第三方库。

## 4. oneMKL Classic 接口迁移到 HML

### 4.1 BLAS 迁移

#### 4.1.1 可替换性

HygonBLAS 提供标准 Fortran BLAS 和 CBLAS 接口。对于目标 HML 已覆盖的 LP64 标准接口，例如 `cblas_dgemm`、`cblas_dgemv`、`cblas_daxpy` 和 Fortran `dgemm`，通常可以保留业务源码。

以下情况不能直接按“零源码改动”处理：

- 原程序使用 `-lmkl_intel_ilp64`、`MKL_ILP64` 或 Fortran `-i8`；
- 使用 oneMKL Classic 扩展、批处理/JIT/compact BLAS 等非标准接口；
- C/C++ 与 Fortran 混合编程时符号修饰或复数返回 ABI 不一致；
- 程序依赖 Intel OpenMP 运行时或 MKL service API。

#### 4.1.2 头文件和链接修改

| 项目 | oneMKL Classic | HML |
|---|---|---|
| C 头文件 | `mkl.h` 或 `mkl_cblas.h` | 优先使用标准 `cblas.h` |
| Fortran 接口 | BLAS module 或外部过程 | 标准 Fortran BLAS 接口 |
| 常用动态链接 | `-lmkl_rt` | `-lhblas` |
| 整数接口 | LP64 或 ILP64 | 当前文档对应接口按 LP64 使用，实际以发行包为准 |

迁移前：

```bash
icx gemm.c -I"$MKLROOT/include" -L"$MKLROOT/lib/intel64" \
    -lmkl_rt -lpthread -lm -ldl -o gemm_mkl
```

迁移后：

```bash
"${CC:-cc}" gemm.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lhblas -fopenmp -lm -o gemm_hml
```

库参数应放在引用这些符号的源文件或目标文件之后。若应用自身不使用 OpenMP，是否仍需显式添加 `-fopenmp` 应以 HML 发行包的链接说明或 pkg-config 输出为准。

#### 4.1.3 线程控制

优先使用 OpenMP 的通用设置作为迁移基线：

```bash
export OMP_NUM_THREADS=8
export OMP_PROC_BIND=close
export OMP_PLACES=cores
```

如果目标 HML 版本提供 HML 专用线程变量或线程控制 API，应以该版本头文件和发行说明为准。不要假定 `MKL_NUM_THREADS`、`MKL_DYNAMIC` 或 `KMP_AFFINITY` 会继续生效。

### 4.2 LAPACK/LAPACKE 迁移

#### 4.2.1 可替换性

HygonLapack 提供 Fortran LAPACK 和 LAPACKE 风格的 C 接口。对目标头文件已声明的常用 LP64 接口，例如 `dgesv`、`dgetrf`、`dpotrf` 和 `LAPACKE_dgesv`，通常可以保持函数名。

迁移前必须核对：

- 目标头文件实际名称和包含路径；
- `lapack_int` 宽度；
- 复数类型定义；
- row-major/column-major 参数语义；
- 原程序使用的函数是否出现在目标 HML 公共头文件和动态符号表中。

#### 4.2.2 头文件和链接修改

| 项目 | oneMKL Classic | HML |
|---|---|---|
| C 接口头文件 | `mkl_lapacke.h` | `hml_lapacke.h`；若发行包提供兼容包装，也可使用 `lapacke.h` |
| Fortran 接口 | `mkl_lapack.h` 或外部过程 | Fortran LAPACK 接口，或 C 中包含 `hml_lapack.h` |
| 常用链接 | `-lmkl_rt` | 示例发行方式使用 `-lhlapack_lp64`，其依赖以实际包为准 |

示例：

```bash
"${CC:-cc}" solve.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lhlapack_lp64 -lhblas -fopenmp -lm -o solve_hml
```

若 `libhlapack_lp64` 在目标版本中已经合并或链接到 HygonBLAS，重复列出 `-lhblas` 通常无害，但最终应以 `pkg-config` 或库的 `DT_NEEDED` 为准。

### 4.3 Sparse BLAS 迁移

HygonSPARSE 与 oneMKL Classic Sparse BLAS 不是二进制直接替换关系。二者对象模型相似，但命名空间、类型和枚举不同，需要源码适配。

| oneMKL Classic | HygonSPARSE |
|---|---|
| `#include <mkl_spblas.h>` | `#include <hml_sparse.h>` |
| `sparse_matrix_t` | `hml_sparse_matrix_t` |
| `sparse_status_t` | `hml_sparse_status_t` |
| `matrix_descr` | `struct hml_matrix_descr` |
| `SPARSE_OPERATION_*` | `HML_SPARSE_OPERATION_*` |
| `mkl_sparse_d_create_csr` | `hml_sparse_d_create_csr` |
| `mkl_sparse_d_mv` | `hml_sparse_d_mv` |
| `mkl_sparse_destroy` | `hml_sparse_destroy` |

不能只做函数名前缀的批量替换。还应逐项核对：

- CSR/CSC/COO/BSR 的索引基准；
- `rows_start`、`rows_end`、列索引和值数组的所有权和生命周期；
- 矩阵描述符默认值；
- 转置、共轭转置和复数类型；
- 返回状态和错误处理；
- oneMKL Classic inspector-executor 优化接口是否有对应能力。

示例链接：

```bash
"${CC:-cc}" sparse.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lhsparse -fopenmp -lpthread -lm -o sparse_hml
```

### 4.4 VML 迁移

HygonVML 提供 `vs*`、`vd*`、`vc*`、`vz*` 形式的数组接口。目标 HML 已覆盖的基础函数可能与 oneMKL Classic VML 保持同名，例如 `vsInvSqrt`、`vdExp` 和 `vdSin`，但仍需替换头文件并核对类型。

| oneMKL Classic | HygonVML |
|---|---|
| `#include <mkl_vml.h>` | `#include <hml_vml.h>` 或目标包指定的 `hygonvml.h` |
| `MKL_INT` | `VML_INT` |
| MKL 复数类型 | `VML_COMPLEX8`、`VML_COMPLEX16` |
| `-lmkl_rt` | `-lhvml` |

```bash
"${CC:-cc}" vml.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lhvml -lm -o vml_hml
```

需要单独评估的内容包括：

- VML 精度/错误模式和状态查询接口；
- 带 `HA`、`LA` 等后缀的扩展接口；
- oneMKL Classic 与 HML 对 NaN、Inf、下溢和舍入模式的处理差异；
- `VML_INT` 的实际宽度；
- 编译器自动向量化所需的向量数学 ABI 和编译选项。

只有目标 HCC/HGCC 版本明确支持相应选项时，才能启用 HygonVML 编译器接口。不要把某一版本的 `-mveclibabi` 或类似选项无条件写入通用构建脚本。

### 4.5 DFTI 迁移到 HygonFFT

HygonFFT 对外提供 FFTW 兼容接口，而不是 oneMKL Classic DFTI 接口。因此，使用 `Dfti*` 的程序必须改写；原本已经使用 FFTW 且所用符号在目标 HygonFFT 发行包兼容范围内的程序，通常只需重新链接。

#### 4.5.1 概念映射

| oneMKL Classic DFTI | FFTW/HygonFFT | 注意事项 |
|---|---|---|
| `DftiCreateDescriptor` | `fftw_plan_dft_*`、`fftw_plan_dft_r2c_*` 等 | FFTW 在创建 plan 时同时指定维度、数据地址和方向 |
| `DftiSetValue` | 选择适当的 `plan_many`/guru 接口及创建参数 | placement、stride、distance、batch 需逐项换算 |
| `DftiCommitDescriptor` | 无独立对应步骤 | FFTW plan 创建成功后即可执行 |
| `DftiComputeForward` | 执行创建为 `FFTW_FORWARD` 的 plan | `fftw_execute()` 本身不接收方向参数 |
| `DftiComputeBackward` | 执行创建为 `FFTW_BACKWARD` 的 plan | 归一化比例需由应用显式处理 |
| `DftiFreeDescriptor` | `fftw_destroy_plan` | 还需按需执行线程层清理 |

迁移时必须检查：

- C2C、R2C、C2R 或 R2R 变换类型；
- 单精度或双精度；
- 原位或异位变换；
- 多维数组顺序；
- batch、stride、distance 和嵌入尺寸；
- 实数变换的共轭偶存储格式；
- forward/backward scale；
- plan 创建失败处理和线程安全要求。

#### 4.5.2 链接方式

双精度顺序接口：

```bash
"${CC:-cc}" fft.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lfftw3 -lm -o fft_hml
```

双精度 OpenMP 线程接口通常需要同时链接线程库和顺序库：

```bash
"${CC:-cc}" fft_omp.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lfftw3_omp -lfftw3 -fopenmp -lm -o fft_hml_omp
```

单精度使用 `fftwf_*` 接口，并链接 `-lfftw3f`；多线程时使用 `-lfftw3f_omp -lfftw3f`。目标发行包是否支持 long double、quad、MPI FFT、线程接口及全部 guru 接口，必须根据公共头文件、符号表和发行说明确认。

### 4.6 ScaLAPACK 迁移

ScaLAPACK 迁移同时涉及 BLACS、MPI ABI、Fortran ABI、整数宽度和链接顺序。当前仓库中的 HML 开发指南未把 ScaLAPACK 列为稳定的 HML 子库，因此不能在通用指南中无条件假定 `libhscalapack.so` 存在。

先检查目标发行包：

```bash
find "$HML_ROOT/lib" -maxdepth 1 -name 'libhscalapack*' -print
nm -D "$HML_ROOT/lib/libhscalapack.so" 2>/dev/null | grep -E 'pdgemm_|pdgesv_' | head
```

只有检查通过后，才能按目标包说明设置类似以下链接顺序：

```bash
mpifort app.f90 -L"$HML_ROOT/lib" -Wl,-rpath,"$HML_ROOT/lib" \
    -lhscalapack -lhlapack_lp64 -lhblas -fopenmp -lm -o app_hml
```

还应确认目标库使用 HMPI/Open MPI 构建，不能把依赖 Intel MPI 的 BLACS/ScaLAPACK 二进制直接与 HMPI 混用。

### 4.7 无直接 HML 等价组件

| oneMKL Classic 功能 | 迁移建议 |
|---|---|
| PARDISO/cluster sparse solver | 评估 MUMPS、SuperLU\_DIST 或具有合适许可证的其他直接求解器 |
| RCI CG/FGMRES | 评估 PETSc KSP、Trilinos 或应用自有迭代算法 |
| VSL 随机数 | 评估应用现有 RNG、Random123、SPRNG 或其他满足统计和并行要求的实现 |
| oneMKL Classic 特有批处理/JIT接口 | 改写为标准 BLAS/LAPACK 循环或目标 HML 已验证的扩展接口 |

这些替代库不是函数级直接替换。迁移时需要重新评估矩阵存储、并行模型、错误码、数值精度、随机数序列复现性和软件许可证。

## 5. 开源数学库迁移到 HML

除 Intel oneAPI 外，许多应用直接依赖 OpenBLAS、Netlib BLAS/LAPACK、FFTW 等开源数学库。这些库使用公开标准接口，迁移到 C86-HPCKit 的重点通常不是改写调用代码，而是**用 HCC/HGCC 重新构建，并把链接切换到 HML 的对应组件**，以获得面向海光 C86 处理器的优化。

### 5.1 迁移总则

开源数学库迁移与 oneMKL 迁移的异同：

- 相同点：都需先识别应用实际调用的接口，再按目标 HML 发行包提供的头文件和库替换链接；
- 不同点：OpenBLAS、Netlib、FFTW 使用标准公开接口，多数情况下无需像 oneMKL 那样替换专有头文件、类型或枚举，只需修改构建脚本中的头文件搜索路径与链接库。

通用步骤：

1. 识别应用使用的开源数学库及接口（构建脚本中的 `-lopenblas`、`-lfftw3`、`-llapack` 等，或 `ldd`/`nm` 结果）；
2. 确认目标 HML 发行包提供对应库与头文件；
3. 在 HCC/HGCC 环境下重新构建并替换链接库；
4. 用相同输入验证正确性、动态依赖与性能（见第 13 章）。

本章各节只给出**接口与链接的替换要点**（可替换性对照 + 迁移前/迁移后 + 注意事项），不重复完整示例；可直接编译运行的完整源码、输入输出与数值校验方法统一放在第 11 章「基础库 C 迁移 Demo」（BLAS 见 §11.1、FFT 见 §11.2、Sparse 见 §11.3）。

### 5.2 数学函数库（LIBM / MATHLIB / LIBIMF）→ HygonLibM

`math.h` 声明的标量数学函数（`sin`、`cos`、`exp`、`log`、`pow`、`sqrt` 等）在 Linux 上通常来自 glibc 的 `libm`；Intel 编译器工具链则自动链接 Intel 数学函数库 `libimf`（头文件 `mathimf.h`）。HygonLibM 提供与 `math.h` 兼容的标量接口，接口格式与 `math.h` 完全一致，因此迁移时**无需修改源码与头文件**，只需替换链接库。

| 项目 | LIBM / MATHLIB / LIBIMF | HML（HygonLibM） |
|---|---|---|
| 头文件 | `math.h` / `mathlib.h` / `mathimf.h` | `math.h`（无需改动） |
| 链接 | `-lm` / `-lmathlib` / `-limf` | `-lhlm` |
| 接口 | `sin`、`cos`、`exp`、`log`、`pow`、`sqrt` 等标量函数 | 同名 |

迁移前（glibc `libm`）：

```bash
gcc app.c -lm -o app
```

迁移前（Intel `libimf`，Intel 编译器默认自动链接）：

```bash
icx app.c -o app
```

迁移后：

```bash
source /path/to/hygon/hpc-setenv.sh hgcc
gcc app.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lhlm -o app
```

Fortran 接口迁移：Fortran 程序的数学内建函数（`SIN`、`COS`、`EXP` 等）由编译器运行时提供，随 `gfortran` 自动链接，通常无需显式指定 `-lhlm`；仅当程序显式调用 `libimf`/`libm` 的 C 接口时才需替换链接库。

注意事项：

- HygonLibM 只对标 `math.h` 标量接口，不覆盖向量数学函数（Intel SVML 的 `__svml_*` 接口）；向量数学迁移见 §4.4（VML → HygonVML）。
- Intel `libimf` 区分高性能（fast）与高精度（precise）两档；迁移到 HygonLibM 后精度语义以 HygonLibM 实现为准，需用相同输入比对数值误差。
- 若构建脚本同时链接 `libm` 与 `libhlm`，应将 `-lhlm` 放在 `-lm` 之前，确保 HygonLibM 的符号优先解析；并用 `nm`/`ldd` 确认实际加载的数学函数库。
- 本节不涉及完整 Demo；标量数学函数的迁移只需替换链接，验证时用相同输入对比迁移前后的函数返回值即可。

### 5.3 OpenBLAS → HygonBLAS

OpenBLAS 提供标准 CBLAS 与 Fortran BLAS/LAPACK 接口，HygonBLAS 同样提供标准 `cblas.h` 与 Fortran BLAS 接口。使用标准 BLAS/CBLAS 调用的程序通常只需**重新链接**。

| 项目 | OpenBLAS | HML（HygonBLAS） |
|---|---|---|
| C 头文件 | `cblas.h` | `cblas.h`（HML 发行包自带） |
| 动态链接 | `-lopenblas` | `-lhblas` |
| 线程数控制 | `OPENBLAS_NUM_THREADS` / `OMP_NUM_THREADS` | `OMP_NUM_THREADS`（及 HML 版本支持的专用变量） |
| 符号 | `cblas_dgemm`、`dgemm_` 等 | 同名 |

迁移前：

```bash
gcc app.c -lopenblas -fopenmp -o app_openblas
```

迁移后：

```bash
source /path/to/hygon/hpc-setenv.sh hgcc
gcc app.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lhblas -fopenmp -lm -o app_hml
```

注意事项：

- 不要继续设置 `OPENBLAS_NUM_THREADS`，改用 `OMP_NUM_THREADS`；
- 若 OpenBLAS 曾静态链接进应用或第三方库，需确认替换后同一进程不会同时加载多套 BLAS 实现（符号抢占）；
- 仅当应用调用标准 BLAS/CBLAS/LAPACK 接口时才能替换；依赖 OpenBLAS 特有扩展或调试符号的程序需单独核对。
- 完整可运行示例与数值校验方法见 §11.1：其 C 源码使用标准 `cblas.h`/`cblas_dgemm` 接口，可直接复用，仅链接参数以本节为准。

### 5.4 Netlib BLAS/LAPACK → HygonBLAS/HygonLapack

Netlib 是 BLAS/LAPACK 的参考实现，接口最为标准。HygonBLAS 与 HygonLapack 分别覆盖 BLAS 与 LAPACK（含 LAPACKE）。

| 项目 | Netlib | HML |
|---|---|---|
| BLAS | `-lblas` | `-lhblas` |
| LAPACK | `-llapack` | `-lhlapack_lp64` |
| C 接口头文件 | `lapacke.h` | `hml_lapacke.h`（或发行包提供的兼容 `lapacke.h`） |
| Fortran 接口 | LAPACK module 或外部过程 | 同名 Fortran 接口 |

迁移前：

```bash
gfortran solve.f90 -llapack -lblas -o solve_netlib
```

迁移后：

```bash
source /path/to/hygon/hpc-setenv.sh hgcc
gfortran solve.f90 -L"$HML_ROOT/lib" -Wl,-rpath,"$HML_ROOT/lib" \
    -lhlapack_lp64 -lhblas -fopenmp -lm -o solve_hml
```

注意事项：

- 链接顺序应保持 `-lhlapack_lp64` 在 `-lhblas` 之前；
- 复数类型、`lapack_int` 宽度、row/column-major 语义与 Netlib LAPACKE 一致，但仍需用目标头文件逐项核对；
- 若发行包的 `libhlapack_lp64` 已合并进 `libhblas`，重复列出 `-lhblas` 通常无害，最终以 `pkg-config` 或库的 `DT_NEEDED` 为准。
- BLAS 部分的完整可运行示例与数值校验方法见 §11.1；LAPACK 部分可沿用同一结构，用相同输入对比 Netlib 与 HML 的结果。

### 5.5 FFTW → HygonFFT

HygonFFT 对外提供 FFTW 兼容接口（`fftw_*`/`fftwf_*`），发行包自带标准 `fftw3.h`、`fftw3.f` 等头文件。原本使用 FFTW 的程序通常**无需修改源码**，只需把链接指向 HML 的 FFTW 兼容库。

| 项目 | 开源 FFTW | HML（HygonFFT） |
|---|---|---|
| 双精度顺序 | `-lfftw3` | `-lfftw3`（HML 发行包） |
| 单精度顺序 | `-lfftw3f` | `-lfftw3f` |
| 多线程 | `-lfftw3_omp` / `-lfftw3f_omp` | `-lfftw3_omp` / `-lfftw3f_omp` |
| 头文件 | `fftw3.h` | `fftw3.h`（HML 发行包自带） |

迁移前：

```bash
gcc fft.c -lfftw3 -lm -o fft_fftw
```

迁移后：

```bash
source /path/to/hygon/hpc-setenv.sh hgcc
gcc fft.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lfftw3 -lm -o fft_hml
```

注意事项：

- 库名与开源 FFTW 相同（`-lfftw3`），关键在于 `-L` 是否指向 HML 发行包目录；
- 多线程接口需同时链接 `-lfftw3_omp -lfftw3` 并加 `-fopenmp`（单精度用 `-lfftw3f_omp -lfftw3f`）；
- 目标发行包是否支持 long double/quad、MPI FFT 及全部 guru 接口，需按公共头文件与符号表确认；
- Fortran 程序使用的 `fftw3.f`/`fftw3.f03` 常量头已随 HML 发行包提供。
- 完整可运行示例（含浮点误差阈值与实际加载库的校验）见 §11.2；其源码使用标准 `fftw3.h` 接口，链接参数以本节为准。

### 5.6 其他开源数学库

| 开源库 | HML 对应 | 迁移建议 |
|---|---|---|
| ScaLAPACK（Netlib） | HygonScaLAPACK（`-lhscalapack`，以发行包实际提供为准） | 确认 MPI ABI（HMPI/Open MPI）与整数宽度后重新链接 |
| libflame | HygonLapack | 改写为 LAPACK 接口 |
| Eigen / Armadillo | 无直接等价组件 | C++ 模板库，通过构建选项切换到外部 BLAS/LAPACK 后端（HML） |
| GSL 等其他数值库 | 按接口评估 | 按实际依赖分别处理 |

这些库不是函数级直接替换，迁移时需逐项确认接口覆盖、MPI ABI、许可证与数值语义。

## 6. Intel 编译器迁移到 HCC/HGCC

### 6.1 编译器映射

| Intel 编译器 | HCC | HGCC |
|---|---|---|
| `icc`/`icx` | `clang` | `gcc` |
| `icpc`/`icpx` | `clang++` | `g++` |
| `ifort`/`ifx` | `flang` | `gfortran` |

建议先使用较保守的优化选项完成正确性验证，再逐步开启目标架构优化。

### 6.2 常见选项处理

| 用途 | Intel | HCC/HGCC 迁移建议 |
|---|---|---|
| 常规优化 | `-O2`/`-O3` | 保持 `-O2`/`-O3` |
| OpenMP | `-qopenmp` | `-fopenmp` |
| 本机架构优化 | `-xHost` | 构建机与运行机相同时可评估 `-march=native` |
| 固定 Intel ISA | `-xCORE-AVX2` 等 | 根据目标 C86 处理器实际指令集选择，不要直接照搬 |
| IPO/LTO | `-ipo` | 评估 `-flto`，并确保编译和链接阶段一致 |
| 优化报告 | `-qopt-report` | Clang 使用 `-Rpass` 系列，GCC 使用 `-fopt-info` 系列 |
| Intel OpenMP | `-liomp5` | 使用目标编译器和 HML 要求的 OpenMP 运行时 |

不要在未确认处理器能力时直接指定 `-march=znver4`、AVX-512 或其他可能生成目标 CPU 不支持指令的选项。

### 6.3 Fortran 注意事项

Fortran 迁移需要额外检查：

- 默认 `INTEGER`、`REAL` 和 `LOGICAL` 的宽度；
- `-i8`、默认双精度等全局类型提升选项；
- module 文件必须由目标编译器重新生成；
- 名称修饰和隐藏字符串长度参数；
- C/Fortran 混合调用应优先使用 `ISO_C_BINDING`；
- 复数函数返回 ABI；
- 固定格式/自由格式、行长度和预处理选项。

所有 Fortran 对象文件和 module 文件都应清理后重新生成，不要混用 Intel 编译器产生的 `.o` 或 `.mod` 文件。

## 7. Intel MPI 迁移到 HMPI

HMPI 基于 Open MPI，标准 MPI 调用通常无需修改，但编译包装器、启动命令参数、环境变量和进程绑定方式需要重新配置。

| Intel MPI | HMPI/Open MPI |
|---|---|
| `mpiicc`/`mpiicx` | `mpicc` |
| `mpiicpc`/`mpiicpx` | `mpicxx` |
| `mpiifort`/`mpiifx` | `mpifort` |
| `mpirun`/`mpiexec` | `mpirun`/`mpiexec`，参数按 Open MPI 语义配置 |
| `I_MPI_*` | 无通用机械映射，按 Open MPI/UCX 和作业调度器重新配置 |

迁移时检查：

- 程序是否调用 `MPI_Init_thread`，请求和实际获得的线程级别是否一致；
- 是否使用 Intel MPI 扩展；
- MPI 派生数据类型、文件 I/O 和单边通信的边界场景；
- 作业调度器集成；
- 网络传输层和 UCX 配置；
- rank、NUMA、核心和 OpenMP 线程绑定。

混合 MPI+OpenMP 示例：

```bash
export OMP_NUM_THREADS=4
export OMP_PROC_BIND=close
export OMP_PLACES=cores

# 每个 rank 分配 4 个处理单元；具体参数需按 HMPI/Open MPI 版本和调度器验证
mpirun --bind-to core --map-by slot:PE=4 -np 16 ./app
```

不要把 Intel MPI 环境变量简单替换为同名或看似相近的 Open MPI 变量。应先确定原变量控制的是传输层、进度线程、线程安全还是进程绑定，再选择 HMPI/Open MPI 的对应配置。

## 8. 其他 oneAPI 组件的迁移处理

oneAPI 中除 oneMKL、编译器和 Intel MPI 之外，还包含多个独立项目。这些项目不能统一替换为某个 C86-HPCKit 库，应按源码依赖分别处理。

迁移前可搜索以下特征：

```bash
rg -n -i \
  'oneapi/tbb|tbb::|dnnl\.h|dnnl::|oneapi/dpl|oneapi::dal|oneapi::ccl' .
```

### 8.1 oneTBB

oneTBB 是独立的开源任务并行库，不是 HML 的组成部分。HML 或 BLAS 内部使用 OpenMP，并不能替代应用直接调用的 `tbb::parallel_for`、flow graph、并发容器或 scalable allocator。

建议处理方式：

- 应用需要保留 oneTBB API 时，在海光平台使用 HCC/HGCC 重新构建 oneTBB 和应用；
- 清理原构建中面向特定 Intel CPU 的选项，并在目标平台重新运行测试；
- 检查项目是否通过 `find_package(TBB)` 和 `TBB::tbb` 链接，避免硬编码 oneAPI 安装路径；
- 只有在项目明确计划取消 oneTBB 依赖时，才逐个算法评估改写为 OpenMP，不能机械替换。

### 8.2 oneDNN

oneDNN 是独立的开源深度学习算子库，不等同于 oneMKL BLAS，也不能通过把 `-lmkl_rt` 替换为 `-lhblas` 完成整体迁移。

建议在海光平台使用 HCC/HGCC 从源码重新构建，并重点验证：

- CPU 指令集探测与 JIT 生成代码是否适配目标 C86 处理器；
- 线程运行时和线程绑定；
- 是否还通过构建选项启用了 oneMKL 或其他 Intel 专用后端；
- 卷积、归一化、矩阵乘和低精度算子的正确性与性能；
- PyTorch、TensorFlow 等上层框架加载的是否为新构建库。

若应用只在 oneDNN 外部调用标准 BLAS，相关 BLAS 调用可独立迁移到 HygonBLAS；这不代表 oneDNN API 本身迁移到 HML。

### 8.3 oneDPL 和 oneDAL

oneDPL、oneDAL 是独立开源项目，C86-HPCKit 当前没有同名替代组件。处理方式取决于应用使用的后端：

- 纯 CPU、标准 C++ 或 OpenMP/TBB 路径可尝试在 HCC/HGCC 环境重新构建；
- 非 CPU 或非标准 C++ 后端不属于本文迁移范围；
- 需要核对项目支持的编译器版本、CPU ISA、并行运行时和第三方依赖；
- 如果目标版本不支持海光平台，应在应用层替换相应算法或选择其他库。

### 8.4 oneCCL

oneCCL 与 MPI 是不同的 API。HMPI 不能作为 oneCCL 的链接时直接替换库。

可选择：

1. 在目标平台重新构建并验证 oneCCL 及其通信后端；
2. 若应用只使用常见集合通信，将 oneCCL 调用改写为 `MPI_Bcast`、`MPI_Allreduce`、`MPI_Allgather` 等 HMPI 接口；
3. 上层框架已抽象通信后端时，改用其 MPI 后端并重新验证语义和性能。

改写时需要处理 communicator、异步 event、数据类型、规约操作、流/队列和错误模型差异，不能只修改函数名。

### 8.5 迁移判定原则

对上述组件应分别得出以下一种结论，并记录到迁移清单：

- **保留并重编译**：项目本身开源且支持目标 CPU/编译器；
- **切换后端**：上层项目已经提供 MPI、OpenMP 或其他 CPU 后端；
- **源码改写**：API 或并行模型没有直接对应；
- **暂不支持**：目标设备、编译器或依赖条件不满足。

## 9. Makefile 构建脚本迁移

### 9.1 迁移前

```make
CC      := icx
CXX     := icpx
FC      := ifx
MPICC   := mpiicx

CPPFLAGS += -I$(MKLROOT)/include
CFLAGS   += -O2 -qopenmp
LDFLAGS  += -L$(MKLROOT)/lib/intel64
LDLIBS   += -lmkl_rt -lpthread -lm -ldl
```

### 9.2 迁移后

```make
# 加载 hcc 环境时使用 clang/clang++/flang；
# 加载 hgcc 环境时可改为 gcc/g++/gfortran。
CC      := clang
CXX     := clang++
FC      := flang
MPICC   := mpicc

HML_ROOT ?= /actual/path/to/hml

CPPFLAGS += -I$(HML_ROOT)/include
CFLAGS   += -O2 -fopenmp
LDFLAGS  += -L$(HML_ROOT)/lib -Wl,-rpath,$(HML_ROOT)/lib
LDLIBS   += -lhblas -fopenmp -lm
```

Makefile 中应保持目标文件在库之前：

```make
app: $(OBJS)
	$(CC) $(LDFLAGS) -o $@ $(OBJS) $(LDLIBS)
```

如果程序同时使用 LAPACK、Sparse、VML 或 FFT，应按实际调用增加相应库，而不是寻找一个等价于 `libmkl_rt.so` 的通用聚合库。

#### 11.1.1 C 源码

```c
#include <math.h>

int main(void)
{

                CblasNoTrans,
                CblasNoTrans,
                2, 2, 2,
                1.0,

                b, 2,
                0.0,
```

### 11.2 FFT 迁移 Demo

FFT demo 演示 oneMKL Classic DFTI 到 HygonFFT（FFTW 兼容接口）的迁移。oneMKL Classic 的 `Dfti*` 接口与 FFTW 接口不兼容，需按 §4.5 改写为 `fftw_*` 调用；原本已使用 FFTW 的程序通常只需重新链接。

#### 11.2.1 C 源码

保存为 `fft_demo.c`：

```c
#include <stdio.h>
#include <math.h>
#include <fftw3.h>

int main(void)
{
    const int n = 8;
    const double pi = 3.14159265358979323846;

    fftw_complex *in   = (fftw_complex *)fftw_malloc(sizeof(fftw_complex) * n);
    fftw_complex *freq = (fftw_complex *)fftw_malloc(sizeof(fftw_complex) * n);
    fftw_complex *back = (fftw_complex *)fftw_malloc(sizeof(fftw_complex) * n);

    fftw_plan fwd = fftw_plan_dft_1d(n, in, freq, FFTW_FORWARD, FFTW_ESTIMATE);
    fftw_plan bwd = fftw_plan_dft_1d(n, freq, back, FFTW_BACKWARD, FFTW_ESTIMATE);

    for (int i = 0; i < n; ++i) {
        in[i][0] = cos(2.0 * pi * i / n);
        in[i][1] = sin(2.0 * pi * i / n);
    }

    fftw_execute(fwd);
    fftw_execute(bwd);

    /* FFTW backward transform is unnormalized: divide by n to recover input. */
    double max_err = 0.0;
    for (int i = 0; i < n; ++i) {
        double re = back[i][0] / n;
        double im = back[i][1] / n;
        double e_re = fabs(re - in[i][0]);
        double e_im = fabs(im - in[i][1]);
        if (e_re > max_err) max_err = e_re;
        if (e_im > max_err) max_err = e_im;
    }

    printf("n = %d, max |backward/n - input| = %g\n", n, max_err);

    fftw_destroy_plan(fwd);
    fftw_destroy_plan(bwd);
    fftw_free(in);
    fftw_free(freq);
    fftw_free(back);

    if (max_err > 1.0e-12) {
        fprintf(stderr, "validation failed\n");
        return 1;
    }
    printf("validation passed\n");
    return 0;
}
```


#### 11.2.4 注意事项

- HygonFFT 的 `libfftw3.so` 为双精度顺序接口；单精度使用 `fftwf_*` 接口并链接 `-lfftw3f`，多线程接口见 §4.5.2。
- FFTW 逆变换默认不做归一化，需自行除以 `n` 才能恢复原始输入。
- 本节示例已在 HML 1.9.0 上使用 hgcc 12.3.0 与 hcc 16.0.4（海光 C86-4G，OPN 7490H）本地实测通过；加载 hcc 环境时把 `gcc` 换成 `clang` 即可，其余命令不变。

### 11.3 Sparse BLAS 迁移 Demo

Sparse demo 演示 oneMKL Classic Inspector-Executor Sparse BLAS（`mkl_sparse_*`）到 HygonSPARSE（`hml_sparse_*`）的迁移。二者对象模型一致，但类型、枚举和函数前缀不同，需源码适配（详见 §4.3）。

#### 11.3.1 类型与枚举对照

| oneMKL Classic | HygonSPARSE |
|---|---|
| `sparse_matrix_t` | `hml_sparse_matrix_t` |
| `sparse_status_t` | `hml_sparse_status_t` |
| `SPARSE_STATUS_SUCCESS` | `HML_SPARSE_STATUS_SUCCESS` |
| `SPARSE_INDEX_BASE_ZERO` | `HML_SPARSE_INDEX_BASE_ZERO` |
| `SPARSE_OPERATION_NON_TRANSPOSE` | `HML_SPARSE_OPERATION_NON_TRANSPOSE` |
| `struct matrix_descr` | `struct hml_matrix_descr` |
| `SPARSE_MATRIX_TYPE_GENERAL` | `HML_SPARSE_MATRIX_TYPE_GENERAL` |
| `SPARSE_FILL_MODE_LOWER` | `HML_SPARSE_FILL_MODE_LOWER` |
| `SPARSE_DIAG_NON_UNIT` | `HML_SPARSE_DIAG_NON_UNIT` |
| `mkl_sparse_d_create_csr` | `hml_sparse_d_create_csr` |
| `mkl_sparse_d_mv` | `hml_sparse_d_mv` |
| `mkl_sparse_destroy` | `hml_sparse_destroy` |

#### 11.3.2 C 源码

保存为 `sparse_demo.c`：

```c
#include <stdio.h>
#include <math.h>
#include <hml_sparse.h>

int main(void)
{
    const HML_INT rows = 4, cols = 4;

    /* 4-array CSR: rows_start[i]/rows_end[i] bound the nonzeros of row i. */
    HML_INT rows_start[4] = {0, 1, 2, 3};
    HML_INT rows_end[4]   = {1, 2, 3, 4};
    HML_INT col_indx[4]   = {0, 1, 2, 3};
    double  values[4]     = {2.0, 3.0, 5.0, 7.0};

    hml_sparse_matrix_t A = NULL;
    hml_sparse_status_t st;

    st = hml_sparse_d_create_csr(&A, HML_SPARSE_INDEX_BASE_ZERO,
                                 rows, cols, rows_start, rows_end, col_indx, values);
    if (st != HML_SPARSE_STATUS_SUCCESS) {
        fprintf(stderr, "hml_sparse_d_create_csr failed: %d\n", (int)st);
        return 1;
    }

    struct hml_matrix_descr descr;
    descr.type = HML_SPARSE_MATRIX_TYPE_GENERAL;
    descr.mode = HML_SPARSE_FILL_MODE_LOWER;
    descr.diag = HML_SPARSE_DIAG_NON_UNIT;

    const double x[4] = {1.0, 2.0, 3.0, 4.0};
    double y[4] = {0.0, 0.0, 0.0, 0.0};

    st = hml_sparse_d_mv(HML_SPARSE_OPERATION_NON_TRANSPOSE, 1.0, A, descr,
                         x, 0.0, y);
    if (st != HML_SPARSE_STATUS_SUCCESS) {
        fprintf(stderr, "hml_sparse_d_mv failed: %d\n", (int)st);
        hml_sparse_destroy(A);
        return 1;
    }

    printf("y = [%.1f, %.1f, %.1f, %.1f]\n", y[0], y[1], y[2], y[3]);

    const double expected[4] = {2.0, 6.0, 15.0, 28.0};
    int failed = 0;
    for (int i = 0; i < 4; ++i) {
        if (fabs(y[i] - expected[i]) > 1.0e-12) {
            fprintf(stderr, "mismatch at y[%d]: got %g, expected %g\n",
                    i, y[i], expected[i]);
            failed = 1;
        }
    }

    hml_sparse_destroy(A);

    if (failed) {
        fprintf(stderr, "validation failed\n");
        return 1;
    }
    printf("validation passed\n");
    return 0;
}
```

#### 11.3.3 使用 C86-HPCKit 构建

```bash

gcc sparse_demo.c -I"$HML_ROOT/include" -L"$HML_ROOT/lib" \
    -Wl,-rpath,"$HML_ROOT/lib" -lhsparse -fopenmp -lpthread -lm -o sparse_demo_hml

./sparse_demo_hml
```

期望输出：

```text

validation passed
```

#### 11.3.4 验证实际加载的数学库

```bash

```

结果中应出现 `libhsparse.so`，不应出现 oneMKL。

#### 11.3.5 注意事项

- HygonSPARSE 的 `hml_sparse_d_create_csr` 采用 **4 数组 CSR**（`rows_start` + `rows_end` 分别给出每行非零元素起止），与部分 oneMKL 版本的 3 数组（单一 `row_ptr`）不同，需核对索引基准。
- 描述符 `struct hml_matrix_descr` 为**值传递**（非指针），需整体初始化。
- 链接需显式带 `-fopenmp -lpthread`（`libhsparse` 依赖 OpenMP 与 pthread 运行时），否则出现 `GOMP_*`/`pthread_*` 未定义引用。
- HML 1.9.0 发行包的 `libhsparse.so` 其 SONAME 为 `libhsparse.so.1`，但安装目录缺少该符号链接，运行时可能报 `libhsparse.so.1: cannot open shared object file`。需补：`ln -s libhsparse.so.1.3.1 "$HML_ROOT/lib/libhsparse.so.1"`（版本号按实际发行包调整）。
- 本节示例已在 HML 1.9.0 上使用 hgcc 12.3.0 与 hcc 16.0.4（海光 C86-4G，OPN 7490H）本地实测通过；加载 hcc 环境时把 `gcc` 换成 `clang` 即可，其余命令不变。

## 12. 应用迁移指南

### 12.1 HPC 应用

#### 12.1.1 VASP

**迁移概述**：VASP 6.4.2 已在海光 C86-4G（OPN 7490H）上使用 C86-HPCKit 完整重建并通过数值验证。将 Intel oneAPI 的 `mpiifort`/`ifort`/`icx`/`icpx` + oneMKL + Intel MPI 替换为 HGCC（gfortran）+ HML + HMPI，只需新增一个 `makefile.include`，VASP 业务源码无需改动。

**验证环境**

| 项 | 值 |
|---|---|
| VASP | 6.4.2（官方源码，构建 `vasp_std`/`vasp_gam`/`vasp_ncl`） |
| 编译器 | HGCC 12.3.0（gcc/g++/gfortran） |
| MPI | HMPI 1.0.0（Open MPI，`mpif90` 包装 gfortran） |
| 数学库 | HML 1.9.0（`libhblas` + `libhscalapack` + `libfftw3`） |
| 处理器 | 海光 C86-4G（OPN 7490H，AVX-512） |

**步骤 1：加载环境**

```bash
source /path/to/hygon/hpc-setenv.sh hgcc
```

该脚本把 HGCC 的 `gcc/g++/gfortran`、HMPI 的 `mpif90`/`mpirun`、HML 的头文件与库目录加入 `PATH`/`LD_LIBRARY_PATH`/`CPATH`。编译与运行都必须先执行此命令。

**步骤 2：确认 FFTW 的 Fortran 接口**

VASP 的 `src/fftw3d.F` 通过 `include 'fftw3.f'` 引入 FFTW 的 Fortran 参数常量。HML 1.9.x 起已随包提供 `fftw3.f`（以及 `fftw3.f03`、`fftw3l.f03`、`fftw3q.f03`），无需手动补充，`-I$(HML_ROOT)/include` 即可找到。

**步骤 3：编写 `makefile.include`**

基于 `arch/makefile.include.gnu_ompi_mkl_omp` 修改，改动集中在 Fortran 编译器、数学库与头文件路径三处：

```makefile
# 前面 CPP_OPTIONS、CPP、FREE、OFLAG、OBJECTS 等与原 gnu 模板一致
CPP         = gcc -E -C -w $*$(FUFFIX) >$*$(SUFFIX) $(CPP_OPTIONS)

FC          = mpif90 -fopenmp          # HMPI 包装器（底层 hgcc gfortran）
FCL         = mpif90 -fopenmp

FFLAGS      = -w -ffpe-summary=none
VASP_TARGET_CPU ?= -march=native       # 启用当前处理器支持的指令集优化
FFLAGS     += $(VASP_TARGET_CPU) -fallow-argument-mismatch

# BLAS/LAPACK（合并于 libhblas）、ScaLAPACK/BLACS（libhscalapack）、FFTW3（libfftw3）
HML_ROOT   ?= /path/to/hpckit/hygon/hml/hgcc
LLIBS      += -L$(HML_ROOT)/lib -Wl,--no-as-needed \
              -lhscalapack -lhblas -lfftw3 -lgomp -lpthread -lm -ldl

# HML 头文件目录（含 fftw3.h 与 fftw3.f）
INCS        = -I$(HML_ROOT)/include
```

关键差异对照（Intel oneAPI → C86-HPCKit）：

| 配置项 | Intel oneAPI | C86-HPCKit |
|---|---|---|
| Fortran 编译器 | `mpiifort` / `ifort` | `mpif90`（HMPI 包装 hgcc gfortran） |
| C / C++ 编译器 | `icx` / `icpx` | `gcc` / `g++` |
| BLAS + LAPACK | `-qmkl` 或 `-lmkl_gf_lp64 -lmkl_gnu_thread -lmkl_core` | `-lhblas` |
| ScaLAPACK + BLACS | `-lmkl_scalapack_lp64 -lmkl_blacs_openmpi_lp64` | `-lhscalapack` |
| FFTW3 | `-I$MKLROOT/include/fftw` + MKL | `-lfftw3`（HML 的 FFTNG 运行时提供 FFTW3 兼容接口） |
| MPI 运行 | `mpirun`（Intel MPI）+ `I_MPI_*` | `mpirun`（HMPI/Open MPI）+ `OMPI_MCA_*` |

**步骤 4：构建**

```bash
make DEPS=1 all -j 24
```

`DEPS=1` 让顶层 `makefile` 先生成模块依赖文件 `.depend`，保证并行编译时模块文件的生成顺序。产物为 `bin/vasp_std`、`bin/vasp_gam`、`bin/vasp_ncl`。

**步骤 5：验证动态依赖**

```bash
ldd bin/vasp_std
```

确认只加载 `libhblas.so.1`、`libhscalapack.so.1.6`、`libfftw3.so`（及其 FFTNG 运行时）、HMPI 的 `libmpi.so.40` 与 hgcc 的 `libgfortran.so.5`，且无 `libmkl_*`、`libiomp5` 或 Intel MPI 残留；否则说明仍错误链接了 oneAPI 组件。

**步骤 6：运行与数值验证**

以 fullerene（80 原子，自旋极化，PREC=high，1×1×1 k 点）算例为例：

```bash
export OMP_NUM_THREADS=1
ulimit -s unlimited
mpirun -np 128 bin/vasp_std > output.log 2>&1
grep -E "F=|E0=" OUTCAR | tail -1
```

运行时确认输出包含 `scaLAPACK will be used`，说明 HML 的 ScaLAPACK 被实际调用。

数值对照（与 Intel oneAPI 基线算例比较）：

| 项 | Intel oneAPI 基线 | C86-HPCKit（HGCC+HML+HMPI） |
|---|---|---|
| 首步收敛自由能 F (eV) | -709.17335E+03 | -709.17335E+03（一致） |
| 首步收敛能量 E0 (eV) | -709.15475E+03 | -709.15475E+03（一致） |
| 磁矩 mag (μB) | 1.7045 | 1.7045（一致） |

三者逐位一致；SCF 迭代轨迹（DAV/RMM 各步）与基线偏差 \< 1e-3 eV，末位差异仅来自不同编译器/数学库的浮点归约顺序。

> **HCC（clang/flang）工具链亦可**：将 `makefile.include` 中的编译器改为 hcc 的 clang/clang++/flang，OpenMP 运行库由 `-lgomp` 改为 `-lomp`，其余（HML、HMPI 路径）不变，参考 `arch/makefile.include.hpckit_hcc`。两种编译器下算例能量一致。

**注意事项**

- HML 的 BLAS 与 LAPACK 合并于 `libhblas`，ScaLAPACK/BLACS 合并于 `libhscalapack`，无需像 oneMKL 那样分别链接多个库。
- HML 的 `libfftw3.so` 是 FFTNG 运行时的 FFTW3 兼容入口，`dfftw_*` Fortran 符号与 `fftw3.f`/`fftw3.f03` 常量头均随包提供。
- 编译与运行前都必须 `source hpc-setenv.sh hgcc`，以使用 hgcc 自带的 gfortran 运行库，避免运行库版本不匹配导致启动失败。
- `make -j` 并行构建必须配合 `DEPS=1`，否则 `.mod` 文件顺序竞争会报 `Cannot open module file`。

#### 12.1.2 GROMACS

**迁移概述**：GROMACS 2024.4 已在海光 C86-4G（OPN 7490H）上使用 C86-HPCKit 完整重建并运行验证。GROMACS 是 CMake 构建的 C++ 程序，将 Intel oneAPI 的 `icx/icpx` + Intel MPI + MKL 替换为 HGCC + HMPI + HML，通过 CMake 选项显式指定 HML 的 FFTW 与 BLAS/LAPACK 即可，业务源码无需改动。产物为 `bin/gmx_mpi`。

**验证环境**

| 项 | 值 |
|---|---|
| GROMACS | 2024.4（官方源码，CMake 构建） |
| 编译器 | HGCC 12.3.0（gcc/g++） |
| MPI | HMPI 1.0.0（Open MPI，`mpicxx` 包装 g++） |
| 数学库 | HML 1.9.0（`libfftw3f` 单精度 FFTW + `libhblas` BLAS/LAPACK） |
| SIMD | AVX\_512（自动检测） |
| 处理器 | 海光 C86-4G（OPN 7490H，AVX-512） |

**步骤 1：加载环境**

```bash
source /path/to/hygon/hpc-setenv.sh hgcc
```

该脚本把 HGCC 的 `gcc/g++`、HMPI 的 `mpicc/mpicxx/mpirun`、HML 的头文件与库目录加入 `PATH`/`LD_LIBRARY_PATH`/`CPATH`，并导出 `HML_HOME`。编译与运行都必须先执行此命令。

**步骤 2：CMake 配置**

GROMACS 关闭 `GMX_DOUBLE` 时精度档位为 mixed（默认），PME 长程静电使用单精度 FFTW（`fftwf_*` 前缀），因此链接的是 HML 的 `libfftw3f.so`（内部由 HFFT 运行时实现），而不是双精度的 `libfftw3.so`。HML 未提供 `fftw3f.pc`，pkg-config 无法自动发现，需用 `FFTWF_LIBRARY`/`FFTWF_INCLUDE_DIR` 显式指定；BLAS/LAPACK 同理，HML 的库名是 `libhblas`（BLAS 与 LAPACK 合并），需用 `GMX_BLAS_USER`/`GMX_LAPACK_USER` 显式指定，否则 GROMACS 会回退到内置实现。

```bash
mkdir build && cd build
cmake .. \
  -DCMAKE_BUILD_TYPE=Release \
  -DGMX_MPI=ON \
  -DGMX_OPENMP=ON \
  -DGMX_FFT_LIBRARY=fftw3 \
  -DGMX_BUILD_OWN_FFTW=OFF \
  -DFFTWF_INCLUDE_DIR=$HML_HOME/include \
  -DFFTWF_LIBRARY=$HML_HOME/lib/libfftw3f.so \
  -DGMX_EXTERNAL_BLAS=ON \
  -DGMX_EXTERNAL_LAPACK=ON \
  -DGMX_BLAS_USER=$HML_HOME/lib/libhblas.so \
  -DGMX_LAPACK_USER=$HML_HOME/lib/libhblas.so
```

关键差异对照（Intel oneAPI → C86-HPCKit）：

| 配置项 | Intel oneAPI | C86-HPCKit |
|---|---|---|
| C / C++ 编译器 | `icx` / `icpx` | `gcc` / `g++`（HGCC） |
| MPI 编译器 | Intel MPI（`mpiicx`/`mpiicpx`） | `mpicxx`（HMPI 包装 g++） |
| FFT 库 | MKL（`-DGMX_FFT_LIBRARY=mkl`） | HML `libfftw3f`（`-DGMX_FFT_LIBRARY=fftw3`） |
| BLAS / LAPACK | MKL | HML `libhblas`（`-DGMX_BLAS_USER`/`-DGMX_LAPACK_USER`） |
| 并行 | Intel MPI `mpirun` + `I_MPI_*` | HMPI `mpirun` + `OMPI_MCA_*` |

**步骤 3：构建**

```bash
cmake --build . --target gmx -j $(nproc)
```

GROMACS 2022 起使用单一构建目标 `gmx`，当 `GMX_MPI=ON` 时输出的可执行文件即为 `bin/gmx_mpi`（不要按旧版习惯使用 `gmx_mpi` 作为构建目标名）。

**步骤 4：验证动态依赖**

```bash
ldd bin/gmx_mpi
```

确认加载 HML 的 `libfftw3f.so`（及其 `libhfftf_rt_base*` 运行时）、`libhblas.so`，HMPI 的 `libmpi.so`/`libopen-pal.so`/UCX/UCC，以及 hgcc 的 `libstdc++.so.6`/`libgomp.so.1`；无 `libmkl_*`、`libiomp5` 或 Intel MPI 残留。另可运行 `bin/gmx_mpi --version`，应看到 `CPU FFT library: fftwf-*` 与 `BLAS library: External - user-supplied`。

**步骤 5：运行验证**

GROMACS 源码包不包含官方回归测试集（需单独下载），但自带 `share/top/spc216.gro`（216 个 SPC 水分子）与力场文件，可搭最小水盒子算例验证编译产物能正确调用 FFTW、MPI 与 OpenMP：

```bash
export GMXLIB=/path/to/gromacs-2024.4/share/top
gmx_mpi grompp -f em.mdp -c spc216.gro -p topol.top -o em
gmx_mpi mdrun -deffnm em -ntomp 8
gmx_mpi grompp -f md.mdp -c em.gro -p topol.top -o md
mpirun -np 4 gmx_mpi mdrun -deffnm md -ntomp 4
```

`md.log` 中 `CPU FFT library: fftwf-*`、`coulombtype = PME`、`Coul. recip.` 项非零，表明 PME 长程静电通过 HML 单精度 FFTW 计算；能量最小化收敛、MD 温度稳定在 300 K、势能约 -8.9e3 kJ/mol（216 水），说明结果物理合理。更严格的数值对照需另下载官方 regression tests 逐项比对。

**注意事项**

- GROMACS 单精度构建使用单精度 FFTW，务必链接 `libfftw3f.so`（HFFT 运行时），而非双精度的 `libfftw3.so`。
- HML 未提供 FFTW 的 pkg-config 文件，`FFTWF_LIBRARY`/`FFTWF_INCLUDE_DIR` 必须显式指定，否则 CMake 检测不到 HML 的 FFTW。
- HML 的 BLAS/LAPACK 合并在 `libhblas`，库名不是 `libblas`/`liblapack`，必须用 `GMX_BLAS_USER`/`GMX_LAPACK_USER` 显式指定，否则 GROMACS 静默回退到内置 BLAS/LAPACK（仍在运行，但未调用 HML）。
- GROMACS 2024 的 `share/top/spc.itp` 等顶层水模型文件是占位符，需从力场目录引用（如 `#include "gromos54a7.ff/spc.itp"`），且 `.top` 需先 `#include "gromos54a7.ff/forcefield.itp"` 提供 `[ defaults ]`/`[ atomtypes ]`。
- 编译与运行前都必须 `source hpc-setenv.sh hgcc`，以使用 hgcc 自带的 `libstdc++`/`libgomp` 运行库，避免运行库版本不匹配导致启动失败。

#### 12.1.3 OpenFOAM

**迁移概述**：OpenFOAM v2106（openfoam.com/ESI，2021-06）已在海光 C86-4G（OPN 7490H）上使用 C86-HPCKit 完整重建并运行验证。OpenFOAM 核心求解器不依赖 BLAS/LAPACK/FFTW，迁移仅涉及编译工具链与 MPI：将 Intel `icx/icpx` + Intel MPI 替换为 HGCC `g++` + HMPI，并在 wmake 规则中追加 `-D_GLIBCXX_USE_CXX11_ABI=0`（原因见步骤 3），业务源码无需改动。

**验证环境**

| 项 | 值 |
|---|---|
| OpenFOAM | v2106（openfoam.com/ESI，wmake 构建） |
| 编译器 | HGCC 12.3.0（g++） |
| MPI | HMPI 1.0.0（Open MPI 5.0.8rc3，`SYSTEMOPENMPI` 自动发现） |
| 数学库 | 无（核心不依赖 BLAS/LAPACK/FFTW） |
| 处理器 | 海光 C86-4G（OPN 7490H，AVX-512） |
| 构建范围 | `src` 全部库 + 6 个关键应用（icoFoam/simpleFoam/interFoam/blockMesh/decomposePar/reconstructPar） |

**步骤 1：加载环境**

```bash
source /path/to/hygon/hpc-setenv.sh hgcc
```

该脚本把 HGCC 的 `gcc/g++`、HMPI 的 `mpicc/mpicxx/mpirun` 加入 `PATH`。`SYSTEMOPENMPI` 规则通过 `mpicc --showme:link` 自动发现 HMPI 安装前缀，无需手动指定 `MPI_ARCH_PATH`。

**步骤 2：选择编译器与 MPI**

OpenFOAM v2106 的 `etc/bashrc` 默认即 `WM_COMPILER=Gcc`、`WM_MPLIB=SYSTEMOPENMPI`，通常无需修改，确认即可（如需覆盖可写 `etc/prefs.sh`）：

```bash
export WM_COMPILER=Gcc            # 使用 wmake/rules/linux64Gcc/
export WM_MPLIB=SYSTEMOPENMPI     # 通过 mpicc 自动发现系统(HMPI) Open MPI
```

`WM_COMPILER=Gcc` 使 wmake 使用 `wmake/rules/linux64Gcc/`（其 C++ 规则包含 `wmake/rules/General/Gcc/c++`）；`WM_MPLIB=SYSTEMOPENMPI` 使 Pstream 层链接系统 Open MPI（HMPI 的 `libmpi.so.40`），输出 `libPstream.so` 到 `lib/sys-openmpi/`。

**步骤 3：修复 C++11 ABI 标签不一致（关键）**

hgcc 的 g++ 12.3.0 默认使用新版 C++11 ABI（`_GLIBCXX_USE_CXX11_ABI=1`）。OpenFOAM v2106 的模板运行时选择表（`src/OpenFOAM/db/runTimeSelection/construction/runTimeSelectionTables.H` 中 `defineTemplateRunTimeSelectionTable` 用 `template<>` 显式特化定义静态成员指针）在定义处与引用处的 `std::__cxx11::basic_string` ABI 标签不一致，导致应用链接阶段出现大量 `undefined reference to ...ConstructorTablePtr_[abi:cxx11]`。解决办法是全局强制旧 ABI，使定义与引用两侧的 `std::string` 符号都不带 `[abi:cxx11]` 标签（OpenFOAM 官方 LUMI 适配采用同一做法）：

编辑 `wmake/rules/General/Gcc/c++`，把 `CC` 行改为：

```make
CC = g++ -std=c++11 -D_GLIBCXX_USE_CXX11_ABI=0
```

hgcc 的 `libstdc++.so.6` 为双 ABI 构建，同时提供新旧两种 `std::string` 符号，因此旧 ABI 下运行不受影响。

**步骤 4：构建**

```bash
cd /path/to/OpenFOAM-v2106
source etc/bashrc
wmake/src/Allmake                 # 先编译 wmake 构建工具
src/Allwmake -j 64                # 编译 src 全部库（106 个 .so）
```

随后按需编译关键应用（每个应用目录内执行 `wmake`）：

```bash

  applications/solvers/incompressible/icoFoam \
  applications/solvers/incompressible/simpleFoam \
  applications/solvers/multiphase/interFoam \
  applications/utilities/mesh/generation/blockMesh \
  applications/utilities/parallelProcessing/decomposePar \
  applications/utilities/parallelProcessing/reconstructPar; do
  (cd "$d" && wmake)
done
```

完整 `Allwmake`（含 tutorials、SCOTCH/METIS 等 ThirdParty 依赖）耗时较长；验证迁移可行性时裁剪为 `src` + 关键应用即可（`decomposePar` 使用 `simple` 分解方法，不依赖 SCOTCH/METIS）。

**步骤 5：验证动态依赖**

```bash
ldd platforms/linux64GccDPInt32Opt/bin/icoFoam
```

确认加载 HGCC 的 `libstdc++.so.6`/`libgcc_s.so.1`、HMPI 的 `libmpi.so.40`，以及 OpenFOAM 自身的 `libOpenFOAM.so`/`libPstream.so`（位于 `lib/sys-openmpi/`）；无 `libimf`、`libiomp5`、`libmkl_*` 或 Intel MPI 残留。

**步骤 6：运行验证**

用自带 tutorial（`tutorials/incompressible/icoFoam/cavity`）分别做串行与并行验证：

```bash

# 并行（4 进程）

```

验证通过标准：`blockMesh`/`icoFoam`/`decomposePar`/`mpirun`/`reconstructPar` 均返回退出码 0；`log.icoFoam` 中 Courant 数（本例约 0.22）、各速度/压力分量残差收敛到 `1e-7`、连续性误差 `global` 项约 `1e-18`，且并行重构后的结果与串行一致。

**注意事项**

- OpenFOAM 核心不依赖 BLAS/LAPACK/FFTW，迁移无需链接 HML；不要为了"平替"而强制链接数学库，否则徒增无依据的依赖。
- GCC 12（hgcc）默认新 C++11 ABI 与 OpenFOAM v2106 的模板运行时选择表不兼容，`-D_GLIBCXX_USE_CXX11_ABI=0` 是唯一必需的编译选项修改；漏掉它会在应用链接阶段报大量 `[abi:cxx11]` 未定义引用。
- `SYSTEMOPENMPI` 依赖 PATH 中的 `mpicc` 定位 MPI，编译与运行前都必须先 `source hpc-setenv.sh hgcc`，否则 `mpicc --showme:link` 找不到 HMPI。
- 并行运行时 HMPI 使用 `OMPI_MCA_*` 环境变量调优，与 Intel MPI 的 `I_MPI_*` 不同。

**步骤 4：模型和性能验证**

执行 TensorFlow 代表性模型或 `label_image.py`，固定 batch size、线程数、NUMA、预热次数和迭代次数，保存 p50/p99 延迟和吞吐量。

**注意事项**

- Bazel 版本必须与目标 TensorFlow 的 `.bazelversion` 或发布说明匹配。
- Python ABI 不匹配时检查 wheel 标签、解释器和 `Python.h` 路径。
- Bazel 内存不足时降低 `--jobs`、`--local_ram_resources` 和 `--local_cpu_resources`。
- oneDNN 是否启用必须由构建日志、`tf.sysconfig.get_build_info()` 和 `ldd` 共同确认。

#### 12.2.3 oneDNN

**迁移概述**：oneDNN 迁移以独立源码构建为主，验证 CPU runtime、OpenMP/TBB/SEQ 线程后端、JIT/ISA 探测、primitive 正确性和 convolution/matmul 性能。oneDNN 与 HML 必须分别确认依赖关系，不能直接互换。

**验证环境**

| 项 | 值 |
|---|---|
| oneDNN | 3.13.1 |
| 编译器 | HGCC 12.3.0（gcc/g++） |
| CPU runtime | OMP |
| 处理器 | 海光 C86-4G（OPN 7490H，AVX-512） |
| 依赖关系 | oneDNN 与 HML 分别确认 |

**步骤 1：配置并构建**

```bash
git clone https://github.com/oneapi-src/oneDNN.git
cd oneDNN
git checkout v3.13.1
rm -rf build

  -DCMAKE_BUILD_TYPE=Release \

  -DDNNL_CPU_RUNTIME=OMP \

  -DDNNL_BUILD_BENCH=ON 2>&1 | tee onednn-config.log

  2>&1 | tee onednn-build.log
```

**步骤 2：检查 ISA 和 Intel 专用选项**

执行 `cmake -LAH -S . -B build` 核对目标版本选项；清理 `-xHost`、`-xCORE-*`、`-march=skylake*`、Intel OpenMP 和 oneMKL 路径，记录 `onednn-config.log` 中的 JIT/ISA 探测结果。

**步骤 3：正确性和动态库验证**

```bash
ctest --test-dir build --output-on-failure 2>&1 | tee onednn-ctest.log

test -n "$BENCHDNN"
```

## 13. 迁移验证与验收

### 13.1 构建验证

- 全量清理旧对象文件和 CMake cache；
- 确认编译日志中不再出现 Intel 编译器、`MKLROOT` 或 `-lmkl_*`；
- 确认目标文件和可执行文件没有意外链接 Intel OpenMP、Intel MPI 或 oneMKL Classic；
- 确认运行环境不依赖原 oneAPI 的 `LD_LIBRARY_PATH`。

### 13.2 数值正确性

不要只比较程序是否退出成功。至少验证：

- 与迁移前基线比较相对误差和绝对误差；
- 零长度、小矩阵、奇异矩阵、非单位步长等边界输入；
- NaN、Inf、下溢和舍入相关场景；
- 单线程和多线程结果；
- 不同 MPI rank 数下的结果；
- 随机算法的统计性质，而不是仅比较随机序列逐项相同。

浮点归约顺序变化可能导致末位差异。验收标准应根据算法稳定性设定容差，不能一律使用二进制完全一致。

### 13.3 性能验证

性能对比应固定：

- 输入规模和迭代次数；
- MPI rank 数和 OpenMP 线程数；
- NUMA 策略和进程/线程绑定；
- CPU 频率策略；
- 预热次数；
- 编译器优化级别和目标架构选项。

若性能明显下降，先检查实际加载库、线程数、绑核、NUMA、矩阵布局和问题规模，再判断是否为数学库实现差异。

## 14. 常见问题

### 14.1 出现 `undefined reference to cblas_dgemm`

确认：

- 使用的库确实导出该符号；
- `-lhblas` 位于目标文件之后；
- `-L` 指向正确的 HML 目录；
- 静态链接时已加入全部传递依赖；
- 没有把 CBLAS 接口误链接到只提供 Fortran BLAS 的库。

### 14.2 使用 ILP64 的程序能否直接迁移

不能默认直接迁移。当前程序若定义 `MKL_ILP64`、使用 `MKL_INT64`、链接 `mkl_intel_ilp64` 或使用 Fortran `-i8`，必须确认目标 HML 是否提供匹配的 64 位整数接口。若只提供 LP64，需要评估问题规模并修改整数类型和构建选项。

### 14.3 DFTI 是否只需更换链接库

不能。HygonFFT 提供 FFTW 兼容接口，不提供 oneMKL Classic DFTI API。必须根据变换类型、布局、步长、批量和缩放规则改写 plan 创建与执行代码。

### 14.4 `MKL_NUM_THREADS` 和 `I_MPI_*` 是否继续有效

通常不会。HML/OpenMP 和 HMPI/Open MPI 使用各自的线程与运行配置。应根据变量原本控制的功能重新设置，不能只做字符串替换。

### 14.5 为什么 CMake 设置了 `CMAKE_PREFIX_PATH` 仍找不到 HML

`CMAKE_PREFIX_PATH` 只有在 HML 提供 CMake package config 或项目调用相应 Find 模块时才有作用。通用做法是使用 `find_path`/`find_library`，或使用发行包实际提供的 pkg-config 文件。

### 14.6 迁移后结果与 oneMKL Classic 不完全相同

不同实现可能采用不同分块、向量化和并行归约顺序，浮点结果末位不同并不一定表示错误。应使用经过定义的数值容差、残差或算法级指标验收；如果原程序依赖 MKL 的条件数值可复现功能，还需要重新制定可复现性方案。
