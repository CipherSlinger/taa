# 1. 产品描述

## 1.1 产品介绍

### 1.1.1 概念介绍

MPI（Message Passing Interface，消息传递接口）是高性能计算领域使用最广泛的并行编程标准。它定义了一套进程间通信的函数接口规范，并行程序通过点对点通信和集合通信在多个进程之间交换数据，从而把一个计算任务拆分到多台服务器、多个处理器核心上协同完成。

MPI 程序采用"单程序多数据"（SPMD）的执行模型：同一份可执行文件被启动为多个进程（称为 rank），每个进程持有独立的内存空间，通过调用 MPI 接口完成数据交换。按通信模式划分，MPI 通信分为两类：

- **点对点通信（P2P，Point-to-Point）**：两个进程之间的定向数据传输，典型接口为 `MPI_Send` / `MPI_Recv` 及其非阻塞版本 `MPI_Isend` / `MPI_Irecv`。
- **集合通信（Collective）**：通信域内所有进程共同参与的通信，典型接口为 `MPI_Allreduce`、`MPI_Bcast`、`MPI_Barrier`、`MPI_Alltoallv` 等。

MPI 标准只规定接口语义，不规定实现方式。业界常见的实现包括 Open MPI、MPICH、MVAPICH2、Intel MPI 等。不同实现在接口层保持一致，在底层传输、集合通信算法和平台优化上各有侧重。

**Hygon MPI** 是海光面向 C86 平台推出的高性能并行计算通信库，基于 Open MPI 5.0.8 与 UCX 1.21.0 构建，符合 MPI 3.1 标准，并对集合通信算法选择与单节点共享内存通信进行了针对性优化。

**适用场景**：气象预报、计算流体力学、分子动力学、石油勘探、结构仿真等传统 HPC 领域，以及需要大规模进程间通信的 AI for Science 场景。

**运行平台**：海光 C86 系列处理器。

**操作系统**：主流 x86\_64 Linux 发行版。

### 1.1.2 价值

Hygon MPI 的价值体现在三个层面。

**点对点通信方面**，Hygon MPI 通过 UCX 统一通信框架承载节点间数据传输。UCX 在传输层屏蔽了不同网络硬件的差异，向上提供统一的通信原语，使同一个 MPI 程序无需修改即可在 InfiniBand、RoCE 以及各类 IB Verbs 兼容网络设备上运行，保证了程序的可移植性。

**集合通信方面**，集合通信是 HPC 应用中开销占比最高的通信模式。Hygon MPI 在集合通信层采用"分层通信 + 算法可配置"的双组件设计，通过 `coll/han` 和 `coll/tuned` 共同提供可调的集合通信能力：

- 应用无需修改代码，仅通过命令行参数或配置文件即可改变集合操作的底层算法。
- 跨节点运行时自动启用分层集合通信，按节点内/节点间两级拓扑组织数据传输，显著削减跨节点通信量。
- 平台随包提供了一份经过离线调优的决策表（`decision.file`），覆盖 64、96、128、192、256 五种典型进程规模，用户直接引用即可获得平台推荐的算法组合。
- 算法选择可按消息长度精细到字节级切换，避免了"一套算法打天下"带来的性能损失。

**可移植性方面**，Hygon MPI 完整保留 Open MPI 的命令行接口、环境变量约定和 MCA 参数体系。已有的 Open MPI 应用、编译脚本和作业提交脚本无需改动即可迁移；同时 Hygon MPI 保持对上游社区的兼容，便于后续跟随社区版本演进。

### 1.1.3 功能

Hygon MPI 提供 MPI 3.1 标准规定的完整通信接口，其中点对点通信与集合通信的主要接口如下。

**点对点通信接口**

| 接口名称 | 功能说明 |
|---|---|
| `MPI_Send` / `MPI_Recv` | 标准阻塞式发送与接收 |
| `MPI_Isend` / `MPI_Irecv` | 非阻塞发送与接收，返回请求句柄，需配合 `MPI_Wait` / `MPI_Test` 完成 |
| `MPI_Sendrecv` | 发送与接收合并为一次调用，由 MPI 内部避免死锁 |
| `MPI_Bsend` / `MPI_Ssend` / `MPI_Rsend` | 缓冲、同步、就绪模式的阻塞发送 |
| `MPI_Sendrecv_replace` | 使用同一缓冲区完成发送与接收 |
| `MPI_Wait` / `MPI_Waitall` / `MPI_Waitany` / `MPI_Waitsome` | 等待非阻塞操作完成 |
| `MPI_Test` / `MPI_Testall` / `MPI_Testany` / `MPI_Testsome` | 非阻塞地查询非阻塞操作是否完成 |

**集合通信接口**

| 接口名称 | 功能说明 | 阻塞/非阻塞 |
|---|---|---|
| `MPI_Barrier` | 通信域内所有进程同步点 | 阻塞 / `MPI_Ibarrier` |
| `MPI_Bcast` | 一对多广播 | 阻塞 / `MPI_Ibcast` |
| `MPI_Reduce` | 多对一归约 | 阻塞 / `MPI_Ireduce` |
| `MPI_Allreduce` | 多对多归约，结果对所有进程可见 | 阻塞 / `MPI_Iallreduce` |
| `MPI_Gather` / `MPI_Gatherv` | 多对一收集（定长 / 变长） | 阻塞 / `MPI_Igather(v)` |
| `MPI_Allgather` / `MPI_Allgatherv` | 多对多收集（定长 / 变长） | 阻塞 / `MPI_Iallgather(v)` |
| `MPI_Scatter` / `MPI_Scatterv` | 一对多分发（定长 / 变长） | 阻塞 / `MPI_Iscatter(v)` |
| `MPI_Alltoall` / `MPI_Alltoallv` | 全交换（定长 / 变长） | 阻塞 / `MPI_Ialltoall(v)` |
| `MPI_Scan` / `MPI_Exscan` | 前缀归约 | 阻塞 / `MPI_Iscan`、`MPI_Iexscan` |
| `MPI_Reduce_scatter` / `MPI_Reduce_scatter_block` | 归约后分发 | 阻塞 / `MPI_Ireduce_scatter(_block)` |

**其他能力**

| 能力 | 说明 |
|---|---|
| 通信域管理 | `MPI_Comm_split`、`MPI_Comm_dup`、`MPI_Cart_create`、`MPI_Graph_create` 等 |
| 派生数据类型 | `MPI_Type_contiguous`、`MPI_Type_vector`、`MPI_Type_create_struct` 等 |
| 单边通信 | `MPI_Win_create`、`MPI_Put`、`MPI_Get`、`MPI_Accumulate`（由 `osc/ucx` 或 `osc/rdma` 组件提供） |
| 并行 I/O | `MPI_File_open` 等 ROMIO 接口 |
| 动态进程管理 | `MPI_Comm_spawn`、`MPI_Comm_connect` |
| 容错 | ULFM（User Level Failure Mitigation）接口 |

**混合编程支持**

| 能力 | 说明 |
|---|---|
| MPI + OpenMP | 支持 `MPI_THREAD_MULTIPLE` 线程级别；配套提供支持多线程的 UCX 版本 |
| MPI + CUDA / ROCm | 通过 Open MPI 的 Accelerator 框架接入加速器内存，支持设备内存直接参与 MPI 通信 |

## 1.2 软件架构

Hygon MPI 构建在 Open MPI 的 MCA（Modular Component Architecture，模块化组件架构）框架之上，整体分为应用接口层、集合通信层、点对点通信层、传输层和通用服务层五个层次。

```
┌─────────────────────────────────────────────────────────────┐
│                        应用程序                              │
├─────────────────────────────────────────────────────────────┤
│  应用接口层    MPI 标准 C / C++ / Fortran 绑定、MPI 3.1 接口│
├─────────────────────────────────────────────────────────────┤
│  集合通信层    coll/han（分层）· coll/tuned（算法选择）        │
│                coll/basic · coll/libnbc（非阻塞）            │
├─────────────────────────────────────────────────────────────┤
│  点对点通信层  pml/ucx（平台默认）·  pml/ob1（回退）           │
├──────────────────────────┬──────────────────────────────────┤
│  BTL 层（ob1 路径）      │  UCT 层（UCX 路径）                │
│  btl/self  · btl/sm      │  uct/sm（xpmem·cma·knem）        │
│  btl/tcp   · btl/uct     │  uct/ib（rc_verbs·ud_verbs）     │
│                          │  uct/tcp                         │
├──────────────────────────┴──────────────────────────────────┤
│  通用服务层    opal（数据结构、内存管理、日志）                │
│                hwloc（拓扑）· PMIx（进程）· PRRTe（启动）     │
├─────────────────────────────────────────────────────────────┤
│  操作系统 / 硬件   共享内存 · IB Verbs 网络 · AVX2 指令集      │
└─────────────────────────────────────────────────────────────┘
```

各层职责说明如下。

**应用接口层** 提供 MPI 标准的 C、C++、Fortran 语言绑定。用户程序通过 `mpicc`、`mpic++`、`mpif90` 等封装器编译链接，封装器在调用后端编译器时自动加入头文件路径和链接参数。

**集合通信层** 由 `coll` 框架下的一组组件构成，各组件通过优先级竞争通信域的控制权：

| 组件 | 默认优先级 | 职责 |
|---|---|---|
| `coll/cuda` | 78 | 加速器相关集合通信 |
| `coll/self` | 75 | 单进程通信域的自环通信 |
| `coll/sync` | 50 | 同步类集合操作 |
| **`coll/han`** | **35** | **跨节点分层集合通信，跨节点运行时默认接管部分集合操作** |
| **`coll/tuned`** | **30** | **算法可配置的集合通信，承载全部底层算法选择逻辑** |
| `coll/basic` | 10 | 基础实现，作为通用兜底 |
| `coll/libnbc` | 10 | 非阻塞集合通信（`MPI_I*` 系列） |

集合通信层的工作方式需要特别说明，它由两个组件协同完成：

- **`coll/han`（分层集合通信，优先级 35）**：当通信域中存在跨节点进程时，`coll/han` 以更高的优先级接管 Barrier、Scatter、Reduce、Gather、Bcast、Allreduce、Allgather 七个集合操作。它本身不实现具体的通信算法，而是把通信域按硬件拓扑拆分为**节点内子通信域**和**节点间子通信域**，分别在两个子通信域上完成集合操作，从而减少跨节点数据量与网络往返次数。
- **`coll/tuned`（算法选择，优先级 30）**：负责承载具体的集合通信算法。它支持三种算法决策模式——固定决策（内置规则）、强制算法（命令行指定）、动态决策（决策表驱动），并通过 `decision.file` 决策表按通信域规模和消息长度自动选择算法。

两个组件的分工关系是：`coll/han` 不直接实现数据传输，而是把通信域拆分为节点内、节点间两个子通信域，在每个子通信域上调用**该子通信域自身选中的集合通信组件**（默认由 `coll/tuned` 承担）完成实际数据传输。因此即使集合操作由 `coll/han` 接管，`coll_tuned_<操作>_algorithm` 等参数对其节点内子通信域依然有效，参见 2.2.1 节。

`coll/han` 提供以下 MCA 参数用于控制其行为：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `coll_han_priority` | 35 | 组件优先级。设为负值可禁用 `coll/han`，使集合操作全部由 `coll/tuned` 处理 |
| `coll_han_verbose` | 0 | 组件调试信息级别，未设置时沿用 coll 框架的全局级别 |
| `coll_han_reproducible` | 0 | 是否要求归约类操作结果可复现；开启后会关闭基于拓扑的优化 |
| `coll_han_<操作>_low_module` | 0（tuned） | 节点内子通信域使用的组件，0 表示 tuned，1 表示 sm |
| `coll_han_<操作>_up_module` | 0（libnbc） | 节点间子通信域使用的组件，0 表示 libnbc，1 表示 adapt |
| `coll_han_use_<操作>_algorithm` | 0 | 指定该操作使用的分层算法编号，0 表示由组件自行决策 |
| `coll_han_bcast_segsize` | 65536 | Bcast 的分段大小，单位字节 |
| `coll_han_reduce_segsize` | 65536 | Reduce 的分段大小，单位字节 |
| `coll_han_allreduce_segsize` | 65536 | Allreduce 的分段大小，单位字节 |

其中 `<操作>` 可取 `bcast`、`reduce`、`allreduce`、`allgather`、`gather`、`scatter`；`_segsize` 系列参数只对上表中列出的三种操作有效。

`coll/han` 同样支持基于配置文件的动态规则，相关参数为 `coll_han_use_dynamic_file_rules`（默认关闭）、`coll_han_dynamic_rules_filename`（规则文件路径）和 `coll_han_dump_dynamic_rules`（打印生效规则）。Hygon MPI 默认不启用该机制，实际分层决策由组件内置规则完成。

> **单机运行的差异**：当通信域内全部进程都位于同一节点时（例如单机多进程运行），`coll/han` 会自行退出竞争，此时所有集合操作直接由 `coll/tuned` 处理。这意味着同一程序在单机与多机环境下的集合操作路径可能不同。

**点对点通信层** 由 `pml`（Point-to-Point Messaging Layer）框架提供，是上层 MPI 语义与下层传输能力之间的桥梁：

- `pml/ucx`：将 MPI 点对点语义直接映射到 UCX 的 `ucp_tag_*` 接口上，是 Hygon MPI 的**平台默认点对点组件**。当 UCX 及可用传输层/设备被探测到时，该组件以较高优先级被选中。
- `pml/ob1`：基于 BTL 的经典实现，负责消息匹配、分段重组和传输通道选择。当 UCX 不可用时自动回退到该组件，也可通过 `--mca pml ob1` 强制指定。

**传输层** 存在两条并行路径：

- UCX 路径下的 **UCT 传输层**：`uct/sm`（同节点，含 `xpmem`、`cma`、`knem` 三种实现）、`uct/ib`（InfiniBand 网络，含 `rc_verbs`、`ud_verbs`）、`uct/tcp`（TCP 网络）。
- ob1 路径下的 **BTL 组件**：`btl/self`（自环）、`btl/sm`（同节点共享内存）、`btl/tcp`（TCP 网络）、`btl/uct`（借道 UCX）。

> **说明**：两条路径是互斥的——`pml/ob1` 工作时使用 BTL 组件，`pml/ucx` 工作时直接使用 UCT 传输层，此时 `btl` 参数不生效。

同节点通信优先使用共享内存。Hygon MPI 通过 Open MPI 的 `smsc`（Shared Memory Single Copy）框架接入三种单拷贝机制，其优先级为 **xpmem（42）\> cma（37）\> knem（23）**。xpmem 内核模块提供跨进程内存映射能力，使数据在共享内存中只做一次拷贝即可完成传输。

**通用服务层** 提供与通信协议无关的基础设施：`opal` 提供动态数组、哈希表、原子操作、内存池等基础数据结构；`hwloc` 提供处理器与 NUMA 拓扑探测，是进程绑定和亲和性的依据；PMIx 负责进程管理与信息交换；PRRTe 提供作业启动运行时（Open MPI 5.x 起由 PRRTe 取代原 ORTE）。

## 1.3 关键特性

### 1.3.1 集合通信算法可配置与平台调优决策表

**特性说明**：Hygon MPI 的集合通信算法选择能力由 `coll/tuned` 组件承担，支持在不修改应用代码的前提下切换集合操作底层算法。平台随包提供了一份经过离线调优的决策表 `decision.file`，按通信域规模和消息长度给出推荐算法。

**支持的集合操作**：Allreduce、Alltoall、Alltoallv、Allgather、Bcast、Reduce 共六种。

**决策表覆盖的规模**：通信域进程数为 64、96、128、192、256 五档。

**与分层集合通信的关系**：跨节点运行时，Barrier、Scatter、Reduce、Gather、Bcast、Allreduce、Allgather 七个操作会先由 `coll/han` 按拓扑拆分为节点内、节点间两级子通信域，再由 `coll/tuned` 在子通信域上执行实际算法。因此上述决策表规则在这些操作上作用于**子通信域**的规模与消息长度，而非全局通信域——详见 2.2.1 节。

**适用条件与限制**：

- 需在 `mpirun` 命令中显式启用，参见 2.2.3 节。
- 实际进程数不在 64～256 区间时，按"不超过实际进程数的最大档位"选取规则，即小于 64 时统一使用 64 档规则。
- 决策表仅覆盖上述六种集合操作，其余操作沿用 Open MPI 的固定决策规则。

### 1.3.2 层次化共享内存单拷贝通信

**特性说明**：Hygon MPI 通过 `smsc` 框架接入 xpmem、cma、knem 三种单拷贝机制。当应用运行在同一节点的多个进程之间时，数据无需经过网络栈，也无需在用户态缓冲区之间反复拷贝，直接通过内存映射完成传递。

**优先级顺序**：xpmem \> cma \> knem。系统安装了海光 xpmem 内核模块时自动优先使用 xpmem。

**适用条件与限制**：

- 仅对同一节点内的进程间通信生效；跨节点通信仍走网络路径。
- xpmem 需要在内核中加载 `xpmem.ko` 模块，并要求 MPI 进程具备相应权限。
- 未安装任何单拷贝机制时自动回退到共享内存缓冲拷贝方式，功能不受影响。

### 1.3.3 UCX 传输层适配海光处理器

**特性说明**：Hygon MPI 配套的 UCX 1.21.0 增加了对海光处理器的识别与适配：

- 新增 Hygon 处理器厂商识别。
- 针对海光处理器开放 NT（Non-Temporal，非临时存储）流式传输路径。当待传输数据量超过 L3 缓存容量的特定比例时，自动采用绕过缓存的写入方式，避免大块数据冲刷缓存导致的性能下降。
- 随包提供海光平台调优。

### 1.3.4 通用 IB Verbs 网络支持

**特性说明**：Hygon MPI 的节点间通信基于 UCX 的 IB 传输层，通过标准的 `rdma-core`（`libibverbs` + `librdmacm`）访问网络设备，使用 `rc_verbs`（可靠连接）与 `ud_verbs`（不可靠数据报）两种传输方式。

**适用条件与限制**：

- 依赖系统提供符合 IBTA 规范的 Verbs 驱动。InfiniBand、RoCE 及各类 Verbs 兼容网络设备均可使用。
- 未针对特定厂商网卡提供专有加速路径。厂商专有加速需依赖对应厂商的驱动与用户态库。

### 1.3.5 完整的 Open MPI 兼容性

**特性说明**：Hygon MPI 完整保留 Open MPI 的命令行选项、环境变量约定与 MCA 参数体系。

- 编译器封装器：`mpicc`、`mpic++`、`mpif90`。
- 作业启动命令：`mpirun` 与 `mpiexec` 完全等价。
- 参数设置：命令行 `--mca <参数名> <值>` 与环境变量 `OMPI_MCA_<参数名>=<值>` 等价。
- 与调度系统集成：自动识别 Slurm、PBS/Torque、LSF、SGE 等调度环境并从调度器获取进程数与节点列表。

**适用条件与限制**：原有 Open MPI 应用可直接迁移，无需重新编译（ABI 兼容性取决于原 Open MPI 版本）。

### 1.3.6 混合编程与加速器支持

**特性说明**：

- 提供线程支持，可在 `MPI_THREAD_MULTIPLE` 线程级别下运行 MPI + OpenMP 混合程序。配套 UCX 提供多线程版本（`--enable-mt`），供高线程级别场景使用。
- 通过 Open MPI 的 Accelerator 框架接入加速器内存，支持设备内存直接参与 MPI 通信，减少主机与设备之间的显式拷贝。

**适用条件与限制**：加速器相关功能需要系统安装对应的运行时库（CUDA 或 ROCm）。

# 2. 操作指南

## 2.1 提交 MPI 作业

Hygon MPI 的作业提交方式取决于集群是否部署了作业调度系统。

### 2.1.1 提交前提

无论采用何种提交方式，都需要满足以下前提条件：

1. **可非交互登录远程节点**。多节点作业要求提交节点能够免密登录所有计算节点。配置方法为在主控节点生成密钥对并将公钥分发到各计算节点：
   
   ```bash
   ssh-keygen -t rsa
   ssh-copy-id -i ~/.ssh/id_rsa.pub user@node1
   ```
   
   完成后使用 `ssh node1` 验证是否需要输入密码。

2. **可执行文件可被找到**。Hygon MPI 的 `bin` 目录需要加入 `PATH`。

3. **动态库可被找到**。Hygon MPI 的 `lib` 目录需要加入 `LD_LIBRARY_PATH`；如果 MPI 以共享库方式编译，所有计算节点都需要设置。

4. **各节点环境一致**。所有计算节点的安装路径、环境变量配置应当保持一致。

典型的 `.bashrc` 配置如下（以安装路径 `/opt/hygon/hmpi/ompi` 为例）：

```bash
export OPAL_PREFIX=/opt/hygon/hmpi/ompi
export PATH=/opt/hygon/hmpi/ompi/bin:$PATH
export LD_LIBRARY_PATH=/opt/hygon/hmpi/ompi/lib:$LD_LIBRARY_PATH
```

> **说明**：`OPAL_PREFIX` 用于告知 MPI 运行时其安装位置，从而正确定位内部的帮助文件和组件库。未设置该变量时，`mpirun` 可能报出找不到 `help-*.txt` 文件的错误。设置 `OPAL_PREFIX` 后通常无需再手工设置 `PATH` 与 `LD_LIBRARY_PATH`，但建议同时设置以确保可靠。当前HPCKIT安装提供了一键设置，无需手动设置，详情参考安装指南。

若无法修改远程节点的 shell 启动文件，可通过 `--prefix` 选项在启动时指定安装路径：

```bash
mpirun --prefix /opt/hygon/hmpi/ompi -n 4 ./myapp
```

### 2.1.2 提交方式

**方式一：SSH 直接提交（无调度系统）**

确认各节点 SSH 免密登录配置完成后，直接执行 `mpirun` 命令即可提交作业。节点列表通过 `--hostfile` 指定，或通过 `--host` 直接给出。

```bash
mpirun -np 16 --hostfile hostfile ./myapp
```

**方式二：通过作业调度系统提交**

集群部署了 Slurm、PBS/Torque、LSF 等调度系统时，推荐通过调度系统提交。Hygon MPI 能够自动识别调度环境，并从调度器获取进程数与节点分配信息。

以 Slurm 为例，编写作业脚本：

```bash
#!/bin/sh
#SBATCH --nodes=4
#SBATCH --ntasks-per-node=32

# 无需指定 -np 和 --hostfile，信息由 Slurm 自动提供
mpirun ./myapp
```

提交作业：

```bash
sbatch job.slurm
```

其中 `--nodes` 指定节点数，`--ntasks-per-node` 指定每节点进程数。若使用 `mpirun -np N`，则 `N` 应等于 `节点数 × 每节点进程数`。

**方式三：调度系统直接启动**

部分调度系统支持绕过 `mpirun` 直接启动 MPI 进程，例如 Slurm 的 `srun`：

```bash
srun -n 128 ./myapp
```

这种方式由调度器直接负责进程创建与通信初始化。需要注意的是，`mpirun` 提供的进程映射、绑定等控制选项在直接启动方式下不可用。

## 2.2 运行 MPI 作业

### 2.2.1 背景信息

**支持的集合操作**

Hygon MPI 的集合通信算法选择能力覆盖以下操作（MPI 3.1 规定的全部集合操作均有可用实现，但并非所有操作都可选择算法）：

| 操作 | 支持算法选择 | 可用算法数量 | 说明 |
|---|---|---|---|
| `MPI_Bcast` | 是 | 9 | 默认模式与指定算法模式均可选 |
| `MPI_Reduce` | 是 | 8 | 同上 |
| `MPI_Allreduce` | 是 | 7 | 同上 |
| `MPI_Allgather` | 是 | 8 | 同上 |
| `MPI_Allgatherv` | 是 | 6 | 同上 |
| `MPI_Alltoall` | 是 | 5 | 同上 |
| `MPI_Alltoallv` | 是 | 2 | 同上 |
| `MPI_Barrier` | 是 | 6 | 同上 |
| `MPI_Gather` | 是 | 3 | 同上 |
| `MPI_Scatter` | 是 | 3 | 同上 |
| `MPI_Reduce_scatter` | 是 | 4 | 同上 |
| `MPI_Reduce_scatter_block` | 是 | 4 | 同上 |
| `MPI_Scan` | 是 | 2 | **仅在指定算法模式下可用**，默认模式下由基础实现完成 |
| `MPI_Exscan` | 是 | 2 | **仅在指定算法模式下可用**，默认模式下由基础实现完成 |
| `MPI_Alltoallw` | 否 | — | 无算法可选，使用基础实现 |
| `MPI_Scatterv` | 否 | — | 无算法可选，使用基础实现 |
| `MPI_Gatherv` | 否 | — | 无算法可选，使用基础实现 |

> **非阻塞集合操作不受算法参数影响**：上表所列的算法选择能力只作用于阻塞形式的集合操作（`MPI_Bcast`、`MPI_Allreduce` 等）。非阻塞形式（`MPI_Ibcast`、`MPI_Iallreduce`、`MPI_Ialltoall` 等）由非阻塞集合通信组件单独实现，`coll_tuned_<操作>_algorithm` 参数对其无效。

**跨节点运行时的分层集合通信**

当作业跨越多个节点时，Barrier、Scatter、Reduce、Gather、Bcast、Allreduce、Allgather 这七个操作会先由 `coll/han` 接管（优先级 35 高于 `coll/tuned` 的 30）。`coll/han` 的作用是把一次跨越全部进程的集合操作拆解为两级：

1. 先在**节点内子通信域**上完成一次局部操作，把参与进程数从"全局规模"压缩到"每节点进程数"；
2. 再在**节点间子通信域**上完成剩余操作，参与进程数等于节点数。

两级子通信域上的实际算法仍由该子通信域选中的组件（默认 `coll/tuned`）执行。这一机制带来两点使用上的影响：

- **算法参数与决策表作用于子通信域**。`coll_tuned_<操作>_algorithm` 和 `decision.file` 的匹配依据是**子通信域的进程数**与当次传输的消息长度，而不是全局进程数。例如 1024 进程、每节点 64 进程运行时，节点内子通信域规模为 64，对应决策表中的 64 档规则。
- **单机运行时不走分层路径**。通信域内全部进程位于同一节点时，`coll/han` 自动退出，集合操作直接由 `coll/tuned` 处理，此时匹配依据就是全局进程数。

上表中 `MPI_Alltoall`、`MPI_Alltoallv`、`MPI_Reduce_scatter`、`MPI_Reduce_scatter_block` 等操作不在 `coll/han` 的接管范围内，始终由 `coll/tuned` 按全局进程数处理。

如需强制关闭分层集合通信、统一按全局通信域行为验证性能，可将 `coll/han` 优先级设为负值：

```bash
mpirun -np 128 --mca coll_han_priority -1 ./myapp
```

**两种运行模式**

Hygon MPI 支持两种运行模式，二者的区别在于由谁来决定集合操作使用哪种算法。

- **默认算法模式**：不指定任何算法参数。集合操作由 Open MPI 编译期内置的固定决策规则（fixed decision）自动选择算法，选择依据为通信域规模与当次通信的数据量。这是应用无感知的默认行为。

- **指定算法模式**：由用户显式指定算法。指定方式有两种——通过命令行参数直接指定某一操作使用哪个算法，或通过配置文件（决策表）由运行时按通信域规模和消息长度自动查表。两种方式都需要事先开启动态决策开关，详见 2.2.3 节。

**作业启动命令的基本结构**

```bash
mpirun [启动参数...] [MCA 参数...] [-x 环境变量...] <可执行文件> [应用参数...]
```

| 组成部分 | 说明 | 示例 |
|---|---|---|
| 总进程数 | 启动的 MPI 进程总数 | `-np 128` |
| 每节点进程数 | 每个节点上启动的进程数 | `-N 32` |
| 节点文件 | 记录节点名与槽位数的文件 | `--hostfile hostfile` |
| 进程映射 | 进程在节点、Socket、核心上的分布方式 | `--map-by socket` |
| 进程绑定 | 将进程约束在指定处理器核心上运行 | `--bind-to core` |
| 可执行文件 | MPI 程序路径 | `./myapp` |

**节点文件格式**

节点文件每行一个节点名，可通过 `slots` 属性指定该节点可用的最大进程数：

```
node1 slots=32
node2 slots=32
node3 slots=64
node4 slots=64
```

未指定 `slots` 时，默认按该节点的物理核心数（不含超线程）计算。当节点数较多、配置一致时，可用命令直接生成节点文件：

```bash
# 生成 8 个节点、每个节点 64 个槽位的节点文件
for i in $(seq 1 8); do echo "node$i slots=64"; done > hostfile
```

节点数较少时，也可不写节点文件，直接用 `--host` 逐个列出，并以 `节点名:进程数` 的形式指定该节点的槽位：

```bash
mpirun -np 128 --host node1:32,node2:32,node3:32,node4:32 ./myapp
```

**进程绑定**

进程绑定将每个 MPI 进程约束到指定的处理器核心上运行，避免操作系统在核心之间迁移进程导致的缓存失效。HPC 应用通常应当开启绑定：

```bash
mpirun -np 128 --map-by socket --rank-by slot --bind-to core ./myapp
```

| 选项 | 含义 |
|---|---|
| `--map-by socket` | 按处理器插槽分布进程，即每个插槽上放置的进程数尽量均衡 |
| `--rank-by slot` | rank 在映射单元内按槽位轮转分配，使编号相邻的进程落在同一插槽内 |
| `--bind-to core` | 将每个进程绑定到一个物理核心 |

> **注意**：进程映射与进程绑定是两个独立步骤。映射决定进程落在哪个节点、哪个 Socket；绑定才真正约束进程运行在哪些核心上。仅设置 `--map-by` 而不设置 `--bind-to` 不会产生绑定效果。

Hygon MPI 的平台默认参数文件中已设置 `hwloc_base_binding_policy = core`，即默认按核心绑定。可通过 `--report-bindings` 查看实际绑定结果：

```bash
mpirun -np 4 --report-bindings ./myapp
```

### 2.2.2 通过默认算法运行 MPI 作业

**运行方法**

不指定任何算法相关参数，直接执行 `mpirun`：

```bash
mpirun -np 128 --hostfile hostfile ./myapp
```

**算法选择规则**

默认算法模式下，`coll/tuned` 组件按通信域进程数和本次通信的数据量共同决定算法。选择逻辑可概括为：

1. 计算本次通信的消息长度。不同集合操作对消息长度的定义不同，具体见 2.3.1 节。
2. 根据通信域进程数落入的区间，结合消息长度，从该操作的内置算法表中选定算法。
3. 对于不满足交换律的自定义归约操作（即归约顺序会影响结果的操作），仅在支持非交换操作的算法子集中选择。

以 `MPI_Allreduce` 为例，其内置决策规则按通信域规模分段（小于 4、4～8、8～16、16～128、128～256、256～512 等），在每一段内再按消息长度切换到 `basic_linear`、`nonoverlapping`、`recursive_doubling`、`ring`、`segmented_ring`、`rabenseifner` 等不同算法。当操作不满足交换律时，可选算法收缩为 `basic_linear`、`nonoverlapping`、`recursive_doubling` 三种。

**预期结果**

作业正常启动并完成，各进程输出与使用其他 MPI 实现时一致。可通过 `--mca coll_base_verbose 10` 观察集合通信组件的加载情况：

```bash
mpirun -np 4 --mca coll_base_verbose 10 ./myapp
```

**算法回退**

默认算法模式下不会发生"用户指定的算法不受支持"的情况，因为算法选择完全由内置规则完成。但存在以下情形会导致算法与预期不同：

- 消息长度恰好落在两个区间的边界上时，实际选择的算法可能是相邻区间的算法。
- 自定义归约操作、非连续派生数据类型等特殊场景会收窄可选算法集合。

### 2.2.3 通过指定算法运行 MPI 作业

指定算法有两种方式，二者都要求先开启动态决策开关。

#### 2.2.3.1 方法一：直接指定算法编号

在 `mpirun` 命令中通过 MCA 参数直接指定某一集合操作使用的算法编号。

**语法**

```bash
--mca coll_tuned_use_dynamic_rules 1 \
--mca coll_tuned_<操作名>_algorithm <算法编号>
```

其中 `<操作名>` 取值为 `allreduce`、`bcast`、`barrier`、`alltoall`、`alltoallv`、`allgather`、`allgatherv`、`reduce`、`gather`、`scatter`、`scan`、`exscan`、`reduce_scatter`、`reduce_scatter_block`。

**示例**：指定 `MPI_Allreduce` 使用 ring 算法（编号 4），`MPI_Bcast` 使用 knomial 算法（编号 7）：

```bash
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allreduce_algorithm 4 \
  --mca coll_tuned_bcast_algorithm 7 \
  ./myapp
```

**算法编号的取值**

各集合操作支持的算法编号见 2.3.1 节「算法地图」。编号 `0` 表示"不指定，使用默认决策规则"。

#### 2.2.3.2 方法二：通过决策表自动选择

通过配置文件指定规则，由运行时根据通信域规模和消息长度自动查表选择算法。

**语法**

```bash
--mca coll_tuned_use_dynamic_rules 1 \
--mca coll_tuned_dynamic_rules_filename <决策表路径>
```

**示例**：使用 Hygon MPI 随包提供的平台调优决策表：

```bash
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_dynamic_rules_filename /opt/hygon/hmpi/ompi/etc/decision.file \
  ./myapp
```

> **说明**：`decision.file` 随 Hygon MPI 一同安装到安装目录的 `etc` 子目录下，是一份针对 C86 平台典型进程规模离线调优得到的算法决策表。它不会自动生效，需要按上述方式显式引用。建议将该命令写入作业脚本，作为平台推荐配置使用。

**决策表的配置字段**

决策表按"集合操作 → 通信域规模 → 消息长度"三级组织，每一条规则由四个字段构成：

```
<消息长度>  <算法编号>  <拓扑因子>  <分段大小>
```

| 字段 | 必填 | 含义 |
|---|---|---|
| 消息长度 | 是 | 规则生效的消息长度下界，单位字节。规则按升序排列，取"不超过实际消息长度的最大档位" |
| 算法编号 | 是 | 该档位使用的算法编号，取值见 2.3.1 节 |
| 拓扑因子 | 是 | 树形或链式算法的扇出/扇入参数；不适用时填 `0` |
| 分段大小 | 是 | 消息分段长度，单位字节；`0` 表示不分段 |

每一档消息规则列表的第一条必须是 `0 0 0 0`，作为该通信域规模下的兜底规则。

**生效与验证**

开启动态决策后，可通过提高组件日志级别确认算法选择结果：

```bash
mpirun -np 4 \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_dynamic_rules_filename /opt/hygon/hmpi/ompi/etc/decision.file \
  --mca coll_base_verbose 10 \
  ./myapp
```

日志中会输出所选中的通信域规则与算法编号。

**取消与恢复默认**

移除 `--mca coll_tuned_use_dynamic_rules 1` 与 `--mca coll_tuned_dynamic_rules_filename ...` 两个参数即恢复默认算法模式。

若通过环境变量方式设置，则执行：

```bash
unset OMPI_MCA_coll_tuned_use_dynamic_rules
unset OMPI_MCA_coll_tuned_dynamic_rules_filename
```

**算法回退**

动态决策模式下，以下情形会导致规则不生效而回退到默认决策：

- 未开启 `coll_tuned_use_dynamic_rules`，所有指定参数被忽略。
- 决策表中没有该集合操作的规则，或该操作的规则数量为 0。
- 实际通信域规模小于决策表中的最小档位时，使用最小档位（64）的规则；大于最大档位（256）时，使用最大档位的规则。
- 消息长度小于规则列表中的最小档位时，使用列表首条规则。

### 2.2.4 指定算法支持的命令参数

指定算法涉及两类参数：**组件级开关**与**操作级算法参数**。

#### 2.2.4.1 组件级开关参数

| 参数名称 | 取值类型 | 取值范围 | 默认值 | 功能说明 | 示例 |
|---|---|---|---|---|---|
| `coll_tuned_use_dynamic_rules` | bool | 0 / 1 | 0 | 是否启用动态决策。设为 1 后，`coll_tuned_<操作>_algorithm` 等参数才会生效 | `--mca coll_tuned_use_dynamic_rules 1` |
| `coll_tuned_dynamic_rules_filename` | string | 文件路径 | 空 | 决策表文件路径。不设置时仅使用命令行指定的算法编号 | `--mca coll_tuned_dynamic_rules_filename /opt/hygon/hmpi/ompi/etc/decision.file` |

#### 2.2.4.2 操作级算法参数

每个支持算法选择的集合操作都有一组同名不同前缀的参数。以 `MPI_Allreduce` 为例：

| 参数名称 | 取值类型 | 取值范围 | 默认值 | 功能说明 | 示例 |
|---|---|---|---|---|---|
| `coll_tuned_allreduce_algorithm` | int | 0～7，见 2.3.1 节 | 0 | 指定 Allreduce 使用的算法编号，0 表示使用默认决策规则 | `--mca coll_tuned_allreduce_algorithm 4` |
| `coll_tuned_allreduce_algorithm_segmentsize` | int | ≥ 0，单位字节 | 0 | 算法的分段大小，0 表示不分段。仅对支持分段的算法有效 | `--mca coll_tuned_allreduce_algorithm_segmentsize 32768` |
| `coll_tuned_allreduce_algorithm_tree_fanout` | int | ≥ 0 | 系统默认 | 树形算法的扇出参数。仅对支持树形拓扑的算法有效 | `--mca coll_tuned_allreduce_algorithm_tree_fanout 8` |
| `coll_tuned_allreduce_algorithm_chain_fanout` | int | ≥ 0 | 系统默认 | 链式算法的扇出参数。仅对支持链式拓扑的算法有效 | `--mca coll_tuned_allreduce_algorithm_chain_fanout 4` |

将参数名中的 `allreduce` 替换为其他操作名，即可得到对应操作的算法参数。支持的操作名与对应参数前缀见下表：

| 集合操作 | 参数前缀 | 算法编号范围 |
|---|---|---|
| `MPI_Allgather` | `coll_tuned_allgather` | 0～8 |
| `MPI_Allgatherv` | `coll_tuned_allgatherv` | 0～6 |
| `MPI_Allreduce` | `coll_tuned_allreduce` | 0～7 |
| `MPI_Alltoall` | `coll_tuned_alltoall` | 0～5 |
| `MPI_Alltoallv` | `coll_tuned_alltoallv` | 0～2 |
| `MPI_Barrier` | `coll_tuned_barrier` | 0～6 |
| `MPI_Bcast` | `coll_tuned_bcast` | 0～9 |

### 2.3.2 指定算法说明

本节按集合操作说明算法选择条件与运行方式。以下示例均以 `hostfile` 为节点文件、128 进程作业为例。

#### 2.3.2.1 Allreduce

**支持的算法**：见 2.3.1 节 Allreduce 算法地图（编号 1～7）。

**应用场景**

- **小消息、少进程**：算法 3（recursive\_doubling）时延最低，是默认决策在小规模下的首选。
- **中等消息**：算法 2（nonoverlapping）通过 reduce + bcast 两阶段实现，在中等规模下表现稳定。
- **大消息**：算法 6（rabenseifner）与算法 4（ring）分别适合不同的消息与进程规模组合。rabenseifner 在消息较大、进程数较多时通信量最优；ring 在中大规模下实现简单、开销稳定。

**进程分布要求**

算法 4、5、6 不支持不满足交换律的自定义归约操作。使用自定义归约操作时，请选择算法 1、2 或 3。

**相关参数**

| 参数 | 说明 |
|---|---|
| `coll_tuned_allreduce_algorithm` | 算法编号 |
| `coll_tuned_allreduce_algorithm_segmentsize` | 算法 5（segmented\_ring）的分段大小 |
| `coll_tuned_allreduce_algorithm_tree_fanout` | 树形算法的扇出 |
| `coll_tuned_allreduce_algorithm_chain_fanout` | 链式算法的扇出 |

**运行方式**

```bash
# 指定使用 ring 算法
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allreduce_algorithm 4 \
  ./myapp

# 指定使用 segmented_ring 算法并设置分段大小为 32KB
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allreduce_algorithm 5 \
  --mca coll_tuned_allreduce_algorithm_segmentsize 32768 \
  ./myapp
```

#### 2.3.2.2 Bcast

**支持的算法**：见 2.3.1 节 Bcast 算法地图（编号 1～9）。

**应用场景**

- **小消息**：算法 6（binomial）与算法 7（knomial）时延随进程数对数增长，是默认决策在小消息下的首选。
- **大消息**：算法 3（pipeline）通过分段流水充分利用网络带宽，适合大消息广播。
- **树形算法调优**：算法 4（split\_binary\_tree）与算法 7（knomial）可通过扇出参数调节树的形状，在特定进程规模下可获得更优性能。

**进程分布要求**

树形与流水线算法对进程分布不敏感，可在任意映射与绑定策略下使用。

**相关参数**

| 参数 | 说明 |
|---|---|
| `coll_tuned_bcast_algorithm` | 算法编号 |
| `coll_tuned_bcast_algorithm_segmentsize` | 算法 3（pipeline）的分段大小 |
| `coll_tuned_bcast_algorithm_tree_fanout` | 树形算法的扇出 |
| `coll_tuned_bcast_algorithm_chain_fanout` | 链式算法的扇出 |

**运行方式**

```bash
# 指定使用 pipeline 算法
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_bcast_algorithm 3 \
  ./myapp

# 指定使用 knomial 算法并设置扇出为 8
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_bcast_algorithm 7 \
  --mca coll_tuned_bcast_algorithm_tree_fanout 8 \
  ./myapp
```

#### 2.3.2.3 Barrier

**支持的算法**：见 2.3.1 节 Barrier 算法地图（编号 1～6）。

**应用场景**

Barrier 不传输用户数据，其性能取决于同步信号在进程间的传递时延。算法 3（recursive\_doubling）在大规模下时延最优；算法 1（linear）与算法 6（tree）在中等规模下开销较低。

**与 Allreduce 算法的关系**

Barrier 的实现与 Allreduce 高度相关——Allreduce 内部通常包含同步步骤。因此在 Allreduce 与 Barrier 同时使用时，建议二者选择同一族的算法，避免同步语义不一致导致的额外开销。

**相关参数**

| 参数 | 说明 |
|---|---|
| `coll_tuned_barrier_algorithm` | 算法编号 |
| `coll_tuned_barrier_algorithm_tree_fanout` | 树形算法的扇出 |
| `coll_tuned_barrier_algorithm_chain_fanout` | 链式算法的扇出 |

**运行方式**

```bash
# 指定使用 recursive_doubling 算法
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_barrier_algorithm 3 \
  ./myapp
```

#### 2.3.2.4 Alltoallv

**支持的算法**：编号 1（basic\_linear）、2（pairwise）。

**应用场景**

- **算法 1（basic\_linear）**：所有进程同时发起非阻塞发送与接收，实现简单，在小规模或消息较小时时延低。
- **算法 2（pairwise）**：按通信域规模进行多轮阻塞式 `MPI_Sendrecv`，逐轮与不同对端交换。这种方式避免了同时驻留大量未完成请求，在网络缓冲区有限或进程数较多时更稳定。

**消息规模**

Alltoallv 的算法决策不使用消息长度字段，因此决策表中的第二个字段（拓扑因子）与第四个字段（分段大小）对 Alltoallv 无实际作用，建议统一填写 `0`。

**相关参数**

| 参数 | 说明 |
|---|---|
| `coll_tuned_alltoallv_algorithm` | 算法编号 |

**运行方式**

```bash
# 指定使用 pairwise 算法
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_alltoallv_algorithm 2 \
  ./myapp
```

#### 2.3.2.5 Scatterv

**支持的算法**：**无**。`MPI_Scatterv` 不支持算法指定。

**说明**

Hygon MPI 当前版本中，变长分发操作 `MPI_Scatterv` 没有提供可选的算法实现，始终使用基础实现完成通信。

**运行方式**

无法通过 `coll_tuned_*` 参数改变 `MPI_Scatterv` 的算法。指定相关参数不会产生效果：

```bash
# 以下参数对 Scatterv 不生效（coll_tuned_scatter_algorithm 只影响定长的 MPI_Scatter）
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_scatter_algorithm 2 \
  ./myapp
```

如需优化变长分发的性能，建议的做法是：

1. 若各进程接收数据量相同，改用 `MPI_Scatter` 并指定算法 1～3。
2. 检查进程映射与绑定是否合理，确保同一节点的进程尽量落在同一 NUMA 节点内。

#### 2.3.2.6 Allgatherv

**支持的算法**：见 2.3.1 节 Allgatherv 算法地图（编号 1～6）。

**应用场景**

- **小消息**：算法 3（ring）与算法 1（default）在中小规模下时延较低。
- **大消息、大规模**：算法 2（bruck）与算法 4（neighbor）通过分阶段交换降低单进程的通信量。算法 4 要求进程在节点内连续分布时效果最好。
- **2 进程场景**：算法 5（two\_proc）为专用实现。

**传输方式**

Allgatherv 的通信在节点内与节点间分别进行。节点内优先使用共享内存单拷贝路径（参见 1.3.2 节），节点间使用网络传输。

**相关参数**

| 参数 | 说明 |
|---|---|
| `coll_tuned_allgatherv_algorithm` | 算法编号 |
| `coll_tuned_allgatherv_algorithm_tree_fanout` | 树形算法的扇出 |
| `coll_tuned_allgatherv_algorithm_chain_fanout` | 链式算法的扇出 |

**运行方式**

```bash
# 指定使用 bruck 算法
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allgatherv_algorithm 2 \
  ./myapp
```

#### 2.3.2.7 Gatherv

**支持的算法**：**无**。`MPI_Gatherv` 不支持算法指定。

**说明**

Hygon MPI 当前版本中，变长收集操作 `MPI_Gatherv` 没有提供可选的算法实现，始终使用基础实现完成通信。

**运行方式**

无法通过 `coll_tuned_*` 参数改变 `MPI_Gatherv` 的算法。指定相关参数不会产生效果：

```bash
# 以下参数对 Gatherv 不生效（coll_tuned_gather_algorithm 只影响定长的 MPI_Gather）
mpirun -np 128 --hostfile hostfile \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_gather_algorithm 2 \
  ./myapp
```

如需优化变长收集的性能，建议的做法是：

1. 若各进程发送数据量相同，改用 `MPI_Gather` 并指定算法 1～3。
2. 若数据量差异较大，可考虑改用 `MPI_Allgatherv` 后由各进程自行筛选，以利用 Allgatherv 的多种算法。

### 2.3.3 推荐命令

以下命令以 128 进程、每节点 32 进程的典型配置为例。

**基础推荐命令（默认算法 + 平台默认绑定）**

```bash
mpirun -np 128 -N 32 --hostfile hostfile \
  --map-by socket --rank-by slot --bind-to core \
  ./myapp
```

适用条件：任意应用，任意消息规模。这是不调优时的推荐起点。

**启用平台调优决策表**

```bash
mpirun -np 128 -N 32 --hostfile hostfile \
  --map-by socket --rank-by slot --bind-to core \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_dynamic_rules_filename /opt/hygon/hmpi/ompi/etc/decision.file \
  ./myapp
```

适用条件：作业进程数在 64、96、128、192、256 附近的应用。决策表按这些规模离线调优得到，直接引用可获得平台推荐的算法组合。

**小消息密集型应用**

```bash
mpirun -np 128 -N 32 --hostfile hostfile \
  --map-by socket --rank-by slot --bind-to core \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allreduce_algorithm 3 \
  --mca coll_tuned_bcast_algorithm 6 \
  --mca coll_tuned_barrier_algorithm 3 \
  ./myapp
```

适用条件：单次通信数据量在数十字节到数 KB 之间、通信调用极其频繁的应用，如迭代求解类程序。

**大消息应用**

```bash
mpirun -np 128 -N 32 --hostfile hostfile \
  --map-by socket --rank-by slot --bind-to core \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allreduce_algorithm 6 \
  --mca coll_tuned_bcast_algorithm 3 \
  --mca coll_tuned_alltoallv_algorithm 2 \
  ./myapp
```

适用条件：单次通信数据量在数百 KB 以上的应用，如大规模数据重分布、矩阵转置类通信。

**自定义归约操作场景**

```bash
mpirun -np 128 -N 32 --hostfile hostfile \
  --map-by socket --rank-by slot --bind-to core \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allreduce_algorithm 2 \
  ./myapp
```

适用条件：使用 `MPI_Op_create` 创建了不满足交换律的自定义归约操作。此时不能使用算法 4、5、6。

**节点内通信为主的应用**

```bash
mpirun -np 32 -N 32 --hostfile hostfile \
  --map-by socket --rank-by slot --bind-to core \
  ./myapp
```

适用条件：进程全部落在单节点，通信主要经由共享内存路径。确保 `--bind-to core` 生效，使共享内存单拷贝机制工作在最优状态。

**关闭分层集合通信（用于对比验证）**

```bash
mpirun -np 128 -N 32 --hostfile hostfile \
  --map-by socket --rank-by slot --bind-to core \
  --mca coll_han_priority -1 \
  ./myapp
```

适用条件：需要将跨节点运行结果与单机运行结果做对比，或需要显式验证 `coll/tuned` 算法参数的全局效果时。将 `coll/han` 优先级设为负值后，全部集合操作直接由 `coll/tuned` 按全局进程数处理。

### 2.3.4 特性支持与功能回退说明

Hygon MPI 的集合通信算法选择遵循"不支持则自动回退"的原则：当指定的算法不适用于当前场景时，运行时自动回退到支持该场景的算法，不会导致作业失败。

**回退场景清单**

| 场景 | 回退规则 |
|---|---|
| 未开启 `coll_tuned_use_dynamic_rules` | 所有 `coll_tuned_<操作>_algorithm` 参数被忽略，全部使用默认决策规则 |
| 指定了算法但当前操作不支持算法选择 | 对 `MPI_Scatterv`、`MPI_Gatherv`、`MPI_Alltoallw`，参数不生效，使用基础实现 |
| 未指定算法时使用 `MPI_Scan` / `MPI_Exscan` | 默认算法模式下由基础实现完成；需显式指定算法编号后才会启用可选的算法实现 |
| 对非阻塞集合操作指定算法 | `MPI_Ibcast`、`MPI_Iallreduce` 等非阻塞形式不受算法参数影响 |
| 使用不满足交换律的自定义归约操作 | Allreduce 仅保留 linear（1）、nonoverlapping（2）、recursive\_doubling（3）；Reduce 仅保留 linear（1）、in-order\_binary（6）；Reduce\_scatter 与 Reduce\_scatter\_block 仅保留 basic\_linear（1） |
| 跨节点运行时的分层集合通信 | Barrier、Scatter、Reduce、Gather、Bcast、Allreduce、Allgather 先由 `coll/han` 拆分为两级子通信域，算法参数在子通信域上生效 |
| 全部进程位于同一节点 | `coll/han` 自动退出竞争，集合操作直接由 `coll/tuned` 按全局进程数处理 |
| 决策表中无该操作的规则 | 该操作使用默认决策规则 |
| 决策表中无匹配的通信域规模档位 | 使用不超过实际进程数的最大档位；实际进程数小于表中最小档位时使用最小档位 |
| 决策表中无匹配的消息长度档位 | 使用不超过实际消息长度的最大档位 |
| 未指定 `coll_tuned_dynamic_rules_filename` | 仅命令行指定的算法编号生效，其余操作使用默认决策规则 |
| 进程数量为 1 | 退化为自环通信，所有算法均无差别 |
| 指定算法编号超出有效范围 | 使用默认决策规则 |

**进程分布不均衡场景**

节点内进程数不均衡（各节点的 `slots` 配置不一致）或 Socket 内进程数不均衡（`--bind-to none`、`--bind-to package` 或未绑定）时，依赖拓扑分布的算法性能会显著下降，部分算法可能不适用。

**建议**：始终显式指定 `--bind-to core`，并保证节点内进程数在各节点之间尽量均衡。

**原地操作场景**

`MPI_IN_PLACE` 提供的原地操作语义对算法的数据搬运方式有额外约束。使用原地操作时，部分算法可能无法启用其最优路径，性能可能低于非原地操作。建议在性能敏感的场景中避免使用 `MPI_IN_PLACE`。

**消息长度超限场景**

当单次通信的数据量超过算法的内部限制（例如按 32 位长度字段寻址的算法）时，运行时自动切换到不受该限制的算法。

# 3. FAQ

## 3.1 故障处理流程

### 3.1.1 操作步骤

出现异常时，按以下顺序定位问题，逐步缩小范围。

**步骤 1：确认是 MPI 使用方法问题还是 Hygon MPI 问题**

将应用替换为 MPI 自带的示例程序，验证 MPI 环境本身是否正常。示例源码位于源码树的 `examples` 目录，先编译：

```bash
cd /path/to/ompi/examples
mpicc -o hello_c hello_c.c
mpicc -o ring_c ring_c.c
```

然后逐项验证：

```bash
# 只测作业启动运行时，不涉及 MPI 通信
mpirun -np 1 hostname

# 测 MPI 初始化与结束
mpirun -np 1 ./hello_c

# 测点对点通信
mpirun -np 2 ./ring_c
```

**预期现象**：三条命令均正常输出。

**判断结论**：

- 若 `hostname` 失败 → 问题在作业启动运行时（环境变量、SSH 配置、节点可达性），跳至步骤 3。
- 若 `hostname` 成功但 `hello_c` 失败 → 问题在 MPI 库加载或通信初始化，跳至步骤 2。
- 若三条全部成功但应用失败 → 问题在应用自身或应用使用的特定通信模式，跳至步骤 4。

**步骤 2：确认是否与算法指定有关**

移除所有集合通信算法相关参数，使用默认算法重新提交。

```bash
mpirun -np 128 --hostfile hostfile --bind-to core ./myapp
```

**预期现象**：作业正常运行。

**判断结论**：

- 若问题消失 → 说明指定的算法不适用于当前场景，参见 2.3.4 节确认回退规则；若确认算法应当支持却仍然失败，请联系技术支持。
- 若问题依旧 → 跳至步骤 4。

**步骤 3：确认环境变量配置**

在提交节点与计算节点上分别检查环境变量。

```bash
echo $OPAL_PREFIX
echo $PATH | tr ':' '\n' | grep hmpi
echo $LD_LIBRARY_PATH | tr ':' '\n' | grep hmpi
which mpirun
ldd $(which mpirun)
```

**预期现象**：`OPAL_PREFIX` 指向 Hygon MPI 安装目录；`mpirun` 可被找到；`ldd` 无 "not found" 输出。

**判断结论**：任一检查项异常则修正环境变量配置，参见 2.1.1 节。修正后重新执行步骤 1。

**步骤 4：提高日志级别收集信息**

```bash
# 查看 MPI 启动运行时日志
mpirun -np 4 --mca plm_base_verbose 5 --mca state_base_verbose 5 ./myapp

# 查看点对点通信层日志
mpirun -np 4 --mca pml_base_verbose 10 ./myapp

# 查看集合通信层日志
mpirun -np 4 --mca coll_base_verbose 10 ./myapp

# 查看 UCX 传输层日志
mpirun -np 4 -x UCX_LOG_LEVEL=info -x UCX_LOG_FILE=/tmp/ucx-%h-%p.log ./myapp
```

**判断结论**：

- 日志指向集合通信组件 → 检查算法参数与决策表配置。
- 日志指向 UCX 传输层 → 检查网卡设备、GID 索引、传输模式配置。
- 日志指向作业启动运行时 → 检查节点可达性、SSH 免密、端口占用。

**步骤 5：定位问题归属**

| 现象 | 归属 | 建议 |
|---|---|---|
| 默认算法下正常，指定算法后异常 | 算法适用性问题 | 按 2.3.4 节核对回退规则；改用默认算法 |
| 关闭算法指定后仍异常 | 通用 MPI 或环境问题 | 按步骤 3、4 继续排查 |
| 单节点正常，多节点异常 | 网络或节点配置问题 | 检查网卡设备名、GID、防火墙、节点时间同步 |
| 单节点即异常 | MPI 安装或应用问题 | 检查安装完整性、库版本一致性 |

## 3.2 环境变量配置错误导致 mpirun 无法运行

### 3.2.1 现象描述

执行 `mpirun` 命令时，命令立即退出并提示找不到帮助文件：

```text
Sorry! You were supposed to get help about:
    opal_init:startup:internal-failure
But I couldn't open the help file:
    /opt/hygon/hmpi/ompi/share/openmpi/help-opal-runtime.txt: No such file or directory. Sorry!
```

受影响范围：所有节点的所有进程。作业无法继续运行。

### 3.2.2 可能原因

- `OPAL_PREFIX` 环境变量未配置或配置错误，导致运行时无法定位安装目录。
- `OPAL_PREFIX` 指向的目录与实际安装目录不一致。
- 计算节点上的环境变量未随作业传递，各节点看到的 `OPAL_PREFIX` 不一致。

可通过以下命令逐项验证：

```bash
echo $OPAL_PREFIX
ls $OPAL_PREFIX/share/openmpi/help-opal-runtime.txt
```

### 3.2.3 恢复步骤

1. 登录作业执行节点，确认 Hygon MPI 的实际安装路径。
   
   ```bash
   ls -d /opt/hygon/hmpi/ompi
   ```

2. 编辑 `~/.bashrc`，配置环境变量。
   
   ```bash
   export OPAL_PREFIX=/opt/hygon/hmpi/ompi
   export PATH=/opt/hygon/hmpi/ompi/bin:$PATH
   export LD_LIBRARY_PATH=/opt/hygon/hmpi/ompi/lib:$LD_LIBRARY_PATH
   ```

3. 使配置生效，并验证。
   
   ```bash
   source ~/.bashrc
   echo $OPAL_PREFIX
   mpirun -np 1 hostname
   ```
   
   **预期结果**：`hostname` 正常输出当前节点名。

4. 将同样的配置同步到所有计算节点，或确保 `~/.bashrc` 位于共享文件系统上。

5. 重新提交作业，确认恢复正常。

## 3.3 作业进程数超过可用槽位数

### 3.3.1 现象描述

提交 MPI 作业时 `mpirun` 报错并退出：

```text
There are not enough slots available in the system to satisfy the 1025
slots that were requested by the application:

  ./myapp

Either request fewer slots for your application, or make more slots
available for use.
```

其中 `1025` 为命令中请求的进程数。作业未能启动。

### 3.3.2 可能原因

- `mpirun -np` 指定的进程数大于所有作业执行节点的物理核心总数。
- 节点文件中的 `slots` 配置之和小于请求的进程数。
- 系统启用了超线程，但 Hygon MPI 默认按物理核心数计算槽位，未将逻辑核计入。

验证方法：

```bash
# 查看请求的进程数与节点文件中的槽位数
grep -c . hostfile
grep slots hostfile

# 查看每个节点的 CPU 核心数
lscpu | grep -E "^CPU\(s\)|Core\(s\) per socket|Socket\(s\)"
```

### 3.3.3 恢复步骤

1. 登录作业执行节点，查询每个节点的 CPU 核心数。
   
   ```bash
   lscpu
   ```
   
   关注输出中的 `CPU(s)`、`Core(s) per socket`、`Socket(s)` 三项。

2. 计算集群作业执行节点的 CPU 核心总数。
   
   例如 8 个节点，每节点 128 核，则总核数为 1024。

3. 调整进程数至不超过总核数。
   
   ```bash
   mpirun -np 1024 --hostfile hostfile ./myapp
   ```
   
   **预期结果**：作业正常启动。

4. 若确实需要超过物理核心数的进程数（例如测试超订场景），可显式允许超订。
   
   ```bash
   mpirun -np 2048 --hostfile hostfile --oversubscribe ./myapp
   ```
   
   > **注意**：超订会使多个进程竞争同一物理核心，性能显著下降，生产环境不建议使用。

5. 若希望按逻辑核（超线程）计算槽位，可使用：
   
   ```bash
   mpirun -np 2048 --hostfile hostfile --use-hwthread-cpus ./myapp
   ```

## 3.4 UCX 建链失败，提示目的端不可达

### 3.4.1 现象描述

多节点作业启动阶段失败，日志中出现：

```text
ib_device.c:848 UCX ERROR ibv_query_gid(dev=mlx5_0 port=1 index=10) failed: No such file or directory
pml_ucx.c:384 Error: ucp_ep_create(proc=1) failed: Destination is unreachable
```

作业无法启动。部分情况下单节点作业正常，仅在多节点时复现。

### 3.4.2 可能原因

- 命令行中通过 `UCX_IB_GID_INDEX` 指定的 GID 索引与实际不符。
- 各作业执行节点使用的 GID 索引不一致。
- 系统 sysfs 中存在无效的 GID 条目，导致读取类型时报 `Invalid argument`。
- `UCX_NET_DEVICES` 未指定，UCX 选中的网卡对对端不可达。

验证方法：

```bash
# 查看设备支持的传输层
ucx_info -d

# 查看设备的 GID 列表与类型
ls /sys/class/infiniband/mlx5_0/ports/1/gids/
cat /sys/class/infiniband/mlx5_0/ports/1/gid_attrs/types/*

# 查看设备名与端口
ibv_devinfo
```

### 3.4.3 恢复步骤

1. 确认网卡设备名与端口号。
   
   ```bash
   ibv_devinfo | grep -E "hca_id|port"
   ```

2. 查找与网卡类型匹配的正确 GID 索引。
   
   ```bash
   show_gids
   ```
   
   对于 RoCE v2，通常索引为 `3`；对于 InfiniBand，通常索引为 `0`。

3. 显式指定网卡设备与 GID 索引重新提交。
   
   ```bash
   mpirun -np 128 --hostfile hostfile \
     -x UCX_NET_DEVICES=mlx5_0:1 \
     -x UCX_IB_GID_INDEX=3 \
     ./myapp
   ```
   
   **预期结果**：作业正常启动，通信建立成功。

4. 若仍然失败，先排除网络传输层，验证 MPI 环境本身。
   
   ```bash
   mpirun -np 128 --hostfile hostfile -x UCX_TLS=tcp,self,sm ./myapp
   ```
   
   **判断结论**：若使用 TCP 传输层可正常运行，说明问题集中在 IB 网络配置，需检查子网管理器、交换机配置与网卡驱动。

5. 确认所有作业执行节点的 GID 配置一致。若各节点网卡型号或固件版本不同，需逐节点核对。

## 3.5 指定的 UCX 传输模式不可用

### 3.5.1 现象描述

指定 `UCX_TLS` 后作业报错或性能异常，日志中出现：

```text
UCX_WARN transport 'rc_x' is not available, please use one or more of:
cma, ib, mm, posix, rc, rc_v, rc_verbs, self, shm, sm, sysv, tcp, ud, ud_v, ud_verbs
```

作业可能仍然启动，但实际使用的传输层与预期不符，导致性能低于预期。

### 3.5.2 可能原因

- 指定的传输模式需要特定硬件或驱动支持，当前环境不具备。例如 `*_x` 系列传输模式需要网卡厂商的专有用户态驱动。
- 系统未安装 `rdma-core` 或版本过低。
- `UCX_TLS` 的取值拼写错误。

验证方法：

```bash
# 列出当前环境实际可用的传输层
ucx_info -d | grep Transport
```

### 3.5.3 恢复步骤

1. 查询当前环境可用的传输层。
   
   ```bash
   ucx_info -d
   ```

2. 从可用列表中选取合适的传输模式组合。常用组合如下：
   
   | 场景 | 推荐取值 |
   |---|---|
   | 通用（含 IB/RoCE） | `UCX_TLS=self,sm,rc` |
   | 共享内存与可靠连接 | `UCX_TLS=shm,rc` |
   | 共享内存与不可靠数据报 | `UCX_TLS=shm,ud` |
   | 仅共享内存（单节点） | `UCX_TLS=shm,self` |
   | 回退到 TCP | `UCX_TLS=tcp,self,sm` |
   
   > **说明**：`shm` 与 `mm` 二者语义重叠，建议只选其一。

3. 使用修正后的取值重新提交。
   
   ```bash
   mpirun -np 128 --hostfile hostfile -x UCX_TLS=self,sm,rc ./myapp
   ```
   
   **预期结果**：作业正常启动，`UCX_LOG_LEVEL=info` 的日志中显示实际选用的传输层与预期一致。

4. 若希望关闭 UCX 传输层、完全使用 MPI 自身的传输机制：
   
   ```bash
   mpirun -np 128 --hostfile hostfile --mca pml ^ucx ./myapp
   ```

## 3.6 多节点运行时报找不到共享库文件

### 3.6.1 现象描述

单节点运行正常，多节点运行时作业启动失败，提示某个动态库文件无法找到或打开：

```text
error while loading shared libraries: libmpi.so.40: cannot open shared object file: No such file or directory
```

### 3.6.2 可能原因

- 计算节点的 `LD_LIBRARY_PATH` 未包含 Hygon MPI 的库目录。
- Hygon MPI 安装在本地磁盘上，但仅在提交节点安装，计算节点未安装。
- 各节点的 MPI 安装路径不一致。

验证方法：

```bash
# 在计算节点上直接检查
ssh node1 'echo $LD_LIBRARY_PATH'
ssh node1 'ls /opt/hygon/hmpi/ompi/lib/libmpi.so*'
```

### 3.6.3 恢复步骤

1. 确认 Hygon MPI 的安装目录。若为共享文件系统（如 NFS），确认各节点挂载路径一致。
   
   ```bash
   mpirun -np 2 --hostfile hostfile bash -c 'echo $HOSTNAME; ls /opt/hygon/hmpi/ompi/lib | head'
   ```

2. 若安装目录在各节点上路径一致且可见，检查环境变量是否传递到远程进程。
   
   ```bash
   mpirun -np 2 --hostfile hostfile -x LD_LIBRARY_PATH bash -c 'echo $LD_LIBRARY_PATH'
   ```

3. 若环境变量未正确传递，显式导出：
   
   ```bash
   mpirun -np 128 --hostfile hostfile \
     -x LD_LIBRARY_PATH \
     -x PATH \
     ./myapp
   ```
   
   或在各计算节点的 `~/.bashrc` 中统一配置，参见 2.1.1 节。

4. 若使用 `--prefix` 方式指定安装路径：
   
   ```bash
   mpirun -np 128 --hostfile hostfile --prefix /opt/hygon/hmpi/ompi ./myapp
   ```

5. 重新提交作业，确认恢复正常。

## 3.7 运行结果多次执行不一致

### 3.7.1 现象描述

同一程序、同一输入、同样的进程数，多次运行得到略有差异的结果。差异通常出现在小数末几位，且仅在进程数较多时出现。

### 3.7.2 可能原因

- **浮点归约顺序不同**。MPI 归约操作按进程组合并数据的顺序取决于所选算法。浮点加法不满足结合律，不同合并顺序会产生末位差异。这是并行计算的固有特性，不是故障。
- **分层集合通信引入两级归约**。跨节点运行时，Reduce 与 Allreduce 由 `coll/han` 拆分为节点内、节点间两级归约，合并顺序比单机运行时更复杂，同一次归约中的数据可能分别沿两条路径合并。
- 使用了不满足交换律的自定义归约操作，但选用了仅对交换律成立的算法。
- 程序本身存在竞态条件，例如未同步就读取共享数据。

验证方法：

```bash
# 固定算法并关闭分层集合通信后重复运行，观察结果是否一致
mpirun -np 128 --hostfile hostfile \
  --mca coll_han_priority -1 \
  --mca coll_tuned_use_dynamic_rules 1 \
  --mca coll_tuned_allreduce_algorithm 1 \
  ./myapp
```

### 3.7.3 恢复步骤

1. 确认程序使用的是标准归约操作还是自定义归约操作。
   
   - **标准操作**（`MPI_SUM`、`MPI_MAX` 等）：差异属于浮点运算的固有特性。若必须保证结果可复现，先关闭分层集合通信，再将归约算法固定为 `basic_linear`（编号 1），使合并顺序在单机与多机环境下都保持一致：
     
     ```bash
     mpirun -np 128 --hostfile hostfile \
       --mca coll_han_priority -1 \
       --mca coll_tuned_use_dynamic_rules 1 \
       --mca coll_tuned_allreduce_algorithm 1 \
       ./myapp
     ```
     
     若希望保留分层集合通信的性能优势，可改用 `coll_han_reproducible`，该参数会关闭基于拓扑的优化，使归约按固定顺序执行：
     
     ```bash
     mpirun -np 128 --hostfile hostfile \
       --mca coll_han_reproducible 1 \
       ./myapp
     ```
   
   - **自定义操作**：确认操作是否满足交换律。不满足时，`coll/han` 会自动退回由 `coll/tuned` 处理，`coll/tuned` 内部则会排除算法 4、5、6；若仍不稳定，显式固定为算法 1、2 或 3。

2. 检查程序中的同步逻辑。归约操作之前如果存在未完成的非阻塞通信，可能导致读取到未更新的数据。在关键位置插入 `MPI_Barrier` 验证。

3. 若固定算法 1 后结果仍然不一致，问题不在 MPI 归约顺序，需检查应用自身的并行逻辑。

后续版本发布后，按版本号新增独立小节，只记录相对前一版本新增或发生变化的参数。
