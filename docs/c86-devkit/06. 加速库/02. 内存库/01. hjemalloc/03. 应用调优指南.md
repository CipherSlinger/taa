# hjemalloc调优指南

## 1. 使用介绍

### 方法 1：编译时指定动态库路径链接

编译阶段直接关联目标内存库，适用于可重新编译的程序场景。

#### 命令示例

```bash

gcc -o 输出程序名 -L$HJEMALLOC_LIB64_PATH -lhjemalloc 源文件.c

```

#### 参数说明

- `-o 输出程序名`：指定编译后生成的可执行程序名称（如示例中的 [xx](file:///home/zhenglang/test/software-validation/vectorization_cases/tsvc-2/src/array_defs.h#L16-L16)）；

- `-L$HJEMALLOC_LIB64_PATH`：指定内存库所在的 64 位库路径（需将 `$HJEMALLOC_LIB64_PATH` 替换为实际路径，如 `/opt/hygon/lib64`）；

- `-lhjemalloc`：指定要链接的内存库（gcc 链接库时默认省略 `lib` 前缀和 `.so` 后缀，为标准写法）。

### 方法 2：运行时通过环境变量强制加载

无需重新编译程序，通过环境变量强制程序优先加载指定内存库，仅对当前 Shell 会话有效。

#### 操作步骤

1. 设置 `LD_PRELOAD` 环境变量，指定内存库绝对路径：

```bash
 export LD_PRELOAD=/opt/hygon/lib64/libhjemalloc.so
```

> 注：需将 `/path/` 替换为内存库实际存放路径（如 `/opt/hygon/lib64`）。

2. 在当前 Shell 环境启动业务应用 / 测试程序：

```bash
 ./业务程序名  # 或 ./测试程序名
```

### 验证库文件是否被调用

通过以下命令确认内存库已成功加载：

```bash

# 方式1：lsof查看进程加载的库文件（替换为实际进程ID）

lsof -p 程序进程ID | grep libhjemalloc.so



# 方式2：pmap查看进程内存映射（替换为实际进程ID）

pmap 程序进程ID | grep libhjemalloc.so

```

## 2. 调优参数

hjemalloc设计的优化策略在多数应用场景下都是最优的表现，同时hjemalloc和开源保持一致，有许多调优参数供用户选择，下面详细介绍各个参数的功能和使用，用户可以针对特定应用负载进行调优，实现更优的系统性能指标或资源权衡。

**调优方法**

```bash
# 通过环境变量MALLOC_CONF使能，多个选项参数用逗号分隔：`option1:value1,option2:value2,option3:value3`，如下：

MALLOC_CONF="calloc_slab:true,slab_align_quantum:true,slab_sizes:1-10240:512,dirty_decay_ms:30000,muzzy_decay_ms:30000" ./your_program
```

### 参数和使用策略

#### `slab_align_quantum（hje新增）`

- **作用：** 使能slab小内存块特性，将内存对齐策略从16Byte改为8Byte，节约内存，提高访存效率
- **默认值：** `false`
- **调优建议：** 适用于高频64Byte范围内的小内存块场景
- **示例：** `slab_align_quantum:true`

#### `calloc_slab（hje新增）`

- **作用：** 使能calloc大内存块特性，提升calloc分配效率，优化访存带宽瓶颈，仅限单线程场景
- **默认值：** `false`
- **调优建议：** 适用于有大量calloc导致的带宽瓶颈场景
- **示例：** `calloc_slab:true`

#### `slab_sizes（hje优化）`

- **作用：** 按需调整指定范围内的slab内存块的占据的内存页面数量，避免反复的slab创建/销毁，增加内存复用的访存局部性
- **默认值：** 4K的整数倍
- **调优建议：** 使用更大的页面如2M，让内存分布更集中、利用大页的优势
- **示例：** `slab_sizes:1-10240:512`，对内存块大小范围在1-10240Byte的区间，每个slab使用512个4K页面，即2M

#### `narenas`

- **作用：** 设置 arena 数量
- **默认值：** CPU 核心数 × 4
- **调优建议：**
  - 高并发：保持默认或 CPU 核心数 × 2-4
  - 低并发：CPU 核心数或更少，避免浪费
- **示例：** `narenas:4`

#### `percpu_arena`

- **作用：** 启用基于运行 CPU 的动态线程-arena 关联
- **可选值：** `percpu`, `phycpu`
- **调优建议：** 线程迁移不频繁时尝试使用
- **示例：** `percpu_arena:percpu`

#### `tcache`

- **作用：** 启用/禁用线程缓存
- **默认值：** `true`
- **调优建议：** 除非内存极度紧张，否则保持启用
- **示例：** `tcache:false`

#### `tcache_max`

- **作用：** 线程缓存的最大大小类别
- **默认值：** 32768 (32KB)
- **调优建议：** 减少可节省内存，增加可提升性能
- **示例：** `tcache_max:4096`

#### `background_thread`

- **作用：** 启用后台线程
- **默认值：** `false`
- **调优建议：** 几乎总是建议启用，改善尾部延迟
- **示例：** `background_thread:true`

#### `metadata_thp`

- **作用：** 对内部元数据使用透明巨页（THP）
- **默认值：** `disabled`
- **可选值：** `always`, `auto`, `disabled`
- **调优建议：** 分配密集的程序建议 `auto` 或 `always`
- **示例：** `metadata_thp:auto`

#### `dirty_decay_ms`

- **作用：** dirty 页面的回收时间（毫秒）
- **默认值：** 10000 (10秒)
- **调优建议：**
  - 节省内存：减小（1000-5000）
  - 优化性能：增大（30000-60000）
- **示例：** `dirty_decay_ms:30000`

#### `muzzy_decay_ms`

- **作用：** muzzy 页面的回收时间（毫秒）
- **默认值：** 10000 (10秒)
- **调优建议：** 通常与 dirty\_decay\_ms 设置相同值
- **示例：** `muzzy_decay_ms:30000`

#### `stats_print`

- **作用：** 程序退出时打印统计信息
- **默认值：** `false`
- **示例：** `stats_print:true`

#### `abort_conf`

- **作用：** 配置错误时立即终止
- **默认值：** `false`
- **调优建议：** 总是建议设置为 true
- **示例：** `abort_conf:true`

#### `prof`

- **作用：** 启用堆剖析
- **默认值：** `false`
- **说明：** 需要编译时 `--enable-prof`
- **示例：** `prof:true`

#### `prof_leak`

- **作用：** 启用内存泄漏检测
- **默认值：** `false`
- **说明：** 需要 `prof:true`
- **示例：** `prof:true,prof_leak:true`

#### `junk`

- **作用：** 填充 junk 数据检测使用未初始化/已释放内存的 bug
- **可选值：** `true`, `false`, `alloc`, `free`
- **示例：** `junk:true`

#### `zero`

- **作用：** 清零新分配的内存
- **默认值：** `false`
- **示例：** `zero:true`

## 3.风险说明

使用该内存库需严格遵守以下前置条件及风险提示：

1. **系统配置强制要求**

必须将透明大页（THP）配置为 `always`，否则会影响内存库性能表现：

```bash
echo always > /sys/kernel/mm/transparent_hugepage/enabled
```

2. **基础库版本依赖**

该内存库要求系统 `Glibc ≥ 2.17`，暂不兼容更早版本的 Glibc；若业务场景需适配早期 Glibc，可联系海光定制专属版本。

3. **内存消耗增加风险**

因内存分配、布局策略与系统默认 `malloc` 不同，使用该内存库可能导致内存消耗量上升；在大内存用量场景（接近物理内存总量）下，易触发 OOM（内存溢出），需提前评估业务内存阈值。

4. **性能收益不确定性**

仅在频繁进行内存分配、释放的场景下，该内存库相比默认 `malloc` 可能体现性能优势；对于内存分配 / 释放频率低的场景，可能无性能提升，建议充分开展实测验证后再上线。

## 4.调优场景

这里记录如何利用工具，在实际业务场景中分析、识别内存库相关的瓶颈，从而使用hjemalloc作为调优手段，具体如下：

### 4.1 内存库热点瓶颈分析

对于常见的客户业务逻辑而言，程序的核心运行时间都是在处理相关的数据，最理想的情况是100%的时间运行在业务处理逻辑上，减少其它非核心业务处理的性能开销，比如内存管理malloc/free。

### 4.2 高频小内存块瓶颈分析

传统的glibc内存管理不支持统计具体内存块的使用频度，hjemalloc基于开源的jemalloc，其内部记录了各个内存库的使用信息，可以通过配置环境变量export MALLOC\_CONF="stats\_print:true"，结合LD\_PRELOAD使用hjemalloc内存库，客户程序执行结束后会自动打印当前内存库的使用情况以及各个内存块的使用频度等，如下所示，如果程序长时间稳定运行，可以在代码逻辑中定时调用jemalloc的malloc\_stats\_print函数，进行监控统计内存行为。

从经验来看，常规程序业务对内存块的申请/释放诉求不会特别大，频度在不会超过1w次+，不会出现内存库相关的瓶颈，因此多数业务场景在各个内存库上的性能差不多。  
但对于一些内存分配/释放请求特别频繁的场景，如统计某个实际的客户场景的内存使用频度统计发现程序存在高频的内存块申请行为，nrequests指标表示申请在16-32Byte的内存块上有2.36亿次，这么高频的内存块请求必然导致内存库的热点开销更大，其次内存使用量也会更大，hjemalloc针对这类高频小内存块场景做了特殊优化，结合参数`slab_align_quantum:true,slab_sizes:1-10240:512`可以有效的降低内存热点开销,提高访存的局部性。

#### 内存块生命周期

内存块的生命周期是指在程序运行过程中，内存块从创建、使用、释放的整个逻辑过程，其中使用会涉及缺页，kernel会进行物理内存的映射处理，释放则有两种形式，一种缓存到内存库中，一种直接释放到kernel，不同内存库处理不一样，长短周期特征如下：

  - 短生命周期：内存块分配，使用后直接释放到kernel，没有长期持有内存，下一次再分配使用内存时，会导致pagefault；
  - 长生命周期：内存块分配后，一直使用，直到程序逻辑处理完成，释放内存，会长期持有，多数常见都是这类情况；

如何衡量内存块是短生命周期？没有直观的数据进行统计，我们可以通过其它特征如perf热点、缺页等指标来进行间接分析识别：

  - 方法1：从perf record统计数据来看，存在明显的kernel上的热点且集中在物理内存页面的处理上，如asm\_exc\_page\_fault/clear\_page\_rep/do\_anonymous\_page/\_\_handle\_mm\_fault等，如下
