## [Unreleased]

### Added
- **Dedicated TEE-LLM Pod For Attested Inference (`deploy-llm.sh remote --create-pod`)**: `teellm` can now run in its own `kata-qemu-csv2` Pod instead of a plain Docker container, which is what makes its attestation report real. A plain container has no `/dev/csv-guest`, so `teellm-service` silently fell back to a mock evidence provider whose HRK is regenerated in every process — TAA then rejected each handshake with `untrusted HRK certificate` and reported the code audit as failed under the fail-closed policy (`code=2`). `attestationMode: "permissive"` cannot rescue that: it softens only a measurement mismatch, and a broken trust chain is fatal in both modes. The Pod's startup command also creates `/dev/csv-guest` itself: a CSV2 guest kernel only registers the csv-guest misc device, and the container's `/dev` is a fresh tmpfs, so a Pod that relies on the RuntimeClass alone comes up Ready with an empty `/dev` and serves mock evidence — the deployment's device gate catches that, and the first run of this feature failed on exactly it. The Pod is sized at 16Gi of container memory rather than the 8Gi the TAA Pod gets away with, because this container also has to hold a whole model: at 8Gi the cgroup OOM-killed `llama-server` while it loaded `qwen2.5-coder:7b` (the blob's page cache plus ~4.5GB of tensor buffers, `memory.events` `oom_kill=128`), and the readiness probe kept seeing 503 until the deployment timed out — TAA's own Pod hides this because its LLM calls never get past the attestation handshake to ask for an inference. `--create-pod` renders `deploy/manifest/k8s/teellm-pod.yaml.tmpl` with a literal Pod name (`generateName` would let a rerun build a second host-resident confidential VM), pins `nodeName`, keeps `restartPolicy: Always` so a container exit does not cost the Pod its IP, and copies exactly one annotation — `io.katacontainers.config.runtime.cc_init_data`, without which the guest's CDH fails to pull the image with TLS errors. The two annotations `tools/csv2-vm/dcu-tee-pod.yaml` carries are deliberately not copied: `io.containerd.cri.runtime-handler` hijacks the runtime away from `runtimeClassName`, and an empty `io.katacontainers.config.hypervisor.kernel_params` erases the `rdinit=` that boots TAA's guest. An existing Ready Pod is reused and never re-applied, because `kubectl apply` onto a Pod fails on immutable fields and delete-then-apply would build a second confidential VM and change the IP that TAA's endpoint points at. The readiness probe alone cannot prove anything about attestation — its client sets `InsecureSkipAttestationVerify` — so the deployment adds two gates the deployment path previously lacked: a hard `test -e /dev/csv-guest` inside the Pod, and a log check that the Hygon hardware evidence provider came up and the mock fallback did not. On the create path a missing attestation certificate is now fatal instead of a warning, and the closing banner prints the `TAA_LLM_ENDPOINT=https://<pod-ip>:8443` to hand to TAA, since a Kata guest cannot resolve cluster DNS. The new `remote pod-down` action tears the Pod down. No Go code and no configuration template changes are needed: TAA's default attestation anchor is already the real Hygon HRK.
- **Container Supervisor Daemon (`deploy/start.sh`)**: Extracted container autostart supervisor into version-controlled source code. Provides automated process keep-alive, 10s exit restart backoff, and manual debugging toggle via `touch /root/taa/manual`.
- **Platform-Mock UI/UX Advanced Polish**:
  - **Lifecycle Pipeline Stepper**: Interactive visual stage indicator (`Register` ➔ `Ingress` ➔ `Audit` ➔ `Switch` ➔ `Train` ➔ `Export`) with live auto-synchronization against TAA state.
  - **Visual Audit Dashboard**: Interactive findings accordion with report-level risk verdict and severity statistics, per-finding line numbers, rule identifiers, matched code snippets, LLM verdict badges, and LLM arbitration reasoning.
  - **Live Dual-Log Streaming Viewer**: Dedicated real-time viewer for training terminal logs (`/v1/taa/modelLog`) and TAA operational logs (`/v1/taa/taaLog`) with log-level filtering, instant search, smart auto-scroll, and pause/resume toggles.
  - **Inbound & Outbound Payload Inspector**: Modal tabs for inspecting raw JSON payloads across all API requests and callbacks.
  - **Global Stacked Toast System**: Non-blocking asynchronous toast notifications and micro-interactions for instant operation feedback.
- **Independent TEE-LLM Inference Microservice (`teellm`)**:
  - Extracted `teellm` into an independent repository and integrated as a recursive Git submodule.
  - Added standalone `teellm/deploy.sh` supporting independent Docker and Remote Kubernetes deployment workflows.
  - Added JSON configuration parsing (`teellm-docker.json`, `teellm-production.json`) for `cmd/teellm-service`.
- **RFC 8998 TEE-TLS 1.3 ShangMi Protocol Submodule (`teetls`)**:
  - Extracted `teetls` into a dedicated submodule providing RFC 8998 TLS 1.3 ShangMi cipher suites (`TLS_SM4_GCM_SM3`, `0x00c6`).
  - Cryptographically bound Hygon CSV hardware attestation reports to X.509 certificate extensions (OID `1.3.6.1.4.1.58270.1.1`).
- **Two-Tier Code Security Audit Engine (Static Rules + TEE-LLM)**:
  - Tier 1 static scanner: 13 built-in pattern rules over Python source (`internal/codeaudit/rules.go`) covering command execution, network egress, sensitive file and environment access, obfuscation/deserialization, dynamic execution, persistence, and result-embedded plaintext data, with a physical ±3 line context window per finding.
  - Added resilient TEE-LLM client over TEE-TLS 1.3 featuring circuit breakers, jittered exponential backoff retries, and fail-closed security gates.
- **The Semgrep Rule Matrix Now Covers The GA-11 Language Set**: The Semgrep engine (selectable through `EngineConfig`; the regex scanner remains the default) admits the GA-11 extensions — `.cs .js .jsx .mjs .cjs .ts .tsx .php .phtml .tpl .rb .scala .hcl .tf .tfvars .tofu .pyi` join the existing Python/C/Go/Java/Shell set — and loads the whole rules tree rather than one pack, dispatching per language by each pack's `languages:` declaration. `.ipynb` is admitted because a notebook is source whose cells execute when it runs; `.json` is deliberately **not**, because admitting it would put every data file of a model package into the pass (`audit-100` carries 920 of them, and a `tokenizer.json` is megabytes no rule reads), so the `json` pack reaches notebooks through a rule-level `paths: include: ["*.ipynb"]` filter and the two halves stand on their own. The tree went from 24 rules to **115**: `go` and `java` were filled to the thirteen families Python already had, five new packs cover C#, JavaScript, PHP, Ruby and Scala at thirteen families each, and Terraform (5) and JSON (2) cover the families their language has a primitive for, with the rest recorded in comments as structurally absent rather than written as dead rules. JavaScript and TypeScript share one pack because measurement showed `languages: [js, ts]` dispatches to both extensions with one grammar. Each pack ships a positive sample that must fire every family it claims and a negative sample written as a **near miss** — it calls the sink of every family whose rule narrows on an argument, with an argument that fails that one predicate, so deleting the predicate turns the test red instead of passing quietly (measured by mutation: java 6/6, csharp 6/7, go 5/6; the families whose rule matches the bare primitive have no predicate to delete, so no benign call exists for them and the positive is their only evidence, as each negative file's header states). Family coverage is not arm coverage: `taa-fil-probe-go`'s second arm narrows `filepath.Join($DIR, $BASE)`, and the Go sample reached that family through a *three*-argument join that only the first arm can match, so the second arm had no positive evidence at all while the family-level assertion stayed green — the sample now carries a two-argument sensitive join. Scans are **per language**: the engine caps a report at `MaxFindings` (200) after sorting, and a whole-tree scan of the samples truncates — measured, the tail lost was exactly the alphabetically last three languages, which is indistinguishable from a dead family. The same pass fixed three defects the new checks exposed: the `go` pack declared `ERROR` on two families the production table calls medium (the engine never reads a rule file's severity, so only a test can hold the two equal, and the validation now does); the `//go:linkname` arm carried the `^(?![ \t]*//)` guard every other line regex uses, which excluded the only form the directive can take and left an arm that could fire only on a string literal spelling it; and the notebook path filter is now pinned by a controlled pair of byte-identical files rather than by a single scan that measured nothing, since a file the filter drops does not appear in `paths.scanned` at all. The smoke run over upstream fixtures is opt-in through `TAA_UPSTREAM_FIXTURES`, and its output states which languages are benchmark-backed (Python) and which are smoke-only.
- **Offline Audit Benchmark Engine (Semgrep + CPG, evaluation-only)**:
  - Added a Semgrep-native scanner (`models/audit/tools/semgrep_runner.py`) with 22 AST and taint rules across Python (13), Go (6), and Shell (3).
- Added an engine rule-parity conformance test (`tests/test_engine_rule_parity.py`) that compares the Semgrep rule set against the regex baseline over 59 source fixtures, taking the expected rule set from the baseline itself rather than writing it down, so a rule ported too loosely (missing detections) or too broadly (invented detections) fails. Added a companion corpus audit (`tests/test_engine_rule_parity_corpus.py`, opt-in via `TAA_CORPUS_PARITY=1`) that runs the same comparison per sample over the 100 `audit-100` samples and writes its numbers to `rule-parity-audit.json`. The two are not substitutes: the fixtures caught what someone thought to enumerate, the corpus audit caught `EMB_001` over-reporting every checkpoint write on a construct no fixture covered. Both assert the control arm actually fired, since two empty finding lists agree trivially. The corpus audit additionally checks that each Semgrep `code_snippet` is the real source line rather than Semgrep CE's `"requires login"` placeholder.
- Added a paired non-inferiority analyser (`models/audit/tools/engine_compare_report.py`) for the engine comparison. The judgement is per pair with zero tolerance, which is not a summary statistic, so the comparison is made sample by sample within a pair: a sample either arm failed to scan is not paired, a pair whose runs are not both complete is void and yields "insufficient evidence" rather than a lenient reading, and a missing run directory reaches the verdict as missing evidence instead of an exception or a silently smaller analysis. It reports the exact two-sided McNemar over the discordant samples and a bootstrap interval over resampled *pairs*, so the two arms stay matched by construction.
  - Added an AST scope slicer and an inter-procedural CPG taint engine with taint trajectory extraction.
  - Wired as selectable engines (`--engine regex|semgrep`) in the offline benchmark evaluator. These engines are evaluation tooling and are **not** wired into the TAA runtime audit path; migrating the runtime scanner to Semgrep is tracked in `TODO`.
- **Active Operational Log Streaming (`/v1/taa/taaLog`)**:
  - Added proactive streaming of TAA internal runtime operational logs with monotonic sequence IDs and ring-buffer deduplication.
- **CipherFlow Specification Alignment**:
  - Aligned model runtime contracts with the three-tier output directory hierarchy (`/opt/taa/output/{result,log,progress}`).
  - Upgraded Python SDK path resolution (`get_output_dir`, `get_log_dir`, `get_progress_dir`).
- **Result Directory Structure In The Training Report (`result_files`)**: The training report now carries the export directory's file tree as a top-level `result_files` field, whose node structure is identical to `/v1/taa/getResourceInfo`. It is produced by the same `pkg/filetree` scanner and is attached on both the normal completion path and the crash-recovery path. It is deliberately advisory: a failed scan logs a warning and omits the field instead of failing the report. The scan runs before `training_report.json` is written, so the tree never contains that file.
- **Table File Previews In `/v1/taa/getResourceInfo`**: Table-like files (CSV, JSONL, JSON array, XLSX, SQLite) now return their first 5 rows as `preview` — one positional array per row, aligned with `fields` and without repeated column names — with cells truncated at 128 characters. SQLite files additionally return per-table `columns` and `preview` under `tables`. Previews are opt-in through `filetree.Options.IncludePreview`, and both callers that report a file tree turn them on: this endpoint and the training report's `result_files` (which reaches the platform only — see the export change below).

### Changed
- **Persistent State Can Be Sealed With The Hygon CSV Hardware Key (`storage.stateSealingKeySource`)**: `state.sealed` used to be sealed with a 16-byte SM4 key derived from the SM2 private scalar D (`SM3(D || "TAA-STATE-SEALING-V1" || 0x00000001)[:16]`), and that private key sits in cleartext PEM in the same directory — so the trust root for the file was as readable as the file. `pkg/csvattest.GetSealingKeyIOCTL` already read the 32-byte hardware sealing key out of a CSV attestation report (session-MAC and mnonce verified, report offset `0x9b4`) but had no production caller. A new `storage.stateSealingKeySource` selects where the key comes from: `csv-hw` fetches the hardware key through `/dev/csv-guest` and derives the SM4 key as `SM3(hwKey(32) || "TAA-STATE-SEALING-CSV-V1" || 0x00000001)[:16]`, and `sm2` keeps the legacy derivation. The label differs from the SM2 one so equal input bytes never collide, and an all-zero hardware key is rejected because the ioctl can succeed while the report's sealing-key field is zeroed. **There is no fallback**: a missing device, a failed ioctl, or an unusable key aborts startup, which is what `configs/taa-production.json` and `configs/taa-initrd.json` select; `configs/taa-docker.json` and `configs/taa-fhe.json` stay on `sm2` — the FHE instance is not a CSV guest, and config validation rejects `csv-hw` for `server.type: "fhe"` rather than letting it fail later at startup. An old binary ignores the new key silently and keeps sealing with SM2, so config and binary must ship together, and moving `configs/taa-initrd.json` changes a built initrd's boot MEASUREMENT. The sealed file now carries an 8-byte cleartext header — magic `TAAS`, format version `1`, a source byte (`1` = `sm2`, `2` = `csv-hw`), two reserved zero bytes — ahead of the unchanged `nonce(12) || ciphertext || tag(16)` payload; a file is treated as new-format only when every field validates, so an old file (whose random nonce makes a false match ~2^-56) keeps reading as `sm2`. **Switching source archives rather than migrates**: a source mismatch is a typed error that renames the old file to `.orphaned.<unix>` and rebuilds clean state on every start, reusing the existing drift mechanism, while a same-source decryption failure stays fail-closed. `DetectAndHandleKeyDrift`'s `isNewKey` argument now means only that the SM2 key pair was just generated, so `csv-hw` never passes it — otherwise a regenerated SM2 key would archive a perfectly good hardware-sealed file. **The hardware key is host/chip-bound, shared by the VMs on one machine, and therefore not a per-VM identity**: sealed state cannot move to another host, where it fail-closes instead, and recovery means archiving `state.sealed` and rebuilding. The header is unauthenticated by design — whoever can write it can already delete the file, so the trust model is unchanged. `deploy/guest-build/taa-init.sh`'s missing-minor warning now says the `csv-hw` key is unavailable as well as that attestation degrades.
- **`docker save` Now Packages A TAA-Only Image, Engine Included**: the packaging action used to compose whatever the base image happened to hold: it compiled `taa`, copied the certificates and the generated production config, and committed. Two things it never did are now part of it. It **provisions the code scan engine**: the default base image (`taa-env:slim-v2`) carries no `semgrep` and no rules directory, while `configs/taa-production.json` selects the semgrep engine, and `codeaudit.NewEngine` treats a missing rules path as a hard error rather than a downgrade — so an image packaged without one started, failed, and then sat in the supervisor's 10s restart loop. The engine now comes from the container payload archive the remote and kata paths already use (`deploy/guest-build/build-semgrep-payload-container.sh` → `out/semgrep-bundle.tar.gz`, `SEMGREP_PAYLOAD_BUNDLE`), extracted with `tar -xzf - -C /` so packaging itself needs no network, with the bundle's own `MANIFEST` checked against `SEMGREP_VERSION` (1.177.0) so a stale archive fails instead of shipping; the rules are copied separately from `SEMGREP_RULES_SOURCE` into the path the template names, so a rules edit does not force a payload rebuild. As on the remote path, presence is not treated as proof — the same bounded, offline scan probe runs with the argv `taa` uses at audit time, and a failure aborts the packaging. It also **installs the supervisor from this repository** (`deploy/start.sh`, the 3082-byte version with the flock singleton guard) instead of inheriting the base image's stale 858-byte copy, because `save` had never copied it and the ENTRYPOINT was whatever the base image carried. And it **strips TEE-LLM and ollama**: every artifact enumerated from the combined images this repository produces (`/root/taa/ollama*`, `teellm-service`, `start-teellm.sh`, `.start-teellm.lock`, the teellm/model configs) is removed and then asserted gone one by one, so the same code covers both a slim base and an already-combined one, and a leftover fails the packaging rather than shipping silently. The resulting image is TAA plus the engine; TEE-LLM is a separate deployment (`./deploy-llm.sh`) and the image reaches it through the variable below. Order is strip → supervisor → engine → binary/certs/config, so the image is assembled once.
- **`TAA_LLM_ENDPOINT` Overrides `codeAudit.llm.endpoint`, And Is The One Variable That Does**: now that the LLM service is deployed independently, the endpoint baked into an image is only a default, so `TAA_LLM_ENDPOINT` lets a container be pointed at a TEE-LLM instance that does not live at that address without rebuilding. An empty or unset value leaves the configuration file's endpoint alone. **The precedence is deliberately the opposite of `PLATFORM_IP`, `DOCKER_ID` and `CONTRACT`**: those three are seeded in `defaultStartupConfig` as defaults that the config file then wins over, which only looks like runtime injection because the packaged config omits the platform block. The endpoint is written into every shipped template, so an environment value that could not override it would never take effect at all — hence a real override, documented in the code comment where the asymmetry would otherwise read as a bug. Relatedly, `resolve_llm_endpoint` in `deploy.sh` no longer bakes docker's placeholder into an image: a **stopped** container does not inspect as "no address", it returns the literal string `invalid IP` (the zero `netip.Addr` rendered), which is non-empty and was being written into the config as `https://invalid IP:8443` — a URL with a space in it. Only a dotted quad is accepted now, with `https://127.0.0.1:8443` as the fallback.
- **The `codeAudit` Block's Flat Scan Keys Are Now An `enabled` Switch And A `codeScan` Block**: `codeAudit` used to carry four flat keys for one thing — `codeScan` (the on/off switch), `codeScanEngine`, `semgrepRulesPath` and `semgrepTimeoutSeconds` — so the switch and the three settings it governs sat at the same level as `resultCheck`, `binaryAudit` and `llm`. The switch is now `codeAudit.enabled` and the settings are one `codeAudit.codeScan` object: `codeScan.engine`, `codeScan.rulesPath` and `codeScan.timeoutSeconds`. The engine name lost its `semgrep` prefix because the block already names the engine — the same reason `TimeoutSeconds` kept its unit but dropped the engine name, matching `semgrepTimeoutSeconds`'s sibling `requestTimeoutMs` under `llm`. `timeoutSeconds` moved with the other two rather than staying flat, even though it is the semgrep engine that reads it (`codeaudit.SemgrepLimits.Timeout`, resolved only in the semgrep branch of `NewEngine`): leaving it beside a block that holds the engine it belongs to would have been the split this change exists to remove. On the Go side `StartupConfig.CodeScanEngine`, `SemgrepRulesPath` and `SemgrepTimeout` collapse into one `CodeScan CodeScanConfig` (`Engine`, `RulesPath`, `Timeout`), the same shape the file now has and the same move the `LLM*` fields made when they became `LLM LLMConfig`. `EnableCodeAudit` keeps its name — bare `Enabled` on `StartupConfig` would be ambiguous next to `BinaryAuditEnabled`, `EnableResultCheck` and `LLM.Enabled`, and it is the file's own nesting, not the Go field's, that the rename was about. `configs/taa-initrd.json`, `configs/taa-docker.json` and `configs/taa-production.json` move in lockstep, and so do `deploy.sh` (its engine/rules reader now descends into `codeScan`), `deploy-docker.sh` (the derivation writes `codeScan.engine` and `codeScan.rulesPath` instead of the flat pair) and `deploy/guest-build/build-initrd.sh`, whose `taa_config_wants_semgrep` gate matched the literal `"codeScanEngine": "semgrep"` and now matches `"engine": "semgrep"` — a stale pattern there would have built an initrd with a semgrep config and no semgrep payload, which boots and then fails every import audit. **The old keys fail the load rather than being ignored**: `codeScanEngine`, `semgrepRulesPath` and `semgrepTimeoutSeconds` are declared solely so their presence is detectable, and a config carrying any of them exits with `uses removed keys:` naming both the old key and its new path, all of them in one message when several are present. `codeScan` needed more than a name because its *type* changed: a bool where a block now belongs would have surfaced as `cannot unmarshal bool into Go struct field`, a message that says nothing about where the switch went, so a custom unmarshaler replaces it with one that names `codeAudit.enabled` and the three keys the block holds. An explicit `null` is still treated as absent for every one of these, `codeScan` included. **This is breaking on upgrade, on the same terms as the rename that preceded it**: on the CSV2 initrd path TAA is a boot gate, so a binary and a `configs/taa-initrd.json` from opposite sides of this change do not boot the VM at all — the two must ship together, `deploy.sh` regenerates the `.local/run/*-taa-config.json` copies from the templates on the next deploy, a pre-built image needs rebuilding, and moving the initrd template changes the bytes of a built initrd and therefore its boot MEASUREMENT. The README's sample block, field table and remote-deploy note follow, and the three scan keys gain table rows they never had.
- **The `security` Config Block Is Now `codeAudit`, And `llm` Has Moved Inside It**: the two top-level blocks whose names no longer matched what they held are one block now. `security` was already the code audit (`codeScan`, `codeScanEngine`, `semgrepRulesPath`, `binaryAudit`) plus two settings that are not an audit of code at all — `resultCheck` (the plaintext-leakage check on training results) and `maxFileBytes`; and `llm` sat at the root even though the inference service exists for exactly one purpose, adjudicating the findings the static scan raised, which after TAA and TEE-LLM became separate deployments read as though TAA owned a model. `codeAudit` now holds all of it, with `llm` nested inside. `resultCheck` and `maxFileBytes` stay where they were inside the block rather than being split out, because that keeps the change to a rename and a move. The Go side already disagreed with the file — `controller.SecurityConfig` nests `LLM` and `Binary` inside one audit aggregate and `buildSecurityConfig` builds them together — so this makes the file say what the code already does. `StartupConfig.EnableSecurityScan` is renamed `EnableCodeAudit`, and the nineteen flat `LLM*` fields collapse into one `LLM LLMConfig`; `CodeScanEngine`, `SemgrepRulesPath`, `SemgrepTimeout`, the six `BinaryAudit*` limits, `EnableResultCheck` and `MaxFileBytes` stay flat, and `controller.SecurityConfig` keeps its name and layout (it also carries `ModelDir`, `DataDir`, `ResultDir` and the staging directories, which a name like `codeAudit` would misdescribe). Every rejection message that names a key now names its new path (`codeAudit.binaryAudit.maxArchiveMembers`, `codeAudit.llm.policy`, and so on), and `deploy.sh`, `deploy-docker.sh`, the templates, the README and the architecture doc moved in lockstep. **The old keys fail the load rather than being ignored**: `encoding/json` drops a key it does not recognise without a trace, so a config still written the old way would have loaded cleanly with every setting under `security` and `llm` discarded — the scan back on the regex baseline, the inference endpoint back to `127.0.0.1:8443` — and nothing in the log saying so. `security` and top-level `llm` are now declared solely so their presence is detectable, and a config carrying either exits with `uses removed keys: "security" (rename to "codeAudit"), "llm" (move under "codeAudit.llm")`, both named in one message when both are present. **This is a breaking change on upgrade, and a loud one**: on the CSV2 initrd path TAA is a boot gate, so a binary shipped against the old `configs/taa-initrd.json` does not boot the VM at all — the binary and that template must move together. A previously baked production image or an on-disk `.local/run/*-taa-config.json` carries the old shape; `deploy.sh` regenerates the `.local/run` copies from the templates on the next deploy, so those recover with a redeploy, while a pre-built image needs rebuilding. Moving `configs/taa-initrd.json` also changes the bytes of a built initrd and therefore its boot MEASUREMENT.
- **The Key Store Moved From `/opt/taa/keys` To `/root/taa/keys`**: `storage.keys` now sits under the same prefix as `storage.model` / `data` / `result` and the attestation certificates, instead of being the one secret directory left under the `/opt/taa` runtime prefix. The two deployment paths that already rewrote it — `deploy.sh` for docker and remote, which passes `$TAA_CONTAINER_WORKDIR/keys` — were setting `/root/taa/keys` all along, so only the production image path (a literal `/opt/taa/keys` in `deploy.sh`) and `deploy-docker.sh` (which created the directory) were actually out of step; both now agree with the templates, and `deploy-docker.sh` no longer creates a second, unused keys directory. The in-code default (`config.StartupConfig.KeysDir`), the two empty-value fallbacks in `internal/app/taa`, the three templates, the README and the architecture diagram moved with them. **This is a breaking change on upgrade**: an instance that already ran under `/opt/taa/keys` will not find its SM2 key pair or `state.sealed` at the new path, so TAA generates a fresh key pair and the old sealed state is left behind. `configs/taa-initrd.json` moved too, which changes the bytes of a built initrd and therefore its boot MEASUREMENT — the initrd in `deploy/guest-build/out/` predates this change and needs a rebuild.
- **A Leaking Result Directory Is Reported As A Rejected Run, Without `result_files`**: when the training-end plaintext leakage check finds training data (or other high-severity plaintext) in the result directory, TAA now reports that run to the platform as failed: `/v1/taa/reportRes` goes out with `code` `2` and the reason in `msg` (`结果目录包含原始训练数据，训练结果拒绝提供目录清单与预览: <details>`), the report body says `training_task.status` `failed` with the same reason in `failure_reason`, and the report carries **no `result_files` at all** — the directory tree's table previews are the data rows being withheld, so TAA does not even scan for them. `exit_code` stays `0`: the training process itself exited cleanly, it is its artifacts that are refused. `code` `2` is distinct from `1` (the run failed on its own) so the platform can tell the two apart. This replaces the earlier `result_files.contains_dataset` boolean, now removed: withholding the tree says more than a flag inside it, and the flag's `absent means never checked` third state is no longer needed. A check that could not run — a verdict recording `error`, no verdict at all, or `security.resultCheck.enabled` off — is **not** a rejection: the report is delivered normally, tree included, and only the export gate's `llm.failClosed` behavior applies. `/v1/taa/export` is unchanged and still returns `400` for a leaking verdict.
- **`training_report.json` Is Packed Out Of The Export And Skipped By The Leakage Check, So The Report Now Carries Table Previews**: the report's `result_files` tree previously shipped previews off, because that report lands inside the result directory and was therefore packed into the `/v1/taa/export` archive — previews there would have sent dataset rows to whoever downloads the export. The report is now excluded from the export archive instead (root matches only: a file of the same name deeper in the tree is still packed), the leakage check skips the same file for the same reason, and the report's tree returns previews like `/v1/taa/getResourceInfo` does (unless the check rejected the run — see below), so the platform sees the sample rows it needs alongside the structure. The report still reaches the platform through `/v1/taa/reportRes`; only the export archive loses it, and the export endpoint still requires it to exist (404 otherwise). The packer's exclusion list and the check's skip list are the same constant, so neither can drift from the file actually written.
- **The Result Leakage Check Moved From Export To The End Of Training**: with `security.resultCheck.enabled` on (the default), the plaintext leakage scan now runs once, right after a training run collects its artifacts and before `training_report.json` is written, and its verdict (`passed`, high-severity `details`, `checkedAt`) is persisted on the task's import index record. `/v1/taa/export` reads that verdict and no longer scans the result directory, so the response starts streaming immediately instead of after a full rescan — on a ~85 MiB result this was ~80 s of a response with zero bytes on the wire, long enough for the caller's timeout to close the connection and turn the first write into a broken pipe. The gate itself is unchanged in what it blocks, and fail-closed in three explicit states: a failing verdict returns the same 400 with the same message as before, a verdict recording that the check could not run returns 500, and a record with no verdict at all (committed before this field existed) also returns 500 until the task is retrained. The two states without a usable verdict are governed by `llm.failClosed`: with it `false` a missing or failed verdict is logged as a warning and the export proceeds, because an operator who has already accepted advisory LLM verdicts should not be blocked by a check that never produced one. A verdict that says the result leaks is not affected by that switch and always returns 400. Two deliberate side effects: `training_report.json` is no longer scanned (it is written after the check, and the check skips it explicitly since the report now carries table previews by design), and a failing check never fails the training process — `exit_code` stays `0` and the report is still delivered, though the run is reported as rejected (see the change above).
- **The Export Public Key Is Optional End To End**: `publicKey` is no longer a required input anywhere in the export chain. `/v1/taa/importModel` accepts a request without one — nothing is validated, nothing is saved, no failure is reported — and `/v1/taa/export` no longer returns 400 for a phase 3 export that has no key available. Phase 3 now resolves its encryption key in order: the key saved at model import → the `publicKey` carried by the export request → plaintext. Phases 1/2 are unchanged (request `publicKey` → plaintext). The consequence is deliberate: a platform that never supplies a key receives phase 3 artifacts in plaintext rather than an error, where the 400 previously was what blocked a cross-phase plaintext export.
- **Model Code Audit Is Now Advisory**: A failing model code audit no longer blocks anything. Its verdict is reported to the platform as a reference result (`/v1/taa/reportAudit`, codes `0` pass / `1` fail / `2` no verdict) and decides nothing on the TAA side: a failing or interrupted audit neither rolls back the import nor cancels a running training, so the model stays imported and trainable and the package on disk stays exactly as uploaded. Previously a failing verdict cleared `ModelImported` and stopped the active training. Concurrency is unchanged: a model import is still refused while another audit is running, and the 409 busy responses are unrelated to the verdict. The crash-recovery path now only reports the interrupted audit instead of rolling the import back, and the audit summary no longer claims TAA blocks the import.
- **The Historical `type` Field Is Fully Ignored on Resource Delivery**: `/v1/taa/import` no longer presents `type` (1=model, 2=debug data, 3=training data) as a routing input. It never was one — the request struct has no field for it, so decoding dropped it and no branch consulted it — but the API spec required it and the architecture diagrams routed on it. The field is now marked ignored on both endpoints, and which resource a request carries is decided by the endpoint alone.
- **The Data Import Endpoint No Longer Accepts `publicKey` Or `runtimeConfig`**: `/v1/taa/import` reads neither field; both take effect where they are already read — `/v1/taa/importModel` saves the export public key at phase-1 model delivery, and training executes the `runtimeConfig` saved there. A request that still carries them is accepted and the two fields are ignored, with a warn log naming them, because a second source for the same setting means the run executes whichever endpoint spoke last and only one of the two ever had a documented precedence. For a platform that sends `runtimeConfig` with its data, the training that this delivery triggers therefore runs the configuration saved at model delivery; if no model delivery saved one, the preconditions fail as before and `/v1/taa/reportRes` reports a run that has an empty `runtimeConfig`.
- **Toolchain Reorganization (`tools/`)**: Reorganized auxiliary tools into top-level `tools/` directory, moving platform mock to `tools/platform-mock/` and cryptographic tools to `tools/sdk/`.
- **Go Workspace Orchestration**: Configured `go.work` multi-module workspace orchestrating `taa`, `teellm`, `teetls`, and `tools/sdk` on Go 1.22+.
- **Configuration Templates**:
  - Streamlined `configs/taa-docker.json` and `configs/taa-production.json` by removing backend LLM server-specific paths.
  - Added `attestation` certificate path configurations (`hrkCertPath`, `hskCekCertPath`) and TEE-TLS transport parameters.
- **Deployment Script (`deploy.sh`)**: Refactored root `deploy.sh` to focus exclusively on `taa` and `platform-mock`, delegating LLM model distribution and runtime management to `teellm/deploy.sh`.
- **Dynamic File Size Threshold**: Replaced hardcoded size limits with configurable `maxFileBytes` (default 3 GB) for export data leakage inspection.
- **100% Training Progress Now Waits For The Result Leakage Check**: the progress watcher used to report the model's `{"percent":100}` the moment it read it, which is the moment the model finished training — while TAA still had to collect the artifacts out of the model output directory and run the plaintext leakage check over them (measured at up to 80 seconds on a real result directory). The platform therefore saw a finished task while TAA was still working on it. A snapshot at 100% is now parked in the watcher instead of sent, and released once the pipeline is past the check, whatever its verdict: a result directory the check rejects is still a run that reached its end, and the rejection travels to the platform through `reportRes` code 2. A model that never reported 100% gets nothing invented for it, and neither does a run that fails or is stopped before the release point — 100% now means TAA carried the task to its end.

### Removed
- **The Model Checkpoint Staging Directory (`/opt/taa/checkpoint`), End To End**: `model.checkpoint` is gone from the configuration templates, along with the legacy flat `modelCheckpointDir` key, the `ModelCheckpointDir` field on the startup and security configs, `DefaultModelCheckpointDir`, and `SecurityConfig.GetModelCheckpointDir()`. TAA no longer creates the directory at startup or before a training run, no longer injects `TAA_CHECKPOINT_DIR`, `TAA_MODEL_CHECKPOINT_DIR` or `CIPHERFLOW_CHECKPOINT_DIR` into the model process, `deploy-docker.sh` no longer creates it, and the architecture document no longer lists it. Nothing read it: TAA itself only ever created the directory and passed the three environment variables, and the reference model package resolves its checkpoint output from `TAA_OUTPUT_DIR` instead, saving `net_XXX.pth` under the output root — which is where the artifacts actually get collected, delivered and leakage-checked. A model that nevertheless wrote to the old path was writing outside the delivered tree, so its checkpoints were silently discarded rather than resumed from. The platform-facing Protocol Buffer contract is deliberately untouched: `api/proto/cipherflow/v1/{checkpoint,sandbox,security}.proto` still declares the checkpoint/resume specification, which nothing in this repository generates code from or implements, and withdrawing it is a protocol decision rather than a configuration one.

### Fixed
- **`deploy.sh` Overwrote `model.output.result`, So Results Landed Beside `log/` And `progress/` Instead Of In Their Own Directory**: all three templates put the exported results one level down, at `/opt/taa/output/result`, and `deploy-docker.sh` creates exactly that three-way split (`/opt/taa/output/{result,log,progress}`). Two call sites in `deploy.sh` passed the output *root* instead — the production image path, as a literal, and the local docker path, through `LOCAL_DOCKER_OUTPUT_DIR`'s default. That mattered because a non-empty `model_output_dir` **overwrites** the template's value rather than falling back to it, so the packaged image and the local container both ran with `result: /opt/taa/output` while the file on disk said `/opt/taa/output/result`. The remote path passes empty for both staging paths and therefore kept the template's value, which is how the divergence surfaced: the same template produced two different locations for the same key depending on how TAA was deployed. The packaged image has been verified to carry `result: /opt/taa/output/result` and to start TAA with it. Both call sites now pass the full path. **On upgrade:** a container or image assembled before this keeps the old value; `deploy.sh` regenerates `.local/run/docker-taa-config.json` on the next `docker` deploy and a pre-built image needs repackaging, after which results move to `/opt/taa/output/result` — anything reading the old location has to follow. TAA creates whichever of the three directories it needs, so nothing else changes.

- **Offline audit benchmark (evaluation-only): the Semgrep rule set was realigned with the regex baseline it is meant to mirror.** The two arms diverged in both directions, which would have made any engine comparison uninterpretable:
  - `FIL_001` had lost its sensitive-path predicate and matched *any* `open()` call while carrying `HIGH` severity where the baseline has `MEDIUM`. This is the rule that flagged all 100 audit-100 samples in the one recorded full-corpus Semgrep run.
  - `CMD_001` kept only the `shell=True` form, so every list-form invocation was missed, including the primary attack of samples M1-02/M1-07 (`subprocess.check_output(["bash", "-c", "whoami"])`).
  - `NET_001` had no `httpx`, `http.client`, `httplib2` or `urlretrieve` coverage (M2-04 uses `httpx.post`).
  - `OBF_001` was expressed as a taint rule (decode → `eval`/`exec`) where the baseline flags decode *use*, so payloads that are decoded and then exfiltrated instead of executed were invisible to it (M4-01), as were `pickle`, `marshal`, `codecs.decode` and `binascii`.
  - `PER_001` required the persistence path to be an argument of `open()` with a write mode, missing a path built on one line and opened on the next (M5-01); `EMB_002` matched every `shutil.copy` while missing `shutil.move`, and `EMB_003`/`EMB_004` matched literal argument names the baseline does not list.
  - Severity is not cosmetic in this comparison: under the production `gate` policy a `HIGH` finding blocks unless the LLM returns `BENIGN`, while a `MEDIUM` finding is counted but never blocks (`internal/codeaudit/verifier.go:160-178`), so a mistranslated severity changes whether a rule can block at all.
  - `EMB_001` was ported as a bare `torch.save($DATA, $PATH)` with only `state_dict()`/`model.pt` exclusions, dropping the baseline's payload-name list. It therefore flagged *every* checkpoint write — a `HIGH` finding on `train.py` in 75 of the 100 samples, most of them benign — while the `np.save`, `np.savez`, `shutil.copy` and `shutil.copytree` branches were missing entirely. Found by re-running the corpus-wide parity audit, not by the fixture tests: `EMB_001` had only a negative fixture, so nothing pinned what it was supposed to *not* catch. Both gates now also assert the control arm actually fired, since two empty finding lists agree trivially.
- **Offline audit benchmark (evaluation-only): the hand-authored matrix generator no longer implies an engine nobody named.** `generate_matrix_results.py` writes its `summary.json` files in the same shape and location as real evaluator runs, but every count in them comes from a hardcoded table, and `engine`/`rule_set_version` were derived from the audit mode name — so `engine: "semgrep"` was recorded without anyone claiming it, and the design report cited the result as a Semgrep measurement. Each row now carries `provenance: "hand-authored-spec"`, and both fields must be declared explicitly: `generate_matrix` takes a required track declaration with no default, and the CLI's `--track MODE:ENGINE:RULE_SET_VERSION` is required.
- **Offline audit benchmark (evaluation-only): `code_snippet` is no longer forwarded from Semgrep's JSON output.** Semgrep CE returns the literal string `"requires login"` in `extra.lines` when not logged in, and that field was mapped straight to `code_snippet` — the code the LLM is asked to adjudicate. No Semgrep+LLM arbitration had therefore ever run on real source. The runner now slices the matched line range out of the source file and records a `slice_error` when it cannot.
- **Offline audit benchmark (evaluation-only): an unfinished scan is no longer scored as a clean one.** A crashed, timed-out, uninstalled or rules-broken scanner produced the same empty finding list as a genuinely clean scan, and that list was recorded as a bypass — so an infrastructure failure improved the score. Scan status (`scan_complete`, `scan_timed_out`, `scan_parser_errors`, `scan_error`, `slice_error_count`, `ast_error_count`, `cpg_error`) now reaches every sample row, `incomplete` samples are excluded from the metrics, and the three swallowed exceptions in the evaluator record their cause instead of passing silently. The exclusion was initially incomplete: counting the failures was not enough, because the confusion matrix still scored the unscanned rows. A smoke-test run where all four samples failed to scan reported `tn: 4` with `accuracy: 1.0` — and since the Semgrep arm is the only one that can be incomplete, and a crashed scan *lowers* the false-positive rate, the defect could have manufactured a pass on the very criterion being judged. `confusion_counts` now drops unscanned rows instead of assigning them a cell (which also corrects the bootstrap intervals, computed through the same function), the metrics state `scored_count` next to `scan_incomplete_count` so a 96-of-100 matrix cannot read as the whole corpus, and each run carries `round_complete` — with the void notice leading `final-report.md` and zeros in `confusion-matrix.json` when it is false.
- **Offline audit benchmark (evaluation-only): the LLM sampling seed is now fixed and recorded.** Added `--llm-seed` (default `42`) to both the analyzer CLI and the benchmark evaluator, threaded through to the Ollama `options.seed`. The three paired repetitions are meant to isolate the engine, and an unpinned seed folds sampling noise into that comparison. Temperature is unchanged at `0.1`.
- **Offline audit benchmark (evaluation-only): the evaluator now times the work it is budgeting for.** The run budget for a paired comparison has to be set before hours of runs are committed, and the two costs behave differently: the static scan is a fixed per-sample cost the engine choice sets, the LLM arbitration is the one that dominates. Only a whole-run `eval_duration_sec` was recorded, which cannot separate them, and `scan_metadata.scan_duration_ms` was being written as a literal `0` — the standalone analyzer CLI measured it correctly, so the evaluator's report bundle carried a duration that no scan had produced. Every sample row now records `scan_duration_ms` (also written into the audit report), `llm_invoked` and `llm_duration_sec`, and the summary reports `per_sample_llm_sec` divided by the samples that actually waited on the model rather than by the corpus, since most samples bypass arbitration and a corpus-wide mean would report a cost no sample ever incurred.
- Fixed HTML browser cache invalidation in platform mock by adding no-cache headers.
- Fixed fail-closed arbitration in code auditing: assist mode now blocks the import when every finding's LLM verification failed (service down or circuit breaker open) instead of silently falling back to the static verdict.
- Fixed the LLM readiness pre-check to require an active `generate` probe against the target model, instead of matching the model name against the `/api/tags` listing.
- Corrected `README.md` and this changelog, which described the Semgrep AST/taint engine as part of the runtime audit path. The runtime path uses the built-in static rule scanner; the Semgrep and CPG engines live in the offline audit benchmark harness only.
- Corrected the documented `llm.policy` values in `README.md`: the strict mode recognized by the code is `gate`, not `enforce`. Setting an unrecognized value silently falls back to `assist` behavior and skips gate arbitration.
- Fixed Hygon CSV attestation mock report byte layout alignment with the `OffsetUserData` hardware specification.
