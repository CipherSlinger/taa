## [Unreleased]

### Added
- **The Audit Rules, Tooling and Evidence Moved Into `teeaudit`**: `models/audit` — the Semgrep
  rule set, the benchmark and CPG tooling, the corpus manifests and the evaluation evidence —
  now lives at `teeaudit/models/audit`, next to the runtime that consumes it. The relative layout
  is unchanged on purpose: every tool derives its repository root as `parents[3]` and
  `semgrep_runner.py` defaults to `../semgrep/rules`, so a wholesale move keeps those defaults
  correct, while splitting the tree would have silently pointed them at missing directories. The
  three deploy scripts that read the rules from the working copy now name the `teeaudit/` prefix,
  and a root `conftest.py` puts `teeaudit/` on `sys.path` so `from models.audit.tools...` still
  resolves (the `models` namespace package merges `teeaudit/models` with the root `models/`, which
  keeps `models/examples`). Git carries the same 743 files TAA tracked, about 61 MB; the 1.2 GB of
  corpora, research material and run output stay local and ignored, under the same force-add
  convention as before. `teeaudit/models/go.mod` exists only as a boundary: the corpus holds 248
  `.go` files written as Semgrep fixtures that import packages this project does not depend on,
  and the boundary both keeps `go build ./...` from walking them — which is what previously forced
  every root build to be scoped — and keeps the data out of the module zip a `go get` downloads.
- **platform-mock：实例连通性改为自动定时检查，失效进入重连/断开状态。** 实例行上的
  「检查连通性」按钮取消——连通行不行不该靠操作者记得去点。平台接受实例注册、控制台观察到后（列
  表每 5 秒拉取一次 `/api/instances`），该行立刻开始检查，此后每 30 秒 `GET /v1/taa/health` 一次；
  请求经 mock 的 `/taa` 代理、按该行自己的 `dockerId` 寻址，因此后台检查既不会切换选中实例，
  也不会把一个实例的应答记到另一个实例名下。检查失败时行状态变为 `重连中` 并继续重试；从**第一次
  失败**起计时满 5 分钟仍然连不上，则标记 `断开连接` 并停止检查——之后只有该实例再次注册
  （平台每次注册都会重写 `receivedAt`）才会重新开始定时检查。中途任何一次检查成功都会回到
  `连通正常` 并清空失败计时。行内只显示检查结论本身：不再提供 `查看结果` 回看窗口，列表头部
  也不再汇总各类状态的数量——结论已在每行自己的标签与提示里，汇总只是把同一份事实再写一遍，
  而且没有检查会去更新它。
- **platform-mock：TEE-LLM 面板取消常驻的「远程证明」折叠区，报告改为点击后弹窗查看。** 报告是
  实例侧的一次性硬件调用结果，只在实例重启时变化；把它常驻在面板上，上一次拉取的内容会一直
  挂着，看起来像当前状态。现在点击「获取证明报告」后，新拉到的结果直接在共享抽屉里打开：
  requestId、实例自检结论（`verifiedPass`）、报告字节数、`attestationValues`（解析后嵌套显示）
  与整份 base64 报告；标题写明「来自实例，未校验」，避免把实例的自检当成平台的验证结论。面板
  不再保留这份副本。
- **platform-mock：面板上直接填 IP / 用户 / 密码连远程海光主机。** 上一版只能靠启动参数
  `-host-ssh` 决定面板读哪台机器，换目标就要重启 mock；而「远程海光服务器」条里那个 IP 输入框
  仍然只是显示/复制用的，操作者在页面上填了 178 的地址，看到的仍是 116 自己的内存与 Pod。
  现在这一栏多了用户、密码输入框和「连接」按钮：点连接把三者 POST 到 `/api/host/target`，
  mock 用它们建立 SSH 探测，与 `-host-ssh` 走同一条路径（登录 shell 里读 `/proc/meminfo`、
  跑 `kubectl get pods -A`），并在响应里直接带回新主机的第一次采集结果，所以密码错、主机不通
  当场就能看到原因，不必等下一轮轮询；「本机」切回 mock 所在机器。密码只用于这次连接：不落盘、
  不回显，只留在内存里直到目标被替换；IP 与用户按浏览器记住，密码不记。目标是一次运行时状态，
  重启后回到配置里的来源。源切换按代号校验：切换瞬间仍在跑的旧采集不会以新主机的名义入库，
  面板也不会把旧主机的数字挂到新标签下。该端点只接受同源请求（控制台页面），避免操作者浏览器
  里的其它页面借它发起 SSH；目标串拒绝以 `-` 开头或含空白的写法，防止被 ssh 当成选项。
  `-host-ssh-options` 里的密钥/跳板参数对控制台连入的目标同样生效。连接成功后 Pod 表默认收回到
  `default` 命名空间（TAA 与 DCU 测试 Pod 所在处），不会停在切换前的筛选或「全部命名空间」。
- **platform-mock：TAA 日志改为每实例独立终端。** 底部「TAA 运行日志」卡片只跟随选中实例，
  切换行会把操作者正在看的日志整个换掉，且暂停/级别过滤/搜索/滚动锁都是页面级变量，无法同时
  对照两个实例。现在每个实例行带 `日志 (N)` 按钮，在该行下方展开独立终端；状态按 dockerId 保存，
  日志请求始终显式带 `?dockerId=`，收起或暂停的终端不再轮询。底部只保留「模型终端日志」并改为整行
  全宽。
- **The Code-Audit Runtime Is Now Its Own Module and Repository (`teeaudit`)**: the audit path is
  no longer a private package of the daemon. `internal/codeaudit` (with `cpg/`), `internal/llmclient`,
  `pkg/crypto`, `pkg/archiveentry`, `internal/hctclient` and `internal/hctproto` moved into the
  `CipherSlinger/teeaudit` repository, mounted here as a submodule and consumed via
  `replace github.com/CipherSlinger/teeaudit => ./teeaudit`. The HCT packages moved with `crypto`
  rather than staying behind because `pkg/crypto`'s HCT backend imports them, and Go's internal
  visibility rule forbids a module from importing another module's `internal/` tree — leaving them
  in TAA would have made the separation uncompilable. `teetls` is a nested submodule of `teeaudit`
  pinned to the same commit as `teellm/teetls` (`06a8123`). Because `taa` and `teeaudit` each
  replace `teetls` with a different relative path, `go.work` lists `teetls` as a replace target
  instead of a workspace member (a module cannot be both), and its own tests keep running under
  `GOWORK=off`. The SDK follows the move through `replace github.com/CipherSlinger/teeaudit =>
  ../../teeaudit`, and `teellm` is untouched.
- **Each Instance Can Publish a NodePort Service (`deploy`)**: a platform that runs outside the
  cluster cannot dial a Kata Pod's address. A Pod dialling another host is SNAT'd by Cilium to
  that host's IP, so the registration's source address names the NAT (here `172.16.10.178`), not
  the Pod, and the address platform-mock derives is the same wrong one for every instance. The
  package can now carry `test/taa-service.yaml`: a NodePort Service named after the instance
  identity (`taa-<dockerId>`, with `.`/`_` folded to `-` and lowercased for DNS-1035), selecting
  the Pod by the `taa-instance-id` label and publishing `TAA_ADDR`'s port. Selection by label is
  what makes it survive Pod recreation — a hostPort dies with the Pod it was declared on.
  `TAA_INSTANCE_ID` defaults to the registered identity (`TAA_DOCKER_ID`), `TAA_SERVICE_NODE_PORT`
  is optional (30000-32767) and is deliberately left out of `SHA256SUMS` together with
  `test-pod.yaml`, because both are operator-editable per deployment. `create-test-pod.sh` applies
  the Service and prints the address to record in platform-mock's `--instance-targets`;
  `delete-test-pod.sh` removes the Service even when the Pod is already gone, since a hand-deleted
  Pod would otherwise leave the NodePort orphaned under a name nothing on the host explains.
- **TAA Can Run Its SM2/SM3/SM4 on Hygon HCT 3.0.10, With the gmsm Software Implementation as the
  Fallback (`crypto`)**: TAA's cryptographic calls go through a `Backend` seam in `pkg/crypto`
  whose default remains the pure-Go gmsm implementation; the new `hct` backend reaches Hygon's
  `libhct` through a long-lived `taa-hct-helper` process over a framed stdin/stdout protocol.
  The helper exists because TAA must keep its `CGO_ENABLED=0` static-link contract — the initrd
  build rejects a dynamically linked TAA — while `libhct` is a shared library, and because a
  vendor library fault must not take the daemon down with it. SM2 signing keeps gmsm's semantics
  by computing `ZA` and `SM3(ZA || M)` locally and handing libhct only the 32-byte digest, so
  arbitrary user IDs still verify across both implementations; ciphertext keeps the `0x04`
  prefix gmsm writes, and SM4-GCM never returns unauthenticated plaintext. The backend is selected
  at startup from the top-level `crypto` block (not `codeAudit`, because every role seals state
  and talks to the platform): an unknown backend name is a configuration error, but a configured
  `hct` that cannot start — missing helper or loader, missing `libhct`/`libnuma`, version
  mismatch, failed known-answer tests, or `accel=ccp` without a `/dev/ccp*` — **does not stop
  TAA**. The original software implementation takes over and the log records both the reason and
  the interface now in use: `crypto backend: hct (Hygon HCT interface; libhct …, accel=…;
  software implementation; engines: sm2=sw sm3=sw hmac-sm3=sw sm4-gcm=sw)`,
  `crypto backend: builtin (original software implementation, gmsm)`, or a `degraded from hct to
  builtin` line carrying the helper error. The helper, not the configuration, is the authority on
  that report: the handshake carries the accel it actually started with plus a per-operation
  engine map, and each operation is dispatched through a capability-selecting router. The router now
  carries a second engine: a `ccp` backend over the hardware `hct_ccp_*` API (`crypto.hct.accel=ccp`,
  helper flag `--accel ccp`) that serves SM2, streaming and one-shot SM3, and SM4-GCM; HMAC-SM3 stays
  on the software engine because the CCP header exposes only a burst call with no incremental
  interface. Asking for `ccp` can never fail startup: TAA checks for a `/dev/ccp*` device before it
  starts the helper, and the helper itself degrades to a pure software router with the reason on
  stderr if `hct_ccp_init` fails — its first act is opening the accelerator manager's `/dev/ccp_share`.
  The hardware path is not reachable from the CSV2 guest TAA runs in: QEMU started with
  `-device hct` does present the vCCP as PCI `1d94:1468` (verified through `/proc/bus/pci/devices`
  inside a running Kata Pod), but the Kata CSV kernel ships without `CONFIG_VFIO_NOIOMMU`, which
  blocks the vendor's documented vfio-pci-noiommu binding of the vCCP, an emulated `intel-iommu`
  under SEV never completes the guest boot, and nothing in the guest provides `/dev/ccp_share`.
  The vendor documentation likewise routes CSV guests to vTKM rather than CAE. An engine that
  covers only part of the interface is skipped for the operations it cannot serve instead of being
  reported as the whole backend. A helper that dies while TAA is running degrades the
  same way: stateless operations (SM2 key generation/encrypt/decrypt/sign/verify, SM3, HMAC,
  whole Seal/Open) are replayed once on the software implementation because no output has
  escaped, while a stream already consumed by the helper fails that one operation and leaves the
  next one on the software implementation — replaying it would require retaining the input.
  Protocol results such as a rejected authentication tag or signature are never retried on
  another implementation. `deploy/guest-build/build-hct-helper.sh` pins the 3.0.10 deb by
  SHA256, builds the helper in glibc 2.31 (the guest has 2.35), and assembles a payload carrying
  `libhct.so`, `libnuma.so.1` and the vendor `/etc/hct_config`; `build-initrd.sh` injects it and
  rewrites the measured config to `"backend": "hct"` byte-for-byte with a read-back assertion.
  Scope is `pkg/crypto` only: TAA's binary still links gmsm through `teellm/teetls`, and the
  helper's SW backend does not change the key-material boundary — private keys are still generated
  in, and returned to, the guest (that guarantee belongs to TKM/vTKM, not HCT).
- **The platform-mock Host Panel Can Read Another Machine (`-host-ssh`)**: the panel that shows the
  Hygon host's memory and Pods used to read the machine the mock itself ran on — `/proc/meminfo`
  plus a local `kubectl get pods -A` — and its editable IP field only changed what the page
  displayed. Once the mock moved off the cluster host (running on a workstation, see the
  `--local` entry below) the panel was labelled 远程海光服务器 while every number in it came from
  the machine doing the displaying, and no setting could point it at the real host. `-host-ssh
  [user@]host[:port]` (`HOST_SSH`, `--host-ssh` on `deploy-platform-mock.sh`) makes the panel run
  those same two reads on the named host over SSH, so the numbers and the label finally agree. The
  source is all-or-nothing by construction — the memory figure and the Pod list always come from
  one machine, because the one combination that is worse than an empty panel is one host's memory
  under another host's Pods. The address the panel reports becomes the remote address (that is what
  an operator copies into TAA's `PLATFORM_IP`), and a new `target` field in
  `/api/host/status` says `local` or `ssh` with the destination. A malformed destination does not
  fall back to the local machine: it starts a probe that reports its own reason, so the fallback
  cannot reintroduce the mislabel. SSH credentials are never in argv — key auth is the default
  (`BatchMode=yes`, so a missing key fails in the connect timeout instead of waiting on a tty that
  is not there), and `HOST_SSH_PASSWORD` reaches `sshpass` through `SSHPASS`. ssh's own failures
  (exit 255) are reported as connection failures rather than echoed as if `kubectl` had said them.
  Because an SSH read costs a handshake and a remote `kubectl`, the snapshot cache now collects off
  the request path: a poll past the TTL gets the last snapshot and starts one background refresh,
  and only a snapshot older than the grace window (30 s) makes a poll wait. The host terminal in the
  API tester is unchanged — it still runs a shell on the mock's own machine, and the page says so.
- **The platform-mock Can Be Told Where Each Instance Answers (`-instance-targets`)**: the address the
  mock dials for an instance was derived from the registration's source IP and the TAA port, which is
  the instance's own address only while the platform shares a network with the Pod. A registration
  relayed across a NAT arrives with its source rewritten — a Kata Pod dialling another host is
  masqueraded to that host's IP — so the derivation named the relay and every instance ended up with
  the same wrong address, which no reachability check can repair because the address itself is a
  guess. `-instance-targets` (`PLATFORM_MOCK_INSTANCE_TARGETS`, `--instance-targets` on
  `deploy-platform-mock.sh`) records the real address per instance as comma-separated `dockerId=URL`
  pairs, e.g. `kata-csv2-taa-test-0001=http://172.16.10.178:31001`, which is what a NodePort Service
  per instance (see the deployment entry below) makes available. The precedence in `targetFor` is now:
  the address configured for that `dockerId`, then the single-instance `-taa-target` fallback, then the
  address derived from the registration, then the static target, then Pod discovery — a configured
  value outranks the derivation because it is the only one known to be routable from the platform's
  network, while everything below it is inferred. An instance without an entry keeps the old
  behaviour, so the map only has to name the instances behind a NAT. The configured value is also what
  the console and `GET /api/taa-target` report, so the address shown is the one actually dialled
  rather than a second derivation. A field that is not `dockerId=URL` (or whose URL has no scheme) is
  logged and skipped instead of turning the whole list into a startup failure, a duplicate `dockerId`
  keeps the later value with a warning, and a trailing `/` is trimmed from the target. Startup logs
  the parsed map so a typo is visible before the first task.
- **`deploy-platform-mock.sh` Can Run On This Host (`--local`)**: the mock was remote-only after the
  positional `local` word was removed, but the platform it stands in for does not have to run on the
  cluster host: a development machine on the same network, or a host that reaches the instances
  through their NodePort Services, is a legitimate place for it, and requiring an SSH hop there only
  added a second machine to keep in sync. `--local` runs the same lifecycle (build, start, stop,
  restart, status, readiness probe) against the local shell instead of SSH — `remote_sh` and
  `copy_to_host` dispatch on the mode, so every step keeps one implementation — and skips the SSH
  requirement entirely. Nothing is uploaded: the binary built under `bin/` is run where it is, since
  copying it elsewhere could only run a different file than the build produced, and the state, log and
  pid defaults move from `<remote-dir>` into the project's own `bin/`. The semgrep CLI is taken from
  the local `PATH` (e.g. `~/.local/bin/semgrep`) with no venv installation, and the rules are read
  from the working copy's `models/audit/semgrep/rules` instead of being packed and unpacked. `--llm-host`
  supplies the node address that the `--llm-target` default would otherwise take from `--host`, which
  local mode does not have; without either, startup stops with a message naming both instead of
  dialling an empty host. The catch this mode exists for: a local mock that is not on the cluster
  network has to name every instance with `--instance-targets`, because the derived address will be
  its own (the NAT it dialled through), not the Pod's. The positional `local` action word stays
  refused, so the action still comes first (`start --local`).
- **`deploy.sh` Publishes Each Instance On Its Own NodePort Service (方案 A)**: with the platform-mock
  moved off the cluster network, the platform needs an address for each instance that is routable from
  where it runs and that does not change when the Pod is recreated — the Pod IP gives neither. The
  obvious mapping, `hostPort`, does not solve it either: the CNI portmap plugin DNATs a `hostPort` to
  one Pod IP, so the mapping is tied to that Pod, and a recreated Pod leaves the platform dialling an
  address nobody owns. A `NodePort` Service is the different mechanism this needs: kube-proxy listens
  on the node and load-balances to whatever Pods currently match the selector, so the Service outlives
  the Pod and its port is allocated once. `create` therefore applies a Service of its own for each Pod
  it creates when `TAA_SERVICE_NODE_PORT` (`30000`-`32767`) is set — empty keeps the previous
  behaviour of reaching the Pod by its own address — with name `taa-<dockerId>` lower-cased and with
  `.`/`_` replaced by `-`, selecting on the `taa-instance-id` label (`TAA_INSTANCE_LABEL_KEY`) that the
  Pod template now carries. The selector is the registered identity rather than the Pod name so a
  replacement Pod under the same `DOCKER_ID` joins the same Service with no second edit, and for the
  same reason the Service is `kubectl apply`-ed rather than created: after a delete it simply has no
  endpoints, and the next create fills them in without touching the port. `delete` removes the Service
  together with the Pod so a half-deleted deployment keeps no route to nothing, tolerating its absence
  for deployments that never published. Since the `DOCKER_ID` has to be a Kubernetes label value,
  `validate_instance_label` checks it (at most 63 characters of `[A-Za-z0-9._-]`, starting and ending
  alphanumeric) **before** anything is built, and the derived Service name is length-checked as well,
  because a manifest rejected at apply time comes after tens of minutes of image build. The NodePort is
  deliberately explicit: it is an address the platform records, so it is allocated by the operator
  rather than by the cluster, and a port already owned by another Service fails the publish while
  leaving the Pod running (the message names the port and points at
  `kubectl get svc -o wide`), because publishing is what failed, not the instance. The platform side
  records the resulting `http://<node>:<port>` with `-instance-targets`.
- **The platform-mock Lists The Instances It Expects, Not Only The Ones That Reported**: the 平台注册
  card could only show an instance once it had registered, so an instance whose Pod never came up
  was indistinguishable from one that was never deployed, and a Pod deleted after registering left a
  row that stayed `已连接` until someone pressed 删除. The card is an inventory now. `-instances`
  (`PLATFORM_MOCK_INSTANCES`, comma-separated `type:dockerId`, `--instances` on
  `deploy-platform-mock.sh`) declares what the platform expects to receive — `tee`, `fhe` or
  `data-anaylsis` — and every entry is listed whether or not it registered, in the configured order,
  with `expected: true`. A registration is matched to its entry by exact `dockerId` and keeps the
  configured type, because the type is not observable: the registration body carries no server type
  field, `data-anaylsis` attests exactly like `tee`, and a TEE instance running without
  `/dev/csv-guest` reports exactly like FHE, so `registrationKind` is a guess the inventory replaces
  rather than supplements. A registration the inventory does not name is listed after it, so nothing
  actually running is hidden; a malformed or unknown-type entry is logged and skipped; with no
  inventory configured the endpoint behaves as before. `未连接` now covers both an entry that never
  registered and a row whose 检查连通性 failed — both mean nothing is answering at that identity, and
  the tooltip says which (尚未注册 versus an instance that may have been deleted) — and a failed check
  therefore turns a previously connected row into 未连接 instead of the old `已断开`. The per-row 删除
  action and `POST /api/instances/delete` are gone with the underlying `remove()`: the list is the
  inventory, so removing a row would only hide an instance the operator still runs, and an instance
  whose Pod is gone now reads 未连接 and recovers by itself when a Pod registers under the same
  `dockerId` again. Clearing one instance's records stays available through its register/report
  reset routes. A connectivity check addressed to an inventory entry that has not registered answers
  `该实例在清单中，但尚未向平台注册` instead of `指定的 dockerId 不存在`, which sent the operator looking
  for a typo in a name they had configured themselves. `defaultDockerId` is the first accepted
  registration as before — never an entry that has not answered.

- **The DCU Guest Resets The Card On The Way Out**: the host has no reset path for the K100_AI
  (`reset_method` is empty, the device does not advertise FLReset, and QEMU logs `vfio: Cannot reset
  device 0000:c3:00.0, no available reset mechanism` at both attach and detach), so every guest
  inherits whatever the previous one left in the chip. A guest that was computing and was then
  destroyed without a driver-level reset leaves the card in a state the next guest's probe cannot
  recover from — `gfx_v9_0_hw_init`, `RLC ucode load fail`, `ring kiq_2.1.0 test failed (-110)`,
  `probe failed with error -110` — and with no `/dev/dri` the CDI hook writes no spec and creation
  dies in the 100-second CDI timeout. The only recovery from that state is a host reboot. The guest
  side does have a reset path (`reset_method` is `bus`, and the driver exposes its recovery entry at
  `/sys/kernel/debug/dri/<minor>/gpu_recover`, which is what `hy-smi --hcureset` uses), so the DCU
  roles now ship a second guest hook at `usr/share/oci/hooks/poststop/guest-hycu-dcu-reset.sh`,
  which calls `hy-smi --hcureset -d <n>` — the vendor's supported entry point, not a reimplementation.
  The hook itself only covers the step hy-smi cannot do: mounting debugfs, which `taa-init` does not
  mount (it mounts proc and sysfs only) and without which the recovery entry hy-smi reads does not
  exist. Reading that entry is what triggers the reset, not writing: the driver registers it with
  `seq_read` and no write method at all, and its show callback calls `gpu_request_reset`, which queues
  the reset work and flushes it, so the read blocks until the driver is done.
  poststop is the one in-guest point that runs after the container's own processes are gone and before
  the VM is destroyed, which is exactly the ordering the driver's recovery expects: it kills every
  process holding the card (`kfd_kill_all_process_on!`, `kill process(pid:name)`), waits for them to
  leave (`wait all process gone ...`), then performs a BACO reset. Two things had to be fixed for that
  to work at all: `taa-init` mounted only proc and sysfs, so debugfs (and with it the recovery entry)
  did not exist — it is now mounted at boot, and the hook mounts it itself as a fallback — and the
  device minor is read from the card's own DRM node rather than assumed from `cardN`, so a guest with
  a display function in front of the DCU does not write to the wrong device. Scope is stated up front
  because it is narrower than "the card is now safe": the hook fires on the normal delete path only (a
  force-deleted Pod, a crashed shim, or a killed hypervisor skips it), and whether a successful reset
  leaves the card clean enough for the next guest has not been proven on hardware.

- **The platform-mock Console Shows Its Host, Splits Into Workspace Tabs, And Prints The Sealed Answer
  A curl Call Could Not Show**: an operator copied the console's generated `curl` for a TAA route and
  saw no result at all. The cause is the protocol, not the command: TAA seals every JSON response with
  SM2/SM3, so a direct call returns an envelope (`{dockerId, cipher, sign}`) whose business content is
  inside `cipher` — the console only reads plaintext because it calls through the mock's `/taa` proxy,
  which unseals. The generated command is now two steps: the first goes to TAA itself, saving the sealed
  body to `/tmp/taa-response.json` and printing only `HTTP <code>` (the one readable signal a sealed
  response offers), and the second posts that file to the new `POST /api/taa/open-response`, which opens
  it with the instance's registered TAA key and prints the business JSON — or, when the body is not an
  envelope at all (the call never reached TAA), prints it verbatim, because an `无法解封` wrapper would
  hide the only useful line. The endpoint also works for a hand-written command that names no instance:
  TAA does not put its `dockerId` in the response envelope, so with no `dockerId` query parameter every
  registered key is tried and the first that verifies wins — the ciphertext still has to open under the
  platform's own private key and the signature still has to verify under a key some instance registered,

  refused. Verified live against the Pod at `10.244.0.135`: `health` returned `HTTP 400` with the

- **The DCU Initrd Ships The Vendor HYCU Userland And Starts `hymgr`**: a DCU guest loaded the

- **TAA Is Restarted Inside The Initrd**: `taa-init` backgrounded TAA once and then `exec`'d kata-agent, and nothing in the initrd respawns a dead daemon. A crash therefore left the VM and the Pod up while registration, heartbeats and `/v1/taa/*` were silently gone, with no log line saying so. The final exec is still the only exit path, so the wrapper now starts a `supervise_taa` subshell instead: it waits on each TAA process, appends the daemon log across restarts, and retries with exponential backoff — `TAA_RESTART_DELAY` starts at 5s, doubles up to `TAA_RESTART_MAX_DELAY` (60s), and resets after a run of at least `TAA_RESTART_STABLE_SECONDS` (60s). The subshell outlives the `exec` because it is not the process being replaced; PID 1 still never waits on it, so kata-agent starts immediately. Three safety details matter because the loop is the only guardian: a non-numeric backoff or log-size value falls back to its default instead of reaching dash arithmetic, where an error is fatal and would kill the supervisor silently; the supervisor logs its own exit to the console; and `/tmp/taa.log` is rotated to one previous generation once it exceeds `TAA_LOG_MAX_BYTES` (1 MiB) before each launch, since `/tmp` is tmpfs and an unrotated crash loop would grow guest RAM. `taa-init.sh` is measured code, so an already-built initrd keeps the old single-shot behavior until the package is rebuilt.
- **The containerd Drop-In Is Seeded Once, Owned By The Package, And Reversible**: the previous installer regenerated `config/containerd-runtimes.toml` from the host on every run, so the package had no copy that an uninstall could edit, and the handler names did not say which device family a role belonged to. Handlers are now `kata-qemu-nondcu-csv2-taa-*` for the CPU-only CSV2 roles and `kata-qemu-dcu-csv2-taa-*` for the DCU roles (runtime_type is unchanged — the handler is just the containerd map key). `install.sh` now seeds `config/zz-taa-runtimes.toml` only when the package has no copy: it takes the last file under `/etc/containerd/conf.d` that defines runtimes (excluding `zz-taa-runtimes.toml` itself), appends this package's handler, and installs the result as `/etc/containerd/conf.d/zz-taa-runtimes.toml`. Reinstalls reuse the package copy (still carrying handlers other TAA packages installed from the live drop-in), so the package owns the snapshot instead of silently following host edits. Each package now ships `uninstall.sh`, the reverse of the containerd step: it removes this package's handler from the installed drop-in — the live file is the superset, so another TAA package's handler cannot be lost — writes the result back to the package copy, and overwrites the installed file; if no `kata-qemu-nondcu-csv2-taa-*` / `kata-qemu-dcu-csv2-taa-*` handler remains, it deletes the drop-in so containerd falls back to the host's own file. Both scripts verify the result with `containerd config dump` and roll back on mismatch. `render.py` gained `containerd-handlers`, `containerd-remove`, and `--base` for `containerd-dropin`; `build-initrd.sh` ships and checks the new script, and the rendered README and deploy template show the uninstall command. **Config edits take effect only on containerd restart** — containerd does not watch its imports — which both scripts do after a change, and running Pods are not killed by it because their shims are separate processes.
- **DCU Full-Encryption Delivery Packages (`taa-train-dcu` / `taa-infer-dcu`)**: the initrd flow built packages only for the CPU-only CSV2 runtime, but the host also runs a Hygon DCU full-encryption class, whose guest kernel is different (`6.6.0-hycu-confidential-csv+`), whose Kata template is `configuration-qemu-hygon-dcu-csv2.toml`, and whose `hycu`/`hycu-sched` drivers are **out-of-tree modules** that exist only inside the DCU guest image's rootfs. The two new roles derive everything from the role the way the CPU roles do: `CONTRACT_TYPE` 1/2, handler `kata-qemu-hygon-dcu-csv2-taa-*`, runtime_type `io.containerd.kata-qemu-hygon-dcu-csv2.v2`, package directory `package-train-dcu`/`package-infer-dcu`, a DCU test image and 20480 MiB of guest RAM. `build-initrd.sh fetch-base` now extracts the module tree, matching firmware and `/usr/bin/kmod` from that image (read-only loop mount, nothing left on the host) into the untracked `base/dcu-payload/`, and the seed cache carries them as a fifth payload kind (`format=3`); the base initrd has no kmod, no modprobe, no udev and no systemd-modules-load, so **nothing would ever load the driver otherwise**. The new identity token `taa.modules=hycu` rides the kernel command line like the other `taa.*` tokens, and the guest's prestart CDI hook runs `modprobe` for each name before it looks for the card (see the entry below for why the load sits there and not in `taa-init`); a failed load is logged and container creation is left to fail with the agent's CDI timeout instead. The test Pod requests and is limited to `hygon.cn/k100_ai`, which is what gets the device into the guest. The package supplies the guest side only — TEE VBIOS, the card bound to `vfio-pci`, host IOMMU, the `cc_init_data` annotation and a DTK-tee image remain host prerequisites — and loading `hycu` from the initrd is new until a DCU Pod boots.
- **The Execution Environment Is Selected By Configuration (`runtime.execution`)**: the container target existed but nothing chose it. `runtime.execution.mode` now does, with three values and one default. `auto` (the default) runs a model inside a container only on an initrd deployment where one is discoverable and otherwise stays local with a warning — the only value that is right on both deployment shapes without being told which one it is. `local` forces the pre-existing behaviour, the rollback switch. `container` fails the task when no container can be discovered instead of running in an environment that may lack the interpreter the model needs. `containerId` disambiguates when several containers are running; the path overrides (`modelDir`, `inputDir`, `outputDir`, `logDir`, `progressPath`) describe the contract the model executes against inside the container; an empty value keeps the packaged `/opt/taa/…` default, and an override must be given as a whole path, since the contract is taken as a set. Overrides are validated at load — absolute, clean, not `/` — because they are cleared before each run, and a `..` under a container root deletes something the deployment never named. **The choice is made per task, not at startup**, and that is the load-bearing detail: on the initrd path TAA is the first userspace process and the container is created later by kata-agent, so a target discovered at boot would always be absent on exactly the deployment the seam exists for. What startup does is state the policy; every run states its own outcome — `local (mode=local)`, `local (mode=auto: 非 initrd 部署)`, `container (pid=…, rootfs=…, 契约路径 …)`, or the fallback/failure and why — on the platform log channel as well as the console, because "the model ran in the wrong place" is the first question when a task misbehaves and a Pod offers no console. `Discover` gained a `Paths` option so the override reaches it, with the zero value meaning the packaged default; the paths are validated by the first `Prepare`, before a byte is staged. With no `runtime.execution` block the daemon resolves `auto`, the deployment is not an initrd in the shipped container templates, and every existing deployment takes the local path it always did.
- **A Container Execution Environment (`internal/execenv` container target)**: on an initrd deployment a model's interpreter and dependencies exist only inside the container image, so the model has to run in that container's namespaces while TAA keeps running outside them. `execenv.ContainerTarget` provides that: `Discover` scans every distinct mount namespace under `/proc` and keeps the ones whose root is not the initrd's `rootfs`; it then finds where that container's root is mounted in TAA's own view by matching the **device number** of the root mount, not by a Kata path convention, falling back to the `…/rootfs` suffix only with a warning; ambiguity is an error rather than a guess, with `ContainerID` (matched against the overlay upperdir) as the only way to choose. The candidate must pass a probe — a shell starts in its mount namespace and the container root is writable from TAA's side. `Prepare` refuses contract paths the container mounts separately (staging through the overlay would look like a missing dataset), checks that the model and dataset fit in the container's writable layer before copying a byte, clears what a previous run left, and stages the model and dataset with a copy that refuses symlinks and special files — clearing first is what makes the copy safe, since nothing it creates afterwards can pre-exist. `Command` wraps the shell in `nsenter -t <pid> -m -r` and keeps `Setpgid`, so a stop still SIGKILLs the whole tree. Two interface changes came with it: `Visible` returns an error because mapping a path back through a symlink or out of the root must fail rather than guess where TAA writes, and `Target` gained `BaseEnv` because the container-executed model must **not** inherit TAA's environment — it carries `PLATFORM_PUBLIC_KEY` and `TAASECRETKEY`, and the model is exactly the code the platform is watching. `LocalTarget` keeps returning `os.Environ()`, so nothing changes for existing deployments. This is groundwork: the daemon does not select a container target yet, which lands with the log/result plumbing that a real run needs.
- **Deployment Shape Is Declared, Not Guessed (`TAA_DEPLOYMENT`)**: TAA runs either as the CSV2 initrd's first userspace process or as a container image entrypoint, and the two need different things from the same binary — starting with where a model's `runtimeConfig` should execute once the model's own runtime lives in the container image rather than in the initrd. Nothing in the process said which it was: the kernel command line's `rdinit=` is VM-wide, so a container inside an initrd-booted VM sees it too, and the parent/PID/cgroup heuristics were measured inconclusive. The starter scripts now declare it — `taa-init.sh` exports `TAA_DEPLOYMENT=initrd`, each `taa-supervisor.sh` exports `TAA_DEPLOYMENT=container` outside the byte-identical `TAA_LOOP` block — and environment does not cross namespaces, so neither side can inherit the other's value. `internal/deployment` reads the marker; a value that is neither `initrd` nor `container` fails startup, because only a typo in a starter script can produce one. When the marker is missing the shape is inferred from the root mount's fstype (`rootfs` is the initrd's ramfs, anything else is a container root) and reported as a warning, since the marker exists to make the misconfiguration visible rather than to paper over it. Startup prints the shape, its source, the raw marker and the observed fstype to the console and, once `TAAState` exists, to the platform log channel (`component: "deployment"`), so a Pod with no console access still shows what TAA believed it was. The shape is a deployment fact that only selects where model work runs — it never feeds a security verdict — and this change alters no runtime behaviour.
- **The Initrd Delivery Package Is Built Per Role**: `build-initrd.sh` and `deploy-taa-vm.sh` take a `taa-train` / `taa-infer` / `taa-analysis` role argument, defaulting to `taa-train`, and the role decides everything that has to differ between them: the baked `CONTRACT_TYPE` (1 training, 2 inference, 3 data analysis — the same mapping `internal/config` already applies to the Pod environment), the runtime handler, the delivery directory on the host (`/root/taa-images/package-train`, `-infer`, `-analysis`), the test Pod name, the default test image and the output initrd. Those cannot be shared: the Kata config lives inside the package and containerd's `ConfigPath` points at it, so two roles under one directory or one handler would silently boot each other's kernel and initrd, and a Pod's role cannot be changed in place. Both identifiers carry the role suffix, training included: `kata-qemu-csv2-taa-train` and `/root/taa-images/package-train`, next to `-infer` and `-analysis`. The bare `kata-qemu-csv2-taa` and `/root/taa-images/package` are no longer produced, so a host still running an older train package has to be re-installed once, and the old handler, RuntimeClass and directory removed by hand. **Only `taa-train` carries the semgrep payload** — inference and data analysis do not audit code where it lands, so their initrd is now ~69 MB compressed instead of ~160 MB, and the payload requirement (`initrd_wants_semgrep`) is the conjunction of the role and the injected config instead of the config alone. Their injected config is the shared production template with `codeAudit.codeScan.engine` rewritten to `regex`: the role turns the audit off anyway, and leaving `semgrep` in place made every boot resolve an engine it cannot construct and log the fallback warning. Two follow-ons: the data-analysis role defaults to the jupyter base image, whose named user cannot be resolved under the nydus guest-pull snapshotter, so `render.py k8s` gained `--run-as-user` and that role renders `runAsUser: 0`; and an inherited `TAA_CONTRACT_TYPE` is now reported and discarded rather than obeyed, since a package whose directory says "infer" while the guest audits like a trainer is a defect nothing downstream would catch.
- **The Delivery Flow Can Stop Before Installing**: the flow had no way to stop between "the package is on the host" and "the host has been reconfigured". `launch` always ran `install.sh`, so placing a package on a node whose handler was still in use — or handing one to somebody else to install — meant either doing the install anyway or running the four steps by hand and remembering that `render` must precede the `scp`. The compile-build-render-upload flow does exactly steps 1-4: it recompiles `bin/taa`, builds the initrd, renders the package and uploads it whole to `REMOTE_PACKAGE_DIR`, then prints the one command that installs it. `build-initrd.sh` gains the matching `upload` (render + upload, steps 3-4), which the flow calls; `launch` is now `upload` plus the `install.sh` ssh, so the two paths share one renderer and one placement function instead of two copies of the scp-and-move logic. Nothing on the host changes except the files: no containerd edit, no RuntimeClass, no Pod. The package itself is replaced atomically (staged in a temporary directory, then moved into place as root), so an interrupted upload cannot leave a half-written bundle where the running handler expects one.
- **platform-mock Polls The TEE-LLM At Its Host Address**: the console's TEE-LLM card showed the Pod IP that kubectl discovery returned, and every `/v1/llm/*` call went to that IP — an address that changes on each recreation of the Pod, and one TAA's deployment no longer needs now that the plaintext platform listener is published on the node (`6001 → 16001`). `deploy-platform-mock.sh` now starts the mock with `-llm-target http://<--host>:16001` (`PLATFORM_MOCK_LLM_HOST_PORT`) when neither an explicit target nor a discovery flag is given, so the card displays the host address and the mock's path performs no kubectl lookup at all. `--llm-target` still wins when given; any of `--llm-pod` / `--llm-ns` / `--llm-port` switches back to Pod-IP discovery for a host that publishes no port, and the start log names which of the two is in effect. A mock already running keeps its old target until it is restarted.
- **The TEE-LLM Pod Publishes The Platform Listener Too (`6001 → 16001`)**: the Pod mapped only the service's `8443` to the node's `18443`, so `/v1/llm/heartbeat`, `/v1/llm/log` and `/v1/llm/getAttestation` on the plaintext `6001` were reachable at the Pod IP alone — an address that changes on every recreation and, from off the cluster network, not at all. A second `ports` entry now maps `6001` to the node's `16001` (`TEELLM_POD_ATTESTATION_HOST_PORT`), which is also the one of the two a person can call with curl: `8443` speaks RFC 8998 ShangMi TLS and drops a plain `curl`/`openssl` handshake, while `16001` answers ordinary HTTP. Each variable set to `0` stops publishing only its own mapping, so a host that can spare one port still gets it. The creation preflight now validates both numbers, refuses two container ports sharing one host port, and checks each host port against the host's listeners and other Pods' declarations before the image build — Kubernetes only rejects a duplicate `hostPort` at scheduling time, which on this path is tens of minutes after the build started. The manifest template, `deploy.md`, the README and the deploy test follow.
- **TEE-LLM Reports A Per-Process `dockerId` On Every Platform Response**: the platform could only tell a restarted TEE-LLM instance from a running one by watching `uptimeSeconds`, and the mock quantizes that into a run id, so a restart inside one bucket was indistinguishable and the log cursor was not reset. `teellm-service` now generates `teellm-<10 random digits>` when the process starts (crypto/rand, in `NewServer`) and puts it at the top level of the `{msg, result, error}` envelope on all three platform-facing interfaces — heartbeat, log pull and attestation — including their 4xx/5xx responses, so one decoder reads it no matter which endpoint answered. It is deliberately neither configurable nor derived from the Pod address: the value has to change on exactly every process start, and a knob or an address-derived id would let it fail to. The platform keeps the last value it saw and reads a change as "this instance was rebuilt". The startup line `instance dockerId=...` is also written to the run-log ring, so the platform's log view carries both halves of a restart. The platform-mock reads it too: its TEE-LLM card displays the id, and a changed id is now the exact trigger for resetting the log cursor, with the old uptime-quantized run id kept only as a fallback for an instance that reports none.
- **Pod Creation Builds And Pushes The Image It Runs**: a deployment-owned Pod used to start from whatever `TAA_POD_IMAGE` named (the registry's mutable `taa-env:slim-v2`), so a new Pod could run a binary older than the tree being deployed. When `TAA_POD_IMAGE` is not set, `deploy.sh` now assembles the production image through the same code path as `docker save`, uploads the archive to the remote host, and pushes it as `TAA_POD_REGISTRY/TAA_POD_IMAGE_REPO:<YYYYMMDD>` (default `taa-train-infer:<today>`). Because the tag is a same-day, mutable tag, the push is conditional on content: the registry manifest's config digest is compared with the image ID Docker reports locally, an identical build is left untouched, and a different one has its old manifest deleted before the tag is repushed. The created Pod then pulls with `Always`, since a cached copy under a mutable tag would defeat the rebuild; an explicitly pinned `TAA_POD_IMAGE` skips the build and keeps `IfNotPresent`. An existing Pod is still reused and never recreated, so a new image reaches it only after `stop` deletes the Pod and its guest writable layer.
- **`deploy.sh` Owns A TAA Pod When `TARGET_POD` Is Unset**: remote mode used to require a Pod that already existed, and its fallback name pointed at a Pod that no longer exists on the host, so a first deployment could not proceed at all. Leaving `TARGET_POD` unset now makes the deployment create a dedicated `kata-qemu-csv2` Pod from `deploy/manifest/k8s/taa-pod.yaml.tmpl` (`TAA_POD_NAME`, default `taa-deploy`), wait for Ready, gate on `/dev/csv-guest`, and pause the daemon baked into the image before the scan engine is provisioned. Later runs reuse the Pod, and `stop` deletes it along with its guest writable layer; an explicitly named Pod is never created or deleted, and `stop` still deletes an owned Pod it cannot exec into. The Pod's registration identity has to arrive through the environment because the remote config path strips the `platform` block; the LLM endpoint is deliberately **not** an env var, since an env value outlives every deploy and would override the endpoint rewritten into `taa-config.json` each run. Creation uses `kubectl create`, not `apply`, so a race cannot rewrite an immutable Pod spec, and a Pod that exists but does not become Ready fails the reuse path with its `describe` output instead of a later, misleading readiness timeout. `cc_init_data` is derived from an existing CoCo Pod (or `TAA_POD_CC_INIT_DATA`); the runtime-handler annotation is not copied and `kernel_params` stays non-empty, both for the reasons `deploy-llm.sh --create-pod` documents. A run that does not deploy TAA keeps its previous target, so `remote platform-mock` is unaffected.
- **Concurrent Multi-Instance platform-mock**: one process now serves several TAA instances; state, reports, progress and logs are isolated by `dockerId` under `<state-dir>/instances/`, and per-instance SM2 public keys are isolated by `dockerId` in `<state-dir>/platform-key.json`; legacy single-instance state migrates at startup; outbound addresses are derived from each registration's source IP, so `-taa-target` is now the single-instance fixed address and the fallback; the console gains an instance selector and `GET /api/instances`, and `/taa/*` routes per `?dockerId=`. `deploy.sh` and `deploy-fhe.sh` no longer start the mock, so multi-instance is the default of `deploy-platform-mock.sh` whenever `--taa-target` is omitted. Known limitation: the source IP is lost behind a reverse proxy or port forward — keep using `-taa-target` there.
- **`codeAudit.llm.attestation.skipChainVerify`: Verify The PEK Signature Without The Certificate Chain**: TEE-TLS has always required a locally trusted HRK to accept the gateway's report (`VerifyChain: true`, and a missing anchor is `ErrMissingCertChain`, not a degrade), which a container that no longer carries the vendor certificates cannot satisfy. The new key, off by default, makes the verifier check exactly what the report proves about itself — the PEK certificate embedded in the report signed the report body — while skipping the HRK → HSK/CEK chain that would anchor that certificate to a vendor root. The public-key binding and measurement checks are unaffected, so a peer still has to hold the private key for the certificate it presented and still has to match `attestation.measurement` when that is set; `insecureSkipVerify` remains the stronger switch that skips all of it. The verifier logs a startup warning when the chain is skipped, because internal consistency is all the verdict then rests on. Implemented as `teetls.Config.SkipChainVerify` (nested `teetls` submodule; zero value keeps the chain required) and plumbed through `internal/codeaudit.LLMConfig`. All three shipped templates that carry a `codeAudit.llm` block (`taa-production`, `taa-docker`, `taa-initrd`) now set it to `true`, so a stock deployment matches the certificate copies that were dropped from the image and needs no vendor files; the code default stays `false` for any configuration that does not name the key, and `TestLoadStartupConfigTemplateFiles` pins the template value.
- **Durable Outbox For Terminal Platform Reports**: every terminal report TAA sends the platform — `reportRes`, `reportModelImport`, `reportAudit` — used to be a single `POST` whose failure was written to a local log and forgotten, so a training run that finished while the platform was unreachable left the platform's view stuck at "running", and a TAA restart could not repair it because a completed task has no `activeTask` left for the recovery path to key on. Reports are now appended to `PendingReports` inside the existing sealed state (`internal/store`, SM4-GCM, atomic fsync, same `StateSeq`), so the queue inherits crash consistency from the state file rather than a second sealing scheme, and a background worker drains it with per-entry exponential backoff from 1s to 60s, repeating until the platform acknowledges — no expiry, no window. At-least-once is the contract: a crash between the platform's 200 and the local seal replays the report, so the platform must stay idempotent per `(dockerId, requestId, taskId, endpoint)`; no dedup table is kept. Retry is **per entry rather than head-of-line**: an entry captured against an address that no longer answers would otherwise block every later report forever, a starvation the FHE tests exposed when a stale `modelImport` froze the queue — ready entries are still delivered in enqueue order, so the natural `modelImport → audit → reportRes` sequence is preserved. `PlatformAddr` and `DockerID` are stored with each entry so a config change cannot redirect an old report to a different platform; an entry with either empty is refused at enqueue (a deployment error, not a transient outage) rather than queued forever. The crash-recovery path's old 2-second-sync + 60-second-backoff worker and `reconcileAbandonedAudit`'s direct call both enqueue now, and the abandoned-audit path enqueues before clearing `AuditPending` so the two steps cannot lose the report to a crash between them. Retry failures log to stderr rather than `s.Logs`, which would feed the retrier's own noise back into the `taaLog` channel; a successful redelivery writes one `LogInfo`. Streaming reports (`modelLog`, `reportProgress`, `taaLog`) are deliberately excluded — they are lossy by nature and a durable queue is the wrong shape for them.
- **SM2 Envelope On Every TAA ↔ Platform Message (`{cipher,sign}`)**: every request the platform sends to TAA and every JSON response TAA sends back is now sealed to the peer's SM2 key and signed over the plaintext, instead of travelling as cleartext JSON. The framing is `{dockerId, cipher, sign}`: `cipher = base64(SM2_Encrypt(recipientPub, utf8(plaintext)))` in raw C1C3C2, `sign = base64(DER(r,s))` computed over the **plaintext** bytes. Signing the ciphertext would let anyone holding the platform public key mint a message TAA's own routes accept, which is why the ordering inside `internal/platform/envelope` is encrypt-then-sign-plaintext and the inbound side decrypt-then-verify-plaintext-then-return — the returned bytes are already verified, so no handler can parse an unverified body. The new package is transport-agnostic; `internal/controller/envelope_middleware.go` is the HTTP half, mounted **inside** `postOnly` so a method rejection is still a 405 rather than "missing cipher/sign". `/v1/taa/fheCallback` is the single unsealed route, and its exemption is explicit: the caller is the FHE service on container loopback, it has no platform private key to seal with, and it keeps its loopback-source check instead. Successful `export` responses remain `application/octet-stream`; export *errors* are sealed JSON, which the platform accepts. Responses go through the existing `writeJSON` family, so all 74 call sites are untouched — the sealed branch uses `json.Marshal` (no trailing newline, because the newline would become part of the signed plaintext) while the plaintext branch keeps `json.Encoder` byte-for-byte. **The platform public key has no default and no fallback**: `PLATFORM_PUBLIC_KEY` (or `platform.publicKey` in the startup config, with the environment always winning — unlike `platform.ip`, where the file wins on a `tee` instance, because an operator setting the key is rotating a credential and a stale baked-in key would make the rotation look applied) is required, and startup refuses to continue without it, before attestation and before the first registration. The signing identity `PLATFORM_SM2_ID` is environment-only and defaults to `1234567812345678`; it is used as raw UTF-8 bytes with no trimming, because SM2 folds the ID into `ZA` and a mismatch surfaces only as "signature invalid" on the receiving side, so the effective ID is logged at startup for comparison. Outbound sealing is one seam at the bottom of the send path (`platform.SealOutbound`, installed from `app.go` with the `dockerId` bound), which covers registration and all six reporting functions; the one sender that owns its own POST (`controller.sendReportingJSON`) applies the same seam. A sealing failure aborts the send — there is no plaintext fallback on either side. **Operational consequence**: `health` and `status` are sealed too, so no local probe can reach them, and the deploy scripts' readiness checks move to a TCP connect on `:6001` plus a confirmation of the `taa service listening on` log line. Configuration templates gain `platform.publicKey`, and an un-templated deployment will crash-loop until the operator supplies a key.
- **FHE Task Logs Reach The Platform (`/v1/taa/modelLog`)**: on an `fhe` instance the model runs inside the FHE service, so the training-side log watcher — which tails `model.output.log` — has nothing to read and the platform's terminal view stayed empty for the whole run. `internal/fhe` now exposes `Client.TaskLogs`, which asks the service for `/tasks/{id}/logs?follow=false`: the endpoint defaults to `follow=true`, which returns only when the task ends, so polling it without that parameter would be a second, slower copy of the callback. A poller in the controller replays the log every 2 seconds while `executeFHETask` runs and forwards new lines as `modelLog` entries (`component: "fhe"`, contiguous `seq`) in batches of at most 100; an entry stays queued until the platform acknowledges it, so a failed report is retried under the same sequence numbers instead of leaving a hole. Because each replay returns the whole log, the poller keeps the byte offset it has already accounted for, and a replay that does not start with the previous one is treated as a restarted log (a `continue` re-run of the same task id) and reported from the top. Only complete lines are taken — the service redraws progress bars with `\r`, so both `\r` and `\n` terminate a line — with an unterminated tail held for the next replay and flushed once the run ends. - **TAA Key Recovery Across Guest Rebuilds (`taaSecretKey` / `TAASECRETKEY`)**: The CSV2 guest keeps `storage.keys` in its in-memory rootfs, so recreating the container lost the SM2 key pair and left the platform holding a stale public key with no way to restore the private half. Registration on a `csv-hw` instance now carries `taaSecretKey = hex(SM4-128-GCM(SM3(hardware sealing key || CONTRACT)[:16], D))`, where `D` is the raw 32-byte private scalar — 60 bytes of ciphertext, 120 hex characters, no PEM. The platform stores it and, when an instance needs its identity back, injects it as `TAASECRETKEY`: TAA fetches the same hardware sealing key, decrypts, recomputes `Q = d·G`, archives any conflicting key files as `*.bak.<unix>`, and registers with the field omitted (the JSON tag is `omitempty`). The variable wins over the keys directory and is idempotent across restarts. Failures are fatal rather than silently ignored: a wrong hardware key, another `CONTRACT`, malformed hex, a wrong ciphertext length, or a scalar outside `(0, N)` aborts startup. Instances without the CSV hardware key (Docker, FHE; `stateSealingKeySource: "sm2"`) neither export the field nor accept the variable. The hardware sealing key is fetched once per boot and shared with the `csv-hw` state sealing path, so key recovery leaves `state.sealed` untouched — its key does not depend on the SM2 pair. Failed register dumps now redact the field instead of logging the ciphertext, the platform mock stores and displays it, and the API docs and OpenAPI schema describe the construction.
- **Dedicated TEE-LLM Pod For Attested Inference (`deploy-llm.sh remote --create-pod`)**: `teellm` can now run in its own `kata-qemu-csv2` Pod instead of a plain Docker container, which is what makes its attestation report real. ### Changed
- **The Attestation Chain Is Walked Again, And Every Packaging Path Carries A Machine's Own**:
  verifying only the signature embedded in the report's PEK proves that the PEK signed the bytes
  that follow it — something anyone able to write the report can produce — and says nothing about
  where that PEK came from, which is the question attestation exists to answer. TAA's boot
  self-check therefore walks HRK → HSK/CEK → PEK again, reading `hrk.cert` and `hsk_cek.cert` from
  the first directory that holds both, searched in order `/root/taa/certs`, `/etc/taa/certs`,
  `deploy/certs`. A missing pair is an error, not a silent fallback to the weaker check; the caller
  still only logs a WARNING and carries on with `verifiedPass=false`, so the process starts, though
  the instance registers with the platform as unattested until a chain matching its report is
  installed. The shipped templates stop opting out of the chain the code already
  required: `configs/taa-production.json` and `configs/taa-docker.json` no longer set
  `codeAudit.llm.attestation.skipChainVerify` (previously `true`), and `taa-docker.json` no longer
  sets `insecureSkipVerify`. The TAA → TEE-LLM handshake now verifies the gateway's certificate
  chain by default, which is what the code defaults already said (`skipChainVerify=false`,
  `insecureSkipVerify=false`); the template overrides existed only because no image carried the
  vendor files. The TEE-side packaging paths now install `deploy/certs/hrk.cert` and
  `deploy/certs/hsk_cek.cert` at `/root/taa/certs` — the TAA production image built by
  `deploy.sh save`, the remote TAA container, the CSV2 initrd guest rootfs (`build-initrd.sh`) and
  the TEE-LLM Pod (`deploy-llm.sh`) — and a missing file fails that build or deploy instead of
  shipping an artifact whose chain is knowably absent. `teellm-service` drops its own hardcoded
  `InsecureSkipAttestationVerify: true`: a client that requests mutual attestation is now actually
  verified against the chain and its CSV evidence instead of being accepted blindly, while mutual
  attestation stays off by default (neither side requires it, and
  `codeAudit.llm.requireMutualAttest` remains `false`). `teellm/configs/teellm-production.json`
  moves `attestation.mode` from `"strict"` to `"permissive"`, because strict rejects every verified
  peer when no expected measurement is configured, and the service has no setting for one. **The
  chain is per machine.** `deploy/certs` holds the development host's pair, so a deployment on any
  other machine reports `verifiedPass=false` and the TAA → TEE-LLM handshake fails, which
  `failClosed=true` turns into rejected imports; such a deployment must install its own
  `hrk.cert`/`hsk_cek.cert` at `/root/taa/certs`. Adding the files to the initrd changes its bytes,
  so the guest's boot MEASUREMENT changes too.

- **The DCU Guest Loads `hycu` From Its CDI Hook, Not At PID 1, And A Pod Restart Waits For The Card**: the DCU initrd loaded the driver in `taa-init`, i.e. in PID 1's first millisecond, while the vendor guest it has to match loads it from systemd/udev on device discovery, after the agent is up. That load timing was the one remaining difference between the two guest shapes, and it is now removed the only way that does not touch the driver: the prestart hook reads `taa.taa_modules=` from `/proc/cmdline` and runs `modprobe` itself, which is the last userspace point before the container that needs the card and therefore the same lifecycle position as the vendor's udev. Because the hook now also spans firmware load and probe, its DRM wait default rises from 10 s to the vendor's 240 s; failures still leave no spec, so the agent's CDI timeout remains the only failure a container sees. The same hook applies the vendor udev rule's `0666` to `/dev/dri/card*`, `renderD*`, `kfd` and `mkfd`, since this guest has no udev and a container may run as a non-root user. On the teardown side, `test/create-test-pod.sh` and `test/delete-test-pod.sh` now wait until no process holds the card's `/dev/vfio/<group>` (groups derived from `/sys` vendor `1d94`, open descriptors found under `/proc`) before another VM may start: `kubectl delete --wait` returns when the Pod object is gone, while the shim can still be releasing QEMU, and a second VM on an unreleased card is the one ordering mistake this path can make. - **Deployment Identity Travels In The Pod's `kernel_params` Annotation, Not A File In The Package**: `config/env.txt` existed so an operator could change the platform address, docker id or LLM endpoint without re-rendering, and `install.sh` re-rendered `config/kata-config.toml` from it. That made the packaged Kata config operator-dependent, so it could not be pinned by `SHA256SUMS`, and it put identity in a file whose name said nothing about where the guest actually reads it. Kata appends a non-empty `io.katacontainers.config.hypervisor.kernel_params` annotation to the config's own parameters and last-wins on duplicate keys, so the tokens (including `taa.taasecretkey`) now live in the delivered `test/test-pod.yaml` annotation: `render.py k8s` gained a repeatable `--kernel-param` and merges the tokens into that annotation (refusing whitespace-bearing values), and the new `render.py pod-kernel-params` reads the merged value back. `install.sh` no longer re-renders anything — `config/kata-config.toml` is identity-free and is now covered by `SHA256SUMS`, with only `test/test-pod.yaml` excluded because it is the file the operator edits. The measured command line is the config's parameters plus the annotation, so both `build-initrd.sh` and `test/create-test-pod.sh` read the annotation from the manifest they ship or apply instead of re-deriving the merge. **Per-Pod consequence:** identity is now a property of each Pod, not of the node — every consumer Pod must carry the same annotation (`install.sh` prints it), and an empty annotation leaves the guest with no registration identity at all.
- **Kernel-Command-Line Identity Keys Are Now The Environment Variable Names, Lower-Cased**: the `taa.<key>` tokens used short local names (`taa.llm_endpoint`, `taa.addr`, `taa.modules`), so `taa-init` needed a hand-maintained mapping table and every new setting was a code change in the measured boot script. Keys are now the environment variable's own name in lower case — `taa.taa_llm_endpoint`, `taa.taa_addr`, `taa.taa_modules`, `taa.taasecretkey` — and `taa-init` exports every well-formed `taa.<key>` after upper-casing it, with no allow-list; a name must match `[a-z][a-z0-9_]*` or it is skipped. That widens what a host-provided command line can set, but the host already chooses the kernel, initrd and boot parameters, so the shorter list only hid that fact. `render.py` keeps its key list for typo detection in `config/env.txt` and now drops every `taa.*` parameter on a re-render, so a token left by an older render cannot shadow the edited file. **`TAASECRETKEY` can now ride this channel as `taa.taasecretkey`**, closing the one identity setting the initrd path had no way to receive; the value is the platform's stored SM4-GCM ciphertext of the private scalar, not the raw key, so a host reading `-append` can replay it into TAA but cannot decrypt it. Older packages and `env.txt` files that still use the short names must be re-rendered or edited, because the short forms now export different, unused variables. The file and the re-render step described here were both removed — see the entry above.

Rendered packages no longer carry `config/zz-taa-runtimes.toml`, so a package directory can be deleted without affecting the table another package installed.

- **A Training Run Now Goes Through The Execution Target End To End**: `executeTraining` resolves one `execenv.Target` per run and uses it for everything the run does to the filesystem — `Prepare` stages the model and dataset into the target's view, the environment receives `TAA_LOG_DIR` and `TAA_PROGRESS_DIR` mapped by `Resolve`, the command runs through `runRuntimeConfigWithTarget`, and the result is copied back from `Visible(outputDir)` into the export directory. Package size rises from ~1 MB of configuration to ~165 MB, almost all of it the initrd.
- **Instance Types 1-3 Do Not Register Until They Can Prove Themselves**: startup used to generate the attestation report for every non-fhe role and register immediately, so a missing `/dev/csv-guest` degraded to an empty report with `verifiedPass=false` — and since there is no periodic re-registration, the platform never saw that instance attested even after the node appeared. That race is the normal case in a Kata CSV2 Pod: TAA is the container's first process, while the node is created by a postStart hook. Registration now goes through `registerInstance` (`internal/app/taa/startup_gate.go`): `fhe` (type 4) keeps the old behavior — an empty report, `verifiedPass=false`, register now, retry in the background — while types 1-3 (`tee` training/inference and `data-anaylsis`) start a background gate that polls the device (5s doubling to 30s, no attempt limit, throttled logging), then generates and self-verifies the report, and only then registers with `verifiedPass=true` and the usual unbounded retry on platform errors. Until the gate succeeds nothing is sent, so the platform never records an unattested instance for these roles; the wait ends only with the process context. `attestation.report` is now produced by that gate instead of the startup path, and `getAttestation` is unchanged. The state sealing key source goes through the same wait: types 1-3 used to choose it from a single startup `stat`, so a boot that lost the race sealed `state.sealed` with the SM2-derived key and the next boot's source check archived that state as drifted; `awaitStateSealingKeySource` now blocks on `/dev/csv-guest` (same 5s doubling to 30s backoff, no attempt limit, throttled logging) before choosing, so these roles seal with `csv-hw` as soon as the node exists, while `fhe` keeps the immediate detection and the SM2-derived key. The consequence is deliberate: a type 1-3 instance that never gets the node — the local Docker template `configs/taa-docker.json` among them — now waits at startup instead of coming up with the weaker key. Tests cover both waits (verified, retried, device-appears-late, context cancelled, never-verified), the source resolution (types 1-3 pick `csv-hw`, `fhe` reads immediately, a cancelled process aborts the wait) and the policy (fhe registers immediately with `verifiedPass=false`; tee and `data-anaylsis` register only after the gate and with `verifiedPass=true`, and never when it fails).
- **Every Role's Container Entrypoint Is `bash /root/taa/taa-supervisor.sh`, And Data Analysis Finally Starts jupyter**: `deploy.sh` already made that path the image ENTRYPOINT, but the repository held one plain supervisor (`deploy/taa-supervisor.sh`, TAA only) plus `deploy/taa-fhe-supervisor.sh` for the FHE role, and the data-analysis role got the plain one — so on a jupyter base image jupyter never started, while the role's landing directory `/home/jovyan/systemAuthData` exists precisely for the jupyter runtime to read. The repository now keeps one file per role under the same basename: `deploy/taa-supervisor.sh` (tee, unchanged), `deploy/dataanaylsis/taa-supervisor.sh` (new: starts `start-notebook.py` with `HOME=/home/jovyan` and TAA beside it) and `deploy/fhe/taa-supervisor.sh` (was `deploy/taa-fhe-supervisor.sh`; starts `/opt/entrypoint.sh` and TAA). The deployment scripts select the role's file (`TAA_SUPERVISOR_SOURCE` in `deploy.sh`, `TAA_ENTRYPOINT_SOURCE` in `deploy-fhe.sh`) but every container still installs exactly one file at `/root/taa/taa-supervisor.sh`, and the file itself decides whether a sidecar starts, so a deployment never has to know which role it is looking at. Because the FHE update path replaces the supervisor in place and must not restart the container (the Kata guest's writable layer would be lost with it), a combined supervisor runs the TAA loop as `bash "$SELF" --taa-loop`; the sidecar decides container liveness — when jupyter or the FHE entrypoint exits, TAA is stopped and the container exits with the sidecar's status, leaving the restart to kubelet — while the loop child exiting only makes the parent restart it after 10s, as before. `deploy-fhe.sh`'s replacement pattern is now `[t]aa-supervisor[.]sh --taa-loop`, which cannot match PID 1; the loop keeps its `flock` singleton, `manual` pause file, 30s wait for a missing `./taa`, 10s restart and `/root/taa/taa.log`, and the block is delimited (`# >>> TAA_LOOP` / `# <<< TAA_LOOP`) so `tests/taa_supervisor_uniform_test.sh` can prove the three copies have not drifted. The FHE role's container-creation path now stages the supervisor into `/root/taa/` *before* `docker start` (the bare FHE image has no `/root/taa`), and the Pod `update` preflight requires a `--taa-loop` process, so a Pod created with the old entrypoint is refused with a message saying it must be recreated rather than silently updated. `deploy.md`, the README, `docs/architecture-design.md` and the Pod templates follow.
- **The Deployment Identity Now Travels On The Kernel Command Line**: every deployment setting used to be baked into `/etc/default/taa.env` at build time, so changing `PLATFORM_IP`, `DOCKER_ID`, `PLATFORM_PUBLIC_KEY`, `PLATFORM_SM2_ID`, `CONTRACT_ID`, `CONTRACT_TYPE` or `TAA_LLM_ENDPOINT` meant rebuilding the measured initrd. `render` now writes them into the Kata config as `kernel_params` tokens (`taa.<key>=<value>`), QEMU passes them on `-append`, and `taa-init` reads them from `/proc/cmdline`. This is the only channel that reaches the guest that early: the Pod's environment does not exist yet (TAA is the initrd's first process, ahead of kata-agent and of guest networking), `shared_fs=none` leaves the container's writable layer unreachable from the initrd, and CSV2 `initdata` is unmeasured and reserved for the guest policy. An identity change is therefore a re-render plus install (`launch`), not a `build`, and the initrd bytes — with them the image half of MEASUREMENT — stay fixed. The tokens override the baked env file, which is kept as the fallback so an image still boots if the command line ever loses them. Only eight names are honoured (`platform_ip`, `docker_id`, `platform_public_key`, `platform_sm2_id`, `contract_id`, `contract_type`, `llm_endpoint`, `addr`), so a host cannot export arbitrary variables through `/proc/cmdline`; a value containing whitespace is refused at render time instead of being silently split into two arguments, and a re-render replaces a token of the same key rather than appending a second one (the stale value would otherwise sit ahead of the new one). Two consequences are deliberate: the command line is itself part of the CSV2 MEASUREMENT, so the identity remains covered by the attested value, and QEMU's `-append` is visible to the host, so `TAASECRETKEY` is never carried. The rendered line is ~750 bytes including the 130-character public key, inside the kernel's 2048-byte limit with room for the rest. `check_initrd_identity` on the `deploy` path now reports a mismatch as a warning instead of refusing the deployment: the rendered command line wins, so refusing on a stale baked value would block a change the guest would apply correctly.
- **The Delivery Package's Deployment Identity Is Editable On The Target Host**: the identity tokens were reachable only by re-rendering on the build host, so standing up a second Pod with another platform address, docker id or LLM endpoint meant going back to that machine and re-uploading the package. `render` now also writes `config/env.txt` — one `taa.<key>=<value>` per line, the command line itself rather than `NAME=value` env syntax, so the file is not sourceable and what it holds is exactly what the kernel will be given — and `install.sh` re-renders `config/kata-config.toml` from it with the packaged `render.py`, while `test/create-test-pod.sh` deletes and re-applies the test Pod so the new command line reaches a new VM. The edit-and-rerun loop is the whole workflow: `vi config/env.txt`, `sudo bash install.sh`, `sudo bash test/create-test-pod.sh`, with no rebuild and no re-upload. The new `render.py kata-config --param-file` replaces the *whole* identity set rather than just the named keys, so deleting a line removes the parameter instead of leaving its previous value on the command line, and it rejects an unknown key, a duplicate key, an empty value, a whitespace-bearing value and a line without `=` before any output is written — a typo must fail the install, not become a token the guest drops while everything else looks fine. `config/env.txt` and the config rendered from it are excluded from `SHA256SUMS`, because they are the two files an operator is meant to change; every other file stays pinned, so a host-side identity edit does not look like a tampered package while a modified `install.sh` still does. The expected MEASUREMENT is recomputed on the target host from the config that was just installed — the only input that can differ from the build host — and `test/create-test-pod.sh` compares it with the running VM's. The identity file is `%q`-free by construction: it never carries `TAASECRETKEY`, which cannot travel on a command line visible in the host's `ps`.
- **The Kata Config The Runtime Handler Points At Ships Inside The Delivery Package**: `/etc/kata-containers/configuration-qemu-csv2-taa.toml` was a second copy the host had to keep — `install.sh` rendered it from the shipped CSV2 config and installed it next to it. It is now the copy inside the rendered package (`config/kata-config.toml`), and the containerd handler's `ConfigPath` points straight at it, so the host carries no second copy and the install has one less step. `REMOTE_KATA_CONFIG` still names the path and still wins when set, but its default is now `${REMOTE_PACKAGE_DIR}/${PACKAGE_KATA_CONFIG}` whenever the package persists, which is what `deploy-taa-vm.sh` produces; `install.sh` recognises source and target as the same file (`-ef`) and skips the copy — `install(1)` would refuse it with "are the same file". **This makes the delivery package a runtime dependency**: containerd reads the config from that directory whenever a Pod using the handler starts, so the package must stay where `launch` left it, and deleting or replacing it without first removing the handler leaves the runtime pointing at nothing — a failure that shows up only when the next Pod of that class starts, not at `config dump` or containerd-restart time. The teardown keeps the order that matters (`delete` removes the handler before the package) and now says the config goes with the package instead of removing it separately; `install.sh` prints the same warning when it detects this layout. `build-initrd.sh` used on its own keeps the old `/etc/kata-containers/...` default and the copy behaviour. (Superseded while still unreleased: `REMOTE_PACKAGE_DIR` now always defaults to a persistent directory, `REMOTE_BUNDLE_DIR` is derived from it, and the `/etc` fallback is gone — see the package-carries-the-bundle entry above.) `PACKAGE_KATA_CONFIG` is now the one definition of the in-package name, shared by the renderer, the manifest and `print-config`; the offline driver test pins the in-package default and the absence of a host-side copy.
- **The CSV2 initrd Runs The Production Template, And Its Guest Environment Carries The Deployment Identity**: `configs/taa-initrd.json` is deleted; `build-initrd.sh` now injects `configs/taa-production.json` into the measured image. The separate template existed to tune the guest's LLM endpoint and audit policy, but the endpoint is deployment-specific rather than role-specific and therefore belongs in the guest's environment, and the rest was a copy that could drift: a field added to one template and not the other would build, boot, and only change the guest's behaviour. Deployment settings now travel through `/etc/default/taa.env`, written at build time because the Pod's environment does not reach an initrd: `PLATFORM_IP`, `DOCKER_ID`, `PLATFORM_PUBLIC_KEY`, `PLATFORM_SM2_ID`, `CONTRACT_ID`, `CONTRACT_TYPE`, `TAA_LLM_ENDPOINT`, plus the wrapper's `TAA_ADDR`. **`PLATFORM_PUBLIC_KEY` is now a build requirement**, not an optional extra: TAA exits 1 at startup without it, and until now a build produced an initrd whose TAA died immediately, leaving a guest whose daemon is dead. The build resolves it from `PLATFORM_PUBLIC_KEY` / `TAA_PLATFORM_PUBLIC_KEY`, or from `TAA_PLATFORM_KEY_FILE` (default `.local/platform-mock/platform-key.json`, accepting the mock's `publicKeyHex` field or bare hex), validates the `04 || X || Y` wire format, and writes it into the measured env file; `deploy` compares the baked key against the one this invocation resolves and refuses a mismatch, on the same reasoning that already covers `PLATFORM_IP`/`DOCKER_ID`. `deploy-taa-vm.sh` supplies `TAA_LLM_ENDPOINT` (default `https://172.16.10.116:8443`) because the template's endpoint is a Pod IP left over from another deployment. **Three guest audit settings change with the template switch**: `codeAudit.llm.failClosed` becomes `false` (an unreachable gateway degrades to static-only instead of rejecting the import), `insecureSkipVerify` becomes `false` (gateway attestation is verified again), and the semgrep whole-scan deadline falls from the template's `900` to the adapter default of five minutes. `TAASECRETKEY` is deliberately not carried: it is secret material, not identity. The README, `docs/architecture-design.md` and the offline driver test follow, and the rebuilt initrd has a new boot MEASUREMENT.
- **The Data-Analysis Role Owns Its Image Repository And Pod Name**: `deploy-dataanaylsis.sh` now exports `TAA_POD_IMAGE_REPO=taa-dataanaylsis` and `TAA_POD_NAME=taa-dataanaylsis` (an operator's value in either variable still wins) instead of leaving both at `deploy.sh`'s defaults, and `./deploy.sh save` derives its default image and archive names from `TAA_POD_IMAGE_REPO` rather than from a hard-coded `taa-train-infer`. Sharing the defaults was wrong twice over: the data-analysis role's image is assembled on a jupyter base and the tee role's on a taa-env base, so one same-day tag (`taa-train-infer:<date>`) named two unrelated images and each build overwrote the other's, and anything keyed by the tag — the registry manifest comparison that decides whether to skip an upload, a cached archive on the host — could hand one role the other's image; a shared Pod name meant one role's Pod blocked the other's `create`, because a Pod's environment (and therefore its role) cannot be changed in place. The Pod is therefore named `taa-dataanaylsis` now; a deployment that relied on the old name should delete the old Pod explicitly. `./deploy-dataanaylsis.sh save` no longer passes `--image/--archive` itself — `deploy.sh` computes the same names from the repository, so a save run and a create run agree.
- **The Instance Role Travels In The Pod Environment, And The Data-Analysis Role Owns Its Landing Directory**: the role used to be split across two mechanisms — `deploy-fhe.sh` injected `CONTRACT_TYPE=4`, but the TAA Pod carried no role at all, so `deploy-dataanaylsis.sh` had to render a copy of `configs/taa-production.json` with `server.type=data-anaylsis` and `storage.data=/home/jovyan/systemAuthData`, and that copy was the only thing that put the data where the jupyter runtime reads it. `deploy.sh create` now writes the role into the Pod environment (`CONTRACT_TYPE`, default `1` for the tee role, `TAA_POD_CONTRACT_TYPE` to override), and the loader derives the rest from it: a data-analysis instance lands its data under `/home/jovyan/systemAuthData` whatever `storage.data` says, because that directory is decided by the base image rather than by the template. `deploy-dataanaylsis.sh` therefore exports `TAA_POD_CONTRACT_TYPE=3` and uses the shared template unmodified; the image no longer bakes a role, and the same archive can be deployed as either role. Because a Pod's environment cannot be changed in place, `create` refuses to reuse an existing Pod whose role differs from the one the current run asks for — reusing a tee Pod for a data-analysis deployment would install the right files into an instance that still audits like a tee, and with the role no longer in the config nothing later in the flow would notice. `verify_pod_contents` also stops demanding the semgrep payload when `TAA_SCAN_ENGINE_PROVISION=skip` was the reason none was installed, which is what made `deploy-dataanaylsis.sh create` fail its own verification after building the Pod. `deploy-fhe.sh` gets the matching gate on its own side: its Pods carry `CONTRACT_TYPE=4`, and reusing one in `create` or adopting one in `update` now refuses a Pod that carries another role (an absent value still reads as fhe from the rendered config). `deploy.md`, the README and `docs/architecture-design.md` follow.
- **`create` Creates, `start` Starts, And The Three Deploy Scripts Agree On The Words**: the lifecycle actions had drifted — `deploy.sh start` built an image and created a Pod, `deploy-llm.sh start` was a full install, `deploy-fhe.sh` had no lifecycle at all beyond two positional words, so "start" meant a different amount of work in each script and nothing named the action that only creates. All three now take the same mutually exclusive set: `create` (default) builds what the deployment runs and brings the target into existence, `update` installs the current build into a target that already exists, `start` and `stop` are the two ends of the supervisor's `manual` switch and touch nothing else, `probe` only reports whether TAA answers, and `delete` removes only what the deployment created. `deploy.sh create` assembles the production image, creates the Kata CSV2 Pod, verifies that the binary, supervisor and config inside are byte-identical to this tree (a mismatch is listed and fails the run, never patched), and starts TAA; an existing owned Pod is kept and verified instead of being recreated, because its guest writable layer holds the SM2 key pair, the sealed state and the imported data. `deploy-llm.sh start` no longer installs: it resumes the Pod supervisor and waits for ollama and `teellm-service`, and `update` is the path that copies files. `deploy-fhe.sh` gains Pod creation as its default target: `create` assembles one image from the FHE handoff image plus TAA, its supervisor, the rendered config and the FHE model tree, pushes it to `FHE_IMAGE_REGISTRY` (the guest pulls through its own CDH, so a host `docker load` is not enough), renders `deploy/manifest/k8s/fhe-pod.yaml.tmpl` with the `cc_init_data` annotation and the identity env vars, and verifies the result the same way; the plain docker container is demoted to `--target container`, and `--pod <name>` now means "adopt this existing Pod" (`update`/`start`/`stop`/`probe` only — `create` and `delete` refuse it). Identity for a created Pod (platform address, SM2 public key, contract, docker id) travels in Pod environment variables rather than `taa-config.json`, as it already did for the TAA Pod.
- **The Deployment Scripts Share One Vocabulary, And An Option Carries Its Value Without An Environment Variable**: the five deploy scripts had grown a different name for the same concept in each of them — the target Pod was `--pod`, `--taa-pod` or `TARGET_POD`, the password was `--password`, `--remote-password` or `REMOTE_PASSWORD`, the TAA image was `TAA_POD_IMAGE` / `TAA_FHE_SAVE_IMAGE` / `--image`, and the work directories, ports, ollama and semgrep directories and readiness timeouts each had one spelling in `deploy.sh` and another in `deploy-llm.sh` / `deploy-fhe.sh`. They now agree: `--pod`, `--namespace`, `--remote-password`, `TAA_IMAGE` / `TEELLM_IMAGE` / `FHE_IMAGE`, `TAA_IMAGE_REGISTRY` / `TEELLM_IMAGE_REGISTRY`, `TAA_PORT` / `TEELLM_PORT` / `FHE_PORT`, `TAA_WORKDIR` / `TEELLM_WORKDIR`, `TEELLM_OLLAMA_DIR`, `TAA_SEMGREP_DIR`, `TAA_READY_TIMEOUT` and `TEELLM_OLLAMA_READY_TIMEOUT`; the mock's listen port is `MOCK_PORT` and its LLM target is `--llm-target` / `--llm-port` / `--llm-pod`. Wherever an option can carry a value, the environment variable is gone and the option default holds it, so a stale export can no longer override what the command line says; the old spellings are refused rather than silently ignored (`TARGET_PASSWORD`, which could otherwise authenticate with a different password than the one passed). `deploy-llm.sh` gains `create` and `delete` actions in place of `--create-pod start` and `pod-down`, and a plain run targets `TEELLM_POD_NAME` instead of an empty `TARGET_POD`; `deploy-fhe.sh` selects its target with `--mode remote|docker` instead of `--remote` / `--local`, and packages an image with `save --image` instead of the `TAA_FHE_SAVE_IMAGE` override; `deploy.sh --config` becomes `--save-config`, and `--output` / `-o` / `--tag` are gone in favour of `--image` / `--archive`. The `taa` and `qwen` component words are accepted nowhere.
- **Creating The TEE-LLM Pod No Longer Installs Anything Into It**: `--create-pod start` used to run the same install sequence as `update` once the Pod came up — pause the supervisor, stop the daemons, stream the ollama runtime and the model into the guest, `scp` the service and the configs and `kubectl cp` them in, write `.teellm-model`. That made the Pod a second definition of what it runs: invisible to `kubectl describe`, not re-derived by any rebuild, and able to keep a Pod working on content its image does not carry, so a defective image stayed hidden until the next recreation. Creation now verifies what the image carries instead: `teellm-service` and `teellm-supervisor.sh` present and executable, both configs, `.teellm-model`, `ollama`, `start-ollama.sh`, `lib/ollama/libllama-server-impl.so`, and every blob the target model's manifest names, present at the size the manifest records. A missing item fails the run with one `missing:` line each and an explicit statement that nothing was copied, leaving the Pod in place for inspection; the same run also skips the binary rebuild and the host upload, since both exist only to feed that install. `update` (or a bare `TARGET_POD=<name>` run) remains the path that installs into an existing Pod, and `TEELLM_IMAGE_FORCE_REBUILD=true` rebuilds the image.
- **The TEE-LLM Pod Publishes Its Port And Keeps The Host's Time Zone**: `deploy-llm.sh --create-pod` produced a Pod reachable only at its Pod IP — an address that changes on every recreation — and running in UTC, so `curl -k https://<node>:8443` was impossible without first asking the cluster, and its log timestamps sat eight hours off the host's and the platform's. The manifest now maps container port `8443` to host port `18443` (`TEELLM_POD_HOST_PORT`; `0` publishes nothing, which is how the Pod behaved before) and sets `TZ=Asia/Shanghai`, both the reference create script's values. TAA itself keeps dialling the Pod IP; the host port is for everything that cannot route a cluster address, and it is the one address that survives recreating the Pod. Because a taken port only surfaces as a scheduling failure tens of minutes into an image build, the check now lives in the creation preflight: a listener already on the host fails the run (the runtime opens the mapping in the host's network namespace, so `ss` sees it), a `hostPort` another Pod merely declares is reported and allowed, since a Pod that is not running does not block scheduling. No `jq` dependency was added — the cluster query runs through a `bash -s` heredoc and kubectl jsonpath.
- **The Platform-Mock Clears TEE-LLM Logs On Demand And When The Instance Changes**: the log panel only ever grew — there was no way to drop records short of the full reset, which also forgot the instance and the read position — and a restarted instance kept the previous process's records, so several runs' seq numbers sat interleaved in one list and read as duplicates. `POST /api/llm/logs/clear` (the 「清空日志」 button next to the pause control) now drops the collected records while keeping the instance identity and the read cursor, so the panel stays empty until the instance writes new records instead of refilling from its buffer on the next poll. A changed `dockerId` in the heartbeat envelope is now the exact trigger for dropping the records as well as resetting the cursor: the instance's seq numbering started over, so the records kept so far belong to a process that no longer exists. The poller seeds its run identity from the persisted state, so a mock restart does not forget which instance it had been collecting from, and a `latestSeq` that moved backwards remains a fallback for a restart the id could not tell apart.
- **The Console Shows The TAA Service Address Instead Of Letting It Be Typed**: the address console calls were sent to was an editable field in the platform-registration card, prefilled by automatic detection and overwritten on every instance switch — a value nobody was meant to type over, since the mock decides between its own reverse proxy and a direct call from the registration it holds. The field is gone; the detected target and its reachability now appear in its place as one pill (green through the proxy, amber when no TAA Pod was found and the console falls back to `http://<console host>:6001`, red when detection itself failed), so the top-right copy of the same badge is gone too. `getTaaAddr()` now reads a value the detection sets rather than an input, and the 'user edited it, do not overwrite' guard went with the input.
- **The TEE-LLM Log Panel Accepts A `sinceSeq` Override**: pulling the instance's log always continued from the stored read position, so exercising the interface at another position meant resetting the poller. A `sinceSeq` field next to 「立即拉取」 now sends that value verbatim in the `POST /api/llm/poll` body; left empty the pull resumes automatically as before. A probe is not a normal pull: the records the instance returns are kept even when their seq is at or below the stored cursor — the whole point of naming the position — and the stored cursor still advances to the instance's `latestSeq`, so the automatic polling after a probe is unaffected.
- **`deploy-llm.sh update` Replaces `--pod <name> start`**: updating an existing TEE-LLM Pod used to be the `start` action aimed by a `--pod <name>` flag, which left both the target and the lifecycle to whatever the command line happened to say. There is now an explicit `update` action: it addresses the dedicated Pod named by `TEELLM_POD_NAME`, builds and installs the binary, supervisor and configuration, restarts the daemons and verifies — and it refuses when the Pod does not exist, so it can never create one, and it never deletes one. `start` with an explicit `--pod` is refused with a pointer to `update` (or `--create-pod start`); `--pod` remains for `stop`, `probe` and `pod-down`, and `TARGET_POD` in the environment still selects the target of a start aimed at some other existing Pod. `--create-pod update` is refused rather than resolved, since creating and updating are different actions.
- **TEE-LLM's Self-Check Verifies Only The Report's Own Signature**: `GET /v1/llm/getAttestation` returned `verifiedPass=false` on a stock deployment because the self-check walked the HRK/HSK-CEK certificate chain and compared the report's USERDATA with the SM3 of the certificate's public key. Neither input exists there: the chain certificates are issued per machine, so a stock image ships none, and the fallback to the certificates carried alongside the evidence still left the check dependent on vendor material. The check now does what TAA's own `VerifyReport` does — `csvattest.VerifyReportWithOptions` with `VerifyChain: false`, which proves the PEK certificate embedded in the report signed the report body — so the platform panel reports a self-consistent report, not a chain-verified one. The distinction is documented: without the chain the PEK is not proven to belong to a genuine Hygon platform, and `docs/api-design.md` now says so.
- **The Platform Pulls From TEE-LLM Instead Of TEE-LLM Reporting Out**: `teellm-service` used to register with the platform at startup (retrying forever), then push a heartbeat and buffered logs on timers, configured through `platform.addr` plus `PLATFORM_IP` / `DOCKER_ID` / `HEARTBEAT_SECONDS` / `LOG_FLUSH_SECONDS`. The whole `platformagent` package is gone, and all three platform interfaces are now platform-initiated on the plaintext `:6001` listener: `POST /v1/llm/heartbeat` answers `{alive, model, uptimeSeconds}` (no `dockerId` — the platform keys instances by the address it called), `POST /v1/llm/log` serves a 2000-entry run-log ring incrementally by `{sinceSeq, limit}` and returns `{entries, latestSeq, dropped}`, and `POST /v1/llm/getAttestation` is unchanged apart from no longer claiming a registered certificate key. There is no registration and no outbound channel at all, so `platform` disappears from both shipped config files and `deploy-llm.sh` loses `--platform` / `TEELLM_PLATFORM_ADDR` (a redeploy also strips a `platform` block left in the Pod's config). The platform finds the instance by Kubernetes Pod discovery. The response envelope and message format stay `{msg, result, error}` and `[timestamp] [LEVEL] [component] text`, so one decoder and one log viewer handle TAA and TEE-LLM alike.
- **The TAA Pod Carries `PLATFORM_PUBLIC_KEY`**: TAA seals every message it sends to the platform with the platform's SM2 public key and exits at startup when it has none, but a Pod could never receive one: the remote config path writes a template without a `platform` block, and the Pod manifest had no environment entry for it, so every deployment-owned Pod started and immediately exited. `deploy.sh` now renders `PLATFORM_PUBLIC_KEY` into the Pod environment. When neither `PLATFORM_PUBLIC_KEY` nor `TAA_POD_PLATFORM_PUBLIC_KEY` is exported, the value is read from `TAA_POD_PLATFORM_KEY_FILE` on the host (default `<REMOTE_DIR>/platform-key.json`, the platform-mock's own state file, field `publicKeyHex`), so the common case needs no setup; a value that is not the published wire format — 130 hex characters, `04 || X || Y` — is refused rather than spent on a guest boot to fail. The Pod is created only once a key is in hand, and an existing Pod is reused as before.
- **CoCo `cc_init_data` No Longer Needs A Running Pod To Copy**: the annotation was always derived from a CoCo Pod that already existed on the host, so creating the first Pod on a freshly booted node failed even though the input for the value was right there on disk. When no Pod carries the annotation, `deploy.sh` now renders it from `TAA_POD_INITDATA_FILE` on the host (default `/root/test/deployment/tools/build-and-install/test-hygon-coco/initdata.v1.toml`) by compressing and base64-encoding that file exactly as the vendor's Pod template does, and reports which source it used. An exported `TAA_POD_CC_INIT_DATA` still wins, and the annotation copied from a running Pod is still preferred because it is the value that is known to work on that host.
- **`deploy-llm.sh` Skips The Payload Import And Commit When Nothing Changed**: every creation run used to stream the multi-gigabyte ollama bundle into a builder container and commit it into a new image, minutes of work that reproduced the identical image whenever the tree, the configuration and the model bundle had not changed. The commit now records a `tee-llm.payload-fingerprint` label over every input that determines the image — the ID of the base image actually used, the model name, the content/ownership/mode of `teellm-service`, the supervisor and the two config files, a digest of the exact tar stream the payload step imports, and the commit instructions themselves — and a rerun whose fingerprint matches the label skips the builder container, the payload import, the verification and the commit, continuing straight to the registry-digest check and the push. The payload is hashed as the same tar stream that is imported, not file by file, because the file list names directories (`models/cache`) that tar expands recursively and a per-file pass would miss: a digest that misses one input would deploy the previous image under the new tree's name. An image that carries no label (every image built before this change, or one built by other tooling) is rebuilt once. `TEELLM_IMAGE_FORCE_REBUILD=true` bypasses the reuse.
- **`deploy-llm.sh` Reuses A Committed Image Across Build Dates, And A Change To The Build Instructions Invalidates It**: the reuse lookup asked only today's tag (`teellm:<YYYYMMDD>`), so the first deployment of a new day rebuilt an image the host already held under the previous day's tag — the same content under a different name, tens of minutes for nothing. The fingerprinted image is now looked up across every local tag and retagged when one matches; the fingerprint is over content, so a match is the same image rather than an approximation, and `docker images --filter label=…` supplies it. Two inputs the check had been missing are now hashed: the **source image ID** (the stripped `teellm-base:<date>` was cached by existence alone, so swapping `TEELLM_IMAGE_BASE` during the day kept building every layer on the old base while the fingerprint, taken over the derived image, never moved — the derived image now records `tee-llm.base-source` and is rebuilt when that differs), and **the build instructions themselves** — the `docker cp` list, the soname-link fixup and the `.teellm-model` write run as shell text inside `build_teellm_pod_image`, so editing them changes the image while no input file changes; the function's own definition is hashed, which also means a future edit to the fingerprint block forces one rebuild (the safe direction). A rebuild now prints the stored and the current fingerprint, so a minutes-long step is never unexplained. Tests cover the cross-tag reuse, the retag, a stale and a matching base-source label, and an edit inside the build function; each gate was mutation-checked by disabling it and watching the suite go red.
- **`deploy-llm.sh` Shows The Image Upload And Push In Progress**: step [15] moved a multi-gigabyte archive with `scp` and then ran `docker load` and `docker push` under `>/dev/null`, so the slowest part of a rebuild printed nothing for minutes and looked hung. The upload now goes through `rsync --partial --info=progress2` (percentage, speed and remaining time on one in-place line, resumable after an interruption) whenever rsync exists on both ends, with `scp` kept as the fallback and a warning that it cannot report progress; the archive size is printed before the transfer. On the remote side the load and push keep their output, prefixed and preceded by a phase line, because docker reports a layer only as it finishes and that is the only progress the registry client offers.
- **The platform-mock Defaults To Port 18081**: the mock used to default to 18080, the port the real control plane (`ccs-node-agent`) already holds on the shared hosts, so a default `deploy-platform-mock.sh ... start` died with `bind: address already in use` — and a mock started first would have contended for that port instead. The default listen port is now 18081, the port the shipped teellm configs and `taa-fhe.json` already name for the mock. Nothing else moves: `deploy.sh` still defaults TAA's platform address to `<REMOTE_HOST>:18080` because that default targets the real platform, so a debug deployment against the mock sets `PLATFORM_PORT=18081` (both scripts read it, so one variable moves both), or passes `--port 18081` to the mock alone.
- **`deploy-llm.sh --create-pod` Builds And Pushes The Image It Runs**: creating the dedicated TEE-LLM Pod used to start whatever `TEELLM_POD_IMAGE` named, so a Pod could run a `teellm-service` older than the tree being deployed — a `teellm/` change reached the Pod only if someone remembered to build and push an image first, and nothing in the Pod said which build it was. The creation path now recompiles `teellm-service` from the working tree, bakes it with the ollama runtime and the model into `TEELLM_IMAGE_REGISTRY/TEELLM_IMAGE_REPO:<YYYYMMDD>`, and renders the Pod from that tag. The builder is **inside `deploy-llm.sh`** (see the Removed entry for the standalone script it came from), so the deployment no longer shells out to a second script that could disagree with it about tags, paths or payload. The binary is rebuilt unconditionally and **before** the builder runs, and the same build is not repeated later in the run (`LOCAL_BINARY_BUILT`), so the file installed into the Pod and the file in the image are the same. The pull policy is forced to `Always` on this path, since the tag is a same-day one that a rebuild replaces in place. An explicit `TEELLM_POD_IMAGE` is still used as given and nothing is built, and `TEELLM_BUILD_POD_IMAGE=false` restores the previous behaviour of adopting the newest date tag the registry lists. The build takes tens of minutes, so it happens only on the branch that actually creates a Pod — an existing Pod is never re-applied, its image being immutable.
- **The TEE-LLM Pod Manifest And Its Create/Delete Flow Follow The Reference Scripts**: `--create-pod` and `pod-down` now use the sizing, annotation, readiness and teardown rules from the `create-teellm-pod.sh` / `delete-teellm-pod.sh` pair that was validated on this host. Three things change in the manifest. The annotation set grows from one to the three every `kata-qemu-csv2` Pod here carries — `io.containerd.cri.runtime-handler` (same value as `runtimeClassName`, so the two cannot drift), `io.katacontainers.config.hypervisor.kernel_params` (`agent.cdh_api_timeout=1200 agent.image_pull_timeout=3600`; an **empty** value is the hazard, because it would erase the `rdinit=` the runtime already carries, while a non-empty one is appended) and the existing `cc_init_data`. **This reverses an earlier decision to omit the first two deliberately**, which running a multi-GB image disproved: the guest pulls through its own CDH and the defaults expire long before such an image arrives. `nodeSelector: katacontainers.io/kata-runtime` and `terminationGracePeriodSeconds: 30` are added beside the existing `nodeName` pin. Creation now sizes the guest before anything is applied: `check_pod_memory_budget` derives the VM size from the kata `default_memory` read from `$KATA_TOML` plus `limits.memory`, compares the image's unpacked size against the guest overlayfs cap (half the guest's visible memory) and against a 15% writable margin, then reads the host's available memory — a VM that cannot fit is refused instead of booting and dying with `ENOSPC` or exhausting the host, with `TEELLM_POD_FORCE_MEMORY` as the named escape hatch and `TEELLM_POD_IMAGE_SIZE_GIB` to size against a real figure. `kubectl wait` is replaced by the reference polling loop: phase and readiness every 5s, printed on change, with `Failed` and the pull/crash waiting reasons failing the run immediately and the Pod left in place with its events. The ready timeout default rises from 600s to 1800s for the same reason. `pod-down` submits `--grace-period=30 --wait=false` and polls for 180s before falling back to a forced delete, reports the host memory that comes back, and then compares three counts that must agree — the cluster's kata Pods, `/run/vc/sbs` directories and `qemu-system` processes — naming any qemu that outlived its sandbox with its RSS and `-m`, and giving the `crictl pods` → `stopsandbox` → `rmp` order rather than suggesting a `kill` (both leak shapes have been seen here: a containerd restart inside a VM's boot window, and a failed `RunPodSandbox` retry). An interactive creation is also confirmed once, printing image, CPU and memory; a non-TTY run proceeds.
- **The TEE-LLM Pod's Preflight, Security Context, Start Command And Defaults Match The Reference Script**: `--create-pod start` now proves the target exists before it starts building. A new `preflight_pod_cluster` checks that the API server answers, that the Pod name is a valid DNS label, and that the namespace and the RuntimeClass exist — a namespace typo used to cost a full image build and push before failing at `kubectl apply`. The registry `tags/list` probe is kept, but only on the paths that did not just push the tag themselves (`TEELLM_POD_IMAGE_BUILT`), so a build that succeeded in this run is never re-queried, and an unreadable listing stays a warning. The container definition is now the reference script's, verbatim in substance: `command: ["/bin/bash", "-c"]` with an `args` script that reads the `csv-guest` minor from `/proc/misc`, creates the node with `mknod -m 666 /dev/csv-guest c 10 <minor>`, and then `exec`s `teellm-supervisor.sh`, so the container's lifetime is the supervisor's and `restartPolicy: Always` brings the service back (the previous shell loop that respawned the supervisor every 2s is gone). `securityContext` is `privileged: true`, `allowPrivilegeEscalation: true`, `runAsUser: 0`, `runAsNonRoot: false` — `mknod` needs `CAP_MKNOD` and both the entrypoint and the supervisor expect root. The CPU default drops from 8 to 2 to match the reference's request, which matters on a host whose CPU requests are already nearly accounted for and because encrypted memory makes every extra vCPU a permanent claim. `check_pod_memory_budget` also reports what is left for the service and the model — `visible - unpacked - 256`, clamped to the cgroup limit — and warns below 1024 MiB, a case the overlay check alone passes and that then shows up as llama-server being OOM-killed after the Pod is already Ready. `--create-pod` no longer adopts an existing Pod: it prints it, says this path only creates, and stops with `pod-down` as the next step, because reusing would deploy into whatever image the Pod happens to run and replacing it in the same path would discard the guest's writable layer and the Pod IP without the operator deciding to. Updating an existing Pod stays `./deploy-llm.sh start` / `--pod <name>`, which never creates or deletes one.
- **The Platform Address Resolves Environment-First, Config-Second**: `teellm-service` used to read `platform.addr` only from the JSON config, so the reporting peer was fixed when the image was built, and `deploy-llm.sh` compensated with a mock address of its own (`TEELLM_PLATFORM_MOCK_ADDR`) that it wrote into the rendered config. The address now resolves as `PLATFORM_IP` in the environment first and `platform.addr` second: the shipped `teellm-production.json` and `teellm-docker.json` name the platform-mock (`http://172.16.10.181:18081`), a bare `host:port` gets the `http://` scheme when the reporter starts, and `off`/`none`/`disabled` clears the address, in either source. A Pod created by `deploy-llm.sh` injects no `PLATFORM_IP`, so it follows its config file and runs in debug mode without being told to, while an orchestrator can point the same image at a real platform with that one variable. `--platform` / `TEELLM_PLATFORM_ADDR` now decides what the rendered config says — an address verbatim, `mock`/`config` to keep the template's value, `off`/`none`/blank to clear it — and `TEELLM_PLATFORM_MOCK_ADDR` is gone, because the mock has one home: the config templates. The deployment prints `platform reporting: <addr|disabled>` (naming the config as the source when that is what decided it) and the closing summary reports the address actually in effect.
- **platform-mock Is Deployed Only By `deploy-platform-mock.sh`**: `deploy.sh` and `deploy-fhe.sh` each carried their own mock deployment path — binary uploads, target discovery from kubectl, state/upload/log/pid paths, `MULTI_INSTANCE` plumbing and stop handling — which drifted from the dedicated script and made every deployment own the platform lifecycle. Both scripts now only configure the address TAA registers with (`PLATFORM_PORT`, `LOCAL_PLATFORM_PORT`, `REMOTE_PLATFORM_IP`, `PLATFORM_IP`) and never build, start or stop the mock. `deploy.sh` drops the `platform-mock` component argument (it now errors with a pointer to `./deploy-platform-mock.sh`), the `MULTI_INSTANCE` switch and the mock-only paths; its default and only component is `taa`. `deploy-fhe.sh` drops the `platform-mock` mode and `--no-platform-mock` (accepted as a deprecated no-op), and its closing registration check becomes advisory: a missing, rejected or mismatched registration is a warning, because the platform is now external and TAA retries until it is accepted. Multi-instance behaviour is unchanged and remains the default of `deploy-platform-mock.sh` when `--taa-target` is omitted.
- **Platform Registration Retries Until The Platform Answers**: startup registration used to stop after a five-minute window, so a platform (or platform-mock) that started later than TAA left the instance permanently unregistered until TAA was restarted. The background retrier now has no window and keeps retrying at 5s→30s until the platform answers or the process shuts down (`registerRetryWindow = 0`; a positive window still means bounded, which the unit tests exercise). Because the loop can now run for days inside a guest whose log lives on tmpfs, failures are logged for the first five attempts and then once every twenty (about ten minutes at the 30s ceiling); the payload itself is still rebuilt identically on each attempt, including the startup timestamp. Deploying the platform before TAA is no longer an ordering requirement.
- **The TEE-LLM Deployment And Image Stop Carrying The Vendor Certificates**: `teellm-service` never used the HRK/HSK-CEK files to verify anything — it only relayed whatever chain it was configured with to its peer in the evidence extension, and it sets `InsecureSkipAttestationVerify` when acting as a server. With TAA's shipped templates now checking only the report's PEK signature, that chain has no consumer, so the service's `attestation.hrkCertPath` / `hskCekCertPath` are gone from `teellm-production.json` and `teellm-docker.json`, and `loadServiceConfig`'s defaults are empty — a non-empty default would have re-injected `/root/taa/certs/…` into a template that no longer names them, and `HygonHardwareProvider.GetEvidence` fails the handshake when a configured file cannot be read (pinned by `TestLoadServiceConfigDefault`). `deploy-llm.sh` loses `resolve_certificates`, the two `prepare_config` arguments that wrote the paths, the `scp`/`container_cp` of both files and the create-path refusal when none were found; `build-teellm-image.sh` no longer requires, copies or verifies them, and `/opt/teellm/certs` is not created. The certificate fields and the `-hrk` / `-hsk-cek` flags remain for a peer that still wants the chain. **Two consequences to know about**: the evidence now carries an empty chain, so a TAA configured with `skipChainVerify: false` rejects this gateway with `ErrMissingCertChain` — chain verification and this deployment shape are mutually exclusive; and a `teellm-service` that falls back to its mock evidence provider becomes indistinguishable from hardware to a chain-skipping TAA, because the mock authority signs a valid PEK report and the templates leave `attestation.measurement` empty. The deployment's `/dev/csv-guest` check and its hardware-provider log gate are therefore the only detector, which is why both stay.
- **The Removed `attestation` Config Block And The Certificates It Named Are Gone Everywhere**: since the report self-check stopped walking HRK → HSK → CEK, `attestation.hrkCertPath` / `attestation.hskCekCertPath` had no reader, and the files they pointed at (`deploy/certs/*.cert` copied to `/etc/taa/certs` by the initrd build and to `/root/taa/certs` by `deploy.sh`) served nothing on the TAA side. The block, its struct and its defaults are deleted from `internal/config`; an older rendered config that still carries the block loads unchanged, because unknown keys are ignored (pinned by `TestLoadStartupConfigIgnoresTheRemovedAttestationBlock`). The four shipped templates, `deploy.sh` (both the `save` and local-Docker copies and the remote path), `deploy/guest-build/build-initrd.sh` (the two `TAA_*_CERT_SRC` inputs and the `install` lines) and the deployment docs no longer mention or copy the certificates. **One consequence to know about**: `codeAudit.llm.hrkCertPath` / `hskCekCertPath` still default to `/root/taa/certs/…`, and TEE-TLS does verify the HRK → HSK/CEK → PEK chain (`VerifyChain: true`) with the HRK anchor required from local material — the provider returns nothing when the file is absent, and the verifier refuses the peer with `ErrMissingCertChain` rather than trusting the chain the gateway carries in its own evidence. A TAA container that no longer receives the certificates therefore fails the TEE-LLM handshake unless it skips the chain — which the shipped templates now do through `codeAudit.llm.attestation.skipChainVerify` (see the Added entry). A deployment that wants the chain checked instead mounts `hrk.cert` and `hsk_cek.cert` at that path or points `codeAudit.llm.hrkCertPath` / `hskCekCertPath` at wherever they are mounted. The TEE-LLM deployment scripts and image no longer copy or bake certificates either (see the entry above); `deploy/certs/` stays in the repository only for `pkg/csvattest` tests and `tools/csv2-vm`'s chain smoke run.
- **A Semgrep That Cannot Start Falls Back To The Regex Engine**: constructing the Tier 1 engine used to be all-or-nothing — `codeAudit.codeScan.engine=semgrep` with a rules path that did not exist made TAA exit FATAL at startup, and the supervisor restarted it every 10s while the readiness gate kept failing, which from outside looks like a hung service. `buildSecurityConfig` now catches that one failure, logs `WARNING: [codeaudit] semgrep engine unavailable (...); falling back to the built-in regex engine`, and starts on the regex scanner, so a missing payload archive or rule tree costs the deployment the semgrep tier instead of the whole instance. The fallback is narrow on purpose: it applies only when semgrep was selected and only to the construction error, and it is visible in the startup log and in the engine name each report carries. An engine name this build does not know (`enforce`, or an empty value) is still refused — substituting a different engine for a name nobody configured would hide the mistake, and the configuration layer rejects those names before they reach here anyway. The regex baseline carries its rules in the binary, so the degraded scan is a real scan, not an empty one; it simply lacks the AST/taint coverage the semgrep packs provide. Deployment scripts keep provisioning the payload before swapping in a new binary, because an unprovisioned engine now degrades silently rather than failing loudly.
- **Data-Analysis Renders Production's `codeAudit` Verbatim, With Provisioning Skipped Explicitly**: `deploy-dataanaylsis.sh` used to rewrite the rendered copy of `configs/taa-production.json` to turn the audit switches and LLM off and drop the engine to `regex`, because `deploy.sh` decides whether to install the semgrep payload by reading that text. The rewrite was redundant at runtime — the loader's role gate (`server.type=data-anaylsis`, or `CONTRACT_TYPE=3`) already forces `EnableCodeAudit`, `BinaryAuditEnabled`, `EnableResultCheck` and `LLM.Enabled` off and the engine to `regex`, and `TestLoadStartupConfigDataAnalysisRole` pins that over the real template — so the rendered template now differs from production in exactly two keys: `server.type` and `storage.data`. The packaging coupling is cut on the packaging side instead: `deploy.sh` gains `TAA_SCAN_ENGINE_PROVISION` (`auto` by default, unchanged for every other caller), and the data-analysis script exports `skip`, which both `provision_remote_scan_engine` and `provision_local_scan_engine` honor with an early return before inspecting the template. Without that skip, `save` would extract a payload the image has no use for and `remote` would fail on a host that has no bundle — the previous behaviour relied on the render to avoid both.
- **Attestation Self-Check Verifies The Embedded PEK Only, Not The Certificate Chain**: TAA's report self-verification used to walk HRK → HSK → CEK → PEK before accepting a report, which ties the binary — and therefore an initrd image that carries it — to the machine whose vendor certificates were baked in: the same image on another CSV host fails the chain even though its report is genuine. `internal/attestation.VerifyReport` now asks `pkg/csvattest` for `VerifyChain: false`, so the check proves exactly one property: the PEK certificate carried inside the report signed the report body. It no longer takes certificate paths, `TAAState` no longer carries them, and `prepareAttestationReport` / `/v1/taa/getAttestation` no longer thread them through. `verifiedPass` keeps its meaning for the platform ("the report we generated is internally consistent"), and its failure behaviour is unchanged: a bad signature is logged as `WARNING` and startup continues. The `attestation.hrkCertPath` / `attestation.hskCekCertPath` keys are still parsed so older rendered configurations load unchanged, but nothing in TAA reads them anymore; no certificate is packaged with TAA, and the TEE-LLM gateway no longer ships its own copy either (see the entry above). Clients that want the chain checked — the teecrypto SDK's `VerifyReport(reportFile, verifyChain)`, for example — still have it available in `pkg/csvattest`.
- **State Sealing Key Source Is Detected, Not Configured (`storage.stateSealingKeySource` Removed)**: where the SM4 key for `state.sealed` comes from is now decided at startup instead of by the config file. TAA stats `/dev/csv-guest`: inside a Hygon CSV guest the node exists and the key is the hardware sealing key (`csv-hw`); anywhere else — docker, an FHE host, a developer machine — the node is absent and the key is derived from the SM2 private scalar. `storage.stateSealingKeySource`, its constants, its validation and the fhe-specific `csv-hw`→`sm2` resolution are gone, along with the field in all four shipped templates and the render in `deploy-dataanaylsis.sh`. The failure semantics are unchanged: once the device is detected as present, a failed ioctl still aborts startup rather than degrading to `sm2`, and any `stat` error other than "not found" is treated as present so an unreadable node is fatal instead of silently downgraded. A `storage.stateSealingKeySource` left in an older rendered config (deployed pods carry one on disk) is ignored rather than rejected, so upgrading the binary does not require re-rendering the config first. `TAASECRETKEY` recovery likewise keys off the detected source: without the device the variable is refused. The sealed file still records the source in its 8-byte header, so moving a state file between a guest and a non-guest archives it as `.orphaned.<unix>` instead of failing to decrypt.
- **platform-mock Lifecycle Owned By `deploy-platform-mock.sh`**: the build, start, stop, pid handling and readiness probe for platform-mock were copy-pasted between `deploy.sh` (local docker and remote k8s) and `deploy-fhe.sh` (remote or `--local`), and the copies had already drifted — the remote `deploy.sh` path passed no `-state-dir`/`-upload-dir`/`-allow-empty-attestation`, `deploy-fhe.sh` reused a running instance and cleared its register state, and only the local `deploy.sh` path wrote a pid file or waited for the status endpoint. The lifecycle now lives in one script with `local|remote` targets and `start|stop|restart|status` actions; both deployment scripts call it. Per-caller behaviour is preserved: `deploy.sh` still discovers the TAA Pod IP itself and omits state/upload/allow-empty on the remote path, `deploy-fhe.sh` still passes explicit state/upload directories, `--allow-empty-attestation`, `--reuse` and `--reset-register`, and builds with `CGO_ENABLED=0 GOOS=linux` through `--static`. `--reuse` probes before stopping, so it cannot kill an instance already serving the port. The local stop path uses `pkill -x` rather than `pkill -f`: the new script's own argv contains `--binary PATH`, and a `-f` match would have killed the script itself. Remote readiness now waits for `GET /api/register/status` (strict) instead of a fixed one-second sleep, and `start`/`restart`/`status` share the same endpoint. `deploy-fhe.sh` also loses the now-unused `host_detach` and `wait_for_platform_mock` helpers, and its mock build/upload moves into the platform-mock step; no ordering dependency exists between them and the image preparation.
- **Role Capabilities Come From `CONTRACT_TYPE`; One Template For Every Role**: `tee` training and `tee` inference now ship one `taa-env:slim-v2` image built from `configs/taa-production.json`; `data-anaylsis` keeps its jupyter base image and its own `taa-dataanaylsis:<date>` archive, but its config is rendered from the same template instead of a template of its own. The role, injected by the platform as `CONTRACT_TYPE` (or left in `server.type`), decides which config sections apply through a `roleCapabilitySets` table in `internal/config`: `tee` keeps the code audit and attestation; `data-anaylsis` keeps attestation and disables the audit, binary channel, result check, LLM and the semgrep engine; `fhe` disables both. A non-auditing role therefore no longer needs — or is trusted to carry — a template that happens to match it: the role wins over the file for the settings it makes impossible. `configs/taa-dataanaylsis.json` is gone; `deploy-dataanaylsis.sh` renders `server.type=data-anaylsis`, the jupyter data path and the audit-off switches into a copy of the shared template, then delegates to `deploy.sh`; `deploy-fhe.sh` injects `CONTRACT_TYPE=4` explicitly. The fhe base image stays `latti/latti-server-node:latest`: the FHE service (redis, `api_server`, worker and CUDA userspace libraries) must share the container network namespace with TAA, so only the TAA payload, the template schema and the role logic are shared with the other roles, not the base image.
- **A Failed Training Run Reports Why, Not Just The Exit Status**: `/v1/taa/reportRes` used to carry `执行 runtimeConfig 失败: runtimeConfig command exited with error: exit status N` and nothing else, so an operator saw the code of a failure whose cause the guest had already captured in memory and written only to its own log. The message — and the report's `failure_reason`, which carries the same text — now appends the **tail** of the command's combined stdout/stderr under `进程输出（末尾）:`. The tail is kept rather than the head because progress logging fills the head while the traceback or last error line sits at the end. It is capped at 4096 bytes with a `...(已截断，共 X 字节，仅显示最后 Y 字节)` notice, cut on a rune boundary: the message crosses the platform API into a store TAA does not control, and the captured buffer itself is unbounded. No section is appended when the command never started (nothing was captured) or when the run was cancelled by `stopTraining` (which reports nothing at all). The full output still goes to the TAA log unchanged, and the report schema is untouched — only the existing string fields grow.
- **`deploy-llm.sh --create-pod` Resolves The TEE-LLM Image From The Registry**: the Pod image tag is the date the image was built, so the previous default — today's date — named a real image only on the day of the build. Deployed a day later it produced the most expensive failure this script has: the Pod was applied, its confidential VM booted, and the in-guest CDH then failed the pull, leaving the Pod in `ImagePullBackOff` with the guest already resident. Before rendering the manifest on the create path, the deployment now asks the registry's `/v2/teellm/tags/list` for the newest date tag and uses that. An explicit `TEELLM_POD_IMAGE` is never replaced — the operator's choice can name a tag a listing does not show — and a listing that cannot be read (401, unreachable, filtered) falls back to the guessed tag with a warning, because the deploy host's view of the registry says nothing about whether the guest can pull. `TEELLM_IMAGE_REGISTRY` / `TEELLM_IMAGE_REPO` name what is queried. The existing-Pod path does not query at all: its image is immutable.
- **Packaging Names Are One Rule Across The Repository**: each packaging path now produces `<repo>:<YYYYMMDD>` and `deploy/out/<repo>-<YYYYMMDD>.tar.gz` — `taa-train-infer`, `taa-fhe`, `taa-dataanaylsis`, `teellm`. `deploy.sh save` had been appending the date to the base image's tag (`taa-env:slim-v2-<date>`), which both embedded a version that no longer described the contents and made the output name depend on `--base`; `build-teellm-image.sh` repeated its repository name inside the tag (`teellm:teellm-<date>`) and used its own archive prefix. `deploy-fhe.sh` and `deploy-dataanaylsis.sh` already followed the rule. Base and intermediate images (`taa-env:slim-v2`, `jupyter-nologin-full:v2.2`, `latti/latti-server-node:latest`, `teellm-base:<date>`) are inputs and keep their names.
- **`deploy-fhe.sh taa save` Reloads The Base Image From The Bundle**: a save run used to skip `docker load` whenever `latti/latti-server-node:latest` already existed, so a host that had deployed an older bundle packaged that older image under the new tag — the FHE service side stayed at the previous version while TAA was rebuilt, and the resulting package paired a new binary with the service it was not built against. The save path now verifies `image/latti-server-latest.tar.gz` against `SHA256SUMS` and loads it unconditionally, which moves the tag to the image the bundle ships. Only when no archive is present does it fall back to the tag already loaded, and that case warns that the version is unchecked. The closing banner prints the base image ID so the packaged service version is visible.
- **FHE Progress Reports Follow The Service Instead Of Counting Finished Cases**: `internal/fhe` used to derive the platform's percentage from the case list alone — `done/total` over cases with a `result_id` or `error` — so a task bar only moved when a case finished and sat still for the whole of a long case. It now parses the task-level `progress` field the v1 service reports (a finished case counts 100, a running case contributes its own percentage, capped below 100 until the task ends) and forwards it unchanged on every poll; the runner callback changed from `(done, total int)` to `(percent float64)`. A service that predates the field omits it, and `TaskStatus.ProgressPercent` falls back to averaging the per-case `progress`/`status` values, which is the same scale at case granularity. Out-of-range values are clamped because `ReportProgress` rejects anything outside 0-100, and the explicit final 100% report on success is unchanged. The handoff bundle under `latti-fhe-handoff/` is synced to the v1 package this targets: the image is rebuilt (the env loses `HEONGPU_DEVICE_POOL_MAX_BYTES`, the app layer adds the task-level progress and `malloc_trim`), the client archive is renamed `latti-e2e-0.1.2-v1.zip`, and the docs and `SHA256SUMS` follow; the model files are byte-identical.
- **`deploy-fhe.sh` Deploys One Unified FHE + TAA Container**: the handoff bundle now ships a self-contained `latti/latti-server-node:latest` (redis, `api_server`, worker, FHE runtime and CUDA libraries), so the separate three-service compose stack, the runtime staging and `./deploy-fhe.sh fhe` are gone. `./deploy-fhe.sh taa` starts one container from that image and injects the TAA binary, the supervisor and the rendered config at start time; the container runs the image's own `/opt/entrypoint.sh` beside `deploy/taa-fhe-entrypoint.sh`, which restarts the supervisor when it exits on its own and exits with the FHE entrypoint's status when that one dies, so the restart policy acts on real FHE failures instead of a wrapper that always looks alive. Port 58996 is never published: TAA reaches the FHE API at `127.0.0.1:58996` over container loopback and the callback reaches TAA at `127.0.0.1:6001`, so a leftover compose stack on the host cannot collide with this container; only 6001 is published, because the platform drives TAA over the host. Redis persistence is bound from `HOST_FHE_REDIS_DIR` (`$HOST_DATA_DIR/redis-unified` by default) instead of `$HOST_DATA_DIR/redis`, because a leftover stack's newer `redis:7-alpine` writes an RDB version the image's redis 7.0 refuses to load, which made the unified container exit on boot. The container runs on `bridge` (`TAA_DOCKER_NETWORK=host` is refused, since it would put 58996 back on the host), and `PLATFORM_IP` is defaulted to the bridge gateway plus `PLATFORM_PORT` and injected with `-e`, because `127.0.0.1` inside the container is the container itself. A re-run reuses the container only when image, binds, environment, network, entrypoint, published port, restart policy and GPU request all match; a running container is refreshed in place by stopping the supervisor and replacing the files atomically. `taa save` now builds `taa-fhe:<date>` **from the FHE image** with the combined entrypoint as `ENTRYPOINT` and `WORKDIR /root/taa`, exports the archive, uploads it and `docker load`s it. `HOST_RUNTIME_DIR`, `HOST_REDIS_DIR`, the `NODE_*` runtime variables and `REMOTE_HANDOFF_DIR` are gone, and the models are staged with `rsync -a` without `--delete`, so models an operator added survive a re-run.
- **`fhe.callbackBaseUrl` And `fhe.callbackToken` Are Removed; The Address Is Derived From `server.addr`**: the callback is a loopback hop between TAA and an FHE stack sharing its network namespace, so neither key described anything the operator could usefully decide. The base URL is now always `http://127.0.0.1:<port>`, with the port taken from `server.addr` at startup — one image is correct on every host it lands on, and a `server.addr` that does not name a port is a startup error instead of a callback that silently times out. Authentication is gone with the token: the FHE service treats `callback_url` as opaque and never had a use for the value, so with no token to check the old handler would have rejected every callback and left polling as the only completion path. The handler now answers 404 to any source that is not a loopback address, which is what keeps an unauthenticated POST from being reachable off-box. The two keys are **rejected by startup validation rather than ignored**, because silently dropping `callbackToken` would downgrade a deployment that still expects authentication without saying so; `configs/taa-fhe.json` and `deploy-fhe.sh` no longer carry them (`TAA_CALLBACK_BASE_URL` and `TAA_CALLBACK_TOKEN` are gone), and the deployment assumes the FHE stack shares the TAA host's network namespace. The earlier `auto` sentinel and its host lookup are removed with the field they served.
- **`taa save` Bakes The Rendered FHE Config Into The Image**: the packaged image carried the binary and `deploy/start.sh` but not `taa-config.json`, on the reasoning that the deploy path installs its own copy at start time. That left the image unbootable anywhere else: `save` bakes `ENTRYPOINT ["bash","/root/taa/start.sh"]`, so a k8s Pod or a bare `docker run` started `taa` with no config, hit `load startup config: read startup config taa-config.json: no such file or directory`, and sat in the supervisor's 10s restart loop. The save path now renders `TAA_FHE_CONFIG` with the same jq filter the deploy path uses — `fhe.endpoint`, `fhe.dataDir`, `fhe.keyCacheDir`, `storage.result` and `storage.keys` — validates the three stateful paths against the two binds, and copies the result to `/root/taa/taa-config.json` before committing. No callback input is required any more, because the address is derived from `server.addr` at startup; `render_taa_config` takes a `0` argument to skip the remote upload the save path does not need. A `deploy-fhe.sh taa` run still renders and copies its own config over the baked one, so the deploy path's behaviour is unchanged. The save step also removes a stale `taa.log` and `manual`/`manual-teellm` markers inherited from the base image, because the former presented a previous deployment's log as this image's own and the latter would have made a freshly packaged node start paused.
- **The Contract Environment Variable Is Now `CONTRACT_ID`**: `platform.contract` used to be seeded from `CONTRACT`, which the orchestration platform injects alongside `PLATFORM_IP` and `DOCKER_ID`; it is now read from `CONTRACT_ID`. The config key, its file-wins precedence and the `deploy.sh` behaviour are unchanged — the script accepts `CONTRACT_ID` and writes it into the generated config exactly as before — and the docs, OpenAPI description and `taaSecretKey` derivation notes follow. **A deployment that still sets only `CONTRACT` starts with an empty contract**, which silently changes the `taaSecretKey` derivation input, so the two sides must switch together or previously reported `TAASECRETKEY` values stop decrypting.
- **Persistent State Can Be Sealed With The Hygon CSV Hardware Key (`storage.stateSealingKeySource`)**: `state.sealed` used to be sealed with a 16-byte SM4 key derived from the SM2 private scalar D (`SM3(D || "TAA-STATE-SEALING-V1" || 0x00000001)[:16]`), and that private key sits in cleartext PEM in the same directory — so the trust root for the file was as readable as the file. `pkg/csvattest.GetSealingKeyIOCTL` already read the 32-byte hardware sealing key out of a CSV attestation report (session-MAC and mnonce verified, report offset `0x9b4`) but had no production caller. A new `storage.stateSealingKeySource` selects where the key comes from: `csv-hw` fetches the hardware key through `/dev/csv-guest` and derives the SM4 key as `SM3(hwKey(32) || "TAA-STATE-SEALING-CSV-V1" || 0x00000001)[:16]`, and `sm2` keeps the legacy derivation. The label differs from the SM2 one so equal input bytes never collide, and an all-zero hardware key is rejected because the ioctl can succeed while the report's sealing-key field is zeroed. **There is no fallback**: a missing device, a failed ioctl, or an unusable key aborts startup, which is what `configs/taa-production.json` and `configs/taa-initrd.json` select; `configs/taa-docker.json` and `configs/taa-fhe.json` stay on `sm2` — the FHE instance is not a CSV guest, and config validation rejects `csv-hw` for `server.type: "fhe"` rather than letting it fail later at startup. An old binary ignores the new key silently and keeps sealing with SM2, so config and binary must ship together, and moving `configs/taa-initrd.json` changes a built initrd's boot MEASUREMENT. The sealed file now carries an 8-byte cleartext header — magic `TAAS`, format version `1`, a source byte (`1` = `sm2`, `2` = `csv-hw`), two reserved zero bytes — ahead of the unchanged `nonce(12) || ciphertext || tag(16)` payload; a file is treated as new-format only when every field validates, so an old file (whose random nonce makes a false match ~2^-56) keeps reading as `sm2`. **Switching source archives rather than migrates**: a source mismatch is a typed error that renames the old file to `.orphaned.<unix>` and rebuilds clean state on every start, reusing the existing drift mechanism, while a same-source decryption failure stays fail-closed. `DetectAndHandleKeyDrift`'s `isNewKey` argument now means only that the SM2 key pair was just generated, so `csv-hw` never passes it — otherwise a regenerated SM2 key would archive a perfectly good hardware-sealed file. **The hardware key is host/chip-bound, shared by the VMs on one machine, and therefore not a per-VM identity**: sealed state cannot move to another host, where it fail-closes instead, and recovery means archiving `state.sealed` and rebuilding. The header is unauthenticated by design — whoever can write it can already delete the file, so the trust model is unchanged. `deploy/guest-build/taa-init.sh`'s missing-minor warning now says the `csv-hw` key is unavailable as well as that attestation degrades.
- **`docker save` Now Packages A TAA-Only Image, Engine Included**: the packaging action used to compose whatever the base image happened to hold: it compiled `taa`, copied the certificates and the generated production config, and committed. Two things it never did are now part of it. It **provisions the code scan engine**: the default base image (`taa-env:slim-v2`) carries no `semgrep` and no rules directory, while `configs/taa-production.json` selects the semgrep engine, and `codeaudit.NewEngine` treats a missing rules path as a hard error rather than a downgrade — so an image packaged without one started, failed, and then sat in the supervisor's 10s restart loop. The engine now comes from the container payload archive the remote and kata paths already use (`deploy/guest-build/build-semgrep-payload-container.sh` → `out/semgrep-bundle.tar.gz`, `SEMGREP_PAYLOAD_BUNDLE`), extracted with `tar -xzf - -C /` so packaging itself needs no network, with the bundle's own `MANIFEST` checked against `SEMGREP_VERSION` (1.177.0) so a stale archive fails instead of shipping; the rules are copied separately from `SEMGREP_RULES_SOURCE` into the path the template names, so a rules edit does not force a payload rebuild. As on the remote path, presence is not treated as proof — the same bounded, offline scan probe runs with the argv `taa` uses at audit time, and a failure aborts the packaging. It also **installs the supervisor from this repository** (`deploy/start.sh`, the 3082-byte version with the flock singleton guard) instead of inheriting the base image's stale 858-byte copy, because `save` had never copied it and the ENTRYPOINT was whatever the base image carried. And it **strips TEE-LLM and ollama**: every artifact enumerated from the combined images this repository produces (`/root/taa/ollama*`, `teellm-service`, `start-teellm.sh`, `.start-teellm.lock`, the teellm/model configs) is removed and then asserted gone one by one, so the same code covers both a slim base and an already-combined one, and a leftover fails the packaging rather than shipping silently. The resulting image is TAA plus the engine; TEE-LLM is a separate deployment (`./deploy-llm.sh`) and the image reaches it through the variable below. Order is strip → supervisor → engine → binary/certs/config, so the image is assembled once.
- **`TAA_LLM_ENDPOINT` Overrides `codeAudit.llm.endpoint`, And Is The One Variable That Does**: now that the LLM service is deployed independently, the endpoint baked into an image is only a default, so `TAA_LLM_ENDPOINT` lets a container be pointed at a TEE-LLM instance that does not live at that address without rebuilding. An empty or unset value leaves the configuration file's endpoint alone. **The precedence is deliberately the opposite of `PLATFORM_IP`, `DOCKER_ID` and `CONTRACT`**: those three are seeded in `defaultStartupConfig` as defaults that the config file then wins over, which only looks like runtime injection because the packaged config omits the platform block. The endpoint is written into every shipped template, so an environment value that could not override it would never take effect at all — hence a real override, documented in the code comment where the asymmetry would otherwise read as a bug. Relatedly, `resolve_llm_endpoint` in `deploy.sh` no longer bakes docker's placeholder into an image: a **stopped** container does not inspect as "no address", it returns the literal string `invalid IP` (the zero `netip.Addr` rendered), which is non-empty and was being written into the config as `https://invalid IP:8443` — a URL with a space in it. Only a dotted quad is accepted now, with `https://127.0.0.1:8443` as the fallback.
- **The `codeAudit` Block's Flat Scan Keys Are Now An `enabled` Switch And A `codeScan` Block**: `codeAudit` used to carry four flat keys for one thing — `codeScan` (the on/off switch), `codeScanEngine`, `semgrepRulesPath` and `semgrepTimeoutSeconds` — so the switch and the three settings it governs sat at the same level as `resultCheck`, `binaryAudit` and `llm`. The switch is now `codeAudit.enabled` and the settings are one `codeAudit.codeScan` object: `codeScan.engine`, `codeScan.rulesPath` and `codeScan.timeoutSeconds`. The engine name lost its `semgrep` prefix because the block already names the engine — the same reason `TimeoutSeconds` kept its unit but dropped the engine name, matching `semgrepTimeoutSeconds`'s sibling `requestTimeoutMs` under `llm`. `timeoutSeconds` moved with the other two rather than staying flat, even though it is the semgrep engine that reads it (`codeaudit.SemgrepLimits.Timeout`, resolved only in the semgrep branch of `NewEngine`): leaving it beside a block that holds the engine it belongs to would have been the split this change exists to remove. On the Go side `StartupConfig.CodeScanEngine`, `SemgrepRulesPath` and `SemgrepTimeout` collapse into one `CodeScan CodeScanConfig` (`Engine`, `RulesPath`, `Timeout`), the same shape the file now has and the same move the `LLM*` fields made when they became `LLM LLMConfig`. `EnableCodeAudit` keeps its name — bare `Enabled` on `StartupConfig` would be ambiguous next to `BinaryAuditEnabled`, `EnableResultCheck` and `LLM.Enabled`, and it is the file's own nesting, not the Go field's, that the rename was about. `configs/taa-initrd.json`, `configs/taa-docker.json` and `configs/taa-production.json` move in lockstep, and so do `deploy.sh` (its engine/rules reader now descends into `codeScan`), `deploy-docker.sh` (the derivation writes `codeScan.engine` and `codeScan.rulesPath` instead of the flat pair) and `deploy/guest-build/build-initrd.sh`, whose `taa_config_wants_semgrep` gate matched the literal `"codeScanEngine": "semgrep"` and now matches `"engine": "semgrep"` — a stale pattern there would have built an initrd with a semgrep config and no semgrep payload, which boots and then fails every import audit. **The old keys fail the load rather than being ignored**: `codeScanEngine`, `semgrepRulesPath` and `semgrepTimeoutSeconds` are declared solely so their presence is detectable, and a config carrying any of them exits with `uses removed keys:` naming both the old key and its new path, all of them in one message when several are present. `codeScan` needed more than a name because its *type* changed: a bool where a block now belongs would have surfaced as `cannot unmarshal bool into Go struct field`, a message that says nothing about where the switch went, so a custom unmarshaler replaces it with one that names `codeAudit.enabled` and the three keys the block holds. An explicit `null` is still treated as absent for every one of these, `codeScan` included. **This is breaking on upgrade, on the same terms as the rename that preceded it**: on the CSV2 initrd path TAA is a boot gate, so a binary and a `configs/taa-initrd.json` from opposite sides of this change do not boot the VM at all — the two must ship together, `deploy.sh` regenerates the `.local/run/*-taa-config.json` copies from the templates on the next deploy, a pre-built image needs rebuilding, and moving the initrd template changes the bytes of a built initrd and therefore its boot MEASUREMENT. The README's sample block, field table and remote-deploy note follow, and the three scan keys gain table rows they never had.
- **The `security` Config Block Is Now `codeAudit`, And `llm` Has Moved Inside It**: the two top-level blocks whose names no longer matched what they held are one block now. `security` was already the code audit (`codeScan`, `codeScanEngine`, `semgrepRulesPath`, `binaryAudit`) plus two settings that are not an audit of code at all — `resultCheck` (the plaintext-leakage check on training results) and `maxFileBytes`; and `llm` sat at the root even though the inference service exists for exactly one purpose, adjudicating the findings the static scan raised, which after TAA and TEE-LLM became separate deployments read as though TAA owned a model. `codeAudit` now holds all of it, with `llm` nested inside. `resultCheck` and `maxFileBytes` stay where they were inside the block rather than being split out, because that keeps the change to a rename and a move. The Go side already disagreed with the file — `controller.SecurityConfig` nests `LLM` and `Binary` inside one audit aggregate and `buildSecurityConfig` builds them together — so this makes the file say what the code already does. `StartupConfig.EnableSecurityScan` is renamed `EnableCodeAudit`, and the nineteen flat `LLM*` fields collapse into one `LLM LLMConfig`; `CodeScanEngine`, `SemgrepRulesPath`, `SemgrepTimeout`, the six `BinaryAudit*` limits, `EnableResultCheck` and `MaxFileBytes` stay flat, and `controller.SecurityConfig` keeps its name and layout (it also carries `ModelDir`, `DataDir`, `ResultDir` and the staging directories, which a name like `codeAudit` would misdescribe). Every rejection message that names a key now names its new path (`codeAudit.binaryAudit.maxArchiveMembers`, `codeAudit.llm.policy`, and so on), and `deploy.sh`, `deploy-docker.sh`, the templates, the README and the architecture doc moved in lockstep. **The old keys fail the load rather than being ignored**: `encoding/json` drops a key it does not recognise without a trace, so a config still written the old way would have loaded cleanly with every setting under `security` and `llm` discarded — the scan back on the regex baseline, the inference endpoint back to `127.0.0.1:8443` — and nothing in the log saying so. `security` and top-level `llm` are now declared solely so their presence is detectable, and a config carrying either exits with `uses removed keys: "security" (rename to "codeAudit"), "llm" (move under "codeAudit.llm")`, both named in one message when both are present. **This is a breaking change on upgrade, and a loud one**: on the CSV2 initrd path TAA is a boot gate, so a binary shipped against the old `configs/taa-initrd.json` does not boot the VM at all — the binary and that template must move together. A previously baked production image or an on-disk `.local/run/*-taa-config.json` carries the old shape; `deploy.sh` regenerates the `.local/run` copies from the templates on the next deploy, so those recover with a redeploy, while a pre-built image needs rebuilding. Moving `configs/taa-initrd.json` also changes the bytes of a built initrd and therefore its boot MEASUREMENT.
- **The Key Store Moved From `/opt/taa/keys` To `/root/taa/keys`**: `storage.keys` now sits under the same prefix as `storage.model` / `data` / `result` and the attestation certificates, instead of being the one secret directory left under the `/opt/taa` runtime prefix. The two deployment paths that already rewrote it — `deploy.sh` for docker and remote, which passes `$TAA_CONTAINER_WORKDIR/keys` — were setting `/root/taa/keys` all along, so only the production image path (a literal `/opt/taa/keys` in `deploy.sh`) and `deploy-docker.sh` (which created the directory) were actually out of step; both now agree with the templates, and `deploy-docker.sh` no longer creates a second, unused keys directory. The in-code default (`config.StartupConfig.KeysDir`), the two empty-value fallbacks in `internal/app/taa`, the three templates, the README and the architecture diagram moved with them. **This is a breaking change on upgrade**: an instance that already ran under `/opt/taa/keys` will not find its SM2 key pair or `state.sealed` at the new path, so TAA generates a fresh key pair and the old sealed state is left behind. `configs/taa-initrd.json` moved too, which changes the bytes of a built initrd and therefore its boot MEASUREMENT — the initrd in `deploy/guest-build/out/` predates this change and needs a rebuild.
- **A Leaking Result Directory Is Reported As A Rejected Run, Without `result_files`**: when the training-end plaintext leakage check finds training data (or other high-severity plaintext) in the result directory, TAA now reports that run to the platform as failed: `/v1/taa/reportRes` goes out with `code` `2` and the reason in `msg` (`结果目录包含原始训练数据，训练结果拒绝提供目录清单与预览: <details>`), the report body says `training_task.status` `failed` with the same reason in `failure_reason`, and the report carries **no `result_files` at all** — the directory tree's table previews are the data rows being withheld, so TAA does not even scan for them. `exit_code` stays `0`: the training process itself exited cleanly, it is its artifacts that are refused. `code` `2` is distinct from `1` (the run failed on its own) so the platform can tell the two apart. This replaces the earlier `result_files.contains_dataset` boolean, now removed: withholding the tree says more than a flag inside it, and the flag's `absent means never checked` third state is no longer needed. A check that could not run — a verdict recording `error`, no verdict at all, or `security.resultCheck.enabled` off — is **not** a rejection: the report is delivered normally, tree included, and only the export gate's `llm.failClosed` behavior applies. `/v1/taa/export` is unchanged and still returns `400` for a leaking verdict.
- **`training_report.json` Is Packed Out Of The Export And Skipped By The Leakage Check, So The Report Now Carries Table Previews**: the report's `result_files` tree previously shipped previews off, because that report lands inside the result directory and was therefore packed into the `/v1/taa/export` archive — previews there would have sent dataset rows to whoever downloads the export. The report is now excluded from the export archive instead (root matches only: a file of the same name deeper in the tree is still packed), the leakage check skips the same file for the same reason, and the report's tree returns previews like `/v1/taa/getResourceInfo` does (unless the check rejected the run — see below), so the platform sees the sample rows it needs alongside the structure. The report still reaches the platform through `/v1/taa/reportRes`; only the export archive loses it, and the export endpoint still requires it to exist (404 otherwise). The packer's exclusion list and the check's skip list are the same constant, so neither can drift from the file actually written.
- **The Result Leakage Check Moved From Export To The End Of Training**: with `security.resultCheck.enabled` on (the default), the plaintext leakage scan now runs once, right after a training run collects its artifacts and before `training_report.json` is written, and its verdict (`passed`, high-severity `details`, `checkedAt`) is persisted on the task's import index record. `/v1/taa/export` reads that verdict and no longer scans the result directory, so the response starts streaming immediately instead of after a full rescan — on a ~85 MiB result this was ~80 s of a response with zero bytes on the wire, long enough for the caller's timeout to close the connection and turn the first write into a broken pipe. The gate itself is unchanged in what it blocks, and fail-closed in three explicit states: a failing verdict returns the same 400 with the same message as before, a verdict recording that the check could not run returns 500, and a record with no verdict at all (committed before this field existed) also returns 500 until the task is retrained. The two states without a usable verdict are governed by `llm.failClosed`: with it `false` a missing or failed verdict is logged as a warning and the export proceeds, because an operator who has already accepted advisory LLM verdicts should not be blocked by a check that never produced one. A verdict that says the result leaks is not affected by that switch and always returns 400. Two deliberate side effects: `training_report.json` is no longer scanned (it is written after the check, and the check skips it explicitly since the report now carries table previews by design), and a failing check never fails the training process — `exit_code` stays `0` and the report is still delivered, though the run is reported as rejected (see the change above).
- **The Export Public Key Is Optional End To End**: `publicKey` is no longer a required input anywhere in the export chain. `/v1/taa/importModel` accepts a request without one — nothing is validated, nothing is saved, no failure is reported — and `/v1/taa/export` no longer returns 400 for a phase 3 export that has no key available. Phase 3 now resolves its encryption key in order: the key saved at model import → the `publicKey` carried by the export request → plaintext. Phases 1/2 are unchanged (request `publicKey` → plaintext). The consequence is deliberate: a platform that never supplies a key receives phase 3 artifacts in plaintext rather than an error, where the 400 previously was what blocked a cross-phase plaintext export.
- **Model Code Audit Is Now Advisory**: A failing model code audit no longer blocks anything. Its verdict is reported to the platform as a reference result (`/v1/taa/reportAudit`, codes `0` pass / `1` fail / `2` no verdict) and decides nothing on the TAA side: a failing or interrupted audit neither rolls back the import nor cancels a running training, so the model stays imported and trainable and the package on disk stays exactly as uploaded. Previously a failing verdict cleared `ModelImported` and stopped the active training. Concurrency is unchanged: a model import is still refused while another audit is running, and the 409 busy responses are unrelated to the verdict. The crash-recovery path now only reports the interrupted audit instead of rolling the import back, and the audit summary no longer claims TAA blocks the import.
- **The Historical `type` Field Is Fully Ignored on Resource Delivery**: `/v1/taa/import` no longer presents `type` (1=model, 2=debug data, 3=training data) as a routing input. It never was one — the request struct has no field for it, so decoding dropped it and no branch consulted it — but the API spec required it and the architecture diagrams routed on it. The field is now marked ignored on both endpoints, and which resource a request carries is decided by the endpoint alone.
- **The Data Import Endpoint No Longer Accepts `publicKey` Or `runtimeConfig`**: `/v1/taa/import` reads neither field; both take effect where they are already read — `/v1/taa/importModel` saves the export public key at phase-1 model delivery, and training executes the `runtimeConfig` saved there. A request that still carries them is accepted and the two fields are ignored, with a warn log naming them, because a second source for the same setting means the run executes whichever endpoint spoke last and only one of the two ever had a documented precedence. For a platform that sends `runtimeConfig` with its data, the training that this delivery triggers therefore runs the configuration saved at model delivery; if no model delivery saved one, the preconditions fail as before and `/v1/taa/reportRes` reports a run that has an empty `runtimeConfig`.
- **Toolchain Reorganization (`tools/`)**: Reorganized auxiliary tools into top-level `tools/` directory, moving platform mock to `tools/platform-mock/` and cryptographic tools to `tools/sdk/`.
- **Go Workspace Orchestration**: Configured `go.work` multi-module workspace orchestrating `taa`, `teellm`, `teetls`, and `tools/sdk` on Go 1.22+.
- **Configuration Templates**:
  - Streamlined `configs/taa-docker.json` and `configs/taa-production.json` by removing backend LLM server-specific paths.
  - Added `attestation` certificate path configurations (`hrkCertPath`, `hskCekCertPath`) and TEE-TLS transport parameters.
- **Deployment Script (`deploy.sh`)**: Refactored root `deploy.sh` to focus exclusively on `taa` and `platform-mock`, delegating LLM model distribution and runtime management to `teellm/deploy.sh`.
- **Dynamic File Size Threshold**: Replaced hardcoded size limits with configurable `maxFileBytes` (default 3 GB) for export data leakage inspection.
- **100% Training Progress Now Waits For The Result Leakage Check**: the progress watcher used to report the model's `{"percent":100}` the moment it read it, which is the moment the model finished training — while TAA still had to collect the artifacts out of the model output directory and run the plaintext leakage check over them (measured at up to 80 seconds on a real result directory). The platform therefore saw a finished task while TAA was still working on it. A snapshot at 100% is now parked in the watcher instead of sent, and released once the pipeline is past the check, whatever its verdict: a result directory the check rejects is still a run that reached its end, and the rejection travels to the platform through `reportRes` code 2. A model that never reported 100% gets nothing invented for it, and neither does a run that fails or is stopped before the release point — 100% now means TAA carried the task to its end.

### Removed
- **The Boot-Time `taa.required` And `taa.require_attestation` Gates**: the initrd's PID 1 used to hold the VM hostage on a TAA failure — `TAA_REQUIRED=1` turned "TAA did not start" or "the attestation degraded to an empty report" into `while true; do sleep 3600; done`, so kata-agent never started and the Pod stayed NotReady forever; `TAA_REQUIRE_ATTESTATION=1` added a 60-second wait for the `attestation report verified successfully` line and failed the boot when it did not appear. Both are gone, along with their `taa-init` allow-list entries, their kernel parameters, their `/etc/default/taa.env` lines, and their keys in `config/env.txt` (eight identity keys remain). The boot path now always reaches `exec /sbin/init`: a missing `/etc/taa/taa-config.json` or a TAA that exits within two seconds is logged to the serial console and the guest's `/tmp/taa.log`, and the VM comes up regardless. Two reasons. The gate made a daemon failure indistinguishable from a broken node — a Pod that never becomes Ready yields no logs, no events and no `kubectl exec`, which is the opposite of what an operator needs while TAA itself is being tested, and it made every unrelated defect (a bad public key, an unreadable config, a csv-guest minor that could not be resolved) present as the same symptom. And the guarantee it appeared to give was never one: the attestation self-verification is TAA checking its own report, so holding kata-agent hostage proved nothing about the report to anyone but TAA, while the report itself is still produced, still logged, and still what the platform verifies. The verdict line is still written, so `./deploy-taa-vm.sh verify` and the guest log remain the place to look. **On upgrade:** `TAA_REQUIRED` / `TAA_REQUIRE_ATTESTATION` in a build environment are now ignored, and a `config/env.txt` still carrying `taa.required` or `taa.require_attestation` makes `install.sh` refuse with `unknown identity key` — delete those two lines.
- **`deploy.sh`'s `docker` Mode And `deploy-platform-mock.sh`'s `local` Mode**: both local deployment paths are gone. `deploy.sh` now has a single target — the remote Kata CSV2 Pod — and `docker`, `local` and `local-docker` exit non-zero with "mode has been removed"; the `remote` word goes with it — it named the only remaining target, so `./deploy.sh remote taa` is now an unknown argument and `./deploy.sh taa` is the only spelling. With the mode went the code only it reached: `ensure_local_docker_container`, `deploy_docker_taa`, the container stop branch, `--container`, the `LOCAL_DOCKER_*` / `LOCAL_PLATFORM_*` / `TAA_TEELLM_PORT` overrides and the unused pidfile/TCP/HTTP readiness helpers. The reason is the one that removed `deploy-llm.sh`'s docker target: a plain Docker container has no `/dev/csv-guest`, so a locally deployed TAA can never produce a real attestation, and keeping a second configuration flow meant every change had to be made twice. **`save` is kept, as a standalone action** (`./deploy.sh save`) that packages the production image and deploys nothing: `deploy-fhe.sh taa save`, `deploy-dataanaylsis.sh save` and the Pod-creation path all still use it, and the image-assembly functions (`save_local_docker_image`, `strip_teellm_from_image`, `provision_local_scan_engine`, `docker_cp_into_container`) stay because the remote Pod build reuses them. `deploy-platform-mock.sh` now always targets the remote host over SSH: the old `remote` word is gone too, so the action comes first (`./deploy-platform-mock.sh start --host ...`), `local` fails with an explanatory error, and `--static` is gone because the build is always static. **On upgrade:** a script still running `./deploy.sh docker ...` or `./deploy-platform-mock.sh local start` exits non-zero with the removal message — `docker save` becomes `save`, `remote <action>` loses the word on both scripts, and mock lifecycle commands need `--host` or `REMOTE_HOST`.
- **The Binary Audit Channel Is Off In The Shipped Templates**: `configs/taa-production.json`, `taa-initrd.json` and `taa-docker.json` now set `codeAudit.binaryAudit.enabled` to `false`. Two facts decided it. First, the channel's evidence is symbol-level: it reads `.dynsym` and `DT_NEEDED`, so it proves a library *imports* `socket` or `system`, never that its control flow can reach one - which is why the import of a legitimate model package carries the channel's findings while a `dlopen`-with-a-built-string payload carries none. Second, on real packages its 50000-line evidence ceiling fires routinely: 4 of the 12 wheels in the DPN example package reach it, the smallest being a 3.4 MB `lightgbm` wheel, and each one adds "二进制可执行文件未完整扫描" to the audit conclusion. A channel whose evidence is too coarse to act on and whose completeness note fires on ordinary input is not worth the noise it costs, so it stays in the tree and out of the templates. **The code default is unchanged (`true`)**, so a deployment that writes no `binaryAudit` block - `fhe` and `data-anaylsis` do not - still gets the channel; disable it explicitly there if that is wanted. Turning it off is the rollback the channel was designed for: the audit is byte-for-byte the one produced before the channel existed. Re-enabling is gated on the control-flow work tracked in `.claude/plans/2026-11-04-binary-cfg-todo.md`.
- **The Binary Audit Channel's Coverage Limits (`maxArchiveMembers`, `maxFullScanBytes`, `maxStreamBytes`)**: the channel used to stop reading at three configurable cuts — after 4096 archive members, above 64 MiB per file (head and tail only), and after a 3 GiB per-file read budget — plus an in-code 64 KiB cap on a pickle operand and a 1024-byte cap on a printable-string run. Every one of those cuts is now gone: every container member is opened, every file and every decompressed stream is read to its end, a pickle operand of any length is resolved rather than turning the stream into a gap, and an unbounded printable run is kept whole. The reason is that a coverage limit is indistinguishable from an evasion — a literal in the middle of a large file, or a target past the 4097th member, was never looked at, and the completeness accounting could only report that as a gap rather than find it. The cost is proportional read time on the asynchronous audit path (at the measured 338 MB/s a 3 GiB shard is about nine seconds), which the audit can absorb because it does not block the import. **Three memory guards stay and are not configurable**: `MaxArchiveMemberBytes` (256 MiB decompressed member), `MaxEvidenceLines` (50000 distinct lines per file) and the pickle interpreter's 1M stack and memo slots. They bound memory, not coverage, and they are what keeps a hostile archive from taking the process down — a Go OOM is a `fatal error`, not a `panic`, so no handler can turn it into a failed audit. **The three removed config keys now fail the load**: a config still carrying `codeAudit.binaryAudit.maxArchiveMembers`, `maxFullScanBytes` or `maxStreamBytes` is rejected at startup with a message naming each key and saying what replaced it, because `encoding/json` would otherwise drop them silently and an operator who was relying on a cut would see the scan quietly widen. On upgrade, delete those keys from the file; the shipped templates never set them.
- **`build-teellm-image.sh`**: the standalone image builder is deleted; its logic lives in `deploy-llm.sh` as `build_teellm_pod_image`, which the creation path calls itself. Two things made a second entry point a liability rather than a convenience: it had to be remembered and run by hand before `--create-pod`, and the two scripts each knew a piece of the answer (which tag, which paths, which payload), so a change to one silently disagreed with the other. The inlined builder keeps the same pipeline — load `TEELLM_IMAGE_BASE` when absent, derive a `teellm-base:<date>` copy with `/root/taa` stripped, copy binary/supervisor/configs into a throwaway container, stream the ollama runtime and the model in, create the soname links the bundle lacks, verify the payload, commit under `ENV`-declared entrypoint/CMD/`USER`/`WORKDIR`/`EXPOSE` — and takes over its configuration as `TEELLM_IMAGE_BASE`, `TEELLM_IMAGE_BASE_ARCHIVE` and `TEELLM_IMAGE_KEEP_BUILDER`. **New: the upload is skipped when the registry already holds the same build.** Committing the image is how its ID is learned, so the build always happens; but before exporting anything the deployment reads the registry manifest for today's tag and compares its config digest with the local image ID (`docker image inspect --format '{{.Id}}'`). When they match, the multi-gigabyte `docker save`, the `scp` and the `docker push` are all skipped and the Pod is simply created against the registry tag. When they differ, the archive is exported, shipped and pushed as before — the remote push still lists and deletes the old tag first, so a re-push of a same-day tag does not collide. The builder container is removed through the deployment's existing `cleanup_display` rather than a private `trap`, because a second EXIT trap would have replaced the script's error banner.
- **`./deploy-fhe.sh fhe`**: the FHE services are no longer deployed as a separate compose stack; they run inside the unified container `./deploy-fhe.sh taa` deploys.
- **The `docker` And `remote-docker` Targets, And The `remote` Keyword That Named The Kubernetes One (`deploy-llm.sh`)**: `deploy-llm.sh` took a target keyword — `docker`, `remote-docker` or `remote` — and each one selected both a transport and a deployment body. Only the Kubernetes path could ever produce a working deployment, so the other two are gone and a bare `./deploy-llm.sh` now does what `./deploy-llm.sh remote` did. The reason is the same one that made `--create-pod` necessary: TEE-LLM needs `/dev/csv-guest` to produce a real CSV attestation, no docker container has that device, and `teellm-service` therefore falls back to a mock evidence provider whose HRK is regenerated on every start — TAA rejects every handshake with `untrusted HRK certificate` and reports the audit as failed under the fail-closed policy. A target that can only ever yield a deployment TAA refuses is worse than no target at all, because its failure is invisible at deploy time: the readiness probe's client sets `InsecureSkipAttestationVerify`, so the deployment reports success and the rejection surfaces later as a failed run. What goes with the keywords: `--container` and `--remote-container` with the `LOCAL_DOCKER_CONTAINER` / `REMOTE_DOCKER_CONTAINER` overrides; `ensure_target_container`, `container_facts`, `print_container_summary` and `allow_pod_access_to_container`; the docker transport layer (`shq`, `dk`, `ctr_cp_in`, `stream_files_into_container`) and the `REMOTE_STAGE_DIR` staging area that only `ctr_cp_in` read; and the `POD_CIDR` FORWARD rule, which existed to let the pod network reach a bridge-networked gateway that a Pod's own network does not need. `deploy-docker.sh` is deleted with them — its only purpose was to drive `deploy-llm.sh docker` to install TEE-LLM into the container it was about to commit as the `taa-env` image, and TEE-LLM is a separate Kata CSV2 deployment now. `deploy.sh`'s `resolve_llm_endpoint()` loses its `docker inspect` branch for the same reason, since it looked for a container the deleted mode used to create: `TAA_LLM_ENDPOINT` names a gateway running elsewhere, and loopback remains the fallback for one that shares taa's network namespace — the deployment summary prints the value to use. **On upgrade:** a script or habit that still passes a target keyword fails loudly with `unknown argument: docker` / `unknown argument: remote` instead of deploying somewhere else, `--create-pod` and `pod-down` are unchanged, and the rest of the `remote` vocabulary stays — "remote pod" and "remote host" are still accurate relative to the machine running the script. `tests/deploy_llm_remote_pod_test.sh` gains a case pinning the bare invocation to the same Pod lifecycle, since that is the only way in now, and the two tests over the deleted modes are removed.
- **The Model Checkpoint Staging Directory (`/opt/taa/checkpoint`), End To End**: `model.checkpoint` is gone from the configuration templates, along with the legacy flat `modelCheckpointDir` key, the `ModelCheckpointDir` field on the startup and security configs, `DefaultModelCheckpointDir`, and `SecurityConfig.GetModelCheckpointDir()`. TAA no longer creates the directory at startup or before a training run, no longer injects `TAA_CHECKPOINT_DIR`, `TAA_MODEL_CHECKPOINT_DIR` or `CIPHERFLOW_CHECKPOINT_DIR` into the model process, `deploy-docker.sh` no longer creates it, and the architecture document no longer lists it. Nothing read it: TAA itself only ever created the directory and passed the three environment variables, and the reference model package resolves its checkpoint output from `TAA_OUTPUT_DIR` instead, saving `net_XXX.pth` under the output root — which is where the artifacts actually get collected, delivered and leakage-checked. A model that nevertheless wrote to the old path was writing outside the delivered tree, so its checkpoints were silently discarded rather than resumed from. The platform-facing Protocol Buffer contract is deliberately untouched: `api/proto/cipherflow/v1/{checkpoint,sandbox,security}.proto` still declares the checkpoint/resume specification, which nothing in this repository generates code from or implements, and withdrawing it is a protocol decision rather than a configuration one.
- **The FHE Task Timeout (`fhe.taskTimeoutMs`)**: an FHE batch is long by nature, and the 30-minute default killed legitimate runs — a task that simply had not finished was reported as `failed` with `timed out after 30m0s`. `Runner.Execute` now carries no task-level deadline, `wait` has no expiry timer, and `CopyResult` streams on the caller's context instead of a task-sized budget. Per-call `fhe.requestTimeoutMs` still bounds each HTTP request, and the polling fallback and callback are unchanged; the only remaining bound on a whole task is the caller, so a service that never reports a terminal state keeps the import goroutine waiting instead of being failed at a fixed hour. The field is gone from `FHEConfig`, `fhe.Config`, the shipped `configs/taa-fhe.json` and the README. **On upgrade:** a config that still carries `taskTimeoutMs` loads and the key is ignored — it no longer prevents or shortens anything.
- **The Other Pod And Namespace Spellings (`--pod` And `--namespace` Are The Only Ones Left)**: the target Pod used to be named three ways — `--pod <name>` in `deploy-llm.sh`, a positional `pod=<name>` in `deploy-fhe.sh`, and the `TARGET_POD` environment variable in `deploy.sh` and `deploy-llm.sh` — and the namespace was either a positional `namespace=<ns>` (`deploy-fhe.sh`) or `TARGET_NAMESPACE` / `POD_NAMESPACE` in the environment, all defaulting to `osr`. All three scripts now take `--pod <name>` (or `--pod=<name>`) and `--namespace <ns>` (or `--namespace=<ns>`), and the removed forms exit non-zero with a message naming the replacement before SSH, docker or kubectl is touched: silently falling back to the default Pod or namespace would deploy somewhere the caller did not name, and on `deploy.sh` that means creating a tens-of-GiB confidential VM at the wrong target. Each script keeps its own Pod lifecycle under the unified flag — `deploy.sh` creates and deletes a Pod only when `--pod` was not given, and `deploy-llm.sh` still refuses a `--pod` that disagrees with `TEELLM_POD_NAME` for `--create-pod`/`update`/`pod-down`. **`deploy-llm.sh` accepts `--pod <name> start` again**: that spelling had been retired in favour of `update`, but it was the only remaining way into a plain `start` with a chosen Pod, and removing `TARGET_POD` without restoring it would have left no way at all; `update` remains the action for updating an existing Pod in place. On upgrade, replace `TARGET_POD=x ./deploy.sh taa start` with `./deploy.sh taa start --pod x`, `POD_NAMESPACE=... ./deploy-fhe.sh --pod x` with `./deploy-fhe.sh --pod x --namespace ...`, and drop `namespace=` from any `deploy-fhe.sh` invocation. `README.md`, `deploy.md` and `docs/architecture-design.md` use the new spelling throughout, and `tests/deploy_modes_removed_test.sh` pins the refusals and the help text.

### Fixed
- **The Platform-Mock Called A Stale Registration "已连接"**: the instance row rendered `已连接` whenever the platform had accepted a registration, which is a historical fact, not evidence that the instance answers now — nothing in the mock polls an instance. An instance whose Pod had been deleted hours earlier, or whose registered address was never routable from the platform host, still read `已连接` by default; on 116 the row for `kata-csv2-taa-test-0001` claimed a connection while `http://172.16.10.178:6001` refused every dial. The wording now states only what is known: an accepted registration reads `已注册` (registered, connectivity unverified), `连通正常` is reserved for a fresh passing 检查连通性, and `已连接` is no longer produced by the row at all. The list summary follows the same rule — it counts verified links, not accepted registrations, and names the unverified rows apart (`共 N 个实例，K 个连通正常，U 个已注册（连接未验证）`). The 环境 chip expires with the same 90-second window as the row instead of keeping a green `连通正常` indefinitely, because that chip was the last place a stale check still vouched for a live link. A failed check is deliberately kept rather than expired: "this identity did not answer when last tried" stays useful until the operator retries. `frontend_instance_state_test.go` pins the new fallback and the summary's counting rule; the README's console section is updated.
- **A Stopped Task Left Its Model Audit Running, And Extraction Could Not Be Interrupted**: two parts of a stopped task kept working after the platform had ended it. The model code audit is launched on a context of its own so it outlives the import goroutine (data delivery and training must not wait for it), which also meant a stop never reached it: the static scan and any LLM adjudication kept running for the model of a task the platform had already abandoned, and its verdict was still reported. `stopTraining` now cancels the audit when it belongs to the stopped task, matched by task id because the request names none — an audit left by an import that already completed is not touched, since a stop for the current task says nothing about it. The launch path closes the race from the other side: registration and the stop's abort share the state lock, so a handle already cancelled before registration drops the audit it would have owed (clearing the durable pending marker with it) instead of scanning it. The second part is extraction: the archive was always unpacked to completion, so a stop that landed there answered immediately while the package was still being written, and the task ended only at the next boundary. Extraction now runs under the task's context and stops at the next archive entry or data chunk; because it stages into a temporary directory and renames only on success, a cancelled extraction leaves the previous model or data directory exactly as it was. Tests cover mid-entry cancellation, the untouched destination, and both audit scoping directions.
- **`stopTraining` Had Several Ways To Answer A Stop That Had Already Succeeded**: five smaller gaps around the same interface. The FHE cancel ran on the incoming request's own context, so a platform that hung up or whose deadline fired while the cancel was in flight aborted the one outbound request that can stop the worker — the service never saw the cancel, the run went on to report a success nobody expected, and the 500 had no connection left to travel on; the cancel now travels on a background context, with `RequestTimeout` still bounding the call. The handler also read the published FHE id and only then cancelled it, so a run that ended in between — `Execute` returns and forgets it, the id is cleared and the stop handle detached — produced `ErrTaskNotInFlight` with no live handle and answered 500 for a task that had in fact finished; that case now answers `FHE 任务已结束` instead. `importModel` was missing the last stop check its data twin `import` already had, so a stop landing in the instant the download finished still answered `模型已接收` for an import the platform had ended (the async pipeline aborted anyway, but the two replies contradicted each other); the check is there now. `reportImportFailure` had no cancellation gate, so a stop that landed while an uninterruptible step was running and that step failed on its own sent a `reportRes` failure for a task the platform had already been told was stopped; it now ends the task through the same unwind the step boundaries use, releasing the import-index reservation. Finally, the 5 s wait answered 500 `中止训练任务超时` even when the process had already exited and only the pipeline's cleanup was still running — a failure reply for a stop that had taken effect; the handler now tells the two apart (the process binding is cleared right after `Wait`), answers 200 with the stop message when the process is gone, and keeps the 500 for a process that is still bound at the deadline.
- **A Stop That Landed While An FHE Task Was Being Staged Was Answered 500 And The Task Was Submitted Anyway**: the FHE task id was published before `Runner.Execute`, but the runner registers the run only at the end of staging — after the eval key download and the multi-gigabyte input copy — so a stop in that window named a task the runner had never seen: `Runner.Cancel` refused it, `stopTraining` answered `取消 FHE 任务失败` with a 500, and `Execute`, which ran on `context.Background()`, ignored the local cancel, created the task, landed its result and reported success for an import the platform had already ended. The id is now published from the runner's `OnCreated` hook, right after the service accepts the task, which is also the first moment a cancel can be scoped to its tenant; until then the stop reaches the task handle `tryAcquireTask` already created, and that handle's context is what `Execute` runs under, so staging aborts at the eval key download or before the create call. The runner also checks its caller's context once between staging and `CreateTask` (the input copy itself is not interruptible) and, when a cancel lands after the create, cancels the task at the service before finishing — otherwise the abandoned task keeps a worker busy for a result nobody collects. Second fix, same path: a run that ended cancelled was classified as `failed` and reported with `reportCodeFHEFailure`, contradicting the platform's own stop; a stopped FHE run (service-reported cancel or a cancelled handle) is now logged as 中止, not reported, and its import-index reservation is rolled back so the same `requestId`/`taskId` can be submitted again. `Runner.Cancel`'s not-in-flight refusal now wraps `ErrTaskNotInFlight`, so the handler can answer "already ended" for a run that finished and was forgotten moments before the stop arrived instead of answering 500.
- **A Stop That Arrived While Data Was Still Downloading Was Answered "不存在训练任务" And The Training Ran Anyway**: the stop handle was created only when the import was promoted to training, so for the whole download/decrypt/extract window `stopTraining` had nothing to point at, answered the idempotent no-task reply, and the pipeline went on to promote itself and run the model. The handle is now created by `tryAcquireTask`, the moment a task takes execution rights, and `promoteCurrentTaskToTraining` promotes that same handle instead of replacing it — a replacement would have split one task into two handles, and a stop delivered in between would have cancelled the one the run no longer used. `stopTraining` is eligible whenever a handle exists: it answers `训练任务已中止` for a running model and `任务已中止` for a task that never got that far, and since a task with no process has nothing to wait for, that reply does not spend the 5 s wait. Cancellation now reaches the work: the three downloads run under the task's context (`DownloadToTempFileWithClient`) so a stop aborts the transfer instead of waiting for it, and the import pipeline checks the handle at every step boundary — decryption and extraction read their whole input and cannot be interrupted mid-way, so a boundary is the earliest point a stopped task can be answered. A stopped import reports nothing through `reportRes` (the platform asked for the task not to happen), rolls back its import-index reservation, does not commit a record for a stopped data import, and does not enter training. The FHE path keeps its own cancel: a stop that landed before the FHE task id was published ends the import without submitting anything. Panic recovery and task release now finish and drop the handle with the task, so a later stop cannot land on a dead one.
- **The Generated Curl Command Doubled Its Line Continuations**: the command the API tester hands to the clipboard presented each line with two trailing backslashes — the line entries of the array ended with one and the join added another. The shell reads the second as an escaped backslash, so the command ended after the first line: a pasted run printed `curl: (3) URL rejected: Bad hostname` / `HTTP 000` and then `-X: command not found`, `--data-raw: command not found` and a syntax error on the `&&`. It looked like a malformed envelope, but the envelope was fine. The continuation now has one definition (`SHELL_CONTINUE`) that the join applies, and the line entries carry none; a regression test reads `apiTesterCurlText` out of the bundled frontend and fails on a line entry that ends in its own continuation, mutation-checked against the shipped defect. Verified with the reported envelope against `10.244.0.135`: `HTTP 200`, then `{"msg":"ok","result":{"currentOp":"idle",...}}` from the second step.
- **A Container-Executed Model Ran With Neither Its Image's Environment Nor Its Image's User**: the container target built the model's process from two hardcoded values — `PATH`/`HOME=/root` and the guest's root identity — rather than from the container's own runtime configuration. Neither matched what the image was built for: a model whose entrypoint relies on `PYTHONPATH`, `LD_LIBRARY_PATH` or a `HOME` under the image's user failed with an import or permission error that pointed at the model, while a model that writes into the staged trees as root produced files the image's user could not read afterwards. The OCI configuration Kata keeps beside the container root (`/run/kata-containers/<id>/config.json`, next to `rootfs/`) states both: `process.env` is the environment the image's own entrypoint would start with, and `process.user` is the user it expects to run as. The target now parses that file once, at discovery, and applies it: `BaseEnv` returns the image's environment, and `nsenter` gains `-S <uid> -G <gid>` when the image declares a non-root user (nothing is added for uid 0, so the packaged images are unchanged). `Prepare` hands the staged model, dataset and output trees to that uid/gid with `Lchown` — the model runs as that user, and a root-owned tree would otherwise be unreadable or unwritable to it. The fallback is explicit rather than silent: if the configuration is unreadable the process environment (`/proc/<pid>/environ`) is tried next and the minimal `PATH`/`HOME` set last, and the task log carries a warning naming the reason. The working directory is deliberately *not* taken from the image: the product contract already says the model runs in its model directory, and the image's `cwd` (`/`, or its service entrypoint's directory) does not contain it. **The task log now states the container configuration the model was given**: hostname, uid/gid, environment variable names (never values — an image may carry credentials there), the image's own `cwd`, the namespaces the image configures against the two that are entered (`mnt,pid`), the size of `/dev/shm` (torch's `DataLoader` and any multiprocessing user allocate there, and the 64MiB default fails far from that cause), and the container's network interfaces. Every value is read at task start, so a container recreated between runs reports what that run actually got.
- **A Container-Executed Model Ran Without The Container's PID Namespace**: the container target entered only the mount and user namespaces (`nsenter -t <pid> -m -r`), so the model stayed in the guest's PID namespace. The container's `/proc` is a procfs mounted in the container's own PID namespace, and a process from outside that namespace has no `/proc/self` in it at all — measured in a live CSV2 guest, `nsenter -m -r -- cat /proc/self/statm` fails with `ENOENT` while the same command with `-p` reads it. CatBoost opens exactly that file in `fit`, so the DPN training run got through data preparation and model construction and then died with `_catboost.CatBoostError: … can't open "/proc/self/statm"`. `nsenterShell` now passes `-p` as well, and the discovery probe uses the same helper, so what is probed is the namespace the model actually runs in. A stop still kills the container-side tree: with `-p` the model's processes remain in nsenter's process group, and `killpg` from the guest's namespace was measured to kill them (the same code path the training control uses).
- **Container Discovery Counted A Kernel Thread As A Second Container**: a live CSV2 initrd run reported `未找到可用容器，auto 模式回退到 local 执行 … found 2 candidate containers (pids 18, 126)`, fell back to the initrd, and then failed with `ModuleNotFoundError: No module named 'numpy'` — the initrd's python has no numpy, the Pod's image (`taa-env:v1-train-infer`) does. Measured in the guest, the two candidates are not two containers: pid 126 is the real one (`overlay … upperdir=/run/kata-containers/image/overlay/<layer>/upperdir`), while pid 18 is `kdevtmpfs`, a kernel thread that lives in its own early-boot mount namespace whose root is `6 5 0:5 / / rw - devtmpfs devtmpfs`. The scan kept every mount namespace whose root is not the initrd's `rootfs`, and a devtmpfs root passes that test, so a kernel thread could make discovery ambiguous and push a task into an environment that cannot run it. Namespaces are now skipped unless they contain a process with a non-empty command line: a container is a mount namespace entered by userspace, a namespace holding only kernel threads is not one. The skip happens before the namespace is marked seen, so a later userspace process in the same namespace is still considered. `containerId` could not have been used as a workaround either: the filter ran before the candidate's root was resolved and matched the overlay's `upperdir=/run/kata-containers/<id>/`, but the measured overlay names a layer id there. The id appears only on the path TAA sees the root at (`/run/kata-containers/<id>/rootfs`), so resolution now happens first and the filter matches that path as well as the old form. Both are covered by tests built from the measured mount tables.
- **`deploy.sh` Built The Daemon With Two Different Compilers In One Run**: `create` builds `taa` twice from the same tree — once into the image, once to verify what the Pod actually carries — and compares the two files by sha256, so an image is only accepted when both builds are byte-identical. `ensure_go_compiler` prepends a locally installed newer Go (`/usr/local/go/bin`, `/snap/bin`) to `PATH`, but it did so without checking whether that compiler was already the active one, and it ran again before the verification build. On a host with both a distro Go and a second installation, the second call switched compilers, and a correct image failed its own verification with two hashes (`taa binary: the Pod carries f102b517c273, this tree built 625c4a89d6ff`). The function now records that it has run and returns immediately on later calls, so one run uses one toolchain; `tests/deploy_go_toolchain_test.sh` calls it twice and pins that neither `PATH` nor the chosen `go` moves.
- **`deploy.sh --help` Ran A Command Embedded In Its Own Text**: the usage heredoc is expanded (`$BASE_DOCKER_IMAGE_ARCHIVE` and the like), so a backtick-quoted upgrade example in the Remote Pod paragraph was executed as command substitution — running `--help` actually invoked `TARGET_POD= ./deploy.sh taa stop`, which reaches for the remote host. The example is single-quoted now and `--help` only prints.
- **platform-mock Found No TEE-LLM Address When The Pod Lived Outside `default`**: the poller discovered the instance with `kubectl get pod <name> -o jsonpath={.status.podIP}` whenever `LLM_NS` was empty, which asks the `default` namespace. The TEE-LLM (and TAA) Pods are created in the platform's namespace (`osr`), so the lookup returned `NotFound`, the poller reported `未发现 TEE-LLM 地址`, and the console showed neither logs nor the attestation report even though the service answered both `/v1/llm/heartbeat` and `/v1/llm/log` on its Pod IP. An empty namespace now means a cluster-wide lookup, accepted only when exactly one Pod carries the name — a duplicate in another namespace is reported instead of silently picked. `--llm-ns` / `--taa-ns` still pin the lookup when a name is ambiguous.
- **platform-mock Lost The URL-Carried Data Key Envelope On Every Listing**: a file uploaded in `urlkey` mode was sealed to TAA's key and delivered as bare ciphertext plus `?dataKeyCipher=<hex C1C3C2>` on the download URL, but `/api/uploads` rebuilt each record's URL from the filename alone. The envelope exists only at upload time — it cannot be recovered from the ciphertext — and the console replaces its list with that listing immediately after an upload, so the URL offered for dragging into `importModel` (or for copying) was a bare `/files/<name>.sm4`. TAA then found no `dataKeyCipher` parameter, took the legacy whole-file-envelope path, and failed the import with `资源非 .enc 后缀且非有效压缩包，尝试解密失败` / `解开 SM2 密钥信封失败`. Each encrypted upload now writes a sidecar under `<upload-dir>/.uploadmeta/` holding the envelope and the encrypted flag, the listing rejoins the query string from it, and delete removes it with the file. The listing's `encrypted` flag now also covers `.sm4`, which the `.enc`-suffix heuristic had reported as plaintext. A regression test uploads in `urlkey` mode, reads the URL back from `/api/uploads`, and decrypts the file with TAA's key through that URL.
- **platform-mock Console Picks Up The TAA Address When Registration Lands**: the mock already derives each instance's TAA target from the registration's source address and serves it through `/api/instances` and `/api/taa-target`, but the console probed it only once at page load and again on an instance switch. A page opened before TAA registered therefore kept the fallback `http://<console-host>:6001` — nothing listens there, since TAA runs inside the Pod — and every health check or button failed in the browser with `Failed to fetch` even though the server-side proxy path was healthy. The existing instance poll now fills the address as soon as the selected instance reports a target, so a registration arriving while the page is open is picked up within one poll without a reload. An address the operator typed is never overwritten: an `input` listener marks it as manual, and that flag, rather than a comparison against the auto-filled value, now also decides whether an instance switch may re-detect.
- **platform-mock Rejected Every Real Registration (`parse register taaPublicKey`)**: the mock opened the registration plaintext and parsed its `taaPublicKey` with `ParseSM2PublicKeyHex`, but TAA has always registered its own key as a PEM body (`app.go` passes `keyPair.PublicKeyPEM`, and `api-design.md` documents the field as PEM). The mismatch was introduced by the envelope work, whose fixtures built the field as hex because that is the mock's internal storage form, so nothing exercised the shape a real TAA sends. A live TAA therefore received `401` on every attempt — `encoding/hex: invalid byte: U+002D '-'`, the first hyphen of `-----BEGIN PUBLIC KEY-----` — and retried forever, while the deployment itself looked healthy. `openRegister` now parses PEM first and keeps the hex form as a fallback for the mock's own fixtures, reporting the PEM error when both fail, and a test seals a registration with the PEM key TAA actually sends.
- **`deploy.sh` Failed Readiness Even Though TAA Was Listening**: `wait_for_remote_taa_ready` probed the daemon with `sh -lc '</dev/tcp/127.0.0.1/6001'`, but `/dev/tcp` is a bash feature and the image's `/bin/sh` is dash, where the redirection fails with `cannot open /dev/tcp/...` no matter what is listening. The probe was introduced with the sealed-transport change, and the pod test's fake `kubectl exec` answered every `/dev/tcp/` command with success, so it could not notice. The deployment now runs the probe under `bash -c 'exec 3<>/dev/tcp/...'`, the same form and for the same reason as `deploy-taa-vm.sh`, and the test's mock now reproduces dash's behaviour: the probe succeeds only when it is run by bash, which fails the suite if it regresses to `sh`.
- **`deploy-llm.sh` Reads `cc_init_data` From The Host When No CoCo Pod Is Running**: creating the TEE-LLM Pod requires `io.katacontainers.config.runtime.cc_init_data` — without it the guest's CDH cannot trust the local registry's self-signed certificate and the Pod stops in `StartError` — and the deployment supplied it only by borrowing the value from an already-running CoCo Pod. A host whose cluster has just booted has none (only runc system Pods), so a first deployment failed with "no Pod carries the cc_init_data annotation" even though the host keeps the same value at `/root/cc_init_data.txt`, written when the CoCo runtime was installed (the certificate embedded there matches the one the local registry currently serves). The file is now the second source, tried only when no Pod carries the annotation and read over the same SSH session; `TEELLM_POD_CC_INIT_DATA` still wins over both, and the path is `TEELLM_POD_CC_INIT_DATA_FILE` because it is a convention of this host's install rather than part of the protocol. A missing or empty file falls through to the original error, which now names all three sources.
- **`deploy-llm.sh --create-pod` Builds `teellm-service` As Its Own Module**: the build ran `go build ./teellm/cmd/teellm-service` from the repository root, which only resolves when the checkout's `go.work` lists `./teellm`; this repository's does not (it lists `./teellm/teetls` but not the module around it, and the file is local and untracked), so the first Pod creation died with `main module (taa) does not contain package taa/teellm/cmd/teellm-service` before any image work began. The build now enters `teellm/` and runs with `GOWORK=off`, where the module's own `replace teetls => ./teetls` is all it needs, so the behaviour no longer depends on a workspace file the checkout happens to have. The pod test's throwaway tree gains the `teellm/go.mod` that layout requires.
- **macOS-Packed Model Archives No Longer Fail The Audit On Their Own Metadata**: a ZIP built by Finder, `ditto` or Info-ZIP on macOS carries AppleDouble files under `__MACOSX/` (`._train.py`), and Finder adds `.DS_Store`; both are binary metadata that keep the original extension. The extraction path wrote them into the model directory, the semgrep walk selected `__MACOSX/._train.py` as Python source because the engine dispatches on extension, and semgrep 1.177.0 then exited 0 and listed the file under `paths.scanned` while putting a `PartialParsing` entry — `Syntax error ... was unexpected` — in its `errors` array. The adapter treats any `errors` entry as an incomplete scan (the completeness gate that exists so "never looked" cannot read as "found nothing"), so `GenerateAuditReport` returned an error and the controller reported the audit as failed (`code=2`); no dangerous rule had matched. The fix filters by entry name in one place (`pkg/archiveentry.IsMetadataPath`): any `__MACOSX` component, any `._*` basename at any depth, and `.DS_Store` are dropped by both `ExtractZipArchive` and `ExtractTarStream` before they reach disk, with a count logged. Name-based filtering is what makes it platform-independent — metadata left by another platform travels inside a package packed on this one — and the backslash spelling a Windows packer may use is normalised. As a second layer, the regex, semgrep and binary walks skip the same names and `__MACOSX` joins the shared `SkipDirs`, so a tree assembled by any other path (an extraction older than this filter, a directory copy) still cannot hand an engine a binary sidecar named like source. The tar arm covers the same sidecars, which a tool materialising extended attributes writes beside real files.
- **`deploy.sh` Overwrote `model.output.result`, So Results Landed Beside `log/` And `progress/` Instead Of In Their Own Directory**: all three templates put the exported results one level down, at `/opt/taa/output/result`, and `deploy-docker.sh` creates exactly that three-way split (`/opt/taa/output/{result,log,progress}`). Two call sites in `deploy.sh` passed the output *root* instead — the production image path, as a literal, and the local docker path, through `LOCAL_DOCKER_OUTPUT_DIR`'s default. That mattered because a non-empty `model_output_dir` **overwrites** the template's value rather than falling back to it, so the packaged image and the local container both ran with `result: /opt/taa/output` while the file on disk said `/opt/taa/output/result`. The remote path passes empty for both staging paths and therefore kept the template's value, which is how the divergence surfaced: the same template produced two different locations for the same key depending on how TAA was deployed. The packaged image has been verified to carry `result: /opt/taa/output/result` and to start TAA with it. Both call sites now pass the full path. **On upgrade:** a container or image assembled before this keeps the old value; `deploy.sh` regenerates `.local/run/docker-taa-config.json` on the next `docker` deploy and a pre-built image needs repackaging, after which results move to `/opt/taa/output/result` — anything reading the old location has to follow. TAA creates whichever of the three directories it needs, so nothing else changes.

- **Offline audit benchmark (evaluation-only): the Semgrep rule set was realigned with the regex baseline it is meant to mirror.** The two arms diverged in both directions, which would have made any engine comparison uninterpretable:
  - `FIL_001` had lost its sensitive-path predicate and matched *any* `open()` call while carrying `HIGH` severity where the baseline has `MEDIUM`. This is the rule that flagged all 100 audit-100 samples in the one recorded full-corpus Semgrep run.
  - `CMD_001` kept only the `shell=True` form, so every list-form invocation was missed, including the primary attack of samples M1-02/M1-07 (`subprocess.check_output(["bash", "-c", "whoami"])`).
  - `NET_001` had no `httpx`, `http.client`, `httplib2` or `urlretrieve` coverage (M2-04 uses `httpx.post`).
  - `OBF_001` was expressed as a taint rule (decode → `eval`/`exec`) where the baseline flags decode *use*, so payloads that are decoded and then exfiltrated instead of executed were invisible to it (M4-01), as were `pickle`, `marshal`, `codecs.decode` and `binascii`.
  - `PER_001` required the persistence path to be an argument of `open()` with a write mode, missing a path built on one line and opened on the next (M5-01); `EMB_002` matched every `shutil.copy` while missing `shutil.move`, and `EMB_003`/`EMB_004` matched literal argument names the baseline does not list.
  - Severity is not cosmetic in this comparison: under the production `gate` policy a `HIGH` finding blocks unless the LLM returns `BENIGN`, while a `MEDIUM` finding is counted but never blocks (`internal/codeaudit/verifier.go:160-178`), so a mistranslated severity changes whether a rule can block at all.
  - `EMB_001` was ported as a bare `torch.save($DATA, $PATH)` with only `state_dict()`/`model.pt` exclusions, dropping the baseline's payload-name list. It therefore flagged *every* checkpoint write — a `HIGH` finding on `train.py` in 75 of the 100 samples, most of them benign — while the `np.save`, `np.savez`, `shutil.copy` and `shutil.copytree` branches were missing entirely. Found by re-running the corpus-wide parity audit, not by the fixture tests: `EMB_001` had only a negative fixture, so nothing pinned what it was supposed to *not* catch. Both gates now also assert the control arm actually fired, since two empty finding lists agree trivially.
- **Offline audit benchmark (evaluation-only): the hand-authored matrix generator no longer implies an engine nobody named.** `generate_matrix_results.py` writes its `summary.json` files in the same shape and location as real evaluator runs, but every count in them comes from a hardcoded table, and `engine`/`rule_set_version` were derived from the audit mode name — so `engine: "semgrep"` was recorded without anyone claiming it, and the design report cited the result as a Semgrep measurement. Each row now carries `provenance: "hand-authored-spec"`, and both fields must be declared explicitly: `generate_matrix` takes a required track declaration with no default, and the CLI's `--track MODE:ENGINE:RULE_SET_VERSION` is required.
- **Offline audit benchmark (evaluation-only): `code_snippet` is no longer forwarded from Semgrep's JSON output.** Semgrep CE returns the literal string `"requires login"` in `extra.lines` when not logged in, and that field was mapped straight to `code_snippet` — the code the LLM is asked to adjudicate. No Semgrep+LLM arbitration had therefore ever run on real source. The runner now slices the matched line range out of the source file and records a `slice_error` when it cannot.
- **Offline audit benchmark (evaluation-only): an unfinished scan is no longer scored as a clean one.** A crashed, timed-out, uninstalled or rules-broken scanner produced the same empty finding list as a genuinely clean scan, and that list was recorded as a bypass — so an infrastructure failure improved the score. Scan status (`scan_complete`, `scan_timed_out`, `scan_parser_errors`, `scan_error`, `slice_error_count`, `ast_error_count`, `cpg_error`) now reaches every sample row, `incomplete` samples are excluded from the metrics, and the three swallowed exceptions in the evaluator record their cause instead of passing silently. The exclusion was initially incomplete: counting the failures was not enough, because the confusion matrix still scored the unscanned rows. A smoke-test run where all four samples failed to scan reported `tn: 4` with `accuracy: 1.0` — and since the Semgrep arm is the only one that can be incomplete, and a crashed scan *lowers* the false-positive rate, the defect could have manufactured a pass on the very criterion being judged. `confusion_counts` now drops unscanned rows instead of assigning them a cell (which also corrects the bootstrap intervals, computed through the same function), the metrics state `scored_count` next to `scan_incomplete_count` so a 96-of-100 matrix cannot read as the whole corpus, and each run carries `round_complete` — with the void notice leading `final-report.md` and zeros in `confusion-matrix.json` when it is false.
- **Offline audit benchmark (evaluation-only): the LLM sampling seed is now fixed and recorded.** Added `--llm-seed` (default `42`) to both the analyzer CLI and the benchmark evaluator, threaded through to the Ollama `options.seed`. The three paired repetitions are meant to isolate the engine, and an unpinned seed folds sampling noise into that comparison. Temperature is unchanged at `0.1`.
- **Offline audit benchmark (evaluation-only): the evaluator now times the work it is budgeting for.** The run budget for a paired comparison has to be set before hours of runs are committed, and the two costs behave differently: the static scan is a fixed per-sample cost the engine choice sets, the LLM arbitration is the one that dominates. Only a whole-run `eval_duration_sec` was recorded, which cannot separate them, and `scan_metadata.scan_duration_ms` was being written as a literal `0` — the standalone analyzer CLI measured it correctly, so the evaluator's report bundle carried a duration that no scan had produced. Every sample row now records `scan_duration_ms` (also written into the audit report), `llm_invoked` and `llm_duration_sec`, and the summary reports `per_sample_llm_sec` divided by the samples that actually waited on the model rather than by the corpus, since most samples bypass arbitration and a corpus-wide mean would report a cost no sample ever incurred.
- Fixed HTML browser cache invalidation in platform mock by adding no-cache headers.
- Fixed fail-closed arbitration in code auditing: assist mode now blocks the import when every finding's LLM verification failed (service down or circuit breaker open) instead of silently falling back to the static verdict.
- Fixed the LLM readiness pre-check to require an active `generate` probe against the target model, instead of matching the model name against the `/api/tags` listing.
- Corrected `README.md` and this changelog, which described the Semgrep AST/taint engine as part of the runtime audit path. The runtime path uses the built-in static rule scanner; the Semgrep and CPG engines live in the offline audit benchmark harness only.
- Corrected the documented `llm.policy` values in `README.md`: the strict mode recognized by the code is `gate`, not `enforce`. Setting an unrecognized value silently falls back to `assist` behavior and skips gate arbitration.
- Fixed Hygon CSV attestation mock report byte layout alignment with the `OffsetUserData` hardware specification.
